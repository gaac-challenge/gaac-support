先看结论

MLPerf 是行业联盟 MLCommons 维护的一组 AI 性能基准。其中的 MLPerf Inference 自 2019 年起每年两轮,由厂商在自己的机器上按统一规则跑、互相评审后发布。2026 年它分出一条新线 MLPerf Endpoints:被测对象变成一个 API 端点,结果变成一条随并发变化的曲线,并且带了一套多轮智能体基准。DeepSeek-V4.1-Flash 是这套智能体基准认可的三个模型之一,榜上已经有 8 卡 H200 加 vLLM 的正式成绩。

1

"MLPerf 成绩"现在指两套很不一样的东西

传统 Inference 是固定数据集上互相独立的单轮请求,规则禁止跨请求复用 KV 缓存。Endpoints 的智能体基准是 613 条多轮轨迹的闭环回放,明文允许前缀缓存。引用之前先问是哪一套。

2

传统 Inference 没有智能体测试项,最接近的一项在边缘侧

数据中心表里的 LLM 项目全部是单轮。v6.1(2026 年 9 月)新增的 Edge Agentic 是单用户、32K 上下文、27B 模型,面向单块边缘加速器。

3

吞吐只算输出 token

两套都是这样。AgentX 的默认口径把缓存命中的输入也算进去,两边的 tokens/s 差一到两个数量级,不能直接比。

4

先过精度,再谈性能,而且在同一配置上测

传统项目的门槛是参考精度的 99% 或 99.9%,外加输出长度约束。智能体基准有三层:平均输出长度区间、性能运行自身输出的内联精度、200 道 SWE-bench 题。

5

厂商自己跑、自己选交哪些项目

把关靠同行评审和抽查式审计。v6.1 有 30 家机构、约 120 个系统,其中约七成是 NVIDIA 加速器;没有 Google TPU,也没有推理专用芯片公司;没有任何一条带功耗的结果。

6

Endpoints 还很新,规则仍标着草案

v1.0 在 2026 年 10 月 13 日开放提交,每月发布两批。截至 11 月 19 日,DeepSeek-V4.1-Flash 名下有 10 条结果,其中 6 条还没过评审。官方说它将取代数据中心 Inference,但没有给时间表。

一 · 它是什么

一个联盟,一族基准,七年的演进

MLCommons

  • 性质。开放工程联盟,2020 年 12 月 3 日成立。渊源是 2018 年 2 月 Baidu、Google、Harvard、Stanford、UC Berkeley 的工程师和研究者的一次会面,MLPerf 也从那一年开始。

二 · 怎么测

LoadGen 和四种场景

本节和下一节讲传统的 MLPerf Inference。所有提交必须使用官方的负载生成器 LoadGen,从仓库的已批准版本原样编译。它负责按场景发请求、记录延迟、校验精度、算出最终指标。被测系统(SUT)用什么框架、什么运行时,规则不管。

场景请求怎么发最短时长延迟口径报告的结果
SingleStream上一条完成后立即发下一条,每次 1 个样本600 秒90 百分位延迟
MultiStream同上,每次 8 个样本600 秒99 百分位延迟
Server / Interactive按泊松分布到达600 秒99 百分位,须满足各项目的上限能支持的最大泊松速率
Offline开始时一次发出全部样本(至少 24,576 个)600 秒无吞吐

计时的起止点

  • 延迟从"LoadGen 计划发出请求的时刻"算起,到收到回复为止。系统来不及接的请求,排队时间算在延迟里。这是开环测试的要点:服务器慢了,请求照样按计划到达。
  • Server 场景的成绩是一个速率。LoadGen 用若干次试跑二分搜索,找出 99 百分位延迟仍然达标的最大每秒请求数。超过约束的那部分能力不计分。
  • Interactive 不是第五种场景。它和 Server 用同一种泊松到达,只是延迟上限更紧。
  • LLM 项目有两个延迟。TTFT 是首 token 延迟;TPOT 在规则里的定义是全部生成 token 之间的平均间隔。两者各有上限,具体数值见第四节。

精度和统计

  • 精度是单独的一次运行。把校验集每条恰好跑一遍,用和性能运行相同的代码。多数项目要求达到参考精度的 99% 或 99.9%,两档分别计成绩。
  • LLM 项目另有输出长度约束。例如 Llama2-70B 要求每样本生成的 token 数不少于参考值的 90%,Mixtral 和 Llama3.1-405B 要求落在 90% 到 110% 之间。提交者不得把最大输出长度调小。
  • 性能运行从题库里有放回地随机抽样。随机种子在提交截止前四周才公布,随机数生成器是固定的。

什么算合规,谁来查

两个维度的分类

维度取值含义
分区Closed模型和前后处理须与参考实现等价;可以量化,不可再训练。只有它能不加限定地称为"MLPerf 成绩"

Closed 分区里允许和禁止的

事项规则
框架与运行时任意。可以按场景换实现,可以按数据集经验调批大小
量化只能用官方校准集做可复现的纯数学量化,方法要公开到别人能重做
连续批处理、分页式 KV允许
跨请求的 KV 缓存禁止。规则原意:KV 缓存只服务单条请求,每条输入都必须完整计算
缓存请求或回复、合并相同请求禁止
基准检测禁止。系统不得识别出自己在跑基准而改变行为
基于输入内容的优化禁止。实现里不能编码数据集内容的任何信息
剪枝、替换权重禁止
只对定长实验有效的技巧禁止(Offline 除外),例如硬编码总请求数
推测解码只在三处允许:DeepSeek-R1 Interactive、GPT-OSS-120B Interactive、边缘 Agentic。必须用指定的预测头和参考配置,不得操纵接受率

评审

  • 四周。提交后第 1 周提异议,第 2 周答辩,第 3 周改正并定稿,第 4 周发布。评审期内结果和代码只对评审委员会和各提交者可见。
  • 互评。每家提交者至少评审另一家。异议以 GitHub issue 提出,须指出违规的代码行和对应的规则条款。委员会先求共识,不成则投票;改不好的结果移到 Open 或撤回。
  • 合规测试。Closed 提交必须自跑。LLM 项目要过 TEST06:单独上报的首 token 与实际输出一致;每条输出末尾至多一个 EOS;上报的 token 数与输出长度一致。
  • 发布之后。任何成员仍可提出异议。若修正后性能累计下降超过 5%,结果可被移到 Open,认定故意作弊的删除。

审计

  • 每轮最多审两个系统:一个随机抽,一个由评审委员会投票选出,也可以投"本轮不选"。只有 Closed 分区的 Available 提交可被审计。
  • 被审方在保密协议下提供材料和两天的硬件访问。整个审计应在 90 天内完成,实质性不通过的结果移到 Open 或删除。审计报告不公开。

按 v6.1 约 120 个系统算,每轮被审计的不到 2%。规则写得很细,但日常把关靠的是竞争对手之间的互相检查。本次没有查到任何公开的审计结论。

这张表说明了什么

  • 数据中心一侧没有多轮,也没有智能体。所有项目都是互相独立的单轮请求,加上第三节那条 KV 规则,前缀缓存在这里既用不上,也不被允许。
  • 输入普遍很短。Llama3.1-8B 的最大序列长度是 2048,Llama2-70B 是 1024。只有 405B 那一项用了长文档,而它已不在 v6.1 里。
  • 延迟上限随模型而定。TPOT 上限 15 ms 相当于每用户约 67 tokens/s,200 ms 相当于 5 tokens/s。

v6.1 的两项新测试

  • 端到端 RAG。一条完整流水线:嵌入、FAISS 检索、ColBERTv2 重排,GPT-OSS-120B 负责拆解问题和生成答案,GPT-OSS-20B 给文档打分,最多迭代 5 轮,由 Llama3.1-8B 当裁判。参考准确率只有约 35%,上下浮动约 3 个点。v6.1 只有 Intel 一家提交。
  • Edge Agentic。Qwen3.6-27B,参考实现用 llama.cpp 跑 4 比特量化,上下文固定 32K,单槽位。精度门槛用单轮函数调用(按语法树匹配判分,不用 LLM 裁判);性能用 20 条录制的编程轨迹共 1,007 轮,始终只有一个在途请求,报告每轮的 TTFT、TPOT 和端到端延迟。

Edge Agentic 的设计说明里有一段对出题的人有用:为什么精度门槛选单轮而不选多轮。57 条多轮任务的门槛,95% 置信区间约为正负 11.6 个百分点,量化实现的细微差异就会让单条判定在不同设备间翻转;995 条单轮样本的分数则稳定得多。

五 · Endpoints

被测对象变成一个 URL,成绩变成一条曲线

MLCommons 在 2026 年 3 月的博客里说了改的理由:传统架构里负载生成器和模型服务跑在同一个进程里,而生成式 AI 的部署是 API 优先的;模型几周一发,半年一轮太慢。Endpoints 的客户端经 HTTP 对任意 OpenAI 兼容端点发请求。

它和传统 Inference 的差别

项目传统 InferenceEndpoints v1.0
成绩的形状每个场景一个数一条曲线:至少 7 个(智能体)或 8 个(单轮)并发点
负载模式泊松开环,或一次发完固定并发闭环;泊松到达不能用于提交点
延迟约束有上限,不达标不计分不设上限,把 TTFT 和每用户速度连同吞吐一起报出来
跨请求 KV 复用禁止允许,规则明说这是有意偏离
分区Closed、Network、OpenStandardized、Serviced(公开商用 API,由 MLCommons 托管客户端经公网测)、RDI
节奏半年一轮随时提交,每月第 1 和第 3 个周三各发布一批
功耗可选的墙端实测Standardized 分区强制按预置功率归一

每个点报什么

  • 系统吞吐。窗口内的输出 token 总数除以时长。
  • 每用户速度。单轮基准是 1000 除以 P90 的 TPOT(毫秒)。智能体基准换成端到端平均交互速度,定义见下一节。
  • TTFT P90。从发出请求到客户端收到第一个非空片段,可见输出、工具调用、推理内容都算。规则专门写了一条:不许为了抢停表而先吐空白或无意义字符。
  • 并发数。在途请求数;智能体基准里是活跃会话数。

曲线怎么画

  • 只画阶梯,不许插值。理由是生成式推理的性能高度非线性,两个实测点之间连一条线,会画出从未实测到的性能。
  • 四个并发区都要有点。超低并发区是 1 到 C_min(不超过 32),其上分低、中、高三区,各至少一个必测点,另有 3 个自选点。最高并发由提交者自己定。
  • 时长。并发 32 以内每点至少 600 秒;32 以上,单轮 1200 秒,智能体 2400 秒。正式成绩取检测出的稳态窗口,去掉爬坡和收尾。

盐值:给缓存复用划边界

允许跨请求复用 KV 之后,数据集反复回放就会让缓存命中率虚高。Endpoints 的办法是由客户端在提示里插入确定性的伪随机串(盐值)。单轮基准把它插在系统提示和用户内容之间,于是两条请求能共享的前缀只剩系统提示。精度运行用不加盐的数据集。直接缓存回复仍然禁止,每条请求都必须真正过一遍前向计算。

评审和状态

  • 每条结果在看板上带状态:Official(已通过同行评审)、Provisional(提交者选择先公开,评审进行中,结果编号以 .p 结尾)、Unverified(从未送审)。
  • 评审改为异步:第 0 周自动合规检查,第 1 到 3 周同行评审,第 4 到 6 周解决异议,之后进入有成文程序的争议仲裁。审计每年 8 个。

规则文档的抬头仍是"Version 1.0 Draft",正文里时长、最小请求数、稳态判定、功率归一等多节标着"暂定"或"待工作组批准",仓库在 11 月 18 日还有改动。关于"取代":v6.1 新闻稿里 MLPerf 负责人的原话是 Endpoints 将在数据中心这一块取代 Inference,并说超过一半的 v6.1 提交者已经用了新的 API 式测试框架;但 10 月的两篇官方文章只说"正在转向",没有说传统 Inference 何时停办。

模型

现在接受三个模型的正式提交:Kimi K3、Qwen3.6-35B-A3B 和 DeepSeek-V4.1-Flash(7 月公布设计时只有前两个)。三者各出各的曲线,不合成一个分数。DeepSeek-V4.1-Flash 的固定参数是 temperature 1.0、top_p 0.95、最大输出 8192 token、开启思考且推理强度设为最高;指定了检查点版本,可以用它自带的 DSpark 推测解码头。服务框架不限,参考命令用的是 vLLM。

回放方式

  • 闭环。每条活跃会话一次只发一轮,等完整回复回来再发下一轮。并发数指同时活跃的会话数。
  • 回合间延迟。按数据集里记录的秒数等待,模拟工具执行。这段时间不计入服务延迟。
  • 提示用录制内容重建。下一轮发什么,取决于数据集,不取决于被测模型刚才生成了什么。这样性能运行才能在不同系统之间重复。
  • 会话标识。每条轨迹带固定的 X-Session-ID 请求头,路由器可以据此把同一会话钉在同一后端上。
  • 盐值。系统提示前后各插一个短标记。效果是:同一条轨迹内部完全可以复用缓存;同一遍数据集里,系统提示可以跨会话复用;数据集的不同遍之间不能复用。

指标

  • 纵轴是系统吞吐,只算输出 token。
  • 横轴是端到端平均交互速度。全部已完成回合的输出 token 之和,除以这些回合的端到端时间之和,不含工具执行时间。它把首字等待也摊了进去,回答的是"一个智能体实际往前走得多快"。
  • 每点另报 TTFT P90。

七 · 功耗

从墙端实测退到按额定功率估算

传统做法:MLPerf Power

  • 在墙端测交流电。被测系统经功率分析仪供电,另一台主控机通过 SPEC 的 PTDaemon 读表,两边用 NTP 对时。
  • 必须测整机,包括跑 LoadGen 的主机、加速器、内存和风扇。Server 和 Offline 场景报系统功率,单流场景报每流能耗。
  • 规则文档的标题仍是 v2.0,更新于 2022 年 1 月。
  • v6.1 的结果表里,492 行的功耗标记全部为否。这一轮没有任何带功耗的结果。更早各轮的数量没有查。

Endpoints 的做法:预置功率

  • 把 CPU、加速器、交换等主要部件的额定功率加总,再按模板加上散热和电源余量,得到"预置功率",用它去除系统吞吐。Standardized 分区强制要求。
  • 规则给的理由:预置功率近似总拥有成本;以前的实测方案因为要额外的功率计和测试时间,采用很少。规则自己把现行算法定为三档精度里最粗的一档。
  • 官方的买方文章说,预置功率是 MLCommons 唯一保证的归一口径;按 GPU 数或每 GPU 小时价格去归一,属于读者自行推导,未经核验。

榜单上的数字例子:8 卡 H200 的 HPE Cray XD670 是 9.73 kW,4 卡的 GB300 NVL72 切片是 7.5 kW,4 卡的 Vera Rubin NVL72 切片是 12.61 kW。它们是算出来的容量值,不是运行时的电表读数。

采购

十 · 局限与批评

它没测到什么

传统 Inference 与智能体负载的差距

  • 单轮。没有会话,没有随回合增长的上下文。
  • 禁止前缀缓存。智能体流量里最要紧的那项优化,在这里是违规。
  • 输入短。在役项目的输入多在一两千 token 以内,与智能体请求动辄数万到十几万 token 的输入不在一个量级。
  • 开环泊松到达。适合描述大量互不相干的用户,不适合描述"上一轮回来才发下一轮"的智能体。

制度上的局限

  • 自选项目。提交者可以只交任意一项、任意场景。难做的项目参与者很少:RAG 各 1 家,Interactive 档个位数。
  • 缺席不受罚。不提交就不出现在表里。主流云商的自研芯片和推理专用芯片公司都不在 v6.1 的加速器名单里。
  • 特调。Closed 分区也允许任意运行时、按场景换实现、按数据集调参。v6.1 的 LLM 结果绝大多数跑在 TensorRT-LLM 上,软件栈字段里能看到为这次提交准备的分支名。生产里更常见的 vLLM 和 SGLang 只占一小部分。
  • 不给价格,功耗数据稀少。MLPerf 不发布成本数据。Endpoints 的预置功率是成本的替身,价格归一被推迟到以后的版本。
  • 慢。半年一轮,模型从立项到出成绩以季度计。MLCommons 自己把这一点列为推出 Endpoints 的理由。
  • 门槛。须是成员;每个结果要跑性能、精度、合规三套,再经四周评审。单次提交的工程成本没有找到可靠数字。

Endpoints 和智能体基准自身的问题

  • 规则未定稿。多个关键参数标着待批准,不同批次的结果是否严格可比,要看之后规则怎么改。
  • 最高并发自选。曲线的右端画到哪里由提交者决定。
  • 被测模型自己的轨迹不回灌。后续回合用录制内容重建,所以它测的是"在这批既定轨迹上服务得多快",不是"这个模型自己干活时的流量"。这一点和 AgentX 相同。
  • 两类任务、613 条。没有子智能体扇出,没有跨天的长停顿。

找到的外部批评

The Next Platform 在 2026 年 3 月的一篇评论说得最直接:MLPerf Inference 既不给价格也不给功耗数据,买方无从知道成本,作者称之为荒谬;并指出 Google 当时没有为新一代 TPU 提交推理成绩。同一篇文章对另外两家也不满意:Artificial Analysis 只有 API 价格,InferenceX 覆盖面不够。

外部批评只查到这一篇有分量的,中文社区和社交媒体没有查。"厂商只挑有利的项目交"有 v6.1 的参与分布作旁证;"提交成本高"我没有找到带数字的出处。

十二 · 对办比赛的启发

哪些可以直接借,哪些不适用

本节是调研者的建议,不是 MLCommons 的说法。前提是比赛的形态:多支队伍在同一套硬件上自选推理框架,先过质量门槛,再比推理效率。

可以借用的

做法出处为什么有用
精度和性能在同一配置上测;性能运行的输出直接拿来打内联分Endpoints 智能体基准堵住"过门槛用一套配置,跑分用另一套"
平均输出长度区间传统规则和智能体基准都有堵住截短回答换速度;区间取参考值上下约一成
"真首 token"定义Endpoints 规则 4.1 节堵住先吐空白抢 TTFT
首 token、EOS、token 数三项核对TEST06防止上报数字与实际输出不一致
负载生成器原样使用,行为只能经配置文件改,并记录代码版本LoadGen 与 Endpoints 客户端各队的测量工具完全一致
赛前才公布随机种子,且定期轮换两套规则都有防止针对固定请求顺序特调
禁止基准检测、禁止编码数据集内容、禁止缓存回复传统规则的通用条款三句话可以原样写进赛规
盐值划定缓存可复用的范围Endpoints 规则 2.9.5 节允许前缀缓存,同时防止数据集重放造成命中率虚高
阶梯曲线,不插值;每点同时报吞吐、每用户速度和 TTFT P90Endpoints 规则第 5 节单点成绩容易被阈值选择左右
互评:每队至少评审另一队,异议须指到具体代码行和规则条款通用提交规则参赛者最清楚彼此可能在哪里取巧
出精度题时算置信区间Edge Agentic 的设计说明57 条多轮任务的门槛有正负 11.6 个点的噪声,题量太小会让名次由运气决定

还有一件现成的东西:Endpoints 的参考客户端对任意 OpenAI 兼容端点可用,已经内置多轮回放、会话标识、盐值、回合间延迟和内联打分。DeepSeek-V4.1-Flash 的官方参数、精度门槛和一份 8 卡 H200 加 vLLM 的完整正式提交都是公开的,可以当对拍基线。客户端仓库的许可证本次没有核对,用之前请先确认。

不适用的

  • 传统规则的"禁止跨请求 KV 复用"。与智能体推理比赛想考察的能力正相反。
  • 四周评审加九十天审计的周期。比赛的时间尺度是几天。能借的是它的形式(异议落到代码行、组委会抽查复跑),不是它的时长。
  • Server 场景"搜索最大泊松速率"。对闭环的智能体负载不贴切;若要考察过载表现,可以在会话到达这一层用开环。
  • "框架任意、可按数据集调参"的宽松度。MLPerf 比的是整机;比赛如果想比可迁移的推理优化,需要自己划线,AgentX 的"上游镜像原样运行"是另一端的参考。
十三 · 清单

有人引用 MLPerf 数字时,先问这十二个问题

  1. 哪一套?传统 Inference,还是 Endpoints?后者是单轮基准还是智能体基准?
  2. 哪一版、哪一批?Inference 报版本号;Endpoints 报发布日期或批次号。
  3. 哪个模型、哪个场景?Offline、Server 还是 Interactive?三者的延迟约束差一个数量级。
  4. 哪个分区?Closed 或 Standardized 才能横向比。Open 和 RDI 可能换了模型。
  5. 什么状态?Available 还是 Preview?Endpoints 上是 Official 还是 Provisional?
  6. 多少个加速器?总吞吐随规模涨。"每卡成绩"是引用者自己除出来的,不是官方指标。
  7. 什么软件栈?是上游的 vLLM、SGLang,还是厂商为这次提交准备的运行时分支?
  8. 是曲线上的哪个点?并发多少?此时的 TTFT P90 和每用户速度是多少?
  9. 比较取的什么阈值?阶梯曲线不插值,阈值恰好压在对手两个点之间时,倍数会被放大。
  10. 拿谁当基线?对手是同一批、同一状态、同等调优程度的结果吗?
  11. 是 MLCommons 榜上的数字吗?还是厂商在发布后用同一套工具自测、尚未送审的数字?
  12. 这个负载像你的负载吗?传统项目是短输入的单轮请求;智能体基准是输入中位数约 6 万 token、八成多回合以工具调用结束的两类任务。你的智能体可能两者都不像。
可靠程度

这份报告本身有多可靠

  • 把握最高的部分:场景与计时定义、允许与禁止、评审与审计流程、LLM 项目的延迟约束、Endpoints 的规则和智能体基准的机制。它们直接读自 2026-11-19 当天的规则仓库和参考实现原文。Endpoints 的规则仍在改,引用时请带日期。
  • 把握较高、但经过我加工的部分:第八节的成绩。v6.1 的计数和归类是我对官方 summary.csv 做的;Endpoints 的读数是我从结果库两个批次分支逐点下载后汇总的,只用 NVIDIA 博客脚注里的一个点做过对照(逐位吻合)。结果文件里的稳态字段是空的,这些读数是否就是榜单采用的稳态口径,没有进一步确认。
  • 把握中等的部分:组织情况、各方用法和外部批评。若干官方文章和厂商博客是经抓取工具摘要后读的,没有逐字读原文;欧盟招标只读了 MLCommons 的转述;会费数字来自搜索摘要。
  • 没有核实的:v3.1、v4.0、v4.1 的发布日期;GPT-J 当年的约束;Llama3.1-405B 和 Mixtral 是否算正式退役;传统 Inference 何时停办;Endpoints v1.0 全部模型的结果总数和提交者全名单;Serviced 分区有没有结果;历史上的审计结论;提交一轮的工程成本;v6.1 之前各轮的功耗结果数量。
  • 官方材料自身有不一致。已在第四节和第六节注明,例如模型名、回合总数、规则表与 README 的模型清单。遇到这种情况,本文以规则仓库和结果文件为准。
  • 与站内旧材料的差别。《AgentX 深度调研》里关于 MLPerf 的几句来自二手报道。本文核对后的结论是:数据中心的智能体基准属于 Endpoints,2026 年 7 月公布设计、10 月随 v1.0 开放、11 月出了首批正式结果;它允许并且专门建模了前缀缓存。
