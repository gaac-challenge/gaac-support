LiteLLM

自托管的开源 LLM 网关:SDK 加代理,统一调用百余家模型 API

与主线一 KV cache · 弱不碰 KV;靠可选的会话亲和把同一会话钉在同一部署,保住上游缓存与主线二 Agent 负载 · 中网关职能从转发模型请求扩展到 MCP 与 A2A 流量、按 key 的预算与权限

它是什么

LiteLLM 是一个开源项目,由创业公司 BerriAI 维护。它有两种用法一手LiteLLM 文档首页:

  • Python SDK:一个库。应用里把对各家模型的调用都写成 OpenAI 的格式(completion()),由库翻译成 Anthropic、Bedrock、Vertex AI、Azure 等 100 多家供应商各自的请求格式,并把返回值和异常统一回 OpenAI 格式。面向应用开发者。
  • Proxy Server(又称 AI Gateway、LLM Gateway):一个自己部署的服务。公司内部所有应用都把它当成 OpenAI 兼容端点来调,由它统一保管上游密钥、发放内部"虚拟 key"、按 key、团队、用户设预算和限流、记日志、算成本。面向平台团队。

它解决的问题是:每家模型 API 的字段、流式格式、错误码、计价方式都不一样,多模型应用要么自己写一堆适配,要么交给一个翻译层。LiteLLM 就是这个翻译层,加上企业需要的治理功能。

它做了什么

翻译层与路由器

SDK 内置一个 Router:同一个"模型组"下可以挂多个部署(例如同一模型的三个 Azure 区域加一个 Bedrock),Router 在它们之间做负载均衡、重试和回退。路由策略有 simple-shuffle(默认,随机加权)、least-busy、延迟优先、成本优先、限流感知等;遇到 429 立即把该部署冷却,一分钟内失败率过半也冷却;限流错误做指数退避重试,部署可用 order 分优先级逐级回退一手Routing 文档。

代理服务器的治理功能

虚拟 key、预算与花费跟踪、护栏(guardrails)、响应缓存、日志回调(Langfuse、MLflow 等)、管理界面。2026 年又加了两类"非模型流量":MCP Gateway(按 key 控制哪些工具可用)和 Agent Gateway(注册并调用 A2A 协议的 agent)一手LiteLLM 文档首页。它也实现了 OpenAI Responses API 规格的端点,对不支持该端点的供应商做桥接(自 v1.63.8)一手Responses API 文档。

许可与商业模式

核心代码 MIT 许可;企业功能(SSO/SAML、审计日志、多团队管理等)在单独的商业许可下,另提供企业支持和 SLA一手(LiteLLM 文档首页、GitHub)。事件通报里提到"LiteLLM Cloud 用户未受影响",说明也有托管版本,但文档首页只讲自托管。

和 OpenRouter 的区别

LiteLLM OpenRouter
形态 开源软件,自己部署 托管服务
上游密钥 你自己和各供应商签约,密钥存在你的网关里 用它的账户和余额,或 BYOK
计费 软件免费,账单由各供应商直接出;企业版另付费 充值收 5.5% 手续费
路由依据 你配置的部署列表和策略 它测量的全平台价格、速度、错误率
数据路径 请求不经过第三方 请求经过 OpenRouter
运维 自己负责可用性、升级、安全 由它负责

一句话:OpenRouter 卖的是"替你接好所有供应商",LiteLLM 给的是"让你自己管好所有供应商"。

2026-03-24 PyPI 供应链投毒

这件事核实后的事实如下。

  • 恶意版本:litellm 1.82.7 与 1.82.8。两者都在 proxy_server.py 里植入了载荷;1.82.8 另带一个 litellm_init.pth 文件。.pth 文件放在 site-packages 下会在任何 Python 解释器启动时自动执行,不需要 import litellm一手LiteLLM 安全通报。
  • 载荷行为:收集环境变量、SSH 密钥、AWS/GCP/Azure 凭证、Kubernetes token、数据库密码,POST 到仿冒域名 models.litellm.cloud;安全公司 HiddenLayer 的分析还指出它会装一个 systemd 用户服务做持久化后门、轮询 checkmarx.zone 取第二阶段程序,并尝试在 Kubernetes 集群每个节点上起特权 pod二手,安全厂商分析HiddenLayer。
  • 时间:官方称恶意包自 10:39 UTC 上线,"约 40 分钟后被 PyPI 隔离";但同一页面"谁受影响"一节把安装窗口写成 10:39 到 16:00 UTC,两者页面内未统一一手LiteLLM 安全通报。
  • 入口:官方措辞是"我们认为"源头是 CI/CD 安全扫描流程里用的 Trivy 依赖,初步证据显示攻击者绕过官方流水线、直接向 PyPI 上传;是推断而非定论。HiddenLayer 把攻击归到 TeamPCP,依据是与此前 Trivy、Checkmarx KICS 的 GitHub Action 被入侵事件共用基础设施。
  • 规模:HiddenLayer 引 PyPI 下载数据,1.82.8 约 10.2 万次、1.82.7 约 1.7 万次下载二手。
  • 不受影响:用官方 Proxy Docker 镜像、ghcr.io/berriai/litellm 镜像、LiteLLM Cloud、或锁定在 1.82.6 及更早版本的用户。也就是说受害面主要是没锁版本的 pip install,包括把 litellm 当传递依赖的项目。
  • 处置:下架恶意包、轮换维护者凭证、聘请 Google Mandiant 取证、暂停发版;新的 CI/CD v2 流水线(隔离环境、发布分离)产出 v1.83.0,之后 Docker 镜像用 cosign 签名。我查了 PyPI:1.82.7 和 1.82.8 已不在版本列表里,1.82.6 上传于 03-22,1.83.0 上传于 03-31 05:08 UTC一手,PyPI JSON API。

这件事的意义在于网关的位置:它持有全部上游密钥,又常装在有云凭证的机器上,是凭证最集中的地方。

  • GitHub 约 6.35 万 star、1.34 万 fork;最新稳定版 v1.110.0(2026-11-18),发版节奏接近每天一版一手,GitHub 与 PyPI API,2026-11-18 查询GitHub。

  • 竞争位置:各类横评(多为厂商撰写)一致把它定位为"供应商覆盖最广的自托管代理";同层的 Portkey 已被 Palo Alto Networks 收购、OpenRouter 被 Stripe 收购,LiteLLM 仍独立。

与主线一(KV cache)的关系

关系弱。LiteLLM 是无状态的翻译和转发层,不持有 KV cache,也不与推理引擎交换缓存信息。它与 KV 的接触只在"别把上游缓存弄丢"这一点上,落到三个机制:

  • 会话亲和(session affinity):Router 的一个可选前置检查,把一段会话的所有请求钉在处理第一个请求的那个部署上。文档直接写明适用场景是"模型组后面的各部署不共享状态,例如供应商侧的 prompt caching";deployment_affinity_ttl_seconds 限定的是两轮之间的空闲时间。不开这个选项时,默认的 simple-shuffle 会把同一会话的各轮随机撒到不同部署,每次都可能落到没有缓存的那台一手Routing 文档。
  • Responses API 的会话连续性:带 previous_response_id 的后续请求路由回原部署;带加密推理项的请求只能由创建它的 API key 解密,encrypted_content_affinity 把这类请求钉回原部署一手Responses API 文档。
  • 缓存标记与计价:把各家的缓存用量统一映射成 OpenAI 的 prompt_tokens_details.cached_tokens 字段;cache_control_injection_points 可在不改应用代码的情况下给消息加 Anthropic 式缓存断点;成本计算区分缓存命中与未命中的 token 单价一手Prompt Caching 文档。

注意 LiteLLM 自带的"caching"功能是响应缓存(同样的请求直接返回存过的答案),和 KV cache 不是一回事。

它出现在图里,是因为它代表接入层的"自托管"一极,而不是因为它在 KV 主线上有分量。

与主线二(Agent 负载)的关系

关系中等。LiteLLM 没有发布 agent 流量数据,也没有专门的 agent 调度机制,但它的产品范围在 2026 年明显跟着 agent 走:

  • 网关管的对象从"模型调用"扩展到"工具调用"(MCP Gateway,按 key 授权工具)和"agent 之间的调用"(A2A Agent Gateway);README 还把 Claude Code、Codex 等 agent 工具列为直接接入对象一手GitHub。
  • 路由里的会话亲和、previous_response_id 亲和,都是把路由单位从单个请求改成会话,这正是主线二说的变化在代理层的体现。
  • agent 一次任务会发出几十上百次调用,按 key、按团队的美元预算和限流因此成为刚需。
  • Rust 迁移的动机是 Python 代理在高并发下 CPU 和内存上涨、pod 被 OOM 杀掉。官方没有把原因归到 agent 流量,这层联系是我的推断,不是来源所述。

与图中其他概念的关系

  • OpenRouter:同层的托管对应物,见上表。LiteLLM 支持把 OpenRouter 作为上游之一未复核,本次未单独打开该供应商页。
  • MCP:LiteLLM 代理内置 MCP Gateway,是 MCP 流量的一个治理点。
  • Open Responses:LiteLLM 实现了 OpenAI Responses API 规格的端点,但其文档页没有提到 Open Responses 这个规范名,是否正式对齐未核实。
  • vLLM:仓库简介把 vLLM 和 NVIDIA NIM 列为支持的后端。企业常见用法是 LiteLLM 在前、自建 vLLM 集群在后,此时会话亲和保护的就是 vLLM 实例里的前缀 KV 缓存。
  • llm-d / GIE:功能上有重叠(都做请求到后端的选择),但层次不同。LiteLLM 在 API 语义层按部署路由,GIE 在 Kubernetes 网关层按 pod 的缓存和队列状态路由;本次没有找到两者集成的一手资料。
