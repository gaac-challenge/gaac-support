TensorRT-LLM

NVIDIA 自家的 LLM 推理引擎,现已改为 PyTorch 原生

与主线一 KV cache · 强KV 管理器 V2 含显存、主机内存、磁盘三层,并有按 token 区间的保留优先级与主线二 Agent 负载 · 中有保留策略、会话路由与 agent 调度实验,但引擎不保存对话,多为原型

它是什么

TensorRT-LLM(官方 README 现在写作 "TensorRT LLM",常缩写 TRT-LLM)是 NVIDIA 自己开发并开源的 LLM 推理引擎,只面向 NVIDIA GPU。它和 vLLM、SGLang 做的是同一类事情:把模型装进 GPU、调度并发请求、管理每个请求的中间状态;区别在于它是芯片厂商的"原厂"实现,新硬件(Blackwell、Rubin)上的专用 kernel 往往最先出现在这里。README 的定位是:为 LLM 与视觉生成模型提供 "specialized kernels for common operations, an efficient runtime, and a pythonic framework"一手TensorRT-LLM 仓库。截至 2026-11-18 有 15,100 个 star。

名字需要拆开解释。TensorRT 是 NVIDIA 早于 LLM 时代的通用推理优化器:把训练好的神经网络(通常经 ONNX 导出)针对某一款具体 GPU 做算子融合、精度选择与 kernel 挑选,产出一个叫 engine 的二进制文件,之后只加载这个文件执行背景知识,本轮未重新打开 TensorRT 文档核对。TensorRT-LLM 最初就是"用 TensorRT 这套编译方式来跑 LLM"。但这个名字今天已经名不副实:项目里的 TensorRT 后端已被移除,引擎完全建在 PyTorch 上。这是理解它在 2026 年位置的关键,也是报告需要更正的地方。

它做了什么

原来的模式:提前编译 engine

早期用法分两步。先离线:把 Hugging Face 权重转换成 TRT-LLM 的 checkpoint,再用 trtllm-build 针对目标 GPU 型号、最大 batch、最大序列长度编译出 engine 文件,大模型要几十分钟。再在线:运行时只加载 engine。好处是图级优化充分、运行时没有 Python 开销;代价是 engine 与 GPU 型号、形状参数绑定,换卡换参数都要重编,新模型架构要先有人写好对应的网络定义才能用。在模型家族每隔几周就翻新一次的 2025–2026 年,这个代价越来越难承受。

现在的模式:PyTorch 原生

README 现在的说法是 "Architected on PyTorch",提供高层 Python LLM API,模型用原生 PyTorch 代码定义(如 tensorrt_llm/_torch/models/modeling_deepseekv3.py),"making it easy to adapt the system to specific needs"一手TensorRT-LLM 仓库。性能不再来自整图编译,而来自三样东西:手写的专用 kernel(注意力、GEMM、MoE)、C++ 写的运行时组件(KV cache 管理器、调度),以及 CUDA graph。直接加载 Hugging Face 权重即可启动,没有 build 步骤。

这次换底座意味着什么:

  1. TRT-LLM 的使用方式变得和 vLLM、SGLang 基本一样,三者的差别从"编译型 vs 解释型"收敛为 kernel、调度策略与默认值的差别。
  2. 它的 kernel 可以被别的引擎直接拿去用。vLLM 的 README 把 TRTLLM-GEN 列为注意力与 MoE kernel 之一,v0.34.0 的性能表第一行就是 "Step5 NVFP4 MoE on TRTLLM-Gen"一手vLLM v0.34.0;SGLang 的 release notes 也有 "FlashInfer TRTLLM" 条目。TRT-LLM 因此兼有两个角色:一个可独立使用的引擎,以及 NVIDIA 向开源引擎输送 kernel 的上游。
  3. 名字成了历史遗留。README 改写为 "TensorRT LLM",但仓库名与包名未变。

与 Triton、NIM、Dynamo 的关系

这是 NVIDIA 推理软件栈的四个层次,容易混:

  • Triton Inference Server:通用的模型服务器(不限 LLM),TRT-LLM 可以作为它的一个后端。README 说 LLM API "integrates seamlessly with ... NVIDIA Dynamo and the Triton Inference Server";1.0 的 release notes 则有 "Remove support for llmapi + TRT backend in Triton"一手。
  • NIM:NVIDIA 的商业化推理微服务容器。NVIDIA 开发者博客(2025-06-11)说明一个 NIM 容器内置 TensorRT-LLM、vLLM、SGLang 三个后端,按模型格式、架构与量化方式自动选择,可用 NIM_MODEL_PROFILE 手动指定一手,厂商博客;NIM 现行文档页本轮未能抓取NVIDIA Developer Blog。也就是说,连 NVIDIA 自己的产品也不只用 TRT-LLM。
  • Dynamo:集群层的分布式推理框架,TRT-LLM 是其三种后端引擎之一。Dynamo 文档的功能矩阵显示 TRT-LLM 后端支持 Disaggregated Serving、KV-Aware Routing、SLA-Based Planner,KVBM 在特性交互矩阵中列为已验证;当前容器 tensorrtllm-runtime:1.5.0 搭载 TRT-LLM v1.3.0rc25一手Dynamo TensorRT-LLM 后端文档。

2026 年的现状

稳定版只有 1.2.0 与 1.2.1;主线以预发布版快速滚动,1.3 线出了 rc7 到 rc29 等二十余个 rc(2026-03 至 2026-09),1.4 线从 10-14 的 rc0 到 11-18 的 rc4,约一到两周一个一手,GitHub releases 列表。值得注意的是,Dynamo 的正式容器搭载的也是 rc 版而非稳定版。

1.4.0rc3(2026-11-06)的要点:三条 breaking change——移除 LlmRequest 的未用字段、"Remove obsolete TensorRT-backend compatibility surfaces"、serving frontend 默认改为 8 个(保留单前端回退);新增 Muse Spark Open、LTX-2.3 文生视频管线等模型支持;OpenEngine gRPC 接口支持图像、视频、音频输入;Responses 与 Anthropic Messages 流的 keepalive一手TensorRT-LLM v1.4.0rc3。其中 "TensorRT-backend compatibility surfaces" 那个 PR 实际删除的是 C++ executor API 里的 BatchingType、ExtendedRuntimePerfKnobConfig 以及 EagleDecodingConfig.num_eagle_layers 这几个遗留类型和字段一手TensorRT-LLM PR #21041——是清扫残留,而不是切换后端。

同一版的 Known Issues 写明:DSA 模型(含 GLM-5.2)使用 NVFP4 KV cache 时可能输出错误;Kimi K3 DSpark 在 GB300 warmup 时可能挂起。rc4 的 Known Issues 又换了一批(如 DeepSeek-R1 FP4 在 B300 上 P/D 分离 + CUDA graph 可能输出错误)一手。这是"特性组合正确性"问题的直接证据。

竞争位置:star 数约为 vLLM 的六分之一。它的不可替代性在于 NVIDIA 新硬件的首发适配——rc4 已有多条 Rubin 专用条目,README 的技术博客列表有面向 Vera Rubin NVL72 的文章(11/11)。

与主线一(KV cache)的关系

关系强。TRT-LLM 的 KV cache 文档是三个引擎里把"分层"和"保留策略"写得最细的。

分块与前缀复用。 KV cache 是一个 block 池,每个 block 存固定数量 token 的 KV。写满的 block 放进一棵 radix 搜索树;新请求的 prompt 与树匹配,命中的 block 直接共享。enable_block_reuse 默认开启。enable_partial_reuse(默认开)允许只匹配某个 block 的一部分;V2 管理器遇到部分匹配的尾页时,总是先拷贝到请求私有的页再续写,被缓存的页保持可共享一手TensorRT-LLM KV Cache 文档。所以它在结构上更接近 SGLang 的 radix tree,而不是 vLLM 的块哈希表。

保留优先级:应用可以告诉引擎"哪段别踢"。 每个 block 有 0–100 的优先级,淘汰时先踢低优先级,同级按 LRU。KvCacheRetentionConfig 允许调用方用 TokenRangeRetentionConfig 给 prompt 的某个 token 区间指定优先级和 duration_ms(到期后回落到默认值 35),decode_retention_priority 管生成出来的 token一手。这是一个按请求、按区间的显式 TTL 接口,vLLM 没有对应物。

三层存储。 KV cache manager V2 是默认(use_kv_cache_manager_v2: true),rc4 已把 V1 标为 deprecated。层级为:GPU 显存(free_gpu_memory_fraction,默认 0.9);主机内存(host_cache_size,默认 0 即关闭,被踢出显存的 block 拷到主机内存,复用时再拷回);磁盘(disk_cache_size 加 disk_cache_path,另有 disk_write_through、disk_prefetch_num_reqs 等标为 prototype 的选项)一手TensorRT-LLM KV Cache 文档。rc3 的 release notes 对应条目是 "Add unified KV cache manager foundations, sparse attention arenas, and host-backed pools",rc4 有 "Optimize KVCM V2 SSD offloading" 与 "Add sparse KV offload for DeepSeek-V4 Flash and GLM-5.2"。注意 TRT-LLM 的分层是引擎内建的,不像 vLLM 那样通过 connector 接 LMCache、Mooncake 等外部系统;跨节点的层由 Dynamo 的 KVBM 承担。

KV 量化。 dtype 可设 fp8;prototype 的 mixed_nvfp4_bfloat16 等混合精度模式把完整注意力历史存成 NVFP4(4-bit),只让开头 mixed_precision_first_n 与结尾 mixed_precision_last_n 个 token 保持常规精度一手。README 最新的技术博客(11/17)标题即 "NVFP4 MLA: Unified 4-bit KV Cache Storage and Attention Compute"。风险也写在明处:上面提到的 NVFP4 KV 已知问题。

KV 事件。 引擎可通过 /kv_cache_events 端点或 ZeroMQ 流把 block 的 stored/removed 事件发布出去,供集群层(Dynamo 的 KV 感知路由)知道哪台机器缓存了什么一手。

与主线二(Agent 负载)的关系

关系中等。NVIDIA 在这个引擎里做了不少面向 agent 的实验,多数仍是原型;引擎不保存对话历史。

  • API 面:支持 Responses 与 Anthropic Messages 接口;rc3 有一批针对 agent 客户端的修复(DeepSeek 工具调用的渲染与解析、Responses 的 namespace 工具调用、thinking block 签名、流式 keepalive),并把 XGrammar 从 0.1.32 升到 0.2.8一手TensorRT-LLM v1.4.0rc3。
  • 每请求 CPU 开销:serving frontend 默认改为 8 个进程,说明单个 Python 前端已是瓶颈;rc4 有 "Reduce executor, sampler, KV scheduler, and long-prompt host overhead"。
  • 会话级路由:rc3 的一个 PR 给 ConversationRouter 加了基于内容的放置——新的 conversation ID 按前缀内容(默认阈值 32 个 block)选服务器,已有 ID 保持粘性;同一 PR 让 KV 管理器 V2 跟踪"正在计算中的前缀",让后到的同前缀请求等一等再复用一手,PR 描述为自动生成的评审摘要TensorRT-LLM PR #20938。这是 P/D 分离部署里协调器层面的"会话"概念,不是引擎保存对话。
  • KV hints:rc3 新增 "trusted KV hints"——请求可携带 KV 复用提示,HTTP 入口默认剥离,只有受信来源才接纳。但 PR 明说 "This PR does not execute actions or activate a backend",目前只完成了准入与传递一手TensorRT-LLM PR #20269。
  • 应用与引擎联合优化:2026-05 的技术博客以 Open Deep Research 这类多 agent 系统为对象,提出两件事。一是 agent 框架在某段逻辑结束后主动发 DropKVCacheTask,引擎调用 truncate_blocks 丢掉不会再用的 KV;在 Qwen3-235B、4×GB200、每秒 4 个 agent 任务加 4 个对话的条件下,同机聊天请求的缓存命中率从 0.30 升到 0.49、TTFT 从 15.90 秒降到 6.65 秒。二是用 agent 调用树的标记让调度器按比例在 agent 与聊天请求之间分配批处理槽位一手,厂商自测;其中一项指标(Compressor 命中率)反而下降TRT-LLM 技术博客:Joint Optimization of Agent Applications。博客自己承认前缀缓存本质上是无状态的,引擎无从知道某个前缀何时会被复用——这正是主线二的核心难题。

一个容易看错的地方:rc3 的 "session reuse" 测试条目指的是 MPI worker 池(MpiSession)的复用,与用户会话无关。

与图中其他概念的关系

  • Dynamo:TRT-LLM 是 Dynamo 的后端引擎之一,两者同属 NVIDIA,KV 事件、P/D 分离、KVBM 都是配套设计。
  • vLLM、SGLang:既是同层竞争者,又是其 kernel 的下游使用者。
  • Vera Rubin NVL72:新硬件适配最先落在这里,rc4 有多条 Rubin 条目。
  • EAGLE-3:支持 EAGLE 系投机解码(被移除的 num_eagle_layers 字段即属其配置)。
  • llm-compressor:rc4 有 "Add compressed-tensors NVFP4 MoE packaging support",即可加载 llm-compressor 生态的 compressed-tensors 格式权重。
  • Open Responses、MCP:实现了 Responses API;未见与 Open Responses 规范或 MCP 的直接对接说明。
  • 与 AMD Helios、TPU Ironwood、Cerebras、昇腾、llama.cpp、MNN、GGUF 等无直接关系——它只支持 NVIDIA GPU。

存疑与未核实

  • 与报告矛盾:报告称 TRT-LLM "正在换底座",并以 v1.4.0rc3 的 "Remove obsolete TensorRT-backend compatibility surfaces" 为依据。按官方文档的 release notes,PyTorch 在 1.0(2025-09)已成为默认后端,TensorRT 后端在 1.2(2026-03)已被整体移除;rc3 的那一条只是删除几个遗留的 C++ 类型与配置字段。准确的说法是"已经换完,仍在清扫残留"。
  • 上一条有一处我未能完全对齐:官方文档站的 1.2 release notes 明确写了 "PyTorch is now the sole execution backend",但 GitHub 上 v1.2.0 的 release 页面正文(经摘要工具读取)没有出现这句话,只提到 PyTorch 后端的采样默认值变化。二手来源中"1.2 移除"与"1.3 线才移除"的分歧可能源于此。我以官方文档站为准,但没有去读代码确认。
  • 报告以 v1.4.0rc3 为最新预发布;2026-11-18 已发布 rc4,README 主干徽章显示 1.4.0rc5。
  • TensorRT 本身的工作方式、早期 engine 编译耗时("几十分钟")是背景知识与二手说法,本轮未用一手来源核对。
  • NIM 现行文档页抓取为空,NIM 内部后端选择规则只依据 2025-06 的开发者博客,可能已变化。
  • Dynamo 的默认 worker 是否通过 Python LLM API 内嵌 TRT-LLM,文档页未明说。
  • GitHub API 把许可证识别为 NOASSERTION,README 徽章写 Apache 2;未打开 LICENSE 文件核对。
  • PR #20938、#21041 的描述是 CodeRabbit 自动生成的评审摘要,非作者手写。
