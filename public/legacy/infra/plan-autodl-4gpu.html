AutoDL 四卡机测试方案

EdgePod 到位前，用 AutoDL 上的 4×RTX PRO 6000 做开发替身：先确认比赛模型能跑，再把 Benchmark 和 KV 实验跑通

这份方案解决什么

比赛用的 EdgePod 计划 11 月 23 日前装完，支持软件和 Benchmark 软件要在 11 月 30 日前 Ready（Plan A；Plan B 是 12 月 3 日）。硬件到位前的这段时间不能空等，所以先在 AutoDL 上租一台四卡机当替身。

这台机器要完成三件事：

  1. 把 Inference Infra Benchmark 做出来。评测第二步的六项指标（任务成功率、任务完成时间、首 token 延迟、生成速度、SLA 并发、每成功任务成本）需要一套能回放 agent 任务并出数的脚手架。
  2. 把两条主线上的关键实验先跑一遍。前缀缓存、KV 分层、路由、工具间隙这些变量各自值多少，先在小机器上摸清，到 EdgePod 上只做确认。
  3. 给选手支持软件一个开发环境。环境复原、冻结重跑、防作弊、资源监控四项，需要宿主机权限。

它不解决的事也要先说清：跨节点的 KV 传输（400GbE、RDMA）、外置 NVMe 存储池、16 卡规模下的性能数字，这三样只能等 EdgePod。

本文是 v0.2，是后续工作的底稿。标待定的地方需要拍板，标未核实的地方需要上机验证。

v0.2 改了什么

v0.1 写完后做了五篇专题调研，带回几处修正：

  • 模型规模。v0.1 按 671B 估算，认为四卡放不下满血 DeepSeek。现行的 DeepSeek-V4-Flash 是 304B，FP8 约 160 GB，四卡可以直接跑。详见 vLLM 与 SGLang 对比分析。
  • 上机第一步。RTX PRO 6000 与数据中心 Blackwell 的计算代号不同，两个引擎在这款卡上都有走回退路径和打补丁的记录，所以先验证原版镜像能不能把比赛模型跑起来。
  • 六项指标的定义。首 token 延迟和生成速度的计时点写精确了，任务完成时间拆成三个数，SLA 并发改按任务数收尾。
  • 负载。压测底座定为 AIPerf；轨迹格式补了字段；合成轨迹不再只用一组画像数字。
  • 实验。SGLang 的 KV 分层在这款卡加 DeepSeek-V4 的组合上官方写明不支持，E4 相应调整。

Benchmark 的整体做法见 Benchmark 总览，本文只保留与四卡机直接相关的部分。

三点需要上机确认：

  • AutoDL 页面上那款卡是 Max-Q、标准工作站版还是 Server Edition。三者同芯片同显存，功耗和散热不同，性能数字会略有差别未核实。
  • EdgePod 的 16 张卡怎么摆。配置图是一台 4RU 服务器，Max-Q 涡轮卡一台通常装 8 张左右，16 张多半是两台待定。这决定支持软件要不要处理跨机。
  • 比赛指定跑哪个模型。计划里写的是“对标 DeepSeek 官方 API”，没写具体型号待定。这是现在最要紧的一条，下一节说明原因。

开机清单

容器实例

  1. 企业认证。对外开放端口只有 6006 和 6008 两个，而且需要企业认证；个人账号只能用 SSH 隧道一手AutoDL 开放端口文档。隧道命令形如 ssh -CNg -L 6006:127.0.0.1:6006 root@<主机> -p <端口>一手AutoDL SSH 隧道文档。
  2. 选主机。四张卡必须在同一台主机上，筛空闲 GPU 不少于 4 的。同时记下每卡配的 CPU 核数和内存：agent 负载下每个请求的 CPU 开销不小，核数太少会先卡在 CPU 上。
  3. 数据盘扩到 500 GB 以上。系统盘 30 GB，数据盘默认 50 GB，都放不下模型。付费扩容的数据盘按日计费，关机也收一手AutoDL 计费文档。
  4. 用包周。按量计费关机后 GPU 不预留，下次开机可能凑不齐四张；包年包月（可按日、周、月）在租期内预留 GPU一手，同上。
  5. 记下主机信息。GPU 版本、驱动版本、CPU 型号、内存、PCIe 拓扑，后面每一份结果都要带上。

裸金属

问客服时一次问清：有没有 RTX PRO 6000 四卡整机、月价、交付时间、能否自己装系统和 Docker、有没有公网 IP、带不带 BMC 或带外管理、能否测功耗。

模型：先定比赛型号

四卡机能跑什么，取决于比赛对标 DeepSeek 的哪个型号。下表的规模和体积来自社区记录与官方配方，出处见 vLLM 与 SGLang 对比分析。

型号 规模 四卡 384 GB 能否放下 说明
DeepSeek-V4-Flash 304B，FP8 约 156–167 GB 能，四卡一个实例 有用户在 8 卡 RTX PRO 6000 上的生产记录，用四卡跑一个实例二手
DeepSeek-V4.1-Flash 552B 放不下 两个引擎的官方配方都没有 RTX PRO 6000 档
DeepSeek-V4-Pro 更大 放不下，8 卡也不够 只能等 EdgePod 的 16 卡，且需确认

由此分两种情况：

  • 比赛用 V4-Flash：四卡机直接跑比赛模型，不需要替身。四卡装一个实例后约剩 200 GB 给 KV 和运行时开销，这台机器上测出的缓存行为可以直接类比 EdgePod。
  • 比赛用更大的型号：四卡机只能用 V4-Flash 或更小的同系列模型当替身，保持分词器、聊天模板和工具调用格式一致。性能数字不能外推，只验证流程和相对趋势。

路由和多副本实验需要一卡或两卡就能装下的模型，另备一个 30B 级的小模型（FP8 约 35 GB）。

聊天模板和工具调用解析器要单独预检：公开数据显示同一模型在不同服务商之间工具调用表现差异明显，原因多在这两处。本地起服后，先用一组固定的工具调用用例对着本地端点和官方 API 各跑一遍，确认格式一致。

四张卡的四种摆法

代号 摆法 模型 测什么
T1 四卡一个副本（TP=4） 比赛模型（V4-Flash） 主力拓扑。六项指标、KV 容量、量化、投机解码、引擎对照
T2 两卡一个副本 × 2，前置路由器 30B 级小模型 前缀感知路由、会话亲和
T3 两卡 prefill + 两卡 decode 30B 级小模型 PD 分离在单机内的收益与开销
T4 一卡一个副本 × 4，前置路由器 30B 级小模型 路由策略在更多副本下的差别

比赛模型占满四卡，所以多副本实验只能用小模型做，结论只看相对趋势。EdgePod 的 16 卡能装四个 V4-Flash 实例，多副本的正式实验留到那里。

副本用 CUDA_VISIBLE_DEVICES 隔开，各占一个端口；路由器对外占 6006。容器实例里没有 Kubernetes，路由器用独立进程形态的：vLLM 的 Rust 路由器或 SGLang 的路由器，两者同源。Dynamo 能否不靠 Docker 在容器实例里本地起未核实。llm-d、AIBrix 需要 Kubernetes，留给裸金属。

vLLM 文档给的 CPU 下限是 N 张 GPU 至少 2 + N 个物理核。agent 负载下前端开销更大，选主机时按每卡 8 核以上挑。

六项指标怎么量

精确定义和理由见 压测工具与方法论 与 Benchmark 总览，这里是定稿建议的摘要。

指标 定义 报告方式
任务成功率 通过质量门槛的任务数 ÷ 发起的任务数。超时、报错、被限速、上下文溢出都进分母 百分比，附失败原因分类
任务完成时间 任务首个请求到达计量代理，到最后一个响应的末个片段 模型时间、工具时间、墙钟时间三个数；P50、P90
首 token 延迟 请求到达计量代理，到第一个非空内容片段。开推理的模型另报到首个答案或工具调用片段的时间 P50、P95；按该请求的缓存命中比例分桶
生成速度 （输出 token 数 − 1）÷（末个片段时刻 − 首个片段时刻）；另算含首 token 延迟的口径 P50 与慢尾；token 数统一用一个分词器在客户端重算
SLA 并发 同时活跃任务数的最大值，使该档内首 token 延迟、慢尾生成速度、任务成功率都达标 闭环固定并发；每档按完成的任务数收尾；拐点重复三次；报整条曲线
每成功任务成本 在 SLA 并发点上，单位时间硬件成本 ÷ 单位时间成功任务数，失败任务的机时计入 元/任务；官方 API 一侧按实际缓存命中的折扣价算，两者并列不相减

四点说明：

  • 首 token 延迟不能看首字节。DeepSeek 官方 API 在排队期间会持续发保活行，量首字节会量到它。
  • 生成速度报两种口径。Artificial Analysis 现行口径和 OpenRouter 公布的数字都含首 token 延迟，对标外部数字时用含的那种。
  • 官方 API 侧测不出 SLA 并发上限。它的限速按账号并发计，参照线只能给出延迟、速度和成本，并发上限只有本地一侧有。
  • 在 SLA 并发点上重跑质量评测。高并发下的超时和截断会悄悄降低质量，不过则该并发点无效。

三个阈值和成本口径仍待定。

工具

  • 压测底座用 AIPerf。不需要 Kubernetes，同一条命令能打本地引擎和官方 API，内建缓存隔离和 SLA 边界搜索。它原样回放自定格式轨迹的能力未核实，开机后先验证。
  • GuideLLM 做交叉验证。同一份负载用第二个工具再量一遍，先对 token 总数，再对延迟。
  • 计量代理要自己写。在推理端点前放一个透明反向代理，记录每个请求的到达、首个推理片段、首个内容片段、末个片段的时刻和服务端返回的用量。回放和选手真实 agent 共用这一套计时点。
  • 服务端指标同步采集。引擎的排队时长、KV 使用率、驱逐次数与客户端时间轴对齐，这是拆出排队时间的唯一办法。

对标官方 API

同一批轨迹对着官方 API 回放，得到参照线。固定出口机房并记录往返时延，分时段多次回放取分布，记录被限速的次数和接口返回的缓存命中与未命中 token 数。官方 API 的缓存是尽力而为的，紧接着的下一轮也可能未命中。

负载：回放什么

详见 负载、trace 与数据集。分三步：

  1. 公开 trace 冒烟。用公开的编程 agent trace（SemiAnalysis 的 AgentX、微软公开的 Copilot 采样）把工具链跑通，并做 KV 实验。它们是编程负载，不能评质量。
  2. 自录三类 agent 的轨迹。在 agent 框架和模型端点之间放代理，录完整请求、流式响应的时刻和每个工具的耗时。排版和财务预测没有任何公开画像，只能自录；深度调查在自录完成前可以先用公开的带全文轨迹。
  3. 选手真实 agent。开赛后质量评测跑真实 agent，效率评测回放冻结的轨迹，两者分开。

合成轨迹只在自录完成前过渡用，至少造轻重两档：单次输入中位约 6.8 万 token 的一档和约 14 万 token 的一档。不同来源的画像中位数相差两倍以上，只用一组会偏。

轨迹格式每行一次模型调用，字段名沿用 MLPerf 端点测试的多轮格式，在 v0.1 的基础上补四类：

  • 依赖关系：父调用、分支号、汇合点，用来表达子 agent 并行。
  • 拆开的时间：录制时的模型耗时，和上一次响应结束到本次请求发出的间隔；每个工具的名字、耗时、状态。只存一个总间隔会把录制系统的快慢混进负载。
  • 录制时的输出：输出文本、输出和推理 token 数、结束原因、最大输出长度和采样参数。
  • 前缀信息：输入 token 数、分词器、按固定块大小算的哈希序列，用来离线算理想命中率。

回放规则：

  • 用录下的历史消息，不用被测系统现场的输出，保证各系统看到的输入逐 token 相同。
  • 任务内闭环，前驱完成并等过工具间隔后再发下一个请求，不按录制的绝对时间戳发。
  • 另设一档把工具间隔压到零，区分引擎慢和工具慢；保留一组真跑工具的对照，量出用等待模拟工具的偏差。
  • 每个并发档位换一次盐值，插在系统提示和工具定义之后，切断跨档残留而保留系统提示的合法共享。

每个实验只动一个变量，其余固定。默认用比赛模型、T1 拓扑、自录轨迹；E2 和 E9 需要多副本，用小模型。

几个实验的背景，方便理解为什么这样设计：

  • E0 是新加的第一关。RTX PRO 6000 的计算代号是 SM120，数据中心 Blackwell 是 SM100，很多专用内核只为后者写。vLLM 在这款卡上有未合并的补丁和未关闭的崩溃报告，SGLang 一侧的用户记录用的是社区补丁加专用镜像二手。两个引擎 2026 年都出过吞吐正常但结果错的缺陷，所以 E0 要核对输出正确性，不只是看能不能起服。
  • E3 和 E4 是主线一的直接检验。E4 里主机内存这一层由引擎自带能力提供，本地盘这一层用 LMCache。SGLang 官方文档写明 DeepSeek-V4 在 RTX PRO 6000 上不支持它的分层缓存，所以比赛模型上的 E4 只在 vLLM 一侧做；vLLM 的主机内存卸载在这款卡上是否可用未核实。取回是否比重算快取决于盘的带宽，要同时记录两者的延迟。
  • E11 按公平开关表做。两个引擎的默认调度取舍相反，投机解码方法也不同，直接比默认配置没有意义。开关对照表见 vLLM 与 SGLang 对比分析。公开横评方向互相矛盾，没有一份有这款卡的数据。
  • E5 的四个间隙取自生产画像：工具执行时间的中位、均值、P99，以及 turn 之间用户空闲时间的中位。
  • E7 必须带长上下文检索测试。vLLM 团队曾在压力测试中发现 FP8 KV 在 128k 上下文下准确率大幅下跌，问题出在上一代 GPU 的内核并已修复，Blackwell 上据其博客不存在。这类问题平均分看不出来，所以单列一项。
  • E8 的 4-bit 浮点格式是 Blackwell 一代才有硬件支持的，这是坚持租同架构卡的原因之一。
  • E10 预期收益有限。公开的生产口径数据是吞吐提升一到两成，长输入时更低，详见 EAGLE-3 一篇。

这台机器做不了的

  • 跨节点 KV 传输（Mooncake Transfer Engine、NIXL 的 RDMA 路径）。单机上只能走本机内存或 TCP 回环，数字没有参考价值。
  • 外置 NVMe 池上的 KV 层。
  • 比 V4-Flash 更大的型号。
  • 比赛模型的多副本路由与伸缩（四卡只够一个实例）。

这四项列为 EdgePod 上的第一批实验。

选手支持软件（裸金属上做）

七支队伍轮流用同一套 EdgePod，每队一周。四项功能各自的验收标准建议如下。

功能 做法（建议） 验收
环境复原 选手环境全部装在容器和独立数据卷里；换队时删容器、删卷、从基线镜像重建 复原后文件哈希与基线一致，GPU 显存清零，无残留进程；全程耗时有上限
冻结与重跑 提交时把容器镜像、配置、模型清单和数据卷做快照，带内容哈希 任取一份快照，在干净环境重跑，六项指标落在约定的波动范围内
防作弊 出网默认全禁，只放行白名单；全部出入流量留审计日志 从选手容器内访问任何外部推理 API 都失败并留痕
资源监控 宿主机侧按 1 秒粒度采集每卡利用率、显存、功耗，以及 CPU、内存、磁盘和网络 监控时间轴能与 Benchmark 的请求时间轴对齐

防作弊里最要紧的一条是出网管控：评测对标的是 DeepSeek 官方 API，选手如果把请求悄悄转发到外部 API，六项指标都会失真。旁证手段是核对 GPU 利用率曲线和 token 产出是否对得上。

模型权重要不要允许选手自带、量化后的模型算不算同一个模型，这两条规则待定，它们决定冻结快照里要存什么。

每次运行必须记下的东西

原报告反复遇到的问题是数字不可比。这套 Benchmark 从第一天起就把配置和结果绑在一起，每次运行输出一份记录，至少包含：

  • 硬件：GPU 型号与版本、数量、驱动版本、CPU、内存、主机 ID。
  • 软件：引擎名称与版本、启动参数全文、Python 与 CUDA 版本。
  • 模型：名称、版本哈希、权重量化格式、KV 量化格式。
  • 拓扑：T1 到 T4 哪一种，路由策略。
  • 负载：轨迹文件的哈希、并发档位、是否加动态前缀。
  • 结果：六项指标的原始分布，不只是汇总值。
  • 成本：实例单价和计费方式。

缺任何一项的结果不进对比表。

预算怎么算

价格以 AutoDL 页面为准，这里只给算法：

  • 容器实例：四卡包周价 × 2 周，加数据盘扩容费（按日计）。
  • 裸金属：整机月价 × 1 个月。
  • 官方 API 参照线：轨迹总输入 token × 输入价 + 总输出 token × 输出价，再乘回放次数。agent 轨迹输入输出比很高，费用主要在输入侧，命中缓存的部分按折扣价算。

裸金属到手后容器实例即可退，两者重叠期越短越省。

待定事项

完整清单见 Benchmark 总览 的“需要拍板的规则”。与四卡机直接相关的：

  1. 比赛对标 DeepSeek 的哪个型号。它决定四卡机跑比赛模型还是替身。
  2. 选手的本地权重是否必须与官方 API 背后是同一版模型，是否允许自行量化。
  3. EdgePod 的 16 张卡是几台服务器。
  4. SLA 并发的三个阈值（首 token 延迟上限、慢尾生成速度下限、任务成功率下限）。
  5. 每成功任务成本在 EdgePod 上的口径（折旧、电价、利用率）。
  6. 裸金属订不订、订多久。
