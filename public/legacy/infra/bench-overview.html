Benchmark 总览：怎么读、怎么选、我们怎么测

业界基准已转向多轮轨迹回放；我们的四个 Benchmark 可以借工具和格式，规则和题目要自己定

这篇是什么

原报告只在硬件和接入层两处顺带提到 MLPerf、InferenceX 和 AA-AgentPerf，没有把 Benchmark 当作一个专题。这次补了四篇调研，本篇是它们的入口和汇总：先说业界现状，再把四篇的建议合成一套做法，分歧处给出裁决，最后列出需要拍板的规则。

文档 回答的问题
行业标准基准 MLPerf、InferenceX、Artificial Analysis 各自怎么测，同名指标差在哪
压测工具与方法论 用什么工具发压，指标的计时点怎么定，哪些做法会量错
负载、trace 与数据集 喂什么负载，哪些公开数据能直接用，三类 agent 的轨迹怎么录
Agent 质量基准 排版、深度调查、财务预测的产出怎么评，质量门槛怎么定

具体出处都在各篇里，本篇不重复引用。

业界现状：五句话

  1. 基准的负载已经从单次请求变成多轮轨迹。 MLPerf 新设的端点类测试、InferenceX 的 AgentX、AA-AgentPerf 都在回放 agent 轨迹，都用固定并发的闭环扫描，都允许跨请求复用 KV cache。这和报告的两条主线一致。
  2. 同名指标各家公式不同。 首 token 延迟从哪一刻算起、每 token 时间含不含首 token、生成速度的分母含不含首 token 延迟，各工具和各基准都不一样。官方文档承认，两个工具用默认配置打同一个服务，结果能差几十个百分点。
  3. 公开的 agent 负载几乎全是编程。 微软已公开 GitHub Copilot 的生产 trace 采样，Kimi、阿里百炼、SemiAnalysis 也有可回放的 trace，但都是聊天或编程。排版和财务预测没有任何公开的服务侧画像。
  4. 质量评测没有现成的整套基准可搬。 三类 agent 各有可借的零件（逐条二元清单、固定语料、检查点判分），但题目、规则检查和门槛都要自己做。
  5. 推理优化伤质量常常不体现在平均分上。 量化后通过率不变但重试变多、上下文压缩掉二三十个百分点、同一模型在不同服务商之间工具调用表现不同，都有公开报告。所以质量和效率不能分两个阶段各测一次就完事。

四篇之间的分歧与裁决

四篇是并行写的，有几处建议不一致。下面是我的裁决和理由，都可以改。

压测底座用谁

  • 分歧：工具篇和负载篇建议用 NVIDIA 的 AIPerf；行业篇建议用 MLPerf 端点测试的客户端。
  • 裁决：AIPerf 做底座，MLPerf 端点客户端的轨迹字段名拿来当我们的格式标准，GuideLLM 做交叉验证，AgentX 回放器当外部参照。
  • 理由：AIPerf 不需要 Kubernetes，能在 AutoDL 容器实例里直接跑；它原生支持几种公开 trace 格式，内建缓存隔离和 SLA 边界搜索，还能读 DeepSeek 接口返回的缓存命中字段，同一条命令能打本地引擎和官方 API。
  • 风险：AIPerf 原样回放我们自定格式的能力只读了文档，没有上机验证。这是开机后第一批要确认的事之一。

档位之间怎么清缓存

  • 分歧：行业篇建议在系统提示之后插入盐值；工具篇和负载篇建议在轨迹最前面加唯一前缀。
  • 裁决：默认用盐值，插在系统提示和工具定义之后；另跑一组前置唯一前缀的作对照。
  • 理由：系统提示跨任务共享是合法的优化，约有一万 token 的命中，不该被测法抹掉。前置前缀那组量的是纯会话内复用，两组之差就是跨任务共享的贡献。

任务完成时间以哪个为主

  • 分歧：工具篇建议主榜用模型时间，墙钟时间作副榜；行业篇建议报墙钟总时间并单列模型时间。
  • 裁决：两个都报，回放模式以模型时间为主，选手真实 agent 上场时以墙钟时间为主。
  • 理由：回放时工具时间是录下来的常数，不反映被测系统；真实运行时工具真的在执行，选手的工具设计也是比赛的一部分。

生成速度的口径

  • 分歧：方案草稿定义为只算 decode 段；Artificial Analysis 现行口径和 OpenRouter 公布的数字都含首 token 延迟。
  • 裁决：两种都算。内部比较用不含首 token 延迟的，对标外部公布数字时用含的，并在结果里写明。

质量和效率的先后

  • 分歧：比赛计划是先过质量门槛再测效率；行业篇和质量篇都指出高并发下的超时和截断会悄悄降低质量。
  • 裁决：流程不变，但在每队声称的 SLA 并发点上重跑一次质量评测，不过则该并发点无效。

六项指标：定稿建议

精确定义见工具篇的表。这里只列相对方案草稿的改动：

指标 草稿 改为
任务成功率 正常结束且通过校验 ÷ 发起数 不变；明确超时、报错、被限速、上下文溢出都进分母
任务完成时间 墙钟时间，拆模型和工具 报模型时间、工具时间、墙钟时间三个数
首 token 延迟 发出到第一个输出 token 请求到达计量代理，到第一个非空内容片段；开推理的模型另报到首个答案或工具调用片段的时间；按缓存命中比例分桶
生成速度 只算 decode 段 两种口径都报；token 数统一用一个分词器在客户端重算
SLA 并发 阶梯加压找拐点 闭环固定并发；每档按完成的任务数收尾而不是按时长；拐点处重复三次；报整条曲线
每成功任务成本 机时成本 ÷ 成功任务数 在 SLA 并发点上算，失败任务的机时计入；官方 API 一侧按实际缓存命中的折扣价算；两者并列展示不相减

首 token 延迟按缓存命中与否分开报这一条，三家行业基准都没有做，是我们比它们细的地方，保留。

负载：三步走

  1. 现在：用公开的编程 agent trace 做脚手架冒烟和 KV 实验。它不能评质量，只用来把工具链跑通。
  2. 本周内：在 agent 框架和模型端点之间放一个代理，录三类 agent 的真实轨迹。回放时用录下的历史消息，不用被测系统现场的输出，这样各系统看到的输入逐 token 相同。
  3. 开赛后：质量评测跑选手的真实 agent，效率评测回放冻结的轨迹，两者分开。

轨迹格式相对草稿要补的字段见负载篇，最重要的一条是把“距上次调用的间隔”拆成模型耗时和工具间隔，否则录制系统自身的快慢会混进负载。

质量门槛：一套流程

三类 agent 用同一套流程：同一个 agent、同一批题、同样的工具和资料，只换推理后端。一边是 DeepSeek 官方 API（参照线），一边是选手的系统。

  • 参照线至少跑五次，量出官方 API 自己的波动。
  • 门槛写成不劣于检验：选手成绩不低于参照线均值减去容差即过。
  • 硬伤（编造来源、文件打不开、格式不合规）单列，设绝对上限，不参与平均。
  • 加输出长度约束，防止靠截短输出或砍推理换速度。
  • 评委不用 DeepSeek 及其同族模型，型号和版本开赛前冻结；所有队伍的原始产出留存，第七周结束后用同一评委统一重评一次。
  • 财务预测的准确性一周内分不出高下，只作事后公布，不进门槛；进门槛的是分析正确性和与参照线的预测一致性。

容差、题量、长度范围的具体数值是质量篇给的建议值，需要用参照线的实测波动校准。

需要拍板的规则

这些问题调研回答不了，要主办方定。前三条最急，因为它们卡住别的工作。

  1. 比赛对标 DeepSeek 的哪个型号。 它决定四卡机能不能直接跑比赛模型，也决定引擎选型的结论。
  2. 选手的本地权重是否必须与官方 API 背后是同一版模型。 不是的话，不劣于参照线里就混入了模型差异。
  3. agent 由谁提供。 主办方固定 agent，还是选手自带并冻结后先对着官方 API 跑一遍。
  4. 深度调查的检索怎么放行。 出网默认全禁的前提下，用离线语料、白名单代理，还是两者都做。
  5. SLA 并发的三个阈值。 首 token 延迟上限、慢尾生成速度下限、任务成功率下限。
  6. 成本口径。 EdgePod 的折旧、电价和利用率假设；官方 API 用标价还是峰谷价。
  7. 是否允许选手自行量化、换投机解码头、压缩上下文。 调研的倾向是都允许，由质量门槛和长度约束把关。

这次调研给原报告补上的事实

  • MLPerf 新设了面向端点的多轮测试，客户端开源；MLPerf Storage 3.0 新增了 KV cache 测试，与主线一直接相关。
  • InferenceX 自 2026 年 9 月起支持 RTX PRO 6000 的服务器版，是与比赛硬件同架构的公开参照，但面板数据这次没能抓到。
  • Artificial Analysis 在 2026 年 11 月改了测速口径，输出速度现在包含首 token 延迟。
  • Copilot 的生产 trace 已公开采样子集，可以直接用来参数化负载。
  • 压测工具方面，两个常被引用的老工具已归档或正在淘汰。

没有解决的问题

  • 四篇都没有上机。工具的实际行为、公开 trace 的字段、这款卡上的引擎表现，都要等四卡机开机后验证。
  • 大型 MoE 模型在 FP8 或 4-bit 浮点下的 agent 任务质量，没有找到公开的对照研究。这正是比赛会遇到的配置。
  • 排版和财务预测两类 agent 的服务侧画像是空白，自录之前无从估计负载形状。
  • 各篇文末都列了各自没能核实的点，引用其中的数字前请先看那一节。
