SGLang

以前缀树复用 KV 起家的开源 LLM 推理引擎,与 vLLM 并列两强

与主线一 KV cache · 强用 radix tree 管前缀 KV,HiCache 再把它扩到主机内存与外部存储与主线二 Agent 负载 · 强为多次调用的 LM 程序而生;引擎内有 session_id 级的缓存保护,但不存对话

它是什么

SGLang 是一个开源的 LLM 推理引擎:把模型装进 GPU、对外提供 OpenAI 兼容的 API、并在一块或多块 GPU 上调度大量并发请求。它和 vLLM 做的是同一件事,是数据中心 GPU 侧开源引擎的另一极。README 现在的自我介绍是 "an open-source inference framework for large language, vision-language, and diffusion models, optimized for agentic workloads, large-scale serving, and RL rollouts";Apache-2.0 许可,截至 2026-11-18 有 39,036 个 star一手SGLang 仓库。

名字里的 "SGLang" 原意是 Structured Generation Language(结构化生成语言):它最初不只是一个服务器,还带一门嵌在 Python 里的小语言,用来写"由多次模型调用组成的程序"。今天大多数人用它只是当引擎用,但这个出身解释了它为什么从第一天起就围绕"前缀复用"设计。

和 vLLM 一样,它背后也有一家 2026 年成立的公司:RadixArk。

它做了什么

最初的前端语言

前端语言让你用带 @function 装饰器的 Python 函数写提示词程序:gen 让模型生成一段并存进命名变量(可带 choices、regex 约束),fork 把当前状态分叉成多条并行分支一手SGLang Frontend Tutorial。这种程序的特点是:多次调用共享同一段开头(系统提示、few-shot 例子、已有对话),只有结尾不同。前端语言至今仍在文档里,但 README 已不再提它,项目的重心是后端运行时。

RadixAttention:用一棵树记住所有前缀

普通引擎在一个请求结束后就把它的 KV cache(模型为每个 token 存下的中间状态)丢掉。RadixAttention 的做法是不丢:把所有请求的 token 序列组织成一棵 radix tree(基数树,一种边上可以挂一整段序列的前缀树),树上每个节点对应一段 token 及其 KV 在显存里的位置。新请求进来,沿树从根往下匹配,匹配到多深,就有多长的前缀不用重算;匹配在某个节点中间断开时,节点会被拆成两段。显存不够时,从叶子开始淘汰(默认 LRU),因为叶子是最长、最不可能被别人共享的尾巴。论文摘要称这是 "automatic" 的 KV 复用一手,摘要arXiv 2312.07104;节点拆分与按页粒度匹配的描述来自 HiCache 设计文档对 HiRadixTree 的说明一手HiCache 设计文档。

它与 vLLM 的 automatic prefix caching 目标相同、数据结构不同。vLLM 给每个写满的块算一条"哈希链",查的是一张扁平哈希表;SGLang 的树把"谁是谁的前缀"显式存下来,于是淘汰顺序、按优先级保留、按会话保护这些策略都可以直接挂在树节点上。两者孰快没有一手的对比数据。

结构化输出

支持 XGrammar(默认)、Outlines、Llguidance 三个语法后端,约束类型为 JSON schema、正则与 EBNF一手SGLang Structured Outputs。

Paged Experts:把 HiCache 的思路用到权重上

v0.5.23 新增的可选功能,面向消费级显卡。MoE(混合专家)模型的大部分参数是"专家"权重,但每个 token 只会用到每层 E 个专家中的 top_k 个。Paged Experts 在 GPU 上每层只留 K 个专家槽位,全部专家放在锁页的主机内存里,某一步需要而不在 GPU 上的专家再拷进来,计算仍在 GPU 上完成。PR 原话是 "It is the HiCache idea applied to expert weights"。自测:相对 SGLang 原有的 --cpu-offload-gb,16 GB 显卡上单流 decode 快 12 倍(int4)到 30 倍(FP8)一手,项目自测;对比对象是 SGLang 自己的旧方案SGLang PR #42557。K 的大小直接与 KV cache 争显存,所以它也是一个"专家驻留 vs 上下文长度"的调节旋钮。

与主线一(KV cache)的关系

关系很强。SGLang 的核心创新本身就是一种 KV cache 的组织方式,后续工作是把这棵树从显存延伸出去。

HiCache:三级缓存。 HiCache 把 RadixAttention 扩成三层:L1 是 GPU 显存,L2 是本机 CPU 内存,L3 是存储后端。L1 与 L2 是单实例私有的,只有 L3 可能跨实例共享。元数据结构叫 HiRadixTree,每个节点记录这段 KV 在哪一层(可同时在多层);L3 的元数据不常驻、不同步,用到时向后端查询一手HiCache 设计文档。一次请求的流程是:

  1. 本地匹配:走树找 L1/L2 命中,不拷数据。
  2. 从 L3 预取:对没匹配上的部分查 L3,命中超过阈值(默认 256 token)才加载到 L2。何时停止等待有三种策略:best_effort、wait_complete、timeout,文档建议生产用 timeout。
  3. 写回:prefill 之后把新 KV 从 L1 写到 L2/L3,策略有 write_through(每次都写)、write_through_selective(只写高频)、write_back(被淘汰时才写)。

L3 后端包括 Mooncake(RDMA、零拷贝)、HF3FS(DeepSeek 的 3FS)、NIXL(统一接口,下接 3FS、GPU Direct Storage、S3 兼容对象存储)、AIBrix KVCache、本地文件(file、fast_file)与自定义后端;另可用 --enable-lmcache 整体换成 LMCache一手HiCache 设计文档。v0.5.23 的 "HiCache & Radix Cache" 一节有数十条改动,其中 "Expose the Mooncake L3 object-key layout for external KV routers" 说明 L3 的键布局已被当作对外接口,供集群层路由器使用一手SGLang v0.5.23。

KV 量化与跨节点传输。 同一版本新增 NVFP4 KV pool(MSA-v1 稀疏后端),并有针对 FP8 KV pool 的优化条目;P/D 分离(prefill 与 decode 分到不同机器)时 KV 经 NIXL 或 Mooncake 传输,并带 KV checksum 校验一手SGLang v0.5.23。

一个需要保留的限定。 "RadixAttention 把首 token 延迟降 50–80%"这类数字只见于二手来源,HiCache 文档中 "GPU-assisted I/O kernels up to 3x faster" 是项目自述;本轮没有找到生产负载下前缀命中率的一手数据。

与主线二(Agent 负载)的关系

关系强,而且是三个引擎里唯一在引擎内部出现"会话"概念的——但要说清它是什么、不是什么。

出身就是"程序"。 论文标题里的 "Language Model Programs" 指的正是多次调用、带控制流、共享前缀的工作负载,评测任务第一项就是 agent control。主线二所说的"服务单位从请求变成程序",SGLang 在 2023 年底的论文里就是这么定义问题的。

Session-aware radix cache(有一手文档)。 启动参数 --enable-session-radix-cache,请求里带顶层字段 session_id。它做的事很克制:请求结束时,把它可复用的缓存叶子登记到这个 session 名下;淘汰时先踢没有任何 session 引用的 KV,再踢被引用的。文档明确了三条边界:其一,ID 只是缓存引用的标签,引擎不保存也不重建对话历史,每次请求仍须带完整 prompt;其二,这是 "soft protection, not memory pins",显存实在不够时被引用的 KV 仍会被淘汰;其三,仅 UnifiedRadixCache 实现了该功能。会话结束应调 POST /close_session,关闭只是撤销引用,不立即释放 KV一手SGLang Session-Aware Radix Cache。

Streaming session 与优先级淘汰(来自 Dynamo 文档)。 NVIDIA Dynamo 的 SGLang agent 文档描述了另外两个引擎开关:--enable-streaming-session(实验性)为会话开一个独占的 KV 槽,会话 KV 不参与淘汰,只在显式 close 或空闲超时(默认 300 秒)时释放,且只支持顺序追加——一次超过超时的长工具调用会导致会话被回收、需要重新 prefill;--radix-eviction-policy priority 让低优先级的叶子先被淘汰。文档写明 vLLM 与 TensorRT-LLM 不暴露这套 streaming session API一手,但出自 Dynamo 而非 SGLang 自己的文档Dynamo: SGLang for Agentic Workloads。v0.5.23 的 PR "session: Cache multimodal prompt token counts across turns" 的描述里出现了 Session.create_req 与 "streaming session shares its media history across turns",可旁证引擎代码里确有 Session 对象一手SGLang PR #44112。

工具调用与 Responses。 v0.5.23 的解析器改动包括按模型修复工具调用解析(GLM、MiniMax-M3、DeepSeek-V4.1)与 "Support Responses namespace tools and defer_loading";Rust 前端开始上报 cached_tokens,并支持 cache_salt一手SGLang v0.5.23。

总结:SGLang 的"会话"是缓存层面的归属标签与保护策略,不是对话存储,也不是程序级调度器。它把主线二的需求翻译成了主线一的机制。

与图中其他概念的关系

  • vLLM:直接竞争者;SGLang 论文的作者 Ying Sheng、Lianmin Zheng、Cody Hao Yu、Ion Stoica、Joseph Gonzalez 也都在 PagedAttention 论文的作者名单里,README 致谢中写明从 vLLM 学习设计并复用代码。

  • AIBrix:AIBrix KVCache 是 HiCache 文档列出的 L3 后端。
  • Dynamo:SGLang 是 Dynamo 的三种后端引擎之一;Dynamo 的 sticky session 路由与 SGLang 的 streaming session 配合使用。
  • llm-d:README 的生态表把 llm-d 列为部署与编排选项之一。
  • TPU Ironwood:v0.5.23 通过 SGLang-TorchTPU 插件支持 TPU7x(README 注明即 Ironwood)。
  • 昇腾:README 硬件表列出 Ascend A2、A3、950PR/DT,release notes 有昇腾部署 recipe。
  • EAGLE-3:SGLang 支持 EAGLE/EAGLE3 投机解码,旗下 SpecForge 用于训练 draft 模型。
