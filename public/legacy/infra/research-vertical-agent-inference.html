垂域智能体定制化推理效率优化

跨层协同提速：方向已明，数字待验。站得住的只有稳定前缀、任务编号、亲和路由这一薄层；三个垂域和 RTX PRO 6000 都没有公开的服务侧测量

截至 2026-11-18 的公开材料给出一个清楚但不讨巧的答案：让智能体一侧和推理框架一侧互相配合来提速，真正站得住的只有最薄的一层——上下文开头保持逐字不变、同一个任务的请求带同一个编号、路由到同一台服务实例、一轮工具循环之内不丢缓存；真实编程智能体靠这一层做到了 90%–97% 的缓存命中率。再往上的做法（预测工具耗时来保留缓存、以整个任务为单位排队、提前猜工具并执行、位置不同也复用缓存）都只有论文作者或厂商自己测的倍数，没有一项被独立第三方复现，而且对比的基线越新，倍数越小：对 2024 年的引擎是 4–15 倍，对已开前缀缓存和亲和路由的引擎是 1.64 倍，对已有全局缓存层的生产系统只剩 9%–15%。模型和解码一侧，不改变输出的手段（约束解码、后缀解码、遮蔽旧的工具结果）证据最干净；会改变输出的手段（4 位量化、换小模型、按步换模型）的损伤常被重试掩盖，只看总分看不出来。三家主要的智能体推理基准全都只测编程智能体，都没有把"任务完成时间"和"每成功任务成本"做成正式指标。演示文稿、深度研究、金融三个垂直领域有任务级的 token 数、花费和耗时，但没有任何缓存命中率、首 token 延迟、达标并发量的公开测量；RTX PRO 6000 上没有任何公开的智能体负载成绩。对比赛来说，这意味着赛题要考的东西（质量优先的整链计分、非编程垂域、这款显卡）恰好落在公开证据的空白处：没有现成数字可以当预期收益，主办方和选手都得先自己量出基线。

先把词说清楚：缓存为什么值钱，证据怎么分等级

大语言模型按 token（词元，模型读写文字的最小计量单位）工作。一次调用分两段：先把输入从头到尾算一遍，叫预填充（prefill）；再一个一个往外写 token，叫解码（decode）。从发出请求到收到第一个 token 的时间叫首 token 延迟（常缩写为 TTFT），主要由预填充决定；之后每秒吐出多少 token 叫生成速度。模型读每个 token 时会在每一层留下一组中间结果（称为 key 和 value），把它们存下来就是 KV 缓存：后面的 token 不必把前文重算一遍。如果一个新请求的开头和某个算过的请求逐 token 相同，这段开头的 KV 可以直接拿来用，叫前缀缓存；输入 token 里由缓存提供、不必重算的比例叫命中率。只能复用"开头"是因为模型的注意力是单向的：第 i 个位置的 KV 取决于第 1 到第 i 个 token，前面改一个 token，后面的 KV 就全部作废。

智能体（Agent）是让模型反复"想一步、调一次外部工具、读回结果、再想"的程序；工具调用就是让外部程序干活（搜网页、跑代码、渲染页面）。智能体每一步都要把全部历史重新发给模型，所以输入极长、输出很短，而且每一步的输入都是上一步输入再加一小段——这正是前缀缓存最能发挥的形状。本报告把一次任务里的全部模型调用和工具调用合称一个程序，其中每一次模型调用叫一个请求。垂域指垂直领域（本报告关心演示文稿、深度研究、金融三类）。纵向（跨层）协同指智能体一侧（怎么组织上下文、怎么拆任务）与推理框架一侧（怎么缓存、怎么排队、怎么路由）一起改，而不是各改各的。副本指同一个模型的多份服务实例；路由指决定某个请求交给哪个副本；SLA 指事先约定的服务水平（例如首 token 延迟不超过几秒），SLA 并发指在不破坏这个约定的前提下能同时服务多少个智能体。

下文每个数字后面带一个证据标记，沿用研究笔记的口径。**实测指研究员读了原文、原文里有测出来的数字；其中绝大多数是论文作者自己测自己的系统，少数由无利益关系的学术团队测得，会写明"独立"。厂商自述指产品方自己公布、无第三方复核的数字。仅摘要指只读到论文摘要页或搜索摘录，数字没有对照正文。转自本地笔记指数字来自此前的本地笔记，本轮没有重新打开原网页核对。推断**指研究员或本报告根据事实做的推理，不是来源里的结论。一个贯穿全文的前提需要先说：研究笔记在 KV 缓存和程序级调度两条线上都明确记录"本轮没有找到任何一项倍数被独立第三方复现"；唯一接近交叉验证的是后发论文把先发系统当基线重测，而那是竞争方自测。

生产数据显示智能体是"读得极多、写得极少"的串行长链

2026 年下半年出现了三份有分量的生产画像，数字相互吻合。微软对 GitHub Copilot 一周流量的分析（320 万用户、7.6 亿次模型调用）显示，单次调用的输入中位数是 6.8 万 token，其中 6.3 万来自缓存，输出中位数只有 247 个 token，输入输出比超过 275:1实测，微软自家数据arXiv 2608.00101。华盛顿大学 TraceLab 采集了 43 名开发者约 4,300 个 Claude Code 与 Codex 会话，中位一步是 11.9 万个前缀 token 加 875 个新追加 token 加 214 个输出 token，按 token 加权的总命中率 95.7%实测，独立学术团队arXiv 2606.30560。蚂蚁集团通用智能体平台两周的数据（1,169 万请求、1 万张以上显卡、全部是自己部署的开放权重模型）给出输入中位 7 万、输出中位 188，缓存输入占输入的中位数 98.1%实测，作者自述局限为单一平台、采样数据arXiv 2609.34432。蚂蚁这一份是研究笔记找到的唯一一份"自己托管开放权重模型加非纯编程智能体"的生产画像，与比赛场景最接近，但它的工具仍以命令和搜索读取为主，不是三个垂域中的任何一个。

这些画像带来三条会改变设计判断的事实。第一，智能体基本是串行的：Copilot 里 93% 的工具批次只含一个工具，蚂蚁平台 82.10% 的会话调用图宽度为 1，逻辑上的"兄弟请求"只有 0.225% 在服务时间上真正重叠实测arXiv 2608.00101arXiv 2609.34432。论文里"并行调用带来数倍加速"的结论依赖任务本身可并行，生产里天然的并行度很低。第二，资源集中在少数重会话上：蚂蚁平台每个任务的请求数中位只有 2，但选出的 14.3% 的会话占了 98.5% 的"上下文驻留量"（token 数乘以停留秒数）；Copilot 里 7.8% 的会话发生过上下文压缩，却占 44.2% 的 token实测arXiv 2609.34432arXiv 2608.00101。第三，工具耗时是"中位极短、尾巴极长"：TraceLab 测得单次工具调用中位 0.3 秒、第 99 百分位 3.6 分钟，超过 1 分钟的调用只占约 4% 却占工具总时间的 85%；Copilot 是中位 166 毫秒、均值 16.7 秒实测arXiv 2606.30560arXiv 2608.00101。

这些生产负载的输入输出比（275:1 到 372:1）比 2025 年以前调度论文常用的测试集高一到两个数量级——那些测试集的输入输出比约为 1:1 到 22:1实测arXiv 2502.13965。所以早期论文的结论外推到今天的负载时要打折推断。另一个要记住的边界是：三份画像都没有把效率和任务质量关联起来，也都不含演示文稿、深度研究、金融的生产数据。

缓存命中靠应用层守规矩；服务侧只有"软保护"没有硬保证

智能体一侧：各家独立得出同一套规则，但数字几乎全来自编程智能体

Manus、Claude Code、OpenAI Codex、Cursor、LangChain 各自公开的工程文章得出了同一套上下文写法。开头保持逐字稳定：Manus 举的反例是在系统提示开头放精确到秒的时间戳，改一个 token，其后的缓存全部失效厂商自述Manus 博客；Claude Code 把会过期的信息（时间、文件变化）放进下一条消息而不是改系统提示厂商自述Claude Code 博客。历史只追加不修改，序列化要确定：Codex 早期有一个缺陷，工具枚举顺序不一致就造成未命中厂商自述OpenAI Codex 文章。工具"屏蔽而不删除"：工具定义排在上下文靠前的位置，增删一个工具会让后面全部作废，所以做法是工具全集常驻，每一步用约束解码（生成时把不允许的输出概率压掉）限定这一步能选哪些工具厂商自述Manus 博客。不要中途换模型：缓存按模型隔离，Copilot 数据里换模型之后的命中率平均只有 8%转自本地笔记arXiv 2608.00101。压缩历史时沿用同一个开头：压缩指上下文快满时把旧历史改写成摘要；做摘要的那次调用如果换一套系统提示，就一点缓存都用不上，正确做法是用与原会话完全相同的系统提示和工具定义，最后追加一句"请总结"厂商自述Claude Code 博客。

实测命中率集中在 90%–97% 一档，但要看清口径。TraceLab 的 95.7% 拆开看，由工具结果触发的步是 97.5%，由用户发话触发的步是 84.4%；间隔超过 5 分钟开始出现低命中，超过 1 小时几乎全不中实测，独立arXiv 2606.30560。Copilot 在一轮交互内平均 90%、中位 98%，跨轮降到 55%转自本地笔记arXiv 2608.00101。未命中主要发生在三处：人停顿太久、换模型、压缩。公开的成本降幅是 41%–80%，出自一篇在三家商用接口上跑了 500 多次深度研究任务的论文；同一篇论文还指出"把全部上下文都缓存"的朴素做法有时反而增加延迟仅摘要arXiv 2601.06007。

这里有三处必须提醒。其一，网上流传的"Claude Code 命中率 92%、成本降 81%"只见于第三方文章，在 Anthropic 原文里找不到，不应引用；原文只说团队把命中率当作可用性指标并设了告警，没有给出数值实测：研究员读了原文确认无此数字Claude Code 博客。其二，这些规则是为按 token 计价的商用接口写的，研究笔记没有找到在自己部署的开放权重模型上逐条做对照实验的公开测量（例如"工具顺序不稳定使命中率下降多少"）；规则在自建环境下仍成立是因为根因在模型的单向注意力，这一点是推断，区别在于自建时省下的是显卡的预填充时间而不是账单折扣。其三，"屏蔽而不删除"是否让模型变笨没有公开的对照实验，Manus 自己也承认动作空间变大时模型表现下降。还有一处来源之间的直接分歧：Manus 主张把出错记录留在上下文里帮模型避免重犯，Cursor 则认为累积的工具错误会造成"上下文腐化"厂商自述Manus 博客Cursor 博客。

服务一侧：多副本时路由决定命中率，各家倍数不可横向比较

单台机器上，vLLM 和 SGLang（两个最常用的开源推理引擎）都默认会自动找最长的公共开头来复用：vLLM 把 KV 切成块，每块的指纹由"上一块的指纹加本块的 token"算出；SGLang 把所有请求组织成一棵前缀树实测：读了官方设计文档vLLM 前缀缓存设计文档。有多个副本时，问题变成同一段开头必须落到同一个副本，否则第 2 轮只有约 1/N 的概率碰上第 1 轮所在的机器厂商自述Dynamo 文档。按前缀或按会话做亲和路由的开源方案已经不少（llm-d、GKE Inference Gateway、AIBrix、NVIDIA Dynamo、SGLang router、Ray Serve），公布的首 token 延迟改善从 35% 到几十倍不等。差距主要来自基线有多差：llm-d 标题里的"57 倍"是对它自己的近似版路由的比值，测的是单一合成负载、单一模型厂商自述llm-d 博客；vLLM 接入共享缓存池后的"首 token 延迟降到 1/46"，对比的基线只命中系统提示（命中率 1.7%），衡量的是"有共享池"对"几乎没有跨轮缓存"转自本地笔记vLLM 博客。研究笔记没有找到任何中立机构在同一硬件、同一真实轨迹上横向比较这些路由方案的报告。

能稳妥引用的只有方向。vLLM 团队在真实编程轨迹回放中发现，简单的会话粘性路由（同一会话始终去同一副本）胜过按排队深度或缓存占用率做的均衡厂商自述vLLM 博客 2026-09-08。反过来，纯亲和有上限：谷歌的经验是所有人都请求同一份热门内容时会压垮一个节点，于是把排队权重调高转自本地笔记Google Cloud 博客。

把 KV 从显存挪到主机内存、硬盘或远端存储（称为卸载）是另一条已经产品化的路线，开源实现有 LMCache、Mooncake、SGLang HiCache、AIBrix。取回是否比重算划算，取决于加载带宽对比预填充速度：Mooncake 论文给的判据是 70B 级模型、8,192 token 的开头，在较新的显卡上需要每秒 19 GB 的加载带宽才划算，建议网络不低于 100 Gbps转自本地笔记Mooncake 论文。显卡越快，重算越快，取回的门槛越高。主机内存几乎总是划算、远端存储只在很长的上下文上有二三成收益，这个简化判断是研究员的推断。

"同一段内容出现在不同位置也复用 KV"的研究（CacheBlend、EPIC、KVLink 等）自报首 token 延迟改善 2–9 倍，但都只读了摘要，质量结论多以"可忽略"带过；研究笔记没有找到任何一家公开声明在生产中默认启用了非前缀复用——这是"未找到"，不是"确认不存在"仅摘要CacheBlendEPIC。

工具等待期间的缓存：论文有办法，开源引擎没有硬接口

默认情况下，引擎在一次生成结束后就把这段 KV 当作可回收。vLLM 的设计是没人引用的块按"最久未用先踢"淘汰，并且把一个请求的最后一块排在最先被踢的位置；设计文档里没有任何钉住或保留时间的内容实测：读了官方文档vLLM 前缀缓存设计文档。智能体只是去等工具，回来时尾部可能已被冲掉。

研究原型用"按预测的工具时长保留一段时间"来解决。最有代表性的一篇是 arXiv 2511.02230，这里有一处需要留意的记录分歧：负责缓存专题的研究员记录它在 v1–v3 名为 Continuum、2026-05-04 的 v4 改名 CacheTTL，页面上尚无代码仓库链接；负责调度专题的研究员记录的是"Continuum，v7 为 2026-09-08"，并给出仓库地址，同时注明正文另一处写"发表后开源"、状态有歧义。两份笔记指向同一个 arXiv 编号，引用时应合并成一条并注明读的是哪一版。它的做法是每次带工具调用的回复之后，给这段 KV 设一个保留时间，时间长短按该工具的历史耗时分布来选，到期自动释放。自报结果是多轮负载延迟降 1.12–3.66 倍，真实编程智能体负载上延迟最多降 8.18 倍；但同一篇论文另一节对小模型写的是"最多 2 倍"，读数字要看是哪一组实验实测，作者自测arXiv 2511.02230v4。

竞争论文之间互相重测的结果并不一致。ThunderAgent（显存不够时暂停整个程序而不是丢缓存）称吞吐是 Continuum 的 1.17–3.31 倍；Continuum 后来的版本则显示自己每分钟完成 144.9 步，ThunderAgent 是 114.8 步——两篇论文各自在自己的设置里赢了对方实测，均为竞争方自测arXiv 2602.13692arXiv 2511.02230。另一个系统 SAGA 自报对已开前缀缓存和亲和路由的 vLLM 任务完成时间降 1.64 倍，代价是峰值吞吐低约 30%；它的集群规模记录不一致：arXiv 摘要写 64 张显卡，本地笔记记录正文里有一组 32 张显卡的实验，引用时须注明出处仅摘要 + 转自本地笔记arXiv 2605.00528。

到 2026-11，开源引擎里实际能用的只有软手段：SGLang 可以让淘汰时先踢没有会话引用的 KV，文档明说这是"软保护，不是内存钉住"转自本地笔记SGLang 文档；NVIDIA Dynamo 提供每个请求的优先级提示。关于 Dynamo 能否按保留时间钉住缓存，两版文档互相矛盾：本地笔记依据 v1.0.1 文档记录，cache_control 字段可按保留时间钉住 KV，仅在 SGLang 上实现，标为实验性转自本地笔记Dynamo v1.0.1 文档；本轮读到的开发版文档明确写这个字段"不是受支持的缓存钉住请求扩展"，受支持的路径是"优先级驱动的"，按保留时间的指令是"未来的接口工作"实测：读了当前官方文档Dynamo 开发版文档。稳妥的说法是：Dynamo 在 1.0 时期以实验形式提供过，当前文档已退回到按优先级淘汰。结论是没有一个主流开源栈提供与商用接口"按时长保留"等价的硬保证。

值得注意的是，这件事的可用空间比论文数字显示的小。vLLM 的一份征求意见稿讨论里，有人用模拟指出保留指令只在暂停时间超过缓存自然驻留时间时才赢，收益上限约 25%，而且"降低一次性流量的优先级"比"钉住"更有效实测：读了讨论帖；模拟由参与者提供vLLM issue #37003。蚂蚁平台的离线分析也显示，按等待类型分别设保留时间比统一设置只少重算 1.0%–13.9%实测arXiv 2609.34432。

缓存不是白拿的：换模型、换适配器、加隔离都会清空它

KV 与具体模型绑定，也与挂在模型上的适配器绑定：vLLM 的块指纹里包含适配器编号，不同适配器之间不共享缓存实测：读了官方文档vLLM 前缀缓存设计文档。多租户共享前缀缓存有已被实证的安全问题：命中时首 token 更快，攻击者可以据此逐个 token 猜出别人的系统提示，一篇论文报告恢复准确率 89.0%实测，作者自测arXiv 2409.20002v5。现行对策是给请求加一个"盐值"，只有盐值相同才共享缓存，代价是不同租户之间相同的系统提示也不再共享。对只服务本组织的集群，公共领域前缀的共享是收益而不是风险推断。

程序级调度：只有"任务编号、会话亲和、优先级"进了开源栈

程序级调度指排队、计量、承诺服务质量时以整个任务为对象，而不是把每次模型调用当作互不相干的请求。相关系统分两代。2024 年的第一代（Parrot、Teola 等）要求开发者交出完整的调用关系图：Parrot 自报在多智能体编程负载上最高快 11.7 倍，但测的是 7B 到 13B 的小模型和 2024 年的基线实测，作者自测arXiv 2405.19888。2025–2026 年的第二代（Autellix、Continuum、ThunderAgent、SAGA、JITServe）把要求降到"每个请求带一个程序编号"，其余信息由服务端自己观察。Autellix 的做法是累计运行时间越多的程序优先级越低，自报同延迟下程序吞吐 4–15 倍，对比的是 2024 年的 vLLM v0.6.1实测，作者自测arXiv 2502.13965。JITServe 让客户端声明截止时间和首 token 目标，自报"满足约定的服务量"是基线的 1.4–6.3 倍、是 Autellix 的 5.3–6.1 倍实测，竞争方自测arXiv 2504.20068v3。顺带一提，Autellix 与会议版本 Agentix、JITServe 与早期版本 Tempo 很可能分别是同一工作改名，计数时应合并推断。

把这些数字按基线新旧排开，趋势很清楚：对 2024 年的引擎 4–15 倍（Autellix），对已开前缀缓存和亲和路由的 vLLM v0.15.1 是 1.64 倍（SAGA），对已有全局缓存层的生产调度器是 9%–15%（SMetric，仅摘要arXiv 2607.08565）。倍数必须连同基线版本一起引用，任何单篇论文的倍数都不宜直接写进方案的预期收益。研究笔记找到的唯一一条"智能体感知的调度已在生产集群上线"的数字来自蚂蚁的 PackServe：在 1,000 张以上显卡的生产集群中比原调度器少占 34.7% 资源，仍是作者自报仅摘要arXiv 2609.33224。

接口方面，开源栈里智能体能告诉服务端的信号只有四类：会话或程序标识、优先级、预期输出长度、缓存保留或预热提示。论文里反复出现的三类信号——提交完整调用图、声明截止时间、声明预期工具耗时——没有任何主流开源栈支持实测：读了 Dynamo、llm-d 文档；部分条目转自本地笔记Dynamo 请求扩展文档llm-d program-aware 说明。已有的接口也各有限制，而且是实现方自己写在文档里的：Dynamo 的优先级只有在真有排队时才生效，路由器排队默认关闭，优先级"不是显卡抢占"；它的服务端输出长度预测器会覆盖客户端给的优先级；llm-d 的"轮次越深越优先"策略在持续拥塞下会让新会话被丢弃而不是被派发实测：读了官方文档Dynamo 优先级调度文档llm-d program-aware 说明。这里还有一对方向相反的目标："已获服务最少者优先"让新任务、短任务先走，优化平均完成时间；"轮次深者优先"让老会话先走，优化缓存命中；同一个集群不能同时用两者推断。

并行与推测执行（提前猜下一步工具并先跑起来）的收益取决于猜得准不准和工具有没有副作用。用外部小模型猜，命中率在 10%–55% 之间；清华的 SPORK 让主模型自己分叉一个探针来猜，自报工具名预测准确率 74.6%–99.6%，一个通用智能体测试集上第 95 百分位延迟降 18%仅摘要arXiv 2607.03333。微软等的 PASTE 自报平均任务完成时间最高降 43.5%，但首选预测准确率最高只有 27.8%，论文没有给出"白跑的推测占多少"实测，作者自测arXiv 2603.18897。没有一篇推测执行论文报告了白跑的工具执行占比这个直接指标。

程序级调度要"有用"，研究员归纳出三个必要条件：集群真的在排队、程序之间长短差异大、KV 容量是约束；三条缺一，收益趋近于零推断。现有实验多在 96 个以上并行程序或人为打满的负载下进行，低并发（几十个智能体、十几张显卡）下程序级调度的边际收益没有论文专门测过。

模型和解码一侧：不改输出的手段证据最干净

约束解码与投机解码

约束解码指生成时用语法规则屏蔽不合法的 token，保证输出一定符合指定格式（例如合法的工具调用）。它已是各主流引擎的标配。一份基准测到，约束解码因为可以直接填入语法上唯一确定的 token（如固定的键名和标点）而不调用模型，反而可以比无约束快约 50%实测，作者中有被测工具的开发者JSONSchemaBench。新一代语法引擎 XGrammar-2 自报在一个函数调用测试集的两个子集上格式合规率到 100%厂商自述MLC 博客。它对推理质量的影响，文献是冲突的：上述基准测到约束后三项推理任务都不低于无约束基线，另一篇论文则报告格式限制越严推理能力下降越多实测 对 仅摘要JSONSchemaBencharXiv 2408.02442。"留一段自由思考、只约束工具调用那一段可以两头兼顾"是研究员的调和推断，未见直接裁决的论文。另外，用了约束解码不等于输出一定合规：同一基准发现第一代 XGrammar 在 38 个类别上放过了本应禁止的输出实测JSONSchemaBench。

投机解码指先便宜地猜出接下来几个 token，再由大模型一次并行核对，猜对的直接收下；在标准核对方式下输出与不用时一致。它分两类，资源特性相反。靠小网络打草稿的方法（如 EAGLE-3）论文数字是单请求时 3–6.5 倍，但红帽在接近生产的条件下（并发 1 到 200 取平均、前缀缓存开启）测到的吞吐提升只有约 20%，长输入摘要负载只有 9.5%转自本地笔记，厂商自测Red Hat Developer；高并发下收益消失，论文自己的表里批大小 56 时只剩 1.01 倍转自本地笔记arXiv 2503.01840。不用任何模型、只从提示和历史输出里查重复片段当草稿的方法（后缀解码和 n-gram 查找）只占处理器和内存，不抢显卡。后缀解码自报在智能体测试集上最高 5.3 倍，但 5.3 倍出自 Snowflake 内部的一条流水线，外部无法复现；公开的编程测试集上是平均 2.5 倍；在重复度低的通用测试集上它反而不如小网络打草稿的方法仅摘要，作者自测arXiv 2411.04975arXiv 2411.04975v2。它已集成进 vLLM实测：读了官方文档vLLM 投机解码文档。研究笔记没有找到独立第三方在公开智能体测试集上对后缀解码的复现。要注意投机解码不改善首 token 延迟，对"长输入、短输出"的步骤帮助有限，它改善的是写文件、写报告这类长输出步骤推断。

缩短输入和输出

输入一侧最稳的做法出人意料地朴素。观察遮蔽指把较早几轮的工具返回内容直接换成一句占位说明；一项独立学术评测在编程智能体上发现，它相对不做任何处理的智能体成本减半，解决率与"另调一次大模型做摘要"持平、有时略高仅摘要，独立arXiv 2508.21433。相反，在句子内部挑"信息量低"的 token 删掉的通用压缩器在智能体上几乎全军覆没：17 个测试组合的平均得分全部不超过 0.05，原因是标识符、括号、动作动词恰好是这类压缩器优先删的东西仅摘要，作者自测arXiv 2605.26596。输出一侧，让模型写一段代码一次调多个工具（而不是一轮一个调用）有节省，但幅度从三成到九成以上随场景变化极大；Anthropic 那个"降 98.7%"是单个示例的最佳情况厂商自述Anthropic 工程博客。这些研究几乎都在编程智能体上做，三个垂域上是否成立没有直接证据。

小模型、适配器、路由与量化

"小模型顶替大模型"最有影响的是 NVIDIA 的一篇立场论文（提出观点并论证，不是实验报告）。它说服务一个 70 亿参数的小模型比 700 到 1750 亿参数的大模型便宜 10–30 倍，但口径是延迟、能耗和计算量，不是每个成功任务的花费；它估计的"40%–70% 的调用可由小模型承担"是作者读代码后的估计，不是实测实测：读了原文，内容为作者陈述arXiv 2506.02153v2。研究笔记没有找到经同行评审的、在多轮智能体测试集上"微调小模型对当前前沿大模型"且同时报告每个成功任务成本的对照研究。这里还有一处来源之间的直接矛盾：这篇立场论文把一个蒸馏推理模型列为正面例子，而一项独立测评显示同一个模型的工具使用准确率约 43.6%、原版约 70%，并明确不推荐蒸馏推理模型用于智能体实测，独立ACBench。

适配器（常见的一种叫 LoRA）是只训练一小组附加参数、底座模型不动的微调方法，多个适配器可以挂在同一份底座上，工程上已成熟。它的坑在缓存：适配器改变了每个 token 的中间结果，底座算好的缓存对适配器无效，一条任务轨迹中途换适配器就要把全部上下文重读一遍。专门解决这一点的 aLoRA 自报端到端最高快 58 倍，但那是长提示、随机权重、对照零命中基线的合成上限；它的代码在作者的分支里，是否并入 vLLM 主线未能确认实测，作者自测，合成负载arXiv 2512.17910。

路由（每一步挑一个模型来答）在单轮聊天上降本证据成熟，搬到多步智能体里才刚有研究，共识是按步路由有路径依赖：前面选错便宜模型，后面会放大。唯一按"每个成功任务成本"报告的实验只有 12 个任务：分阶段用不同模型使每个解出任务的花费从 0.31 美元降到 0.17 美元，但模型调用轮数从 112 增到 205，作者自己说样本小、仍是实验厂商自述，小样本LiteLLM 博客。

量化指用更少的位数存模型权重以省显存、提吞吐。2026 年几项独立研究指向同一个结论：4 位量化通常不让总分明显下降，但会放大模型原有的毛病。一项研究里，调用"工具列表之外的工具"的比例从 19.5% 升到 38.3%，而测试集允许 10 次出错，这个容错把损伤藏住了；把容错缩到 2 次就出现 17 分的差距仅摘要，独立arXiv 2607.27275。另一项研究里，一个 7B 编程模型量化后"一次做对"从 17 题降到 0 题，"靠反复试出来"从 10 题升到 25 题，总准确率却没有统计显著变化仅摘要，独立NeurIPS 2026。KV 缓存本身也可以量化，vLLM 的 8 位 KV 缓存曾在 12.8 万 token 的长上下文检索测试上把准确率从约 91% 掉到 13%，修复后恢复到约 89%转自本地笔记vLLM 博客。多种有损手段叠加（量化的小模型再加路由降级）的交互效应没有任何研究覆盖。

推理框架被编程基准牵着走，垂域和这款显卡都在视野之外

框架做了什么，哪些数字能迁移

vLLM 和 SGLang 在 2026 年下半年的主要工作都围绕 SemiAnalysis 公司的 AgentX 基准展开。AgentX 回放 393 条真实的 Claude Code 会话，每请求输入中位 14.2 万 token、输出中位 444 个，前缀命中率 96% 以上转自本地笔记数据集卡片。vLLM 最醒目的成绩是每张显卡每秒 95.4 万 token，但这个数把缓存命中的输入也算进去了：图表背后的原始数据显示其中输出 token 只占 0.72%，该工作点第 90 百分位首 token 延迟是 7.97 秒而正文没有提，而且那篇博客完全没有输出质量数据转自本地笔记：本地精读报告读的是博客图表源文件vLLM 博客图表源文件。作为对照，DeepSeek 公布的线上服务首 token 延迟平均 0.4 秒转自本地笔记，厂商自述，原表为图片InfoQ。两者差一个数量级以上，一个是留有冗余的真实服务，一个是压到深度排队的基准点推断。

这些工作里能搬到别的模型和硬件上的是方法，不是数字：先量模型哪部分占时间，再把"显卡纯计算时间"和"系统开销"分开量，逐项开关报增量推断。有两个实用的事实值得记住。一是两个引擎的调度默认方向相反：vLLM 默认护生成速度，SGLang 默认预填充优先；比较两者时必须把这个旋钮显式调到同一目标转自本地笔记SemiAnalysis AgentX 文章。二是引擎在多种功能组合下出过"跑得快但结果错"的缺陷，例如缓存写错位置导致长共享前缀测试只有 2/128 正确，而吞吐基准看不出来转自本地笔记，SemiAnalysis 转述上游修复记录SemiAnalysis AgentX 文章。

框架为智能体做的事目前止于"把它当作前缀重复率很高的多轮聊天"。让外部程序告诉引擎"这段缓存留多久、搬到哪"的接口，在 vLLM 和 SGLang 里都还是征求意见稿：vLLM 那份已完成的只有"请求带会话编号"这一步，接口尚未定稿实测：读了讨论帖vLLM issue #51428。

基准怎么测，三个关键词各家怎么定义

三家主要基准（SemiAnalysis 的 AgentX、Artificial Analysis 的 AA-AgentPerf、MLCommons 的 MLPerf Endpoints）做了同一件事：把负载换成多轮智能体轨迹回放，允许跨请求复用缓存，固定并发数量逐档扫描。但三家都只测编程智能体（MLPerf 另含企业客服流程），都没有把任务完成时间和每成功任务成本做成正式指标。AgentX 自己承认"无法判断模型写的代码对不对、选的工具对不对"，它回放的是合成填充内容，输出长度被钉死，另用一个容易的数学题集做质量门槛——有批评指出 4 位与 8 位量化在这个题集上分数几乎相同，不足以裁定精度影响实测：读了方法指南；批评为一方意见，转自本地笔记AgentX 方法指南。需要留意，研究员抓到的这份方法指南页面自称是"与 SemiAnalysis 无关联"的非官方镜像，尽管域名属于 SemiAnalysis。

三个词都没有行业统一定义。goodput（满足服务目标的有效吞吐）有两个同名不同义的定义：学术上的定义是在满足达标率（例如 90% 的请求首 token 延迟低于某值）的前提下系统能承受的最大请求速率转自本地笔记DistServe 论文；各压测工具的定义是当前这一档负载下每秒完成的达标请求数转自本地笔记AIPerf 指标参考。前者是一个找出来的上限，后者是某个工作点上的读数，同一套系统两种算法给出的数不同。SLA 并发最成型的做法是 AA-AgentPerf 的：先定两项门槛，再把并发指数加倍直到破线，然后二分找最大值转自本地笔记AA-AgentPerf 方法页。它的门槛数值在两个来源里不一致：方法文章写三档速度是每秒 20、60、180 token，NVIDIA 博客写的是 30、100、300。每成功任务成本在智能体评测圈的通行算法是所有尝试的总花费除以成功次数，失败、重试、超时的花费都算进去；但现有数字全是商用接口价格，不是硬件成本实测，厂商合写Arize 博客。研究笔记没有找到任何把"质量、成功率、完成时间、首 token 延迟、速度、SLA 并发、成本"按优先级串成一套计分规则的公开先例。

连基础指标的名字也不能直接互比：同叫"每 token 时间"，有的工具含首 token，有的不含；一份社区记录里两种算法对同一次运行算出每秒 14.7 对 60.1 个 token转自本地笔记GuideLLM 指标文档Level1Techs 论坛。智能体场景的首 token 延迟门槛应该多严也没有公认答案：AA 给 3–10 秒，DeepSeek 线上是平均 0.4 秒，AgentX 的说法是 0.2–5 秒可用。

RTX PRO 6000：正式支持名单上有它，成绩栏是空的

研究笔记找不到任何一份在 RTX PRO 6000 上跑智能体负载（多轮、长上下文、带缓存命中）的公开结果。SemiAnalysis 的基准从 2026-09 起把 RTX PRO 6000 Server 列为正式支持硬件，但研究员查到的对比页上它的吞吐、成本、并发全是空值；研究员只查了一个对比页，没有穷举实测：读了仓库说明和对比页InferenceX 仓库InferenceX 对比页。

这款卡与数据中心显卡有两处实质差别。第一是计算代号不同（它是 SM120，数据中心同代产品是 SM100），许多专用算子只为后者写：以近期被各框架重点优化的 DeepSeek-V4.1-Flash 为例，vLLM 配方、SGLang 配方和 DeepSeek 自家开源的引擎 DeepInfer 三套软件都没有这款卡的档位实测：读了三处官方页面vLLM 配方SGLang 配方DeepInfer 仓库。第二是没有 NVLink（英伟达的显卡间高速直连），卡间通信走普通的 PCIe 总线，这会抬高每一层都要卡间通信的并行方式的代价。按总量算，16 张 96 GB 的卡共 1,536 GB 显存，装得下这个最低需要 614 GB 的模型，但"装得下"不等于"能跑"推断。一个在 8 张 RTX PRO 6000 Server 版上做生产部署的团队写道他们还没有在自己的硬件上跑起这个模型；同一团队在上一代模型上自报解码吞吐每秒 946.6 token，没有报告首 token 延迟和缓存命中，也没有第二来源复现实测 + 转自本地笔记，用户自述Helix 博客 2026-09-10Helix 博客 2026-08-14。

还要多一层小心：比赛硬件是 Max-Q 版（功耗上限 300 瓦），而上述支持名单、成本参数和用户记录都是 Server 版。三者同芯片同显存，但时钟和功耗策略不同，别人的数字不能直接套用；研究笔记没有找到 Max-Q 版多卡跑大型模型的任何公开数据。机柜里 16 张卡是一台机器还是两台、卡间是什么拓扑，研究笔记无从判断。

三个垂域有任务级的花费和耗时，没有服务侧的任何测量

三个垂域的公开数据有一个共同的缺口，需要先说：没有任何一个垂域的公开材料报告过前缀缓存命中率、缓存前后的首 token 延迟，或 SLA 约束下的并发量；现有成本数字几乎全是商用接口价格，没有一项是自己托管开放权重模型加推理框架调优的端到端对比。下面的数字回答的是"任务花多少 token、多少钱、多少时间、花在哪"，不回答"推理服务这一层能省多少"。

演示文稿：开销相差约 60 倍，差在轮数而不在写字

"固定蓝图加逐页生成"的结构天然适合多页共享同一段开头再并行展开，理论上缓存命中率会很高，但研究笔记没有找到任何演示文稿论文报告命中率——这一条是合理但未见实证的推断。Gamma、Manus、Kimi 等商业产品的内部架构也没有找到一手工程文章。

深度研究：一半到四分之三的时间在等网页，不在等模型

深度研究是"读得极多、写得很少"的负载。一个由 Perplexity 团队发布的基准上，各系统平均每个任务读入约 4 万到 78 万 token、写出约 0.9 万到 2.5 万 token厂商自述，经第三方聚合站转录DRACO 聚合页。各家的输入输出比从约 1.8:1 到约 88:1，相差近 50 倍；最可能的解释是统计口径不同（有的接口没有把搜索工具内部读到的网页计入输入），这是研究员的推断，来源没有明说。所以"深度研究的输入输出比是多少"没有统一答案。自己托管开放权重模型时网页全文必然进自己的模型，会更接近"几十万到上百万输入"的那一端推断。

唯一找到的时间拆解来自加州大学圣迭戈分校的一项试点研究：网页搜索平均占一个系统端到端时间的 73%（个别任务高达 91%），另一个开源框架是 50%；长任务抓回的网页量为 50 万到 250 万 token 以上。样本只有 10 个任务，原文还有两句互相矛盾的话实测，试点规模Demystifying Delays in Reasoning。这个比例如果在比赛任务上也成立，那么仅靠优化推理引擎最多只能压缩剩下的一半到四分之一的时间推断。

有文档记录的省法多数是厂商自述、没有公开数据可复核：子智能体各自用独立上下文并行搜索（Anthropic 称复杂查询的研究时间最多缩短 90%，并称多智能体系统比聊天多用约 15 倍 token）；读完先压缩再上报；原始网页存到外部只传引用；最终报告一次写成而不是并行写各节（LangChain 早期并行写各节，更快但各节互不衔接，后来改回）厂商自述Anthropic 工程博客LangChain 博客。有实测的一条是改善检索质量比多搜更省：同一个模型把检索器从关键词匹配换成向量检索，准确率从 55.9% 升到 70.1%，搜索次数还更少实测BrowseComp-Plus。"抓取结果缓存"没有找到任何一手文章给出命中率或节省数字。

金融：成本和耗时最公开，结论是"贵不等于准"

金融是三类里数据最公开的：Vals AI 的金融智能体榜单对每个模型同时公布准确率、每题成本和每题耗时。在它的 v1.1 版上，最好的模型准确率 64.37%，每题 0.80 美元、4 分 31 秒；第二名更贵（1.44 美元）而更不准。开放权重模型中，最好的是 60.39%、0.59 美元、9 分 48 秒实测Vals AI v1.1。v2 版上财务建模类最难，最好成绩只有 34.52%；榜单方的评语是中档模型只比领先者低几个点，成本却只是零头实测Vals AI v2。这些成本是接口价格，榜单没有公开每题的 token 构成、首 token 延迟或并发数据。

领域专属的做法里有证据的是三条。把算术交给计算器或代码：对多数前沿模型，计算器是用得最多的工具实测Vals AI v2。智能体之间传结构化报告而不是长对话：一个多角色交易系统每次预测约 11 次模型调用、20 次以上工具调用，便宜模型做取数和摘要，贵模型做决策；论文没有给美元成本，回测只覆盖三个月实测TradingAgents。小模型在智能体任务上有明确反例：榜单上一个最小档模型用了 34 轮（前沿模型 12 轮），逐个顺序调用计算器，多数检查项得零分实测Vals AI v2。领域微调的 7B 模型在封闭式金融问答上自报超过大模型，但作者承认训练集中在被测的两个数据集上厂商自述Fin-R1。

金融数据的稳定部分（已发布的披露文件）和易变部分（行情、新闻）界线清晰，榜单的工具设计本身就把两者分开，行情工具最多只占调用的 4.22%。据此"披露文件的解析结果长期缓存、行情放在提示词尾部"很合理，但研究笔记没有找到任何金融智能体实测这样做的收益推断。

横向看：多花未必更好

三份跨领域的成本受控研究结论相近。一项在通用助手测试集上的系统实验发现：把步数上限从 4 提到 8 有用，再往上准确率不涨而成本继续涨；每一步都做总结的记忆方案最贵；多次采样取最优从 1 次加到 4 次，准确率只从 53.33% 到 53.94%实测Efficient Agents。这与 Anthropic"token 用量解释 80% 的成绩差异"表面矛盾，研究员的调和是：把 token 花在读更多不同来源上有效，花在同一条路径上多想、多总结、多采样则收益很低推断。这三项研究同样都基于接口价格，没有一项测自托管条件下的每个成功任务成本。

对比赛方案的含义：考点落在证据空白处，基线只能自己量

以下分两部分。第一部分是从上述调研直接读出的含义；第二部分是改进思路，只作候选，未经验证。

从调研直接读出的含义

打分顺序与公开基准的测法是反着的，这是比赛的价值所在，也是它的难处。 比赛先看结果质量，质量达标后再看任务成功率、任务完成时间、首 token 延迟、生成速度、SLA 并发、每成功任务成本。现有三家基准先量吞吐和延迟，质量只做一道门槛，任务成功和任务成本都不在正式指标里；研究笔记没有找到把这七项按优先级串起来的公开先例。因此不存在可以直接照搬的考卷，可以借的是方法零件：固定并发逐档扫描、每档清缓存、只取稳定运行区间、报整条曲线、输出长度区间约束、质量与效率在同一工作点上各验一次。

"质量优先"需要过程指标和真实文本。 有损手段的损伤会被重试掩盖，所以质量门槛如果只看最终得分，量化和小模型带来的轮数膨胀、工具调用错误会漏过去，然后在任务完成时间和成本上显形。引擎在功能组合下出过吞吐基准看不出来的静默错误。合成内容回放下，任何依赖 token 内容的优化（投机解码、约束解码、内容感知的缓存淘汰）都测不出真实效果，所以垂域比赛必须回放真实文本或真跑任务推断，依据 AgentX 自述局限AgentX 方法指南。

任务成功率和任务完成时间主要由智能体一侧决定，推理框架一侧的可压缩空间需要先量出来。 一篇企业视角的论文在摘要里给了一个算例：每步 2% 的失败率会抹掉一个 20 步智能体的 2 倍解码优势仅摘要，全文未读，公式不能引用arXiv 2610.07094。演示文稿的开销由"渲染、检查、修改"的轮数决定；深度研究有一半以上的时间在等网页；金融的弱模型输在轮数。各基准对"任务完成时间"是否包含工具时间做法不一（Artificial Analysis 和 MLPerf 都不含），比赛规则需要明确这一点，因为它决定选手把力气花在推理上还是工具上。

首 token 延迟、生成速度、SLA 并发三项互相牵制，而且定义必须写死。 低延迟和高吞吐在现有框架里是两套不同的配置，不是一个参数的两端。同名指标各家公式不同，"并发"的含义也不同（存活的会话树数、活跃会话数、同时走轨迹的智能体数）。goodput 若要使用，须先说明取两个定义中的哪一个。统计上，给第 95 百分位一个可信区间至少要 72 个请求，第 99 百分位要 368 个转自本地笔记GuideLLM 指标文档；垂域任务每个要跑几分钟到几十分钟，样本量会是硬约束。固定并发的闭环测法量不出过载和积压，如果想考准入控制，需要在任务到达这一层另加开环过程。

每成功任务成本没有硬件口径的现成定义。 现有数字全是接口价格。把零件拼起来，一个自洽的写法是：在 SLA 并发点上，（显卡数 × 每卡每小时成本）÷ 每小时成功任务数，失败和超时任务占用的机时自然留在分子里。这是研究员拼装出来的定义，没有哪家基准正式这样做推断。它只有在指定工作点上才有意义。

清缓存的方式会直接改变名次。 AgentX 在每次播放的最前面加唯一标记，有意排除跨会话的缓存复用；MLPerf 把随机串插在系统提示之后，保留跨任务共享系统提示的命中转自本地笔记Endpoints 规则草案。垂域智能体的系统提示、工具定义、模板往往很长且每个任务都相同，选哪一种测法，决定了"共享领域前缀"这类优化算不算分。

硬件是最大的未知数。 没有这款显卡的智能体成绩，没有 Max-Q 版多卡大模型的数据，没有 PCIe 互联下各种并行方式的通信代价测量，近期最受框架关注的模型在这款卡上没有官方档位。模型选型和"能不能跑起来、单卡能到多少"必须真机实测，这是其余一切门槛的前提。同样，程序级调度的收益在十几张卡、几十个并发智能体的规模下没有人测过，而它的三个必要条件（真在排队、任务长短差异大、缓存容量吃紧）在这个规模下未必满足。

改进思路（候选，未经验证）

以下各条都是从空白处推出来的方向，没有一条有现成的实测支撑，只应作为候选交给实验去裁决。

候选一，让垂域智能体直接向服务栈声明结构。垂域智能体的步骤、工具集和每种工具的耗时分布比通用智能体可预测，而选手同时掌握智能体和服务栈，客户端的声明是可信的。开源栈目前不接受"预期工具耗时"这类字段，vLLM 讨论帖里的模拟提示收益上限约 25%，且只在暂停时间长于缓存自然驻留时间时出现；深度研究的慢工具可能落在这一段，演示文稿和金融未必。

候选二，把领域公共前缀（系统提示、工具全集、模板、固定资料）在服务启动时预热，并让并行的子任务以逐字相同的开头展开。三个垂域在结构上都具备条件（逐页生成、子智能体、多分析师），却都没有公开测量，幅度无从估计；它是否计分还取决于上面说的清缓存方式。

候选三，一条任务轨迹固定用一个模型或一个适配器，用"调思考长度"代替"换模型"。依据是换模型后命中率 8%、适配器之间不共享缓存；按阶段固定分工比每步动态路由更保缓存是推断，没有对照实验。

候选四，先上不改输出的手段，再逐项验证会改输出的手段。约束解码把工具名做成枚举以消除不存在的工具名；后缀解码用于模板化的长输出；观察遮蔽用于旧的工具结果。量化、小模型、路由每上一项，用同一套任务复测成功率、轮数、工具调用错误率三项。其中观察遮蔽和后缀解码的证据都来自编程智能体，在三个垂域上需要重测。

候选五，垂域内的减轮数做法：演示文稿用规则或页面几何计算代替每次看图检查（有两篇论文采用，无单项节省数字）；金融让模型一次写一段代码完成多步计算以代替多轮计算器调用（榜单只记录了现象）；深度研究并行搜索、压缩上报，压缩频率放低。

候选六，16 张卡怎么分组。没有 NVLink 时，每层都要卡间通信的并行方式代价上升，"多个小组各自服务、靠路由把同一会话钉在同一组"可能比一个大组划算；首轮长输入与后续短追加分开处理（Together 自报约 40% 的每卡容量提升）在开源栈里没有现成实现。这两条都没有在这类硬件上的实测。

结论

这次调研改变的认识有两点。第一，"纵向协同"在公开材料里的实际形态比口号窄得多：它不是引擎学会预测智能体，而是智能体守住几条写上下文的纪律，再把一个编号交给路由器；这一薄层已经拿走了大部分可拿的好处，其上每加一层机制，就多一份对预测准确率的依赖和一种饿死新任务的方式。倍数随基线变新而缩小的趋势说明，方案的预期收益应该用"相对一个配置良好的基线还能多出多少"来表述，而这个数字今天没有人替我们量过。

第二，比赛最有价值的产出可能不是名次，而是数据。公开领域缺的正是比赛要做的事：三个非编程垂域在自托管开放权重模型上的服务侧画像（输入输出比、命中率、工具耗时分布）、这款显卡上的智能体负载曲线、一套把质量、任务成功和硬件成本接在一起的计分方法，以及低并发小集群下程序级调度到底值不值。先把基线和测法立住，再谈优化幅度，顺序不能反；否则选手之间比出来的差异，很可能主要来自清缓存的方式、并发的定义和首 token 延迟的停表规则，而不是来自优化本身。
