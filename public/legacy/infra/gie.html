GIE

Kubernetes 官方推理路由标准:网关把选 Pod 交给外部调度器

与主线一 KV cache · 中标准本身不含 KV 逻辑,但它规定的插槽正是前缀/KV 感知打分器接入网关的位置与主线二 Agent 负载 · 弱只提供优先级这类请求级语义;会话与程序级调度在 2026-08 后都归 llm-d

它是什么

GIE 是 Gateway API Inference Extension 的缩写(项目自己也写作 GAIE,或称 Inference Gateway / IGW)。它是 Kubernetes 社区的一个官方项目,由 WG-Serving(服务工作组)和 SIG-Network(网络特别兴趣组)推动,官网的自我定位是"一个优化在 Kubernetes 上自托管生成式模型的官方 Kubernetes 项目",目标是让通往推理工作负载的路由在整个生态里"改进并标准化"一手GIE 官网。

要理解它,先要知道两个背景概念:

  • Gateway API 是 Kubernetes 上描述"流量怎么进集群"的标准接口,是老的 Ingress 的继任者。用户写 Gateway(一个入口)和 HTTPRoute(哪些路径转给哪个后端)两类资源,具体由 Envoy、Istio、NGINX、各家云负载均衡器等二十多种实现去执行。
  • 普通 HTTP 负载均衡假设请求短、无状态、彼此差不多,所以轮询就够了。LLM 请求不是这样:Kubernetes 官方博客的原话是,LLM 推理会话"往往长时间运行、资源密集、且部分有状态",一个 GPU 模型服务器会同时维持多个会话并保有内存中的 token 缓存一手Kubernetes 博客。轮询不知道哪个副本队列短、哪个副本已经缓存了这段 prompt。

GIE 做的事情就是在 Gateway API 上加一个标准的"插槽":网关在转发推理请求之前,先去问一个外部组件"这次该发给哪个 Pod"。这个外部组件懂模型服务器的指标和缓存状态。GIE 规定插槽的形状,不规定里面的算法。

它做了什么

InferencePool:一类新的后端

InferencePool 是 GIE 的核心资源,也是目前唯一稳定(v1)的 API。它描述"一组跑着同一种模型服务器的 Pod",可以像普通 Service 一样被 HTTPRoute 当作后端引用。Kubernetes 博客的说法是它"类似 Service,但专为 AI/ML 服务需求而设,并且了解模型服务协议"。它比 Service 多出的关键字段是 endpointPickerRef——指向负责为这个池子选 Pod 的那个外部服务。面向的角色是平台管理员:管"在哪里、怎么服务"。

Endpoint Picker 与 ext-proc

被 endpointPickerRef 指向的组件叫 Endpoint Picker(EPP)。网关和 EPP 之间用 Envoy 的 External Processing 协议(ext-proc)通信:这是一个 gRPC 流,代理把请求头和请求体发给外部进程,外部进程可以读、改、并告诉代理把请求送到哪个具体地址。请求流程是一手GIE 官网:

  1. 网关按标准的 Gateway 与 HTTPRoute 规则,判定这个请求属于哪个 InferencePool。
  2. 网关把请求信息转给该池子的 EPP。
  3. EPP 依据从各 Pod 抓取的指标(排队长度、KV cache 占用、已加载的 LoRA 适配器等)和配置的目标,选出一个 Pod。
  4. EPP 把结果告诉网关,网关把请求路由过去。

因为走的是 ext-proc 这个已有协议,任何支持 ext-proc 和 Gateway API 的代理都可以变成"推理网关",不需要各家重新发明调度器接口。这是 GIE 作为标准最实际的价值。

模型与优先级:InferenceModel 到 InferenceObjective,再到迁出

最初的设计里还有第二个资源 InferenceModel,面向模型负责人:把一个对外的模型名映射到池子里的实际模型,并附带流量拆分或优先级策略一手Kubernetes 博客。之后它演变为 InferenceObjective(只表达优先级等服务目标),始终停留在 alpha(v1alpha2);更名发生在哪个版本我没有逐一核对未复核。到 v1.6.0,发布说明写明 InferenceObjective、InferenceModelRewrite、EndpointPickerConfig 三个实验性 API 从 GIE 中移除,迁到 llm-d(在那里的 API 组是 llm-d.ai)。

所以今天的 GIE 比很多介绍文章里描述的要"瘦":稳定的只有 InferencePool 和 EPP 协议。

v1.6.0 的分家

v1.6.0 发布说明的三条要点一手GIE releases:

  • 功能完整的 Endpoint Picker、Body-Based Routing(BBR,从请求体里读出模型名用于路由)、Latency Predictor "已迁到 llm-d 仓库,进入它们专属的生态";
  • GIE "现在专注于核心的 Kubernetes Gateway API 推理规范、CRD 与一致性定义";
  • 新增 Lightweight EPP(lwepp),一个最小的参考 ext-proc 实现,专门用来跑一致性测试;同时 endpointPickerRef 变为可选字段。

这次迁移之前,GIE 仓库既是标准又是参考调度器,前缀缓存打分器、flow control、延迟预测都在这里开发;之后分工变成"标准留在 kubernetes-sigs,调度器实现归 llm-d"。报告对这一点的描述属实。

2026 年的现状

  • 最新版本 v1.6.2(2026-09-17)。llm-d v1.0.0 的组件表里,GIE 一栏的类型从"Helm Chart + CRD"划掉了 Helm Chart,只剩 CRD,印证了分家后的定位一手llm-d releases。
  • 谁实现了它:官网的实现列表目前列出五个——阿里云 ACK Gateway with Inference Extension(唯一附了一致性报告,通过 v1.5.0 的 Gateway profile)、Istio(建议 1.28.0 以上)、Agentgateway(Rust 写的 AI 网关)、Higress、NGINX Gateway Fabric一手GIE 实现列表。官网首页另外提到 Envoy Gateway、kgateway、GKE Gateway 可以扩展成推理网关。列表规则是:最近三个小版本内没有通过一致性报告的实现可能被移除,所以它会变动。
  • GKE Inference Gateway 是最重要的托管实现,2025-09-10 GA。Google 的迁移文档说明它已从预览期的 v1alpha2 迁到 v1 InferencePool。
  • 生产证据:Google 2026-02-06 的工程博客披露,Vertex AI 采用 GKE Inference Gateway 后前缀缓存命中率从 35% 升到 70%,Qwen3-Coder 的 TTFT 降 35% 以上,DeepSeek V3.1 在突发聊天负载上 P95 TTFT 改善 52%厂商自述,生产流量Google Cloud 博客。这是 GIE 路线目前最硬的一条数据,但它来自 Google 自己的产品和自己的网关。
  • 竞争位置:在 Kubernetes 生态内它是事实标准,KServe、llm-d、多家网关都围绕 InferencePool 对齐;NVIDIA Dynamo 的路由器也可以作为 EPP 插件接入(v1.6.0 变更日志里有 dynamo integration 的修复条目)。不走 Kubernetes Gateway 的方案(如 Ray Serve LLM)不需要它。

与主线一(KV cache)的关系

关系中等,而且是间接的。要分清两层:

标准层面没有 KV 的内容。 InferencePool 和 ext-proc 协议里没有任何字段描述 KV cache。GIE 只规定"网关去问一个外部组件"。

但这个插槽就是 KV 感知路由进入网关的地方。 KV cache 从"单进程内的数据结构"变成"集群级资源"的第一步,是路由器必须知道哪个副本缓存了什么;在 Kubernetes 上,这个路由器就是挂在 InferencePool 后面的 EPP。在 2026-08 分家之前,前缀缓存打分器就是在 GIE 仓库里开发的(v1.4.0 加了 prefill-aware prefix 插件,v1.6.0 的变更里还有前缀缓存最大 token 参数与基准场景)。打分的做法有两类:一类是 EPP 自己记一张"最近把哪些前缀哈希发给了谁"的近似表;另一类是让引擎上报真实的 KV 块增删事件。两者现在都归 llm-d 维护,细节见 llm-d 一篇。

Vertex AI 的案例说明了机制上的一个要点:不能只最大化命中率。Google 写道,若只按缓存亲和路由,"所有人都请求同一份热门文档时,会造出一个被压垮的节点,而其他节点闲着"。他们用三个打分器加权:前缀、排队长度、KV 占用率,默认权重 3:3:2;上线新的聊天模型时调成 3:5:2,让调度器"即便有缓存命中也绕开过热节点"厂商自述Google Cloud 博客。

至于 KV 的分层卸载、跨节点传输,GIE 完全不涉及。

与主线二(Agent 负载)的关系

关系弱。GIE 的抽象单位仍然是单个 HTTP 请求。它和 agent 负载沾边的地方有两处:

  • 官网把"服务优先级"列为特性:让延迟敏感的在线聊天优先于可以等的任务。这是请求级的优先级,不是会话或程序级的。
  • Vertex 博客把负载分成"上下文很重的(如编码 agent,瓶颈是重复计算)"和"突发的(如聊天,瓶颈是排队)"两类,前缀感知路由主要帮到前一类。

真正面向 agent 的机制——按程序做公平性、按会话轮次排优先级、会话亲和、带优先级带的 flow control——最初有一部分是在 GIE 的 EPP 里孵化的,但 v1.6.0 之后都随 EPP 迁到了 llm-d,连 InferenceObjective 这个表达优先级的 API 也迁走了。因此今天说"GIE 支持 agent 负载"并不准确:它提供的是让这些策略能插进任意网关的标准接口。

它仍然出现在图里的理由是:没有这个标准,llm-d 的调度器就只能绑定某一个代理;有了它,同一个调度器可以挂在 GKE、Istio、Envoy、阿里云 ACK 等不同网关后面。

与图中其他概念的关系

  • llm-d:GIE 定标准,llm-d 是主要实现;2026-08 起 GIE 的完整 EPP 代码归 llm-d。llm-d v1.0.0 依赖 GIE CRD v1.6.2。
  • KServe:KServe 的 LLMInferenceService 控制器会自动创建 InferencePool 和对应的 HTTPRoute,并在 v0.18 起把 GIE 的 CRD 打进自己的安装包。
  • Dynamo:Dynamo 的路由器可作为 EPP 插件运行在 GIE 网关之后。
  • AIBrix:Kubernetes 博客的作者之一来自 ByteDance;AIBrix 本身是并行方案,是否实现 InferencePool 本文未核实。
  • vLLM、SGLang、TensorRT-LLM:它们是 InferencePool 里被路由的模型服务器,EPP 依赖它们暴露的指标。阿里云 ACK 的文档称其网关支持这三种引擎报告笔记,未复核。
  • LiteLLM:GIE 官网把 LiteLLM 列为可与自托管模型配合的 AI 网关之一;两者层次不同,LiteLLM 管跨供应商的 API 聚合,GIE 管集群内选 Pod。
  • 与 OpenRouter、MCP、Open Responses、AA-AgentPerf、Mooncake、llama.cpp、MNN、压缩与编译层各概念、硬件层各概念未发现直接关系。

存疑与未核实

  • 报告称 GIE、llm-d 各版本"年份是推断的"。本次通过 GitHub API 的 published_at 取到了带年份的完整时间,报告里列出的 v1.4.0(2026-03-20)、v1.5.0(2026-04-19)、v1.6.0(2026-08-17)、v1.6.2(2026-09-17)全部核实无误。
  • 报告笔记写"InferencePool v1 GA 的确切日期未能确认"。现已确认:GIE v1.0.0,2025-09-09,发布说明明确写 InferencePool 升 v1。
  • 报告说组件"迁入 llm-d 仓库"。发布说明原文链接的是 llm-d 这个 GitHub 组织;具体落在 llm-d/llm-d-router 等仓库,不是 llm-d/llm-d 主仓库。
  • InferenceModel 改名为 InferenceObjective 的确切版本未核对。
  • 官网实现列表里只有阿里云 ACK 附了一致性报告;报告笔记提到的 agentgateway 一致性报告我没有单独打开。Envoy Gateway、kgateway、GKE 是否通过了当前版本的一致性测试,未核实。
  • Kubernetes 博客里的早期基准(H100、10 个副本、ShareGPT、100 到 1000 QPS)只有定性结论,且测的是 2025 年中的版本,不宜引用为现状。
