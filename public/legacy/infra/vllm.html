vLLM

伯克利起源的开源 LLM 推理引擎,数据中心 GPU 侧的事实标准之一

与主线一 KV cache · 强分页 KV 的发源地;块哈希前缀缓存、多级 offload 与 connector 都在引擎内与主线二 Agent 负载 · 中引擎本体无状态,靠前缀缓存与解析器支撑 agent;会话状态放在外置网关

它是什么

vLLM 是一个开源的"推理引擎"。所谓推理引擎,是指把一个训练好的大语言模型装进 GPU、对外提供 API、并负责把成百上千个并发请求排进同一块 GPU 里高效执行的那层软件。模型本身只是一堆权重;谁先算、谁后算、每个请求的中间状态放在显存哪里、显存不够时踢掉谁,都由引擎决定。vLLM 自己的定位是 "A high-throughput and memory-efficient inference and serving engine for LLMs",Apache-2.0 许可,截至 2026-11-18 在 GitHub 上有 97,174 个 star一手vLLM 仓库。

它同时是一家公司的基础:2026 年 1 月,vLLM 的核心维护者成立 Inferact,做 vLLM 的商业化。所以图里的"vLLM"既指项目,也隐含这家公司。

它做了什么

连续批处理:让 GPU 不等人

LLM 生成文字是一个 token 一个 token 往外吐的。最朴素的批处理是凑齐一批请求一起算、等这批全部生成完再接下一批,短回答要陪长回答空等。连续批处理(continuous batching,学术源头是 Orca)改成每生成一步就重新组一次批:谁结束了就让位,新请求随时插进来。这是 vLLM README 列出的基础能力之一一手vLLM 仓库。

PagedAttention:把操作系统的分页搬到 KV cache

模型每处理一个 token,都要为它在每一层存下一对 key/value 向量,供后面的 token 做注意力计算时查阅,这份中间状态就叫 KV cache。它很大,而且随着生成不断变长。早期系统给每个请求预留一整块连续显存,按最大长度留,结果大量显存被占着不用。PagedAttention 的做法和操作系统的虚拟内存一样:把显存切成固定大小的块(block),请求需要多少就按需领多少块,块不必连续,用一张"块表"记录逻辑位置到物理块的映射。论文摘要称这样几乎消除了碎片浪费,并允许请求内与请求间共享同一块 KV一手,摘要arXiv 2309.06180。分块之后,"共享前缀"才变得可行:两个请求开头相同,就让它们的块表指向同一批物理块。

2026 年的现状

v0.34.0(2026-11-16)含 "1,061 commits from 412 contributors (120 new)",最近五个版本间隔都在两周左右(v0.30.0 为 09-22,v0.31.0 为 10-05,v0.32.0 为 10-18)一手vLLM v0.34.0。这一版的三件大事:extensible KV cache 默认开启;Model Runner V1 移除、V2 成为唯一 GPU runner;默认 block size 从 16 改为 64。官方发布 CUDA 13.0、ROCm 10.0、Intel XPU 与 CPU 的 wheel 和镜像。同一份 release notes 中列出的性能数字(如 Step5 在 4×GB200 上 decode 最高 1.95 倍)都是项目自测,绑定具体模型与硬件厂商自述。

与主线一(KV cache)的关系

关系很强,而且全部落在引擎内部的具体机制上。

分配:从"估算"到"实测"。 过去 vLLM 在捕获 CUDA graph 之前就要确定 KV cache 大小,只能靠估算,并留出约 8% 的显存余量防止估错(PR 描述写旧默认是 gpu_memory_utilization=0.92,192 GiB 的卡约闲置 15 GiB)。extensible KV cache 改为先用驱动的虚拟内存 API 预留一整段地址空间而不挂物理内存,warmup 之后实测真正空闲的显存,再一次性把物理内存映射进去;地址不变,所以已捕获的 CUDA graph 仍然有效。PR 自报在 GB200 上八个模型的 KV 容量多 4–10%,引擎初始化(不含权重加载)快 21–34%一手,项目自测vLLM PR #56492。release notes 给的例子是 MiniMax-M3 在 H200 上从 433k 增至 672k tokens,代价是部分模型并发 128 时 TPOT 上升 6–18%一手vLLM v0.34.0。

前缀共享:块哈希链,不是树。 vLLM 的 automatic prefix caching 给每个写满的 block 算一个哈希,输入是"父块的哈希 + 本块的 token + 额外信息(LoRA ID、多模态输入哈希、cache salt)"。因为含父块哈希,一个块的身份就代表了它之前的整段前缀。新请求到来时逐块查哈希表,命中就把引用计数加一、直接复用。空闲块放在一条双向链表里按 LRU 淘汰。文档明说 "We only cache full blocks",所以复用粒度是 block:默认 block size 改成 64 之后,前缀末尾不足 64 个 token 的零头不会被缓存一手;最后一句是由文档规则推出的结论vLLM Prefix Caching 设计文档。与之相对,SGLang 用一棵 radix tree 显式保存 token 序列之间的前缀关系,淘汰与调度可以沿树的结构做;vLLM 是一张扁平的哈希表,结构更简单,但"哪些前缀互为父子"这层信息不在数据结构里。

offload 与 connector:KV 离开显存的出口。 vLLM 用 --kv-transfer-config 配置 KV connector。内置的 OffloadingConnector 默认只有一层 CPU 内存(CPUOffloadingSpec);换成 TieringOffloadingSpec 后可在 CPU 层之下串接次级层:文件系统(fs)、经 NIXL 访问的 S3 兼容对象存储(obj)、经 NIXL/RDMA 在实例之间共享的 p2p,以及树外自定义类型。文档写明次级层在多节点引擎上不支持一手vLLM KV Offloading 用法。v0.34.0 的 connector 更新包括 NIXL(P/D 分离时传输 KV,新增 push 模式)、Mooncake(selective leases、每 GPU 一个 RDMA 设备)与 LMCache MP connector一手vLLM v0.34.0。也就是说,报告里"KV 变成跨显存、主机内存、SSD 与网络存储的层级",在 vLLM 里对应的就是这套 connector 接口。

KV 量化。 --kv-cache-dtype fp8 把 KV 存成 FP8,每 token 的 KV 存储约减半。vLLM 博客披露,在 H100 + FlashAttention-3 上,128k 的 needle-in-a-haystack 准确率曾从 91% 掉到 13%,原因是超长上下文下 Tensor Core 的累加精度不足;改成两级累加后恢复到 89%一手vLLM 博客 2026-04-22。

调度感知缓存。 v0.34.0 新增可选的 cache-aware admission:严格先来先服务时,一个"冷"请求先被放行,它申请显存块会把后面排队请求马上要用的缓存块挤掉;新选项让调度器在等待队列的一个有限窗口内,优先放行前缀已在缓存里的请求。默认关闭一手vLLM PR #54625。

与主线二(Agent 负载)的关系

关系中等。引擎为 agent 负载做了不少事,但引擎本体没有"会话"或"程序"这个概念,这一点有一手证据。

  • Responses API 是无状态的。 v0.34.0 的 Rust 前端新增的是 "stateless Responses API",PR 描述写明 "store-dependent features rejected or 404"一手vLLM PR #63902。
  • 状态被放到引擎之外。 vllm-project/agentic-api 是一个独立的 Rust 网关,README 的说法是真实 agent 应用需要 "conversation state, tool-call loops, and multi-turn orchestration",这些由网关负责:用 previous_response_id 或 Conversations API 管理历史,用 SQLite/PostgreSQL 持久化,在网关侧执行 web search、MCP、代码解释器等工具;它转发给 vLLM 的请求在架构图里标注为 stateless一手agentic-api。
  • 工具调用与结构化输出。 工具调用靠 --enable-auto-tool-choice 加按模型家族选择的 --tool-call-parser(文档列出约 35 个解析器名);tool_choice 为指定函数或 required 时,引擎用结构化输出约束解码,保证输出能被解析一手vLLM Tool Calling。结构化输出后端是 xgrammar 与 guidance,默认 auto 按请求选择一手vLLM Structured Outputs。
  • 多轮前缀复用。 agent 每一轮都把完整历史重新发来,引擎靠上面的块哈希前缀缓存避免重算;cache_salt 可把复用限制在同一信任组内。这是隐式的、按内容匹配的复用,引擎并不知道两次请求属于同一个 agent。
  • 每请求 CPU 开销。 v0.34.0 把 prompt token id 改为 int32 缓冲区保存,128K prompt 的每请求 CPU 开销降为原来的 1/40;KV 块分配的 CPU 开销降 45–50%一手,项目自测vLLM v0.34.0。长上下文、高频次的 agent 请求正是这类开销的放大器。

需要说明的边界:上述"无会话概念"的判断基于我读到的 release notes、设计文档与 agentic-api 的 README,没有通读源码。

与图中其他概念的关系

  • llm-compressor、AIBrix:同在 vllm-project 组织下,分别是配套的量化工具与 K8s 编排组件。
  • Mooncake:作为 KV connector 进入 vLLM 主线,v0.34.0 有多项 Mooncake 更新。
  • Dynamo:Dynamo 把 vLLM 作为三种后端引擎之一;vLLM 的 P/D 分离用 NIXL 传 KV(NIXL 1.5.2 是 v0.34.0 的依赖)。
  • SGLang:直接竞争者,也是"近亲"——PagedAttention 论文作者中有两位后来主导 SGLang。
  • TensorRT-LLM:vLLM 直接使用其 TRTLLM-GEN kernel。
  • EAGLE-3:vLLM 的投机解码方法之一,release notes 中有 ngram/EAGLE3/MTP 的条目。
  • GGUF:通过 vllm-gguf-plugin 以量化插件形式加载。
  • Open Responses、MCP:由 agentic-api 而非引擎本体对接——README 称其通过 Open Responses 兼容性测试,并在网关侧执行 MCP 工具。
  • TPU Ironwood、昇腾、Vera Rubin:TPU 与昇腾走插件仓库(vllm-torchtpu、vllm-ascend);v0.34.0 release notes 有 Rubin 专用 MoE 量化路径的条目。
  • llm-d、GIE、KServe:这些集群层项目以 vLLM 为主要模型服务器之一未复核,本轮未打开它们的文档核对。
