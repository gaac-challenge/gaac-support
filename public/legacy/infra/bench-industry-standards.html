行业标准推理基准:MLPerf、InferenceX 与 Artificial Analysis

三家都已转向多轮轨迹回放加固定并发扫描,但同名指标的计时口径各不相同

先看结论

业界目前有三套被广泛引用的推理性能基准,出身和立场不同:MLPerf 是厂商联盟的同行评审制,InferenceX 是研究机构自己每天跑的开源流水线,Artificial Analysis(下称 AA)是商业评测公司对线上 API 和厂商提交配置做的独立测量。2026 年三家做了同一件事:把负载从固定长度的单次请求换成多轮 agent 轨迹回放,把结果从单个数字换成一条随并发变化的曲线,并且允许跨请求的 KV 复用。

对我们最有用的三点:

  • MLPerf Endpoints 的客户端和 InferenceX 的 AgentX 回放器都是 Apache 2.0,都能直接对着任意 OpenAI 兼容端点跑,可以拿来当脚手架或对拍工具。
  • InferenceX 自 2026-09 起正式支持 RTX PRO 6000 Server,有与比赛硬件同架构的公开曲线可作参照一手InferenceX README。
  • TTFT、生成速度、并发这三个词在各家定义不同,AA 在 2026-11-03 还刚改过一次口径。拿别人的数字对标 DeepSeek 官方 API 之前,必须先对齐定义。

MLPerf Inference

组织与流程

MLPerf 由 MLCommons 维护。MLCommons 是一个开放工程联盟,自称有 130 多家成员与附属机构,MLPerf 系列始于 2018 年一手,新闻稿转载HPCwire。Inference 一年两轮,厂商在截止日前把代码、配置和日志打包提交,之后进入约四周的评审:第一周提异议,第二周答辩,第三周改正,第四周发布。评审委员会由每家提交者的代表加工作组主席组成,每家提交者至少要审另一家的提交;争议先求共识,不成则一家一票一手通用提交规则。

结果按两个维度分类:

  • 分区:Closed 要求与参考实现等价,模型、数据集、精度门槛都固定,结果可横向比较;Open 允许换模型或改算法;数据中心另有 Network 分区,LoadGen 经网络发请求。
  • 可得性:Available(硬件可买或可租,软件已发布)、Preview(承诺在下一轮或 140 天后转为 Available,届时性能不得低于预览值 2% 以上)、RDI(研究、开发或内部系统)。v6.1 里 Vera Rubin NVL72 的数字就属于 Preview。

审计每轮最多两个:一个从全部可审计提交中随机抽,另一个由评审委员会投票选出。只有 Closed 分区的 Available 提交可被审计。被抽中的厂商要签保密协议并提供两天的硬件访问,审计应在 90 天内完成,不通过的结果移到 Open 或撤销一手Inference 规则。

四种场景与 LoadGen

所有提交必须使用官方负载生成器 LoadGen(C++ 实现,带 Python 绑定),由它发请求、计延迟、校验精度。延迟定义为"LoadGen 计划发出请求的时刻"到"收到回复的时刻",也就是说排队等待算在内。

场景 请求怎么发 最短时长 尾延迟口径 结果
SingleStream 上一条完成后立即发下一条 600 秒 90 百分位 延迟
MultiStream 同上,每次 8 个样本 600 秒 99 百分位 延迟
Server 按泊松过程到达,LoadGen 二分搜索目标速率 600 秒 99 百分位,各项目自定上限 满足延迟约束的最大泊松速率
Offline 开始时一次性发出全部样本,至少 24,576 个 600 秒 无 吞吐

Interactive 不是第五种场景,而是 Server 的一个更严档位:同样的泊松到达,延迟上限收紧。规则建议 99 百分位场景至少跑 270,336 条请求,以保证统计置信度(同上)。

多数项目还要求输出长度落在参考值的 90% 到 110% 之间,防止靠截短输出刷速度。规则明确禁止跨请求缓存:KV cache 只能在单次请求内使用,每条输入都必须完整计算。投机解码(speculative decoding,用小头预测多个 token 再验证)只在 DeepSeek-R1 Interactive、GPT-OSS-120B Interactive 和边缘 agentic 三处允许,且必须用指定的预测头。

v6.1 的两项新测试

v6.1 于 2026-09-16 发布,30 家机构提交,创参与数纪录一手,新闻稿转载HPCwire。报告所说的两项新增测试属实,具体做法如下。

端到端 RAG。 用 FRAMES 数据集的 824 道多跳问题。流程是:嵌入模型把问题转成向量,FAISS 索引检索,ColBERTv2 重排,GPT-OSS-120B 负责拆解问题、判断资料是否足够和生成答案,GPT-OSS-20B 给文档相关性打分,最多迭代 5 轮;答案由 Llama3.1-8B 当裁判评分。分两个计时任务:建库(文档嵌入加建索引)和问答(从问题输入到答案生成)。只跑 Offline。参考准确率只有约 35%,上下浮动 3 个点,原因是推理模型采样的随机性逐步放大。性能测试为了可重复,用缓存的 LLM 输出替换实际生成内容,但仍然调用并计时 LLM一手Inference 规则。

边缘 agentic。 模型是 Qwen3.6-27B,参考实现用 llama.cpp 跑 Q4_K_M 量化,上下文固定 32K,单槽位,关闭推理。它拆成两部分:

  • 精度门槛用 BFCL v4 的单轮函数调用,约 995 条,按语法树匹配判分,不用 LLM 裁判;参考值 86.23%,过线为其 97%。选单轮而非多轮的理由值得注意:57 条的多轮门槛置信区间约正负 11.6 个百分点,量化内核差异会让单条判定在不同设备上翻转。
  • 性能用 20 条录制的编程轨迹(1,007 轮)闭环回放:发一轮、等流式回复结束、按录制的间隔暂停、再发下一轮,始终只有一个在途请求。报告每轮的 TTFT、TPOT、端到端延迟,取 P50、P90、P99 和最大值。回放过程中顺带算一个零成本的内联精度:把模型发出的 shell 命令与录制轨迹做多重集交并比。

以上出自 MLCommons 的征集公告一手Edge Agentic 公告。Lambda 在 Open 分区把模型换成 Kimi K2.6 在八卡 B200 上跑了同一套流程,自称是该轮唯一在数据中心硬件上的 agentic 提交厂商自述Lambda 博客。

MLPerf Endpoints:正在取代数据中心 Inference

MLCommons 在 v6.1 新闻稿里说,超过一半的提交者已使用新的 API 式测试框架,Endpoints 将取代数据中心的 Inference 基准。Endpoints 于 2026-03 在 GTC 公布,被测对象就是一个 URL,客户端经 HTTP 发请求,不再与服务端同进程一手MLCommons 博客。规则草案(标注 1.0 草案)的要点一手Endpoints 规则:

  • 结果是曲线不是点。每个测量点是一个固定并发下的闭环运行;泊松到达不能用于提交点。非 agentic 至少 8 个点,agentic 至少 7 个点,并发范围在对数空间分成超低、低、中、高四个区,每区必须有点。曲线只画阶梯,不许插值,理由是插值会画出从未实测到的性能。
  • 分区改名:Standardized(对应 Closed)、Serviced(公开商用 API,由 MLCommons 托管客户端经公网测)、RDI(对应 Open)。
  • 跨请求 KV 复用被允许,文档明说这是有意偏离传统 Inference 规则。配套措施是盐值:客户端在系统提示与用户上下文之间插入每请求唯一的随机串,使得不同请求之间只能共享系统提示这一段。
  • 稳态窗口:正式结果只取检测到的稳态区间,剔除爬坡和收尾。并发 32 以内至少 600 秒;32 以上非 agentic 1200 秒、agentic 2400 秒。
  • 滚动提交:计划 2026-10-12 开放 v1.0 并开始滚动提交,目标双周发布。

Agentic 基准是 Endpoints 的一部分。数据集 613 条轨迹:113 条编程轨迹(来自 DataCurve 的 DeepSWE,约 1.6 万轮,上下文增长快,考验 KV 容量)和 500 条企业客服流程轨迹(Workato 提供的合成数据,共享一段很长的系统提示,考验前缀复用与路由)。客户端做闭环回放,按数据集里的间隔模拟工具等待(这段等待不计入延迟),每条轨迹带固定的 X-Session-ID 头供路由器做会话亲和;后续轮次的提示用录制内容重建而不是用模型的实时输出,保证可重复一手Agentic 介绍。仓库里当前接受三个模型:Kimi K3、Qwen3.6-35B-A3B、DeepSeek-V4.1-Flash。精度分三层,每个曲线点都要过:平均输出长度落在区间内、回放时的内联精度、以及用 200 道 SWE-bench Verified 题目跑的独立精度一手参考实现 README。

功耗

传统的 MLPerf Power 在墙端测交流电:被测系统经功率分析仪供电,另一台主控机通过 SPEC 的 PTDaemon 读表,两边用 NTP 对时,功耗与性能必须来自同一次运行,只统计性能阶段。使用 PTDaemon 需是 MLCommons 成员并签许可一手Power 规则。该文档标题仍是 v2.0、更新于 2022 年,并写明不适用于分离式系统。Endpoints 草案承认实测功耗"采用率很低",因为要额外的功率计和测试时间,于是改用预置功率:按 MLCommons 的模板把各部件的 TDP 加总,再加散热与电源余量,报告每千瓦吞吐。

局限

  • 不测缓存与多轮(传统套件)。规则禁止跨请求 KV 复用,负载是独立单轮请求,与 agent 负载的主要矛盾无关。Endpoints 正是为此而设。
  • 提交成本高、厂商自调。每个结果都是厂商工程团队调到极限的配置;旧评论指出很多芯片厂不参加或不连续参加二手,2022 年文章,仅见搜索摘要。
  • 半年一轮跟不上软件迭代,MLCommons 自己在 Endpoints 博客里承认这一点。
  • 功耗结果稀少,原因见上。

相邻套件

  • MLPerf Storage v3.0(2026-09-01)新增 KV Cache 测试,测存储系统对 LLM 推理缓存读写的性能,另加向量数据库测试与 S3 接入层;19 家提交一手,新闻稿转载BigDATAwire。这与主线一直接相关,比赛的 NVMe 池若用于 KV 分层,可参考其负载定义。
  • MLPerf Client 面向个人电脑上的本地 LLM,v1.6 于 2026-04 发布仅摘要。与本题关系弱。
  • MLPerf Automotive v0.5 发布于 2025-08,测车载感知仅摘要。无关。

InferenceX(SemiAnalysis)

它是什么

InferenceX 是半导体研究机构 SemiAnalysis 的开源推理基准,前身 InferenceMAX 于 2025-10 发布 v1,2026-02 改名并发布 v2,2026-08 随 AgentX 进入 v3。它的出发点是:硬件一年一代,软件每周都在变,定点测一次的数字很快过时,所以要持续重跑一手InferenceMAX v1 文章。

定长场景怎么测

用 GitHub Actions 编排:GPU 服务器挂成自托管 runner,每个配置是一个 job,经 Docker 或 SLURM 启动推理服务,再由客户端压测。v1 的做法:

  • 引擎用 vLLM、SGLang、TensorRT-LLM,每个模型先只选一个默认引擎,以免变成引擎之争。
  • 请求是随机 token 序列,有意避开前缀缓存;三组长度 1k 入 1k 出(聊天)、1k 入 8k 出(推理)、8k 入 1k 出(摘要),输入长度在 80% 到 100% 之间随机。
  • 请求速率设为无限、限制最大并发,扫描并发(4、8、16……)与并行方案,把结果画成吞吐对交互性的帕累托前沿。交互性指单个用户收到 token 的速率,单位 tok/s/user,是 TPOT 的倒数。
  • 配置由 AMD 和 NVIDIA 提交,要求接近各自公开文档里的部署配方。v1 曾因是否允许预热产生分歧,最后统一禁止并延长测试时间。

成本与每兆瓦

每百万 token 成本的算法是:每 GPU 每小时 TCO 乘以一百万,除以 3600 乘以每 GPU 的 tok/s。TCO 取自 SemiAnalysis 自家的 AI Cloud TCO 模型,分三种买家情景(超大规模自有、新兴云自有、三年期租用)。每兆瓦吞吐按"机房总供电"口径,含 GPU、CPU、网络和散热配电损耗;v1 文章承认功率是各部件 TDP 相加估出来的,不是实测(同上)。2026-10 起仓库里有开源功率模型(GPL-3.0),用实测 GPU 功率推算整机;2026-11 起多节点运行默认采集实测功率一手InferenceX README。SemiAnalysis 自己提醒:场地与电费通常不到 TCO 的两成,所以每兆瓦差 20% 只对应总成本约 4% 的差别。

AgentX

AgentX 1.0 确有其事,2026-08 发布,Apache 2.0一手AgentX 文章。做法见官方方法页一手AgentX 方法页:

  • 数据:参与者自愿接入一个 HTTP 代理,只记录请求到达与完成时间、输入输出 token 数、会话与子 agent 编号。输入内容被替换成每 64 个 token 一块的会话内链式哈希,保留前缀共享关系而不保留内容。v1.0 选了 393 条 Claude Code 会话,请求中位数为输入 142,016 token、输出 444 token,44% 的会话含子 agent。完整版上下文到 100 万,另有 256k 截断版。
  • 回放:用 NVIDIA 的 AIPerf 把每条会话还原成依赖图,主 agent 是一条链,子 agent 分叉后在指定位置汇合。闭环执行。并发指"活跃的 agent 客户端数",由于子 agent 扇出,服务端在途请求数可以超过它。
  • 控制:固定种子从会话 25% 到 75% 处切入;先用一次只生成 1 个 token 的请求把前缀填进缓存,每条通道再跑 10 个预热请求,之后一小时为计量窗口。每个并发点重启服务。合成内容下投机解码的接受率不真实,所以按 SPEED-Bench 实测值强制设定。没有标准内存配置的服务器,KV 卸载用的主机内存上限 3 TB,且只能按 GPU 占比使用。
  • 不测质量。内容是合成的,无法判断模型答得对不对。

批评与局限

  • 定长场景的随机 token 不触发缓存,也不反映真实负载,SemiAnalysis 自己在 AgentX 文章里称之为"不准确的测法"。
  • 功率长期是 TDP 估算;成本依赖其付费 TCO 模型的假设,外人难以核对。
  • 硬件由被测厂商提供,配置由厂商提交;项目原则文档明说只比加速器、不比引擎。
  • 闭环回放下,快的系统在同一小时内走得更远,各系统见到的请求组合略有不同,低并发时最明显。这是方法页自己列出的。
  • 轨迹全部来自 SemiAnalysis 内部的 Claude Code 使用,只代表编程 agent。

独立第三方对其方法的系统批评,本次没有搜到。

Artificial Analysis

对 API 端点的常规测速

方法页当前为 3.0.0 版,2026-11-03 生效一手AA 性能方法页。

  • 负载:约 1k、10k、100k 输入 token 的单次请求各一档,加一档多轮 agent 任务(取自其编程、知识工作、自动化评测)。所有档位都在并发负载下测。
  • 频率:每 6 小时一次(此前每 3 小时)。从 Google Cloud 的 us-central1 发起,延迟含公网时间。
  • 汇总:每次运行取各档样本的中位数,端点的值是过去 5 天各次中位数的平均;头条数字是各档等权平均。
  • 输出速度:输出 token 数(含推理 token)除以请求的全部时长,从发出请求到收到最后一个 token,包含 TTFT。多轮会话则除以端点实际应答的时间,不含工具执行时间。3.0.0 之前不是这个口径。
  • TTFT:发出请求到收到第一个 token;推理模型的第一个推理 token 就算。另设"首个答案 token 时间",把推理时间算进去。
  • 失败:端点侧的失败(5xx、429、超时)按输出速度 0 计入;己方原因的失败剔除。
  • token 计数:采用各供应商 API 返回的数字(此前统一用 tiktoken)。
  • 防作弊:要求供应商不得识别并优待 AA 的流量,AA 用匿名账号交叉核对。

硬件侧

System Load Test 是较早的硬件测法:固定并发,一条完成立即补一条,每档 3 分钟,并发按 1、2、4 直到 64,之后每次加 64,直到系统吞吐不再上升;负载为 1k 入 1k 出。这里的"单请求输出速度"是首 token 之后的速度,与端点测速的口径不同一手AA-SLT 方法页。

AA-AgentPerf 详见本站概念文档 concepts/aa-agentperf.md。一句话:回放 OpenCode 生成的编程轨迹,找出在 P25 输出速度和 P95 TTFT 都达标时的最大并发 agent 数,按实测加速器功率折成每兆瓦 agent 数。它与另两家的对照:

  • Hugging Face、LMArena:本次未核实它们是否有在维护的推理性能榜。

同名指标的定义差异

TTFT

基准 起点 终点 报告百分位 备注
MLPerf Inference LoadGen 计划发出的时刻 第一个 token Server 场景的尾延迟约束 含排队;同机测量,基本不含网络
MLPerf Endpoints 客户端发出请求 第一个非空文本片段,答案、工具调用、推理内容都算 P90(v0.7 时为 P95) 明文禁止用空白字符抢停表;含网络
InferenceX AgentX 客户端发出 第一个 token P90 认为 0.2 到 5 秒可用,超过 5 到 10 秒算不上在线服务
AA 端点 客户端发出 第一个 token,推理 token 也算 中位数再五天平均 含公网;另报首个答案 token 时间
AA-AgentPerf 同上 同上 P95,上限 3 到 10 秒
OpenRouter 平台转发 第一个 token 滚动统计

两个坑:推理模型下"第一个 token"与"第一个答案 token"可以差几十秒;AgentX 文章里有一例,调度参数一改,吞吐涨 141%,中位 TTFT 却从 36.5 秒升到 59 秒。只报吞吐或只报 TTFT 都会误导。

生成速度

说法 公式 谁在用
只算解码段 1 除以 TPOT,或首 token 之后的 token 数除以之后的时间 MLPerf(TPOT)、Endpoints 单轮(1000 除以 P90 TPOT)、InferenceX(由 P90 token 间隔推出)、AA-SLT
端到端 输出 token 数除以从发出到收完的全部时间,含 TTFT AA 端点测速 3.0.0、OpenRouter、Endpoints 的 agentic 交互性、AgentX 的实验性指标

同一次请求,5 秒 TTFT 加 5 秒流出 500 个 token,前一种算法是 100 tok/s,后一种是 50 tok/s(例子取自 OpenRouter 文档)。agent 负载输出短、输入长,两者差距尤其大。另外 TPOT 与 ITL(token 间隔)也不完全等价:TPOT 是一个请求内的平均,ITL 通常逐间隔统计,取高百分位时后者对卡顿更敏感。

系统吞吐

MLPerf 与 AgentX 的主曲线只算输出 token;AA-AgentPerf 的输入吞吐把缓存命中的 token 也算进去;InferenceX 的成本可按总 token 或输入输出分开算,官方词条提醒比较前要先看分母。把输入输出加在一起的吞吐,在缓存命中率九成的负载里基本只反映命中率。

并发

基准 "并发 N"的意思
MLPerf Server 不设并发,设泊松到达速率
MLPerf Endpoints N 个在途请求;agentic 为 N 个活跃会话,每会话一次一轮
AgentX N 个活跃 agent 客户端,在途请求可多于 N
AA-AgentPerf N 个同时走轨迹的 agent,中间夹工具等待
AA-SLT N 个并行请求,完成即补

闭环并发与开环泊松不可互换:闭环下系统变慢,发请求的速度也跟着降,不会出现排队爆炸;开环才会暴露过载行为。

Goodput

这三家的规则文档里都没有把 goodput(满足 SLO 的有效吞吐)作为正式指标名。意思最接近的是 MLPerf Server 的"满足延迟约束的最大泊松速率"和 AA-AgentPerf 的"满足 SLO 的最大并发 agent 数":两者都是先定门槛、再报容量,不达标的部分不计。Endpoints 和 InferenceX 走另一条路:不设门槛,给整条曲线。

对我们做 Benchmark 的启发

可以直接借用

  1. MLPerf Endpoints 客户端当脚手架底座或对拍工具。Apache 2.0,对任意 OpenAI 兼容端点可用,已内置固定并发闭环、多轮回放、会话头、盐值、稳态检测、TTFT 与 TPOT 统计。它的多轮数据格式(每行一条消息,字段含会话号、轮次、角色、工具定义、工具结果、等待秒数)与方案草稿里设想的轨迹格式几乎一致,建议直接沿用字段名Endpoints 仓库说明。
  2. AgentX 回放器做同硬件的外部参照。pip 安装后一条命令即可对已启动的服务跑一小时回放,数据集公开独立运行说明。InferenceX 面板上有 RTX PRO 6000 Server 的曲线,我们在替身机上跑同一配方,数字若差得离谱,先查自己的环境。
  3. SLA 并发按阶梯曲线报。固定并发闭环,不插值;并发 32 以内每点至少 600 秒稳态;同时采用 AA-AgentPerf 的有效性条件(每档至少完成 30 条任务、每个 agent 至少 3 条)。草稿里"报拐点并发和整条曲线"的做法与 Endpoints 一致,保留。
  4. 防截短的输出长度带。给每类任务定平均输出长度区间(MLPerf 用参考值上下约一成),落在区间外的运行无效。这能堵住"少说话换速度"。
  5. 失败按零计、失败点照常公布。AA 把端点侧失败计为速度 0;AgentX 要求把不稳定的配置也报出来。六项指标里的任务成功率之外,速度类指标也应把失败请求算进分母。
  6. 禁止抢停表。照抄 Endpoints 的条文:TTFT 以第一个非空且属于真实回复的片段为准。

需要改造

  1. TTFT 报两个。三类比赛 agent 多半开推理,应同时报"首 token"和"首个答案或工具调用 token"。草稿里按缓存命中与否分开报的做法,三家都没有做到,是我们比它们细的地方,保留。
  2. 生成速度报两种口径。草稿定义为"只算 decode 段",而 AA 3.0.0 与 OpenRouter 公布的 DeepSeek 数字都是含 TTFT 的端到端速度。对标官方 API 时,要么自己用同一脚本回放得到两种口径,要么引用外部数字时注明口径,不能混比。
  3. 清缓存用盐值,不必重启。每个并发档位和每次数据集重放都换盐,盐插在系统提示之后,这样系统提示的共享前缀仍可复用(这是合法优化),跨档残留则被切断。比 AA 的"整段动态前缀"保留了更真实的复用,比 AgentX 的逐点重启省时间。
  4. 任务完成时间拆开报。三家在回放时都把工具时间排除在延迟之外,只把它作为请求之间的间隔。我们开赛后跑的是选手的真实 agent,工具真的在执行,所以要报墙钟总时间,同时单列"模型应答时间之和",后者才可与别家的端到端指标对照。
  5. 精度逐点校验。MLPerf Agentic 要求曲线上每个点都过内联精度,理由是高并发下的超时、截断会悄悄降低质量。我们的流程是先过 Agent Bench 再测效率,建议在每个并发档位抽样复核产出质量,至少在声称的 SLA 并发点上重跑一次质量评测。
  6. 每成功任务成本的公式。借 InferenceX 的结构:机时单价乘以 GPU 数乘以墙钟小时,除以该并发点上成功完成的任务数,并注明取的是哪个并发点。对标 DeepSeek API 一侧用 OpenRouter 的"有效价格"思路:按实际缓存命中 token 的折扣价计,而不是按标价。
  7. 功耗只作附加项并写明边界。墙端功率计方案对比赛不现实。用每秒采样的每卡功率积分,明确写"仅加速器",与 AA-AgentPerf 同口径。

不适用

  • 泊松到达的 Server 场景与 Offline 场景。agent 任务是闭环的,Endpoints 自己也把 agentic 排除在 Offline 之外。
  • 禁止跨请求缓存的规则。那是传统 MLPerf 为可比性做的取舍,与比赛想考察的能力相反。
  • 模型等价与指定投机解码头。比赛允许自选框架和量化,质量由 Agent Bench 把关即可,不必规定权重。
  • AgentX 的合成内容与强制接受率。我们要评产出质量,必须用真实内容。
  • 预置功率归一与整机柜的最大占用规则。七支队伍用同一套硬件,这类跨规模归一没有意义。

要避开的坑

  • 闭环下的负载漂移。快的系统在同样时间里走得更远,见到的请求组合不同。对策:每个测量点完成的任务数取任务集大小的整数倍,而不是只定时长。
  • 长尾拖尾。个别长任务会让收尾拖很久。Endpoints 的做法是第一个用户做完全部任务时停止性能计量,之后只为精度继续跑完。
  • token 计数来源不一。AA 改用供应商返回值后,不同供应商之间的 tok/s 不再严格可比;Endpoints 草案把它列为未决问题。我们应统一用一个分词器在客户端重算,本地与官方 API 都用它。
  • 对标官方 API 的环境差异。AA 的数字从美国中部发起、含公网。我们的参照线要从国内同一出口、分时段多次回放,取分布而不是单次值,并记录 API 返回的缓存命中 token 数。
