主线一 · KV cache 成为跨层的独立存储层级

KV cache 从引擎内部的显存数据结构,变成有容量、有价格、可传输的一层存储

一句话论点

大模型每处理一个 token 都会留下一份中间结果,叫 KV cache。它原本只是推理引擎在显存里的一块临时缓冲,请求结束就丢。2023 年以后,它先被分页管理,再被做成跨请求共享的前缀索引,然后被搬到主机内存和 SSD,接着在机器之间传输,最后有了专门的硬件。到 2026 年,它在引擎、集群、硬件和 API 定价里都有独立的名字、容量规划和价格,这就是报告所说的"独立存储层级"。

这条主线成立的依据有三类:引擎的默认值在为它让路,生产系统公布了命中率数据,三家头部 API 都把它单独计价。它的弱点也有三处:搬运是否划算取决于带宽与算力的比值,缓存与模型绑定而不可移植,共享缓存会泄露信息。下文逐项说明。

先讲清基本概念

KV cache 是什么

Transformer 的每一层都有自注意力:当前位置算出一个查询向量(query),去和此前所有位置的键向量(key)比对,再按比对结果加权取它们的值向量(value)。生成是自回归的,一次只出一个 token,而旧位置的 key 和 value 只依赖它自己和更早的 token,不会因为后面多了新 token 而改变。所以引擎把每一层、每个位置的 key 和 value 存下来,生成下一个 token 时只算新位置的那一份。存下来的这些张量就是 KV cache。不存的话,每出一个 token 都要把整段上下文重算一遍。

一次请求因此分成两段:prefill(把输入一次性并行算完,产出全部 KV 和第一个输出 token)和 decode(逐 token 生成,每步读取全部 KV)。首 token 延迟(TTFT)主要由 prefill 决定。

它有多大:一个算例

每 token 的 KV 字节数为 2 × 层数 × KV头数 × 每头维度 × 每个数的字节数,其中 2 表示 key 和 value 各一份。以 Llama-3.1-70B 为例,公开配置是 80 层、8 个 KV 头(分组查询注意力,64 个注意力头共享 8 组 KV)、隐藏维度 8192 即每头 128 维一手模型 config.json,unsloth 镜像。按 16 位浮点存储:

  • 每 token:2 × 80 × 8 × 128 × 2 = 327,680 字节,约 0.33 MB。
  • 10 万 token 上下文:约 32.8 GB(30.5 GiB)。
  • 同一段上下文的原始文本按每 token 4 字节估算只有约 0.4 MB,KV 约是它的 8 万倍。
  • 模型权重按 16 位约 140 GB,一条 10 万 token 的会话就要占掉相当于权重四分之一的显存。

以上是本文按公式自行计算的结果,有两处旁证:Mooncake 论文写 LLaMA3-70B 在 128k token 时缓存约 40 GB一手FAST '25,SAGA 论文写同一模型 32K 会话约 10.7 GB一手arXiv 2605.00528,与公式一致。把 KV 量化到 FP8 可减半,见后文。

前缀缓存,以及为什么必须是前缀

如果新请求的开头和某个已缓存请求完全相同,这段开头的 KV 可以直接复用,prefill 只算后面不同的部分。这叫前缀缓存(prefix caching),API 侧叫 prompt caching。

必须是"前缀"的原因在于因果注意力:第 i 个位置的 KV 由第 1 到第 i 个 token 共同决定。开头改一个 token,后面所有位置的 KV 都变了;中间相同的一段文字,只要前面不同,KV 也不同。Mooncake 论文的表述是:同一输入前缀对应的 KV 可以复用而不影响输出精度一手FAST '25。由此得出两条工程规则:稳定内容(系统提示、工具定义)放最前,易变内容放最后;任何改动历史的操作都会让改动点之后的缓存全部失效。

几处细节:

  • HiCache 把显存称 L1、主机内存称 L2、分布式存储称 L3;L1 与 L2 是单实例私有的,只有 L3 可以跨实例共享。L3 后端包括 Mooncake、3FS、NIXL、AIBrix KVCache 和本地文件。它还定义了三种写回策略和带超时的预取一手SGLang HiCache 设计文档。
  • KVBM(Dynamo 的 KV Block Manager)用 G1 到 G4 命名四层:GPU、主机锁页内存、本地 NVMe、远端存储;不同版本文档对 G4 的定义不完全一致(对象存储或网络文件系统)仅摘要,来自搜索结果中的官方文档片段KVBM 设计文档。需要注意:Dynamo v1.5.0(2026-09-21)的发布说明已宣布 KVBM 弃用、计划在 v1.7.0 移除,分层改由引擎自带能力或 LMCache、HiCache、FlexKV 完成,Dynamo 只保留对 KV 位置的索引与路由一手,见 Dynamo 一篇的核实Dynamo releases。也就是说,"编排框架自己管 KV 分层"这一步在 Dynamo 上已经退回给了引擎。
  • NIXL(NVIDIA Inference Xfer Library)是点对点传输库,用插件抽象各类内存与存储,后端有 UCX、GDS、对象存储、3FS、Mooncake 等一手NIXL README。README 没有直接写"传 KV cache",这一用途来自 Dynamo 与 NVIDIA 新闻稿的描述。
  • CMX 由 BlueField-4 数据处理器管理闪存,经 Spectrum-X 以太网用 RDMA 访问,新闻稿称其与 NIXL 和 Dynamo 集成,"2026 下半年可用"。分析文章把它叫作 G3.5 层,即介于节点本地盘与共享存储之间二手The Register。2026 年 3 月 NVIDIA 又发布 BlueField-4 STX 参考架构,CMX 是其首个机架级实现仅摘要NVIDIA newsroom。本轮没有找到它已在生产中出货的证据。
  • CXL(一种让服务器外接大容量内存的互连标准)是另一条硬件路线,目前只有研究论文和厂商演示。

在五层里的样子

  • 引擎与运行时:KV 是显存里的分页块加前缀索引。vLLM v0.34.0 把 extensible KV cache 设为默认,按预热后实际空闲显存确定容量(MiniMax-M3 在 H200 上从 433k 增至 672k token),并接受部分模型在并发 128 时 TPOT 上升 6–18%;默认块大小从 16 改为 64;同版本还有 NIXL、Mooncake、LMCache 连接器与主机内存 offload一手vLLM v0.34.0。
  • 压缩与编译:KV 可以单独量化。vLLM 的 FP8 KV cache 把每 token 的缓存减半,但在 128k 长上下文检索测试上,修复前准确率曾从 91% 跌到 13%,改用两级累加后恢复到 89%;该测试使用未校准的统一缩放,属最差配置一手vLLM 博客。
  • 集群服务与编排:KV 的位置成为路由信号。前缀或 KV 感知路由把请求送到已经持有其前缀的副本;PD 分离(prefill 与 decode 放在不同节点)要求在节点间传 KV,传输库因此成为关键组件。llm-d v1.0.0 的说明写到会话亲和的目的是让多轮对话靠近其缓存的上下文一手llm-d releases。
  • 硬件与算力:KV 是容量规划的对象。HBM(GPU 上的高带宽内存)最快但最贵最少,于是向主机内存、CXL 内存、CMX 这类闪存层外溢。
  • 接入层与经济性:KV 是计价单位(上表),也是网关做粘性路由的理由。Anthropic 2025 年的事故复盘提到其路由是粘性的,后续请求往往落到同一台服务器一手Anthropic Engineering;OpenAI 文档说 prompt_cache_key 影响路由但不保证命中一手OpenAI prompt caching 指南。

证据有多硬

较硬的证据(一手,且来自生产或可复核的发布物):

  1. Google 披露 Vertex AI 采用 GKE Inference Gateway 后前缀缓存命中率从 35% 提到 70%,Qwen3-Coder 的 TTFT 降 35% 以上,DeepSeek V3.1 突发聊天负载的 P95 TTFT 改善 52%;并把 prefix、queue、kv-utilization 三个打分器的权重从 3:3:2 调为 3:5:2,以免持有热门前缀的节点被压垮一手,厂商工程博客,2026-02-06Google Cloud blog。它仍是厂商讲自己的产品,但给出了前后对比与调参细节。
  2. Microsoft 的 GitHub Copilot trace 研究:turn 内 KV 命中率平均 90%(中位 98%),跨 turn 降到 55%,换模型后平均 8%;重度循环用户一次未命中的中位重算量是 110 万 token一手,已读正文arXiv 2608.00101。
  3. vLLM 默认值的变化(见上)。开源引擎愿意用解码延迟换缓存容量,是维护者基于用户负载作出的判断,可在 release notes 逐条核对。
  4. Mooncake 论文称 Kimi 在 A800 与 H800 集群上分别多处理 115% 与 107% 的请求一手,但属作者自报的历史统计,对比对象是其旧系统。
  5. 三家 API 的缓存定价结构(见上)。

只能算厂商叙事的:

  • CMX 的"最高 5 倍 tokens/s、5 倍能效",新闻稿没有给出测试条件厂商自述。
  • LMCache 的 15 倍吞吐、CacheGen 的压缩倍数,均为论文作者在选定负载上的自测。
  • The Register 引述的"KV 卸载到 CXL 内存可把 GPU 内存占用最多降 87%":文章链接的论文是 arXiv 2511.00321,其摘要给出的是吞吐 21.9 倍、每 token 能耗降 60 倍、成本效率 7.3 倍,没有出现 87%一手摘要与二手转述不一致,本文未读全文arXiv 2511.00321。
  • 三条存储路线(软件分层、CXL、专用闪存层)之间没有独立的对比基准。

反方与局限

取回不一定比重算划算

搬运 KV 要付带宽和存储的钱,重算要付 GPU 时间。Mooncake 给出了判据:复用在 TTFT 上有利的条件是加载带宽与计算吞吐之比超过一个由模型维度和前缀长度决定的阈值。以 LLaMA3-70B、前缀 8192 token 为例,8×A800 机器需要至少 6 GB/s,8×H800 需要 19 GB/s——GPU 越快,重算越便宜,搬运的门槛越高。论文建议网络不低于 100 Gbps,并报告其传输引擎在 4×200 Gbps 与 8×400 Gbps 下传 40 GB 分别达到 87 GB/s 与 190 GB/s一手FAST '25。这意味着普通 TCP 网络和慢速盘上的 KV 取回可能比重算还慢;SGLang HiCache 为 L3 预取设置超时(上限 30 秒),超时就回退到重算,也说明了这一点。

存储时长也有盈亏点。按 Gemini 3.8 Flash 的公开价,显式缓存每百万 token 每小时 0.50 美元,而重新输入一次是 0.75 美元:缓存放超过约 1.5 小时而没有被再次读取,就不如到时重算(本文按定价页自行计算)。

不可移植

KV 是特定权重在特定数值格式下的中间结果。换模型、换版本、换量化格式、换注意力实现,旧 KV 都不能用。Copilot 数据里换模型后命中率只有 8% 是直接证据。OpenAI 文档还写明缓存不能跨区域处理边界复用。目前没有跨引擎的 KV 交换格式,各传输库也未统一。

应用层操作会摧毁缓存

上下文压缩(把旧历史改写成摘要)改动了前缀,效果等同于换模型。Copilot 研究里 7.8% 的会话发生过压缩,这些会话占日 token 量的 44.2%。LMCache 论文摘要也指出,截断上下文这一常见做法会让前缀命中率大约减半仅摘要。

安全与多租户隔离

共享缓存使命中与未命中的延迟不同,这是一个时序侧信道。斯坦福的审计(ICML 2025)在 2024 年 9–10 月测试 17 家 API,检出 8 家有缓存,其中 7 家存在跨用户的全局共享;披露后至少 5 家作了修改一手arXiv 2502.07776。NDSS 2025 的 PROMPTPEEK 进一步展示了在多租户共享 KV 的服务中逐 token 重建他人提示词的攻击仅摘要NDSS 论文页。现行对策是按组织或 workspace 隔离,代价是不同租户之间相同的系统提示无法共享,命中率的上限被隔离粒度限定。KV 一旦写到 SSD 和网络存储,加密、访问控制和删除也成为新问题,本轮没有找到这方面的系统性公开研究。

量化 KV 的尾部风险

FP8 KV 的 91% 到 13% 这次缺陷说明,压缩缓存的错误可能只在长上下文下出现,常规基准看不到。需要说清它的性质:这是 vLLM 团队在压力测试中发现并已修复的内核问题(Hopper 上 Flash Attention 3 的累加精度),不是线上事故;同一篇博客的结论是 FP8 KV cache 已可作为许多长上下文部署的默认起点。

与另一条主线的关系

主线二说 agent 负载把服务单位变成了程序。KV cache 之所以从优化项变成核心资源,正是这种负载造成的:agent 每一步都重发全部历史,前缀重复率很高,缓存的收益因此很大;每一步之间还夹着工具调用的等待,缓存在这段时间里既占显存又不能丢,于是才有了"下沉到便宜一层再取回"的需求。聊天负载下,前缀短、间隔由人决定且难以预测,KV 分层的投入很难收回。反过来,agent 的程序级调度(保留、固定、预取)操作的对象就是 KV。两条主线在"状态放在哪"这个问题上合为一处,详见主线二文档。

未决问题

  • 经济性没有独立基准:显存、主机内存、CXL、闪存、网络存储各层的每 GB 成本与取回延迟,在真实 agent 负载下的最优配比没有公开的中立测量。
  • 缓存价值无法跨层传递:应用知道某段前缀接下来会不会再用,引擎的驱逐策略不知道。OpenAI 的缓存 TTL 选项、Anthropic 的 1 小时写入档是 API 侧的粗粒度表达,开源栈里没有对应的标准接口。
  • 格式与传输库未统一:NIXL、Mooncake Transfer Engine、LMCache 连接器并存,KV 块格式随引擎版本变化。
  • 跨区域:缓存不跨区域,容量调度与缓存亲和相互冲突,没有公开的跨区域 KV 感知路由方案。
  • 隔离与共享的折中:按租户隔离消除侧信道,也消除了跨租户共享;是否存在兼顾二者的机制仍是开放的。
  • 专用硬件是否必要:CMX 这类产品的实际采用情况未知,软件分层加通用网络是否已经足够,没有证据可以判断。
