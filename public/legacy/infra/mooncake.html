Mooncake

Kimi 的 KV 中心分离式推理架构,开源了 KV 传输库与分布式 KV 池

与主线一 KV cache · 强它本身就是主线一:把 KV 存进跨节点的内存与 SSD 池,用 RDMA 搬运,按 KV 位置调度与主线二 Agent 负载 · 中论文针对长上下文聊天而非 agent;开源的 KV 池 2026 年被用于 agent 多轮负载

它是什么

Mooncake 这个名字指两样东西,需要分开看。

第一样是一篇论文描述的系统:月之暗面(Moonshot AI)为其聊天产品 Kimi 搭建的推理服务平台,与清华大学合作完成。它的核心主张写在论文标题里:Trading More Storage for Less Computation,用更多存储换更少计算。大模型处理一段输入后会留下一份中间结果,叫 KV cache;下次遇到相同前缀的输入,只要这份 KV 还在,就不必重算。Mooncake 的做法是把 GPU 服务器上本来闲着的 CPU、内存、SSD 和网卡组织成一个跨机器的 KV 存储池,让调度器围绕「KV 在哪里」来决定每个请求去哪台机器。

第二样是一个开源项目(kvcache-ai/Mooncake,Apache-2.0)。论文里的完整平台,包括全局调度器,并没有开源。开源的是其中的数据搬运和存储部分:Transfer Engine(传输引擎)和 Mooncake Store(分布式 KV 存储),后来又加了面向 MoE 模型的 Mooncake EP 与 Process Group。到 2026 年,这个开源项目已经被 vLLM、SGLang、TensorRT-LLM 等主流引擎集成,实际影响力超过了论文本身。

它做了什么

论文里的架构

以下机制据 arXiv 第 5 版全文一手arXiv HTML v5。

Prefill 与 decode 分成两个集群。Prefill 是一次性处理全部输入,算力密集,关心首 token 时间(TTFT);decode 是逐个生成输出 token,受显存限制,关心 token 间隔(TBT)。混在一台机器上,长输入的 prefill 会打断别人的 decode。分开后,KV 要从 prefill 机搬到 decode 机。

分离式 KV 池。KV 以分页的块存在各节点的 CPU 内存里,溢出到 SSD。每个块 512 个 token,块的键是「本块 token 加上前一块的键」一起哈希的结果,所以键相同就意味着从开头到这一块的整个前缀都相同,可以安全复用。块在 CPU 内存与 GPU 显存之间、在机器之间的搬运由一个叫 Messenger 的组件负责,走 GPUDirect RDMA。

全局调度器 Conductor。对每个请求,它为每台候选的 prefill 实例估算 TTFT = 排队时间 + prefill 计算时间(本地已命中的前缀越长越短)+ 可能的 KV 传输时间(如果别的机器有更长的前缀,就把那部分搬过来),选 TTFT 最小的那台。如果别处的最佳前缀比本机的长出不多(低于一个阈值),宁可重算也不搬。搬过来的 KV 就地留一份,热点块于是自动复制到多台机器。

长输入的 prefill 加速。两个技巧:分块流水线并行(CPP),把一个长请求切成块,由一组节点接力处理,只在块边界跨节点通信;逐层 prefill,每算完一层就把这一层的 KV 异步发往 decode 机,传输与计算重叠。

面向过载的调度。论文强调 Kimi 长期处于供不应求的状态,不可能处理所有请求,所以问题是「拒绝谁」。如果一个请求做完 prefill 才发现 decode 侧没位置,prefill 的算力就白费了。「早拒绝」是在 prefill 开始前就同时检查两侧负载。但直接这样做会让 prefill 与 decode 的负载反相位振荡,所以改成「基于预测的早拒绝」:预测 prefill 完成那个时刻的 decode 负载,再决定收不收。预测是系统级的(假设每个请求的 decode 耗时相同),不预测单个请求的输出长度。

论文的数字

两个版本的头条数字不同,引用时要说明版本。

指标 arXiv 版(至 2026-10 的第 5 版仍如此) FAST '25 版
模拟或 trace 实验的吞吐提升 模拟长上下文场景最高 525% 真实 trace 下有效请求容量提升 59% 至 498%
真实负载 多处理约 75% 请求 A800 集群多 115%,H800 集群多 107%
规模 未给 数千节点,每天处理超过 1000 亿 token

均为一手,论文自报。几点限定条件:arXiv 版的实验为保护商业信息,用的是与 LLaMA2-70B 同架构的假模型重放 trace;75% 这个数来自 10 台 prefill 加 10 台 decode 对比 20 台 vLLM 的重放实验,差距主要在 TBT 达标率(vLLM 只有 57% 的请求达标);FAST 版的 115% 与 107% 是「与此前系统相比」的线上数字。基线 vLLM 是 2024 年的版本,当时还没有分离式服务和跨实例缓存。

论文公开的 trace 有一个常被忽略的数据:平均输入 8,590 token,平均输出 182 token;即使假设存储无限,这份 trace 里最多也只有约 55% 的 KV 可复用,论文说这远低于公开基准给人的印象,但在「对着论文聊天」这类场景可达 90%。

开源项目现在是什么

  • Transfer Engine:一个统一的批量数据搬运接口,屏蔽底层传输。支持 TCP、RDMA、AWS EFA、NVMe-oF、NVLink、CXL 以及昇腾、海光、寒武纪、摩尔线程等国产加速器的专有通道;能把多块 RDMA 网卡的带宽聚合起来,按 NUMA 拓扑选路,传输失败自动换路。README 自称:传 40 GB 数据(相当于 LLaMA3-70B 在 128k token 时的 KV 大小),在 4×200 Gbps 与 8×400 Gbps 的 RoCE 网络上分别达到 87 GB/s 与 190 GB/s,约为 TCP 的 2.4 倍与 4.6 倍厂商自述。
  • Mooncake Store:建在 Transfer Engine 上的分布式对象存储,专存 KV cache、隐藏状态和模型权重。一个 master 管元数据(块哈希、大小、位置)、服务发现和节点健康;每个 GPU 节点上跑一个 client,贡献本机的内存与 SSD;client 之间用 RDMA 直接传数据。支持多副本、条带化、内存与 SSD 两级、按对象设置软钉住与硬钉住。v0.3.14 加了对象存储与分布式文件系统后端,以及在 Grace-Blackwell 和 Vera Rubin 平台上经 NVLink 让 GPU 直接访问共享主机内存的池化方式。
  • Mooncake EP 与 PG:给 MoE 模型的专家并行通信加上容错,某个 rank 挂掉后不必重启整个服务。

v0.3.14 这一个版本有 689 个提交、99 位新贡献者一手Mooncake releases。仓库约 7,100 star。

2026 年的现状

开源的 Mooncake 已经成为 KV 传输与共享存储的事实标准之一。集成方按 README 的集成目录,并逐项对照其他来源:

  • vLLM:三个连接器,分别用于 P/D 传输、共享 KV 池、多模态编码器缓存。vLLM 官方博客专文介绍,属实一手。
  • SGLang:P/D 与 E/P/D 传输、HiCache 远端层、弹性专家并行、RL 训练中的权重同步。集成最深。
  • TensorRT-LLM:Transfer Engine(2025-12)与 Mooncake Store(2026-10)。
  • LMCache:Mooncake Store 作为远端后端(2025-04)与多进程模式的 L2 适配器(2026-04)。属实,但两者同时也是竞争关系,都想当 KV 存储层。
  • Dynamo 与 NIXL:NIXL 有 Mooncake 后端插件;Dynamo v1.5.0 的路由器消费 Mooncake 共享缓存事件;Dynamo v1.6.2 的 SGLang 与 vLLM 镜像内置 Mooncake 0.3.14一手,Dynamo 发布说明,已交叉核对Dynamo releases。
  • llm-d:Mooncake P/D 部署指南与 Mooncake Store 分层卸载。
  • 其他:FlexKV、vllm-ascend、LMDeploy、FastDeploy、京东 xLLM、AMD ATOM。

月之暗面自己的用法:README 称 2025-07 用 Mooncake 在 128 块 H200 上以 P/D 分离部署 Kimi K2;同源的 checkpoint-engine 用于 K1.5 与 K2 的生产训练,在数千 GPU 上约 20 秒更新 1T 参数的权重厂商自述。

README 首段至今仍写「多处理 75% 请求」,用的是 arXiv 版数字,没有换成 FAST 版。

与主线一(KV cache)的关系

Mooncake 就是主线一的源头之一,关系不需要论证,这里只落到机制。

  • 索引:块的键是带前缀的链式哈希。论文里由 Conductor 持有全局视图;开源版由 Mooncake Store 的 master 持有,引擎的调度器在请求到来时把 prompt 分块哈希后向 master 查询命中情况。
  • 传输:RDMA 为主。vLLM 的集成把显存中的 KV 区域直接注册为 RDMA 缓冲区,网卡经 GPUDirect RDMA 读写显存,不经 CPU 内存中转,也不占用 GPU 的计算单元;所有 RDMA 操作放在后台线程,不阻塞推理主循环一手vLLM 博客。
  • 分层:显存(引擎管)到本机主机内存,到 SSD,到其他节点的内存与 SSD,v0.3.14 再到对象存储。论文的原始洞察是这些资源在 GPU 服务器上本来就闲着,所以这个池「不额外花钱」。
  • 路由如何利用位置:论文里是 Conductor 把传输时间算进 TTFT 估计。开源生态里,这个角色由别人承担:Dynamo 路由器读 Mooncake 的对象事件来知道共享池里有什么。vLLM 博客把「缓存感知路由与 KV 池协同设计」列为待做事项,当时的扩展实验故意用轮询路由来压测跨节点取 KV 的路径。
  • 与另外两套传输库的关系:报告把 NIXL、Mooncake Transfer Engine、MORI-IO 并列为尚未统一的传输库。实际情况更微妙:NIXL 可以把 Mooncake 当后端,Mooncake 又在 v0.3.14 支持了 NVIDIA 的 NVLink 与 Data Direct。二者在接口层竞争,在实现层互相嵌套。

与主线二(Agent 负载)的关系

要分论文和开源项目两段说。

论文:关系弱。FAST 版标题写明服务对象是 LLM Chatbot,负载特征是长文档、长上下文对话(输入输出比约 720 比 1),通篇没有工具调用、多步程序这些概念。调度单位是单个请求,优化目标是请求级的 TTFT 与 TBT。它与 agent 的联系是事后的:长上下文加多轮对话恰好与后来的 agent 负载形状相似,都是「巨大的重复前缀加很短的增量」。

开源项目:关系在 2026 年明显变强,但方式仍是「提供存储」,不是「理解 agent」。

  • vLLM 的 Mooncake Store 博客标题就是 Serving Agentic Workloads at Scale。它分析了 610 条 Codex 在 SWE-bench Pro 上的 trace:中位 33 轮,到第 30 轮上下文约 80K token,输入输出比约 131 比 1,理论缓存命中率 94.2%,轮间间隔中位 5.2 秒、P99 为 81.4 秒。结论是单机缓存有两个问题:容量不够(10 万 token 的上下文在 Kimi-2.5 上约占 3.8 GB),以及会话被调度到别的实例时完全不命中。
  • 接入共享池后,在 12 块 GB200、1 prefill 加 1 decode 的配置上重放这份 trace:吞吐 3.8 倍,P50 TTFT 降到 46 分之一,端到端延迟降到 8.6 分之一,原因是缓存命中率从 1.7% 升到 92.2%一手,vLLM 与 Mooncake 团队自测。基线只命中系统提示词,所以倍数偏大;这衡量的是「有共享池」对「几乎没有跨轮缓存」,不是对一个配置良好的会话亲和路由。
  • Mooncake Store 的软钉住与硬钉住可用来保护重要的 KV 不被驱逐,但由上层决定钉什么;项目本身没有会话、程序或工具调用间隙的概念。
  • README 称 SemiAnalysis 的 AgentX / InferenceX v3 提到了 Mooncake 对 agent 推理负载的贡献项目自述,未打开原文核对。

存疑与未核实

  • 数字版本:报告与笔记正确指出两版数字不同。补充一点:arXiv 在 2026-10-08 更新到第 5 版,摘要仍是 75% 与 525%,README 首段也仍用 75%;FAST 版的 115%、107%、59% 至 498% 只见于 USENIX 页面与会议 PDF。
  • 笔记称 87 GB/s 与 190 GB/s「只见于第三方博客,未核实」,不准确:这两个数字就写在官方 README 里,属于项目自测。
  • 笔记的 Mooncake 时间线引自 gitlink 镜像页并标为二手;本次直接读了 GitHub 上的 README,内容一致,可升级为一手(项目自述)。
  • FAST 版论文 PDF 本次没有打开全文,架构细节取自 arXiv 第 5 版;两版在调度算法和实验设置上是否有实质差异没有逐节比对。
  • 「数千节点、每天 1000 亿 token」是 2025 年初的数字,Kimi 目前的规模没有公开更新。
  • 论文里的 Conductor 调度器没有开源,生产版与开源版之间有多大差距无从判断。
  • README 列出的二十多项集成中,只交叉核对了 vLLM(官方博客)和 Dynamo(发布说明)两项,其余按项目自述转述。
  • Mooncake Store 的设计文档页面抓取失败,master 与 client 的分工转述自 vLLM 博客。
