AIBrix

字节跳动开源、挂在 vllm-project 下的 K8s 推理控制面

与主线一 KV cache · 强自带 L1 内存加 L2 分布式两级 KV 卸载框架,网关按引擎上报的 KV 事件做前缀路由与主线二 Agent 负载 · 中有跨网关副本的会话亲和与前缀路由,但没有程序级调度或 agent 提示接口

它是什么

AIBrix 是一套跑在 Kubernetes 上的 LLM 推理控制面。用户自带推理引擎(vLLM、SGLang 或 TensorRT-LLM),AIBrix 负责引擎以外的事:请求进来发给哪个 pod、什么时候加减副本、几十上百个 LoRA 适配器怎么挂到共享的基座模型上、KV cache 怎么卸载到显存之外并在副本之间共用、一个要占多台机器的大模型怎么作为一个整体部署和升级。

它由字节跳动开发并开源,代码仓库放在 vLLM 项目的 GitHub 组织下(vllm-project/aibrix),Apache-2.0 许可。README 现在的一句话定位是「a Kubernetes control plane for production LLM inference」一手AIBrix README。

它与 llm-d、Dynamo 做的是同一类事,区别在出身:llm-d 来自 Red Hat、Google、IBM 主导的社区,Dynamo 来自 NVIDIA,AIBrix 来自一家自己有大规模推理业务的应用公司。

它做了什么

网关与路由

网关基于 Envoy Gateway,用 ext-proc(Envoy 的外部处理插件机制)挂上 AIBrix 自己的路由逻辑,对外是 OpenAI 兼容接口,后来加了 Anthropic 的 /v1/messages 和 OpenAI 的 Responses API。路由策略是可插拔的,历史上实现过:

  • 前缀缓存感知:把 prompt 的 token 分块哈希,匹配各 pod 已缓存的前缀;
  • Preble(ICLR '25 论文的实现):在「复用 KV」与「GPU 负载」之间按成本打分;
  • VTC(OSDI '24 论文的实现):按 token 用量做租户间公平;
  • 最少请求、吞吐、最少显存占用、SLO 感知等。

v0.7.0 起这些策略可以加权混合,写成类似 least-request:2,throughput:1 的配置;网关可多副本部署,副本之间通过 Redis 同步在途请求数和前缀缓存状态。v0.8.0 加了 least-request-top-k(从负载最轻的几个副本里挑,避免多个网关副本同时压向同一个刚就绪的 pod)、按副本的容量上限、以及实验性的外部路由(路由决策由 AIBrix 之外的系统给出)一手v0.8.0 发布博客。

LoRA 高密度管理

LoRA 是在基座模型上叠加的小型微调权重。AIBrix 用 ModelAdapter 这个自定义资源描述一个适配器,控制器负责把它动态加载到某些基座 pod 上,并通过 Kubernetes 的 Service 与 EndpointSlice 让网关能按适配器名找到 pod。开源时的博客自称在低流量场景成本降 4.7 倍、高流量 1.5 倍厂商自述,条件未详AIBrix 首发博客。

自动伸缩与 GPU 优化器

自带 PodAutoscaler,提供 KPA、APA 等算法,用滑动窗口聚合引擎指标(队列深度、KV cache 占用率、token 吞吐)而不是轮询 Prometheus。v0.7.0 把 KV cache 使用率加入 APA 信号;v0.8.0 加了预测式伸缩 API 和按时间表设定副本上下限。

GPU 优化器是一个旁路组件,解决「同一个模型部署在几种不同 GPU 上时,各放多少」。它统计网关看到的输入输出长度分布,用 Melange 论文的整数线性规划求出满足 SLO 的最便宜 GPU 组合,再把结果作为外部指标喂给 PodAutoscaler。需要事先对每种 GPU 做离线 profiling。首发博客给的实验是 A10 与 L20 混部比纯 L20 省约 10% 成本,代价是延迟最多升 20% 但仍在 SLO 内厂商自述。README 至今把异构 GPU 标为 Experimental。

StormService:多角色、多节点编排

v0.4.0 引入 StormService 与 RoleSet 两个自定义资源。一个 RoleSet 是一组有角色的 pod(例如 2 个 prefill 加 4 个 decode),StormService 管理多个 RoleSet 的副本、滚动升级和缩容顺序。v0.5.0 加 PodSet(一个 worker 本身跨多个 pod)和按角色独立伸缩;v0.8.0 加带排空的滚动与缩容、进度截止时间、与 Volcano 的 gang 调度集成。这与 llm-d 的 DisaggregatedSet、Dynamo 的 Grove 是同一类抽象。早期的多节点方案 RayClusterFleet(Kubernetes 管粗粒度资源、Ray 管细粒度执行)仍保留。

分布式 KV cache

详见「与主线一的关系」。

其他

  • AI Runtime:每个引擎 pod 旁的 sidecar,负责下载权重、加载卸载适配器、把不同引擎的指标统一成一种格式。
  • Batch API(v0.7.0 重写)、Web 控制台(v0.7.0 预览)。
  • ModelClaim(v0.8.0,实验性):把「模型」的生命周期与「pod」解耦。GPU pod 作为长期存活的运行时池,空闲模型被休眠并归还显存,流量回来再唤醒,用于长尾模型共享 GPU。
  • ModelWarmup(v0.8.0,实验性):在节点上预拉镜像、预先执行准备动作。
  • 加速器诊断与故障模拟工具,支持 NVIDIA GPU 和昇腾 910B。

2026 年的现状

  • 最新版本:v0.8.0,GitHub 发布时间 2026-10-13(UTC),443 个提交,104 位贡献者一手。约 5,200 star、770 fork。
  • 引擎:vLLM、SGLang、TensorRT-LLM 均为一等支持,v0.7.0 起对三者做跨引擎的 P/D 分离端到端测试。
  • 定位:报告把它归为 llm-d 与 Dynamo 两条主路线之外的「并行替代方案」,这个判断与一手材料相符。AIBrix 没有进入 CNCF,也没有硬件厂商的整机架绑定;它的差异点是功能面最宽(LoRA、Batch、控制台、异构 GPU、模型休眠都自带)。
  • 字节内部使用情况:公开信息只有开源时的两句话(多个业务场景、生产运行 6 个月以上),以及白皮书提到多节点编排方案「来自字节内部托管 Kubernetes 与 Ray 负载的经验」。没有公开的集群规模、请求量或具体业务名称。发布说明里出现火山引擎的对象存储 TOS 和 EIC、PrisKV 等后端名,说明它与字节云的基础设施有对接,但这只是从代码痕迹推断未复核。
  • 社区:首发博客称贡献者来自密歇根大学、UIUC、华盛顿大学、Google、DaoCloud 等。

与主线一(KV cache)的关系

关系强。AIBrix 是少数自己实现了一整套 KV 卸载与共享框架的控制面,机制如下一手KVCache Offloading 文档:

  • 连接器:一个加载进引擎进程的插件。在 vLLM 里通过 --kv-transfer-config 选用 AIBrixOffloadingConnectorV1Type3;SGLang 里有对应的 aibrix_kvcache 存储后端。
  • L1:引擎 pod 内的主机内存缓存,默认 10 GB,驱逐策略默认 S3FIFO(一种抗扫描的 FIFO 变体)。算出来的 KV 块存到主机内存,前缀再次出现时读回显存。
  • L2:pod 之外的分布式 KV 集群,多个引擎副本共用,所以副本 A 算过的前缀副本 B 可以直接取。后端可插拔:InfiniStore(RDMA 或 TCP)、HPKV、PrisKV(v0.7.0 发布说明称之为生产后端)、RocksDB、EIC、SHFS,早期是 Vineyard。集群由 KVCache 自定义资源创建,成员列表存在 Redis 里,由一个 watcher pod 维护。
  • 写入策略:L1 与 L2 同开时,默认只有在 L1 里变热的块才写到 L2(HOT 策略),避免把一次性的 KV 也搬过网络。
  • 传输:v0.5.0 加入 GPUDirect RDMA,KV 可在网卡与显存之间直接读写。
  • 这套框架可以脱离 AIBrix 其余部分单独使用。

路由一侧是另一条独立的机制:v0.4.0 引入 KV 事件同步,vLLM 实例把「我持有哪些前缀块」的事件发给网关,网关据此把请求送到缓存最热的 pod。文档明确区分两者:事件同步只发布位置,卸载才移动内容。

P/D 分离方面,v0.7.0 把数据面重构为「以 KV cache 为中心」:prefill 与 decode 之间不再只靠点对点传输,而是都接到同一个 aibrix_kvcache 底座上,新增的 AIBrixPDReuseConnector 让 P/D 传输与前缀复用走同一条路。同一版本里出现了 KVTransferAgent 抽象和一个 Mooncake 的占位实现(stub),说明接入 Mooncake 尚未完成。

性能数字:白皮书摘要称分布式 KV cache 使吞吐提升 50%、延迟降低 70%;首发博客给出的条件是 Bird Text2SQL 负载、对比对象是已开启前缀缓存的 vLLM,峰值吞吐约升 50%,平均与 P99 TTFT 约降 60% 与 70%厂商自述。另一方向的数字:LMCache 团队 2025-03 的自测称其 production-stack 在 prefill 重的负载上比 AIBrix 快约 10 倍厂商自述,竞品自测,报告笔记所引,本次未复核。

与硬件层的 KV 存储(NVIDIA CMX、CXL)没有查到集成。分层止于主机内存与远端 KV 集群,本地 SSD 一层靠 RocksDB 后端间接提供。

与主线二(Agent 负载)的关系

关系中等。有针对多轮会话的路由功能,但没有把「程序」作为调度单位。

  • 会话亲和:v0.6.0 加入插件式的会话亲和路由;v0.8.0 把会话到后端的映射存进 Redis,同一会话的后续请求即使经过不同的网关副本也会落到同一个引擎副本。发布博客把这一节标题直接叫 Stateful Routing for Agentic Workloads,并把目标概括为「会话亲和 + 前缀缓存局部性 + 副本负载」三者组合一手。
  • 前缀路由与 L2 共享:agent 多轮调用的长前缀能命中,是间接受益。
  • 公平性:VTC 路由按 token 计量做租户间公平,单位是租户,不是会话或程序。
  • 没有的东西:没有类似 Dynamo agent_hints 的每请求提示接口,没有 llm-d v1.0 那种 program-aware fairness 或按轮次优先级打分,没有工具调用间隙的 KV 保留策略。首发博客把「把 QoS、优先级、公平性引入请求级多租户」列为未来方向。
  • v0.8.0 博客的展望里把「richer agentic workloads」列为下一步,目前只是规划。

与图中其他概念的关系

  • vLLM:AIBrix 挂在 vllm-project 组织下,最初只支持 vLLM,并向 vLLM 上游贡献了 LoRA 动态加载等功能。同组织下还有 LMCache 团队的 production-stack,vLLM 博客的 FAQ 专门解释过两者的区别。
  • SGLang、TensorRT-LLM:受支持的引擎;SGLang 仓库内有 AIBrix KV cache 的存储后端。
  • GIE:字节参与了 Kubernetes WG-Serving 和 Gateway API Inference Extension 的制定(Google 方面的背书原话);但 AIBrix 的网关是自己的 Envoy 插件,不是 GIE 的实现。
  • llm-d、Dynamo、KServe:同层的替代方案。AIBrix v0.4.0 把 Dynamo 列为可部署的后端之一;NVIDIA 把字节列为 Dynamo 的生产用户。
  • Mooncake:首发博客的致谢把 Mooncake 论文列为设计灵感之一;v0.7.0 有 Mooncake 传输的占位实现。
  • 昇腾:加速器诊断工具支持昇腾 910B。
  • Open Responses:v0.7.0 支持 OpenAI Responses API 端点。
  • 与图中接入层、压缩层、其余硬件概念没有查到直接关系。

存疑与未核实

  • 版本日期有三种说法:v0.7.0,GitHub API 的发布时间是 2026-06-18(UTC 零点后),README 写 06-16,发布博客 URL 也是 06-16;v0.8.0,GitHub 是 10-13,README 写 10-09,博客 URL 是 10-12。报告采用的 GitHub 日期没有错,但与项目自己的 README 差 2 到 4 天,应是打 tag、写博客、正式发布三个时间点。
  • 字节内部的实际部署规模、哪些业务在用,没有任何公开数字。字节同时出现在 NVIDIA 的 Dynamo 生产用户名单上,AIBrix 在其内部是否仍是主力,无从判断。
  • PrisKV、EIC、HPKV、SHFS 这些 L2 后端的归属与公开程度没有逐一核实。
  • 白皮书的性能数字均为自测,且测的是 2025 年初的版本,当时的 L2 后端是 Vineyard,与现在的实现已不同。
  • 白皮书全文只读了前半部分(架构与功能概述),评测章节未读。
  • KV 卸载文档写「目前仅支持 FlashAttention 和 XFormers」,这句话是否已过时未核实。
