llm-d

Kubernetes 上的分布式 LLM 推理栈,核心是懂 KV 缓存的路由器

与主线一 KV cache · 强路由器按各副本 KV 缓存里已有的前缀块打分选 Pod,并把 KV 分层卸载做成标准部署路径与主线二 Agent 负载 · 强1.0 起按程序和会话排队:程序级公平性、轮次优先、会话亲和

它是什么

llm-d 是一个开源项目,目标是把"在 Kubernetes 集群里用很多块 GPU 跑大模型推理"这件事做成一套可复用的标准栈。它自己不执行模型——真正做前向计算的是 vLLM、SGLang 这类推理引擎(每个引擎实例跑在一个 Pod 里,Pod 是 Kubernetes 的最小部署单元)。llm-d 管的是引擎之上的事:一个请求进来该发给哪个 Pod、过载时谁先排队谁被拒绝、prefill 和 decode 两个阶段要不要拆到不同机器、KV cache 放不下时卸载到哪里、副本数怎么伸缩。

CNCF 项目页对它的定义是"Kubernetes 原生的高性能分布式 LLM 推理框架,构建在 vLLM 之上",提供智能推理调度、前缀缓存感知路由、prefill/decode 分离、分层 KV 卸载,以及跨 NVIDIA、AMD、Intel、Google TPU 的伸缩一手CNCF 项目页。

理解它最简单的办法是记住三层分工:Gateway API Inference Extension(GIE)是标准接口,规定"网关怎样向一个外部调度器询问该选哪个 Pod";llm-d 是这个调度器的主要实现,外加一整套部署配方;KServe 是更上层的控制面,用户写一份 YAML,它替你把 llm-d 的各个部件创建出来。

它做了什么

官方架构文档把 llm-d 分成七块:Router、模型服务器、分离式部署、KV 缓存管理、模型服务器编排、自动伸缩、批处理与异步一手llm-d 架构文档。下面挑最关键的讲。

Router 与 Endpoint Picker

Router 是请求入口。它由一个 L7 代理(通常是 Envoy 或兼容 GIE 的网关)加一个叫 Endpoint Picker(EPP) 的进程组成。代理每收到一个请求,就通过 Envoy 的 ext-proc 协议(External Processing,允许代理把请求交给外部进程处理的 gRPC 接口)问 EPP:"这个请求发给池子里哪个 Pod?"EPP 内部是一条插件流水线:先过滤掉不合格的 Pod,再让若干"打分器"(scorer)各自给每个 Pod 打分,加权求和后选出目标。常见打分器看三样东西:该 Pod 的排队长度、KV cache 占用率、以及它是否已经缓存了这个请求的前缀。

prefill/decode 分离与 DisaggregatedSet

LLM 推理分两段:prefill(一次性读完整个 prompt,算力密集)和 decode(逐个吐 token,受显存带宽限制)。llm-d 支持把两段放到不同 Pod 上,中间通过 NIXL(NVIDIA 的传输库,支持 RDMA)把 KV cache 从 prefill 节点传到 decode 节点。v1.0.0 新增的 DisaggregatedSet 把一组 prefill 副本和 decode 副本当作一个逻辑单元管理:协同滚动升级、锁步换版本、按修订版路由,避免新版 prefill 把 KV 发给旧版 decode。这个 API 实际位于 kubernetes-sigs 的 LeaderWorkerSet 项目里,要求 LWS v0.11.1 以上并显式开启一手llm-d releases;CNCF 博客提到它由 Mistral AI 贡献一手。

流量控制(flow control)

过载时请求不再直接压到各引擎自己的队列里,而是停在 EPP 的中央队列。每个请求有一个 flow key =(公平性 ID,优先级),每个 key 一条队列;出队按三层决定:先服务最高优先级带(priority band),同一带内由公平性策略决定轮到哪条流,流内由排序策略(先到先服务、最早截止时间、按 SLO 截止时间)决定哪个请求。负优先级的请求可被拒绝(HTTP 429),甚至在已经开始执行后被驱逐。需要注意两点:文档写明 flow control 默认不开,要在配置里打开 flowControl 特性门;队列在内存里,EPP 崩溃即丢失一手flow control 文档。

其他部件

  • 自动伸缩:用 EPP 的排队指标驱动 KEDA,或按延迟余量做 SLO 感知伸缩。早期的 Workload Variant Autoscaler(WVA)在 1.0 架构文档里已标注为 deprecated。
  • Batch Gateway(OpenAI 兼容的批处理 API)、Async Processor(从消息队列取请求)、延迟预测器(训练一个小模型预测每个 Pod 的 TTFT/TPOT,供 predicted-latency 打分器使用)。
  • 一组称为 well-lit paths 的参考部署:优化基线、精确前缀缓存路由、分层前缀缓存、P2P KV 共享、P/D 分离、宽专家并行、有状态 Responses API 等。

和 vLLM 的关系

vLLM 是默认引擎,但不是唯一的。1.0 的发布说明同时列出 SGLang、TensorRT-LLM 镜像,并明确"不再自建推理镜像",硬件伙伴的支持回到各引擎上游一手。可以这样理解:vLLM 负责单个 Pod 内的效率(批处理、前缀缓存、KV 卸载接口),llm-d 负责跨 Pod 的决策,并依赖 vLLM 暴露的指标和 KV 事件来做决策。

与主线一(KV cache)的关系

关系很强,而且落在三个具体机制上。

一、按 KV 缓存位置路由。 前缀缓存只在"同一前缀的请求落到同一个 Pod"时才生效,所以路由器必须知道哪个 Pod 缓存了什么。llm-d 有两种实现一手前缀缓存感知路由文档:

  • 近似版(approx-prefix-cache-producer):EPP 没有分词器,按字符数估算 token,把 prompt 切成默认 64 token 的块做滚动哈希链,在自己内存里维护一张 LRU 表,记录"最近把哪些前缀哈希发给了哪个 Pod"。打分 = 命中的块数 / 总块数。它完全是路由器的自我记忆,引擎那边把缓存淘汰了它并不知道。
  • 精确版(precise-prefix-cache-producer):引擎每次新增或淘汰 KV 块都通过 ZeroMQ 发出 KVEvents,路由器订阅每个 Pod,建一张"块 → Pod"的全局索引;prompt 先调用 vLLM 的 render 接口拿到真实 token ID 再比对。因为事件到达有延迟,路由后会先写入"推测条目"(示例中 TTL 为 2 秒)。代价也写在文档里:该路径下路由器只能跑单副本,重启后索引可能长期不完整,SGLang 没有事件重放缓冲一手精确前缀路由指南。

二、KV 分层卸载。 显存里放不下的 KV 块不是丢弃,而是下沉到主机内存,再可选地落到共享文件系统。llm-d 自己不实现卸载,而是把引擎侧的 connector(vLLM 原生 OffloadingConnector、LMCache、MooncakeStore、SGLang HiCache、TPU 专用 connector)组装成"分层前缀缓存"部署路径;路由器侧则增加第二个前缀打分器和一张独立的 CPU 层索引,让请求也倾向于"前缀在内存层"的 Pod。由于 vLLM 不上报内存层容量,这张索引的容量要手工按公式填,填大了路由器会把请求导向已经不存在的块。该指南明确不含性能基准一手分层前缀缓存指南。早期 llm-d 自带的文件系统 connector 已在 v0.10.0 因并入 vLLM 上游而弃用报告笔记,未逐条复核。

三、KV 作为准入信号。 过载时的 probabilistic admitter 用"排队深度与 KV 占用率两者较大值"计算集群饱和度,按 p = min(sat^5 × 300, 1) 的概率拒绝负优先级请求,饱和度约 0.34 时全部拒绝一手probabilistic-admitter README。

与主线二(Agent 负载)的关系

关系强,且主要是 1.0 新增的。

  • program-aware fairness:一种公平性策略,把同一个公平性 ID 的所有请求视为一个"程序",按程序而不是按请求统计排队时间、在途数和已获得的服务量。它有两种策略:las(Least Attained Service,累计消耗加权 token 最少的程序先出队,并按半衰期衰减)和 turn-priority一手program-aware README。
  • turn-priority:打分公式是 轮次数 + 权重 × 队首等待秒数,轮次越深的会话越优先。理由直接来自主线一——聊了很多轮的会话前缀大概率还在 KV cache 里,优先服务它省 prefill,也更快腾出槽位。文档坦率写出副作用:默认权重 0.05、请求 TTL 60 秒时,新会话最多攒到相当于 4 轮的分数,在持续拥塞下新会话会被丢弃而不是插队。
  • session-state-producer:为每个 agent 身份维护已派发轮数、在途请求数、累计输入/输出/缓存命中 token 数,供上述策略读取。状态只存在单个 EPP 副本的内存里,且属于 Alpha 插件一手session-state README。
  • 会话亲和:session-affinity-scorer 把同一会话粘到上次的 Pod,可以靠响应头回传编码后的 Pod 名(无状态),也可以按会话 ID 在服务端记绑定;P/D 分离时 prefill 和 decode 各配一个实例。
  • Responses API:支持 previous_response_id,让多轮状态可以留在服务端。

需要保留的判断:这些能力多数要显式配置才生效,公开的效果数据只有发布会演示(1000 个沙箱 agent,缓存命中率从约 30% 到约 75%)二手转述的厂商演示,没有独立复现。

与图中其他概念的关系

  • GIE:llm-d 的路由器实现 GIE 的 InferencePool 与 ext-proc 协议;2026-08 起 GIE 的完整 EPP 代码归入 llm-d。
  • KServe:KServe 的 LLMInferenceService 控制器替用户创建 llm-d 的调度器和工作负载。
  • vLLM、SGLang、TensorRT-LLM:三者都是 llm-d 支持的模型服务器,vLLM 为默认。
  • Dynamo:路线上的对手,部件上的合作者(NIXL、ModelExpress)。
  • Mooncake:1.0 的生态组件表里有 mooncake-master-store,MooncakeStore 是分层缓存的可选后端之一(需要 RDMA)。
  • AIBrix:功能高度重叠的并行方案,未见代码级依赖。
  • TPU Ironwood:llm-d 有 vLLM TPU 镜像和 tpu/v7 部署变体;v7 是否即 Ironwood 本文未单独核实未复核。
  • AMD Helios:llm-d 有 ROCm 路径,但未见针对 Helios 机架的专门内容。
  • Open Responses:llm-d 支持的是 OpenAI 风格的 Responses API;是否对齐 Open Responses 规范未核实。
  • 与 OpenRouter、LiteLLM、MCP、AA-AgentPerf、llama.cpp、MNN、llm-compressor、GGUF、ExecuTorch、LiteRT、EAGLE-3、Vera Rubin NVL72、Cerebras、昇腾未发现直接关系。
