KServe

Kubernetes 上的模型服务控制面:一份 YAML 建好整套推理服务

与主线一 KV cache · 弱自己不做 KV 路由或卸载,只负责把 llm-d 调度器和引擎的 KV 传输参数配置出来与主线二 Agent 负载 · 弱只做了 Responses 与 Messages 接口的路由透传,会话级调度交给 llm-d

它是什么

KServe 是一个开源的模型服务平台,跑在 Kubernetes 上。它解决的问题是:把一个训练好的模型变成一个可以被调用、能自动伸缩、能灰度发布的在线服务,需要在 Kubernetes 里创建一大堆东西(部署、服务、路由、证书、伸缩规则、模型下载逻辑)。KServe 把这些收拢成一个自定义资源:用户只声明"我要服务这个模型,用这个运行时,放在这种硬件上",KServe 的控制器负责把底下的一切建出来并持续维护。

这类组件在 Kubernetes 里叫控制面:它不处理任何一个推理请求,只负责创建和管理处理请求的那些东西。这也是它在本报告"三层分工"里的位置——GIE 是标准接口,llm-d 是调度器实现,KServe 是把它们装配起来的控制面。

KServe 的出身是传统机器学习(scikit-learn、XGBoost、TensorFlow、PyTorch 模型),2025 年起才为大模型专门加了一个新资源 LLMInferenceService。CNCF 的公告里它的定位是"标准化的分布式生成式与预测式 AI 推理平台"一手CNCF 博客。

它做了什么

InferenceService:老的通用资源

InferenceService 是 KServe 一直以来的核心资源。用户指定模型存放位置和运行时,KServe 创建服务,并提供:基于 Knative 的无服务器部署(按请求并发数伸缩,没流量时缩到零)、金丝雀发布、与 Istio 服务网格和 Gateway API 的集成、统一的推理协议(Open Inference Protocol),以及一批现成的运行时。它也能跑大模型,但官方文档写明只适合"基础的单节点部署"一手LLMInferenceService 概览。

LLMInferenceService:为大模型新开的资源

大模型服务需要的东西,老资源的数据模型表达不了:一个模型跨多台机器、prefill 和 decode 拆开、请求要按 KV 缓存位置路由。于是 KServe 没有去改 InferenceService,而是新开了一个资源。文档原话是它"构建在 llm-d 的基础之上"。一份 LLMInferenceService 的主要字段:

  • spec.model:模型来源(Hugging Face、S3、PVC)、对外模型名、可选的 LoRA 适配器。
  • spec.template:单节点工作负载,或在分离部署里充当 decode 一侧。
  • spec.worker:出现这个字段就表示多节点,控制器改用 LeaderWorkerSet(一种把一组 Pod 当作一个副本管理的 Kubernetes 资源)。
  • spec.prefill:出现这个字段就表示 prefill/decode 分离,另起一组只做 prefill 的 Pod。
  • spec.router:入口 Gateway、HTTPRoute,以及 scheduler——也就是 llm-d 的 Endpoint Picker。
  • spec.parallelism:张量并行、数据并行、专家并行的配置。

v0.17 的发布博客描述,提交这一个资源后,控制器会创建"包括 Deployment、Service、Gateway、HTTPRoute 在内的完整服务栈",外加 InferencePool 和 EPP 调度器 Pod一手KServe 0.17 博客。通用配置可以抽成 LLMInferenceServiceConfig,多个服务引用同一份再各自覆盖。

和 llm-d、GIE 的分工

KServe 维护者、Red Hat 的 Yuan Tang 在 2026-03-05 的博客里把边界说得很直白:KServe 是"负责生命周期、伸缩与运维治理的那一层";KServe 自身不会按 KV 缓存位置跨副本路由请求、不会在集群范围拆分 prefill 与 decode、不会做 SLA 感知的路由决策。这些是 llm-d 的事,而单个 Pod 内的执行效率是 vLLM 的事一手,维护者博客Yuan Tang 博客。

换一种说法:

  • GIE 定义 InferencePool 这个资源和网关与调度器之间的协议;
  • llm-d 提供调度器本身(EPP 镜像、打分插件、P/D 分离用的 sidecar);
  • KServe 的控制器读取用户的 LLMInferenceService,生成 InferencePool、HTTPRoute、调度器的 Deployment 和配置、模型服务器的 Pod 及其启动参数,并在版本升级时做迁移。

从变更日志可以看出这种"跟随关系"的成本:KServe 每个版本都有一批提交是在追 llm-d 的变化——v0.18 升到 llm-d 0.6 并把 GIE 的 CRD 打进安装包,v0.19 加"llm-d v0.6 组件升级的迁移逻辑",v0.20 升到 llm-d 0.8.0 与 GIE v1.5.0,v0.21 迁移 EndpointPickerConfig 的 API 版本、把分词 sidecar 换成 vLLM 的 render 部署、跟进 llm-d 改名的启动参数一手KServe releases。

2026 年的现状

  • 最新版本 v0.21.0(2026-09-25)。KServe 至今没有发布 1.0。
  • "生产可用"的确切含义:v0.17 博客的用词是 production-ready,没有用 GA;示例里的 API 版本是 serving.kserve.io/v1alpha2,v0.18 博客和 v0.21 的变更日志里仍是 v1alpha2。也就是说项目方宣称功能可用于生产,但 API 仍处于 alpha 阶段,字段还可能变一手。
  • v0.17 的其他内容:集成 GIE v1.3.0、Envoy AI Gateway 与按 token 限流、调度器高可用、基于 Workload Variant Autoscaler 配合 KEDA 或 HPA 的伸缩 API;Helm chart 重组为 10 个,对从 v0.16 升级是破坏性变更;共 167 个合并 PR、38 位以上贡献者一手。
  • v0.18(2026-04-29):多节点推理不再需要 Ray;LeaderWorkerSet 可作为伸缩目标;HTTPRoute 开始转发 /v1/responses;vLLM 升到 v0.19.0一手KServe 0.18 博客。
  • v0.20 与 v0.21 没有找到官方发布博客,以下取自变更日志:v0.20 增加 /v1/messages 路由(Anthropic Messages API)、托管 DRA 支持、分布式追踪、有 LoRA 时自动启用 lora-affinity 打分器、把 vLLM 列为受支持运行时;v0.21 增加金丝雀发布的端到端测试、agent 工具调用的指南与示例。
  • 采用:llm-d 官方博客 2026-04-21 的文章由 Red Hat 与 Tesla 工程师合写,描述 Tesla 生产环境用 KServe 的 LLMInferenceService 加 llm-d 路由加 vLLM,替换了原先"StatefulSet 包 vLLM 加轮询"的做法;文中没有给出集群规模厂商自述llm-d 博客。Red Hat 的 OpenShift AI 以 KServe 为模型服务基础,这是它在企业里最主要的分发渠道二手,本次未单独核实。
  • 竞争位置:在"Kubernetes 上的声明式模型服务 API"这个位置,它是资历最老、治理最中立的一个(CNCF 孵化级)。NVIDIA Dynamo 和字节的 AIBrix 各自带控制器和 CRD,不需要 KServe。

与主线一(KV cache)的关系

关系弱,而且全部是"转手"。KServe 不读、不写、不移动任何 KV 块,也不看 KV 指标做决定。它和 KV cache 的接触点只有配置:

  • 为 LLMInferenceService 生成 EPP 调度器的配置,其中可以启用 llm-d 的前缀缓存打分器。KServe 的示例仓库里有"精确前缀 KV 缓存路由"的样例,v0.19 的一条修复是把该样例的哈希算法改为 sha256_cbor,以便和引擎侧一致。
  • 在 prefill/decode 分离模式下,为 vLLM 生成 --kv-transfer-config 启动参数(v0.21 有一条修复是给这个参数里的引号转义),让 KV 块经 NixlConnector 从 prefill Pod 传到 decode Pod;v0.17 博客说明走的是基于 RDMA 的 RoCE 网络。
  • 文档里有 KV cache 卸载的配置指南;CNCF 公告提到与 LMCache 的集成。实际卸载由引擎和 LMCache 完成。

所以对主线一,KServe 的作用是降低使用门槛:把"前缀感知路由 + P/D 分离 + KV 卸载"这套原本要手工拼装的配置,变成一个资源上的几个字段。它在图里出现,是因为很多企业实际接触这套能力的入口是 KServe,而不是直接部署 llm-d。Tesla 的例子里,前缀缓存感知路由上线后输出吞吐约 3 倍、TTFT 约降一半(Llama 3.1 70B、4 块 MI300X)厂商自述——但产生收益的机制在 llm-d 调度器和 vLLM 的前缀缓存里,不在 KServe。

与主线二(Agent 负载)的关系

关系弱。KServe 的资源模型以"一个模型服务"为单位,没有会话、程序、轮次这些概念,也不参与请求排队。和 agent 相关的只有接口层面的跟进:

  • v0.18 让 HTTPRoute 转发 OpenAI Responses API(/v1/responses);v0.20 增加 Anthropic Messages API(/v1/messages)的路由。这只是把路径放行到后端,状态管理不在 KServe。
  • v0.21 加了 agent 工具调用的指南和示例。
  • spec.model 里有调度关键度(criticality)字段,对应到调度器的优先级。

llm-d 1.0 的 program-aware fairness、turn-priority、会话亲和这些机制,理论上可以通过 LLMInferenceService 的调度器配置启用,但 KServe 目前跟到的是 llm-d 0.8(v0.20)加若干 1.0 前的参数迁移(v0.21);KServe 是否已支持 llm-d 1.0 的这些新策略,我没有找到一手说明未复核。

与图中其他概念的关系

  • llm-d:LLMInferenceService 构建在 llm-d 之上,KServe 负责创建和升级 llm-d 的调度器与工作负载。
  • GIE:KServe 控制器创建 InferencePool 与 HTTPRoute;v0.18 起把 GIE 的 CRD 打进安装包,v0.20 升到 GIE v1.5.0。
  • vLLM:LLMInferenceService 的默认引擎,v0.20 起也是 KServe 正式列出的受支持运行时。
  • Dynamo:P/D 分离用到的 NixlConnector 依赖 NVIDIA 的 NIXL 传输库,这是间接关系;Dynamo 自己的编排不经过 KServe。
  • AIBrix:同一位置的并行方案,未见集成。
  • SGLang、TensorRT-LLM:llm-d 支持它们,但 KServe 的 LLMInferenceService 文档只围绕 vLLM;是否支持未核实。
  • Open Responses:KServe 转发的是 /v1/responses 路径;与 Open Responses 规范是否对齐未核实。
  • 与 OpenRouter、LiteLLM、MCP、AA-AgentPerf、Mooncake、llama.cpp、MNN、压缩与编译层各概念、硬件层各概念未发现直接关系。Tesla 案例恰好用了 AMD MI300X,但那是用户的硬件选择,不是 KServe 的特性。

存疑与未核实

  • 报告称"KServe v0.17 把基于 llm-d 构建的 LLMInferenceService 标为生产可用"。博客原文确实写 production-ready,发布日期 2026-03-13 也核实无误。需要补充的限定是:API 版本仍是 v1alpha2,博客没有使用 GA 一词;报告的表述容易让人以为 API 已稳定。
  • 报告只写到 v0.17。截至 2026-11-18 最新版本是 v0.21.0(2026-09-25),中间有 v0.18、v0.19、v0.20 三个版本,报告没有覆盖。
  • v0.17 集成的 GIE 版本:博客写 v1.3.0,变更日志里能看到的一条提交是升到 v1.2.0;应是发布前又升了一次,我没有找到对应提交。
  • Yuan Tang 的博客说 LLMInferenceService 通过 Knative 伸缩并支持缩到零;而 v0.17/v0.18 博客描述的伸缩路径是 WVA 配合 KEDA 或 HPA。两种说法指向不同机制,以发布博客为准更稳妥。
  • KFServing 改名与捐赠 LF AI & Data 的确切月份,各来源不一致,未找到当年的一手公告。
  • KServe 是否已适配 llm-d 1.0(2026-10-20 发布,晚于 KServe v0.21.0)未核实。
  • Tesla 的部署规模、OpenShift AI 的采用数字均无一手数据。
