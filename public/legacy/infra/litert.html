LiteRT

Google 的端侧推理运行时，由 TensorFlow Lite 改名而来

与主线一 KV cache · 中LiteRT-LM 的会话带写时复制 KV cache，并能把 KV 状态序列化后跨会话恢复与主线二 Agent 负载 · 中LiteRT-LM 提供函数调用、受约束解码与有状态会话，支撑端侧 agent 演示

它是什么

LiteRT（Lite Runtime 的缩写）是 Google 的端侧推理运行时，也就是让模型直接在手机、浏览器、手表、笔记本上运行而不经过云端的那层软件。它就是原来的 TensorFlow Lite（TFLite），2024 年改了名字，之后逐步换了内核。

图里写的是 LiteRT，但和大模型直接相关的其实是建在它上面的 LiteRT-LM。两者的分工，Google 自己的说法是三层一手Google Developers Blog, 2025-09-24：

  • LiteRT：底层运行时，负责高效执行单个模型，并把计算分派到 CPU、GPU 或 NPU（手机芯片里专门跑神经网络的单元）。
  • LiteRT-LM：C++ 写的 LLM 管线框架，处理大模型特有的事情：分词、采样、KV cache 管理、会话、提示缓存、多模态编码器的装卸。
  • LLM Inference API（属于 MediaPipe）：再上面一层给 Kotlin、Swift、JS 用的高级接口，底下由 LiteRT-LM 驱动。

来历与时间线

报告把"接替 TFLite"系在 2026-01-28，这个说法不准确。实际是三个节点：

  1. 2017 年：TensorFlow Lite 问世。到 2024 年，Google 称它跑在 27 亿台设备、10 万个以上的应用里厂商自述。
  2. 2024-09-04：改名。博客标题就是"TensorFlow Lite is now LiteRT"，并明说当时"唯一的变化是名字"，理由是它早已不只支持 TensorFlow，也支持 PyTorch、JAX、Keras 写的模型。.tflite 文件格式与扩展名不变一手Google Developers Blog, 2024-09-04。GitHub 仓库 google-ai-edge/LiteRT 也创建于这一天一手，GitHub API。
  3. 2025 年 5 月（Google I/O '25）：预览新一代运行时，包括新的 CompiledModel API 与新的 GPU 引擎 ML Drift一手，2026-01-28 博客的回顾。
  4. 2026-01-28：博客"LiteRT: The Universal Framework for On-Device AI"宣布，上述加速能力"已全部毕业进入 LiteRT 生产栈"。这篇的内容是新内核转正，不是改名一手Google Developers Blog, 2026-01-28。

LiteRT-LM 这条线：仓库创建于 2025-04-14一手，GitHub API；2025-09-24 首次向外部开发者开放 C++ 接口（预览），同时披露它早已在 Google 内部产品里使用；2026-05-19 的博客宣布新增 Swift、JavaScript、Flutter 接口一手Google Developers Blog, 2026-05-19。

它做了什么

LiteRT：换内核

2026-01-28 的博客列了四件事一手，性能数字均为厂商自述：

  • GPU：新引擎 ML Drift 覆盖 OpenCL、OpenGL、Metal、WebGPU，支持 Android、iOS、macOS、Windows、Linux 与 Web，自称平均比旧的 TFLite GPU delegate 快 1.4 倍。
  • NPU：把各家芯片厂的 SDK 藏在统一流程后面。可以提前为目标芯片编译（AOT），也可以在设备上现场编译（JIT），跑不了就回退到 GPU 或 CPU。首批生产级集成是 MediaTek 与 Qualcomm，自称最高比 CPU 快 100 倍、比 GPU 快 10 倍，测试条件见其各自的专题博客，本次未读。
  • 多框架：PyTorch 模型经 LiteRT Torch 库一步转成 .tflite。
  • 兼容：旧的 Interpreter API 继续可用，新功能走 CompiledModel API。

LiteRT-LM：大模型的编排层

核心是两个类一手，2025-09-24 博客。Engine 是单例，持有昂贵的共享资源：基座模型、各模态编码器，并按需装卸。Session 是有状态接口，一个会话代表一段对话或一项任务，带自己的历史、KV cache 和 LoRA 小适配器。这样 Chrome 里的摘要、校对等多个功能可以共用同一份几 GB 的模型。

它的模型文件扩展名是 .litertlm，命令行工具 litert-lm 可以直接从 Hugging Face 拉模型运行一手，READMELiteRT-LM README。

2026 年的重点特性是 MTP 投机解码：Gemma 4 自带多 token 预测的 drafter，LiteRT-LM 让 drafter 与主模型在同一块硬件上运行并共享 KV cache，避免跨硬件单元搬数据，自称在 Samsung S26 Ultra 的 GPU 上解码最高快 2.2 倍厂商自述。

与 Gemini Nano、AICore、MediaPipe 的关系

  • Gemini Nano：Google 的端侧闭源模型。Google 称 LiteRT-LM 驱动了它在 Chrome（内置 AI 接口）、Chromebook Plus、Pixel Watch（智能回复）上的部署，覆盖"数亿台设备"厂商自述。Pixel Watch 没有用完整的 Engine/Session，而是只挑了执行器、分词器、采样器几个模块拼成最小管线。
  • AICore：Android 的系统级 AI 服务，模型由系统提供，应用通过接口调用。2026-05 的博客说 Gemma 4 可以经 AICore 作为系统服务运行以获得更高性能。它和 LiteRT-LM 是两条交付路径：AICore 是系统替你装好模型，LiteRT-LM 是应用自带模型。
  • MediaPipe LLM Inference API：LiteRT-LM 之上的高级封装。搜索结果显示 Google 的文档称其已进入"仅维护"状态并建议迁移到 LiteRT-LM仅摘要；我打开原文档地址时，页面已是 LiteRT-LM 的介绍，看不到这句话。

2026 年的现状

LiteRT 最新版 v2.3.2（2026-10-26），仓库约 3601 星；LiteRT-LM 最新版 v0.19.1（2026-11-05），约 6898 星，星数已是底层运行时的近两倍一手，GitHub API，2026-11-18。LiteRT-LM 版本号仍是 0.x，v0.19 还对 C API 做了破坏性改动，但官方自称 production-ready。

LiteRT v2.3.0 新增 Samsung Exynos NPU，把 ML Drift 单独开源；v2.2.0 新增 Intel NPU（Lunar Lake、Panther Lake）一手，release notes。LiteRT-LM 的 NPU 支持目前在 Android 上可用，Windows 为预览一手LiteRT-LM 概览。

官方给的 Gemma 4 E2B（2.58 GB）数字：S26 Ultra GPU 上预填充 3808 tok/s、解码 52 tok/s；iPhone 17 Pro GPU 解码 56 tok/s；树莓派 5 CPU 解码 8 tok/s厂商自述，同上。2026-01 博客称 Gemma 3 1B 在 S25 Ultra 上 CPU 与 GPU 都快于 llama.cpp厂商自述，对比配置未详列。

与主线一（KV cache）的关系

中等。它不涉及数据中心的存储分层，但在单台设备上做了同一类事情，机制很具体一手，除注明外均出自 2025-09-24 与 2026-05-19 两篇博客：

  • 上下文切换：每个 Session 把 KV cache 和 LoRA 权重封装成自己的上下文。切换任务时保存旧会话状态、恢复新会话状态，博客自己类比成操作系统的进程切换。
  • 会话克隆：共享的提示前缀只算一次，克隆出的会话从那个 KV 状态分叉。这是端上的前缀缓存。
  • 写时复制：克隆时不复制 KV 缓冲区，只加引用，到某个会话要写入冲突位置时才真正复制。自称克隆耗时低于 10 毫秒。博客脚注说明，部分优化在 2025-09 的预览版里尚未放出。
  • 保存与恢复：2026-05 的博客说支持把较大的 KV cache 状态序列化保存，之后恢复，回到会话时跳过预填充。这是把 KV 从内存落到设备存储，和主线一的"KV 下沉到更慢的介质"是同一个动作，只是范围在一台手机内。
  • NPU 上按需增长：v0.18.0 加入 NPU 上的 KV cache 动态增长一手，release notes。NPU 通常要求固定形状，此前只能一次分配到最大长度。

与主线二（Agent 负载）的关系

中等。主线二讲的是云端服务单位从请求变成会话；LiteRT-LM 在端上从一开始就以有状态的 Session 为接口，并补齐了 agent 需要的几样东西：

  • 函数调用：README 把"面向 agentic 工作流的函数调用"列为核心特性。FunctionGemma 是 Google 专为函数调用做的 2.7 亿参数模型，LiteRT 版 289 MB。2026-02-26 的博客用它在 AI Edge Gallery 应用里做了两个离线演示：Mobile Actions（把"打开手电筒""建一个日程"翻译成系统调用）和 Tiny Garden，自报 Pixel 7 Pro CPU 上解码 142 tok/s一手，数字为厂商自述Google Developers Blog, 2026-02-26。
  • 受约束解码：强制工具调用的输出符合 JSON schema；v0.19.0 在 GPU 上加速了 logit 掩码一手，release notes。
  • 思考模式与 KV：Gemma 4 的思考内容可以在多轮会话里剥掉，博客给的理由就是节省 KV cache 空间。
  • Agent Skills：Gallery 应用里的多步工作流，Google 称是最早完全在端上跑的多步自主 agent 应用之一厂商自述Google Developers Blog, 2026-04-02。

这些都还是演示应用和开发者接口层面的证据，没有看到端侧 agent 的真实使用规模数据。

与图中其他概念的关系

  • ExecuTorch：正面对手，Meta 的同类栈；两者 CPU 路径都用 XNNPACK。
  • llama.cpp：Google 自己选的性能对照对象。
  • MNN：阿里的端侧运行时，同类。
  • GGUF：对位的模型文件是 .tflite 与 .litertlm。
  • EAGLE-3：LiteRT-LM 用的投机解码是 Gemma 4 自带的 MTP drafter，同属"draft 加验证"一族，但不是 EAGLE-3。
  • TPU Ironwood：没有关系。LiteRT-LM 性能表里的"TPU"指 Pixel 手机 Tensor 芯片里的单元，和数据中心的 Ironwood 不是一回事。

存疑与未核实

  • 报告称"Google 于 2026-01-28 宣布 LiteRT 接替 TensorFlow Lite"。改名与接替发生在 2024-09-04；2026-01-28 那篇宣布的是新一代加速栈转入生产。
  • 报告把"LiteRT-LM 支撑 Gemini Nano 的部署"挂在 2026-05-19 的博客上。这句话的出处是 2025-09-24 的博客；2026-05-19 那篇讲的是 Gemma 4 与新语言接口。
  • Android 手机上的 AICore 内部是否也用 LiteRT-LM 运行 Gemini Nano，官方博客没有明说。它点名的三个部署是 Chrome、Chromebook Plus、Pixel Watch。
  • MediaPipe LLM Inference API 进入维护状态只见于搜索摘要。
  • KV 状态保存与恢复的文件格式、是否跨设备可用、是否加密，没有找到说明。
  • MTP 的 2.2 倍、NPU 的 100 倍、对 llama.cpp 的领先，都是 Google 自测，没有找到独立复现。
