GGUF

llama.cpp 生态的单文件模型格式,本地量化模型的事实标准

与主线一 KV cache · 弱它只装权重和元数据,不装 KV cache;唯一的交集是量化类型名被 KV 量化借用与主线二 Agent 负载 · 弱文件里内嵌的 chat template 决定工具调用的拼写格式,除此之外没有关系

它是什么

GGUF 是一种模型文件格式。一个 .gguf 文件里装着运行一个大语言模型需要的全部东西:量化后的权重、模型结构参数、分词器、对话模板。用户下载一个文件,交给 llama.cpp、Ollama 或 LM Studio 就能跑,不需要再配一堆 JSON 和 Python 代码。

它由 llama.cpp 的作者 Georgi Gerganov 主导设计,是早期 GGML、GGMF、GGJT 三种格式的后继一手GGUF 规范。大家在 Hugging Face 上看到的 Q4_K_M、Q8_0、IQ3_M 这类后缀,指的就是 GGUF 文件采用的量化档位。报告把它放在"模型压缩与编译"层,是因为它实际上定义了本地阵营的量化标准:服务端用 FP8 和 INT4(llm-compressor 产出),本地用 GGUF 的 K-quant。

来历与时间线

  • 2023 年 3 月起:llama.cpp 使用 GGML 系列格式。这些格式只有张量和一串写死的超参数,每加一种模型结构或量化方式,往往要改加载代码并让旧文件失效二手Wikipedia。
  • 2023-06-05:Iwan Kawrakow 的 K-quant 合并进 llama.cpp,带来 2 到 6 bit 的新量化方式一手PR #1684。
  • 2023-08-21:GGUF 作为不向后兼容的新格式推出二手;Wikipedia 正文与信息框的日期相差一天Wikipedia。
  • 2024 年初:依赖重要性矩阵的 I-quant 系列和 imatrix 流程陆续合并(llama.cpp 的 #4773、#4861、#4930 等)一手,官方 README 列出的 PR 清单quantize README。
  • 2026-02-20:ggml.ai 团队加入 Hugging Face,GGUF 的制定方与最大的分发平台成了一家(见 llama.cpp 一篇)。

它做了什么

文件里有什么

按规范,一个 GGUF 文件依次是一手GGUF 规范:

  1. 文件头:四个字节的魔数 GGUF、版本号(当前为 3)、张量数量、元数据条目数量。
  2. 元数据键值对:键是字符串,值可以是整数、浮点、布尔、字符串或数组。常见的键有:
    • general.architecture:模型结构,如 llama;
    • 结构参数:上下文长度、层数、注意力头数等;
    • tokenizer.ggml.tokens 等:完整词表和特殊 token;
    • tokenizer.chat_template:一段 Jinja 模板,规定对话消息怎样拼成模型的输入文本。
  3. 张量信息:每个张量的名字、形状、数据类型和偏移量。
  4. 张量数据:权重本体,按 general.alignment(默认 32 字节)对齐。

设计目标写在规范里:单文件部署;可扩展而不破坏旧文件;可以用 mmap 直接映射进内存,不必整体读入;加载所需的信息全在文件里。与只存张量的 safetensors 相比,差别就在这一套标准化的元数据一手HF Hub: GGUF。

量化命名:Q4_K_M 是什么意思

以 Q4_K_M 为例,拆开看:

  • Q4:量化(Quantized),名义上每个权重用 4 bit 表示。原始模型通常是 16 bit。
  • K:K-quant 家族。早期的"legacy"方式(如 Q4_0)把每 32 个权重分成一块,每块配一个缩放系数,简单四舍五入。K-quant 改用两级结构:若干小块组成一个超级块,每个小块的缩放系数和最小值本身也被量化成 6 bit,省下来的空间让同样体积下误差更小。例如 Q4_K 是 8 个小块、每块 32 个权重,折合每权重 4.5 bit一手HF Hub: GGUF。
  • M:Medium,指"混合配方"的档位。并非所有张量都用同一精度。PR 原文的定义是:Q4_K_M 对一半的 attention.wv 和 feed_forward.w2 张量使用更高精度的 Q6_K,其余用 Q4_K;Q4_K_S(Small)则全部用 Q4_K一手PR #1684。

所以 Q4_K_M 的实际平均位宽比 4 高。官方在 Llama-3.1-8B 上的测量:Q4_K_M 为 4.89 bit/权重、4.58 GiB,而 F16 是 14.96 GiB一手quantize README。

另外两个常见词:

  • I-quant(IQ4_XS、IQ3_M、IQ2_XXS 等):另一套更激进的量化方式,以 256 个权重为超级块。同样体积下精度通常更好,主要用在 4 bit 以下,例如 IQ4_XS 约 4.25 bit、IQ2_XXS 约 2.06 bit一手HF Hub: GGUF。
  • imatrix(重要性矩阵):先让模型跑一遍校准文本,统计哪些权重对输出影响大,量化时优先保住它们。它不是一种格式,而是一个可选的辅助步骤:工具是 llama-imatrix,结果传给 llama-quantize --imatrix。I-quant 依赖它,K-quant 和 legacy 格式也可以用。

格式里还有三值量化 TQ1_0、TQ2_0 和 4 bit 微缩放浮点 MXFP4 等较新的类型。

2026 年的现状

  • Hugging Face 上的体量:按 GGUF 库筛选,2026-11-18 页面显示 222,943 个模型仓库一手,当日页面读数HF models: gguf。Hub 为 GGUF 提供元数据与张量查看器、在线转换工具 gguf-my-repo(每 6 小时同步 llama.cpp 主线)和 JavaScript 解析库。
  • 谁能读它:Hub 文档列出的工具是 llama.cpp、LM Studio、GPT4All、Ollama一手HF Hub: GGUF;Jan、koboldcpp 等也直接读取二手Wikipedia。Ollama 可以用 ollama run hf.co/用户/仓库 直接拉取 Hub 上的 GGUF,默认选 Q4_K_M 档,并依据文件内的 tokenizer.chat_template 自动匹配模板一手HF docs: Ollama。这也是"Q4_K_M 是本地默认档"的一个直接证据。
  • vLLM 的支持是实验性的:文档写明 GGUF 支持"高度实验性且未充分优化",可能与其他特性不兼容,目前只是一种降低内存占用的办法;该功能已迁出主仓库,需要另装 vllm-gguf-plugin;并建议使用原始模型的分词器,因为从 GGUF 转换分词器耗时且不稳定一手vLLM GGUF docs。换句话说,GGUF 在数据中心引擎里只是能加载,不是正路。
  • 精度评测:报告引用的 "Which Quantization Should I Use?"(Uygar Kurt,arXiv 2026-01-11)在 Llama-3.1-8B-Instruct 上统一评测了 13 种 GGUF 档位。五项基准均分:F16 为 69.47,Q8_0 为 69.41,Q5_K_M 为 69.36,Q4_K_M 为 69.15(体积减少 69.41%),Q3_K_M 为 68.07,Q3_K_S 为 65.49一手,已读原文arXiv 2601.14277。需要注意三点:论文推荐的是 5 bit 档(Q5_0 均分最高,为 69.92,作者承认可能是噪声),需要更高压缩时建议的默认档是 Q4_K_S 而非 Q4_K_M;评测只在一台双路至强 CPU、一个模型上做;完全没有覆盖 I-quant 和 imatrix,所以不能用它来判断 4 bit 以下的档位。

与主线一(KV cache)的关系

关系弱,接近于无。GGUF 存的是静态的模型权重和元数据;KV cache 是推理过程中随对话产生的中间状态,两者不是一类东西。规范中没有任何关于 KV cache 或会话状态的内容一手GGUF 规范。llama.cpp 把 slot 的 KV 落盘时,用的是另一套状态文件,头文件里为它定义了独立的魔数 ggsn(会话)和 ggsq(单序列),不是 GGUF一手llama.h。

能找到的交集只有两处,都很间接:

  • llama.cpp 的 KV 量化参数 --cache-type-k/v 可取 q8_0、q4_0、q5_1 等值,这些就是 GGUF 权重所用的同一套 ggml 数据类型。也就是说,KV 量化借用了为权重设计的量化内核。
  • 权重量化得越小,同一台机器上留给 KV cache 的内存越多,能开的上下文越长。这是资源上的此消彼长,不是机制上的联系。

与主线二(Agent 负载)的关系

关系弱。唯一落到机制上的一点是 tokenizer.chat_template:模型怎样表示工具定义和工具调用,由这段内嵌在文件里的 Jinja 模板决定。llama.cpp 的函数调用文档说,服务器根据模板识别出原生的工具调用格式,识别不了就退回通用格式,后者更费 token、效率更低;模板缺失或不支持工具时需要用 --chat-template-file 覆盖一手function-calling.md。因此同一个模型,换一个转换者打包的 GGUF,工具调用可能表现不同。

此外,量化档位会影响 agent 的可靠性(上述评测发现困惑度相近的格式在指令遵循基准上可以有明显差异),但这属于量化的一般后果,不是 GGUF 特有的。

既然两条主线都弱,它为什么在图里:它代表"量化事实标准"和本地阵营的分发方式。报告的压缩一节要说明"量化工具已全部绑定到具体运行时、没有跨运行时的统一交换格式",GGUF 是本地一侧的那个标准。

与图中其他概念的关系

  • llama.cpp:原生运行时,同一团队维护;量化工具 llama-quantize 和 llama-imatrix 都在其仓库中。
  • llm-compressor:服务端的对应物,产出 safetensors 加 compressed-tensors 格式的 FP8、INT4 权重,供 vLLM 使用。两者是互不通用的两套量化产物。
  • vLLM:可通过插件实验性地加载 GGUF。
  • MNN、ExecuTorch、LiteRT:各有自己的端侧模型格式(MNN 格式、.pte、.tflite),不读 GGUF,是并列关系。
  • 其余概念(网关、集群编排、硬件):无直接关系。

存疑与未核实

  • 笔记称 vLLM 的量化文档把 GGUF 列为支持项之一。更完整的事实是:该支持已迁到主仓库之外的插件,且官方自称高度实验性。报告若把 GGUF 写成 vLLM 的常规量化来源之一,会给读者错误印象。
  • 报告引用评测时突出 Q4_K_M 一档。数字本身与论文一致;但论文的推荐其实是 5 bit 档与 Q4_K_S,且未评测 imatrix 和 I-quant。Q4_K_M 的"事实标准"地位来自社区惯例和 Ollama、Hub 的默认选择,而不是这篇论文的结论。
  • GGUF 的推出日期(2023-08-21)只有 Wikipedia 一个二手来源,没有读到当时的原始 PR。
  • 笔记中"imatrix 对 3 bit 及以下帮助最大"来自社区博客,本次没有找到一手数据核实。
  • Hugging Face 文档里"45K 个公开 GGUF"是较早写下的数字,与当日页面显示的 22 万多不一致,应以后者为准。
  • GGUF 名称的全称各处说法不一,规范本身没有给出。
