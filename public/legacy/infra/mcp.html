MCP

让 AI 应用以统一方式接入外部工具与数据的开放协议

与主线一 KV cache · 中不碰 KV 本身,但规范明文要求工具列表顺序稳定以保住 prompt 缓存前缀与主线二 Agent 负载 · 强agent 调工具的事实标准;2026-07-28 版去会话化并用 Tasks 句柄承接长时工具

它是什么

MCP(Model Context Protocol,模型上下文协议)是一套开放协议,规定 AI 应用怎样向外部系统要"工具"和"上下文"。没有它之前,每个 AI 应用要接 GitHub、数据库、Slack,都得各写一套集成;有了它,服务方写一个 MCP server,任何支持 MCP 的应用都能用。Anthropic 在发布时把它描述为连接 AI 助手与数据所在系统(内容库、业务工具、开发环境)的开放标准一手Anthropic 公告。

需要先说清一点:MCP 不是推理协议。它不传 token、不碰模型权重和 KV cache,走的是应用与工具之间的那条线。它出现在推理基础设施的图里,是因为 agent 负载的形状(调哪些工具、工具返回多大、要等多久)由它决定,而这些会直接变成推理侧的 prompt 前缀和调用间隙。

它做了什么

host / client / server 三个角色

  • Host:用户面对的 AI 应用(Claude Desktop、IDE、ChatGPT 等)。它持有完整对话、调模型、做授权与安全决策。
  • Client:host 内部为每个 server 建的一个连接对象,与 server 一对一。
  • Server:提供能力的一方,可以是本机进程,也可以是远程服务。

规范的一条设计原则是:server 不应读到整个对话,也看不到其他 server;完整对话历史留在 host一手架构页。Server 暴露三类原语:tools(模型可调用的函数,含 name、description、inputSchema、可选 outputSchema)、resources(可读数据)、prompts(提示模板)。底层消息格式是 JSON-RPC。

传输方式的演变

  1. stdio:host 把 server 当子进程启动,通过标准输入输出通信。本地场景至今沿用。
  2. HTTP+SSE(2024-11-05):远程场景的第一版,需要一条长期保持的 SSE 流。2025-03-26 起弃用,2026-07-28 正式列入弃用登记,给一年过渡期。
  3. Streamable HTTP(2025-03-26 起):单一 HTTP 端点,POST 请求,响应可按需升级为流。早期版本仍带 Mcp-Session-Id 会话头。
  4. 无状态的 Streamable HTTP(2026-07-28):会话头取消,见下节。

2026-07-28:协议核心改为无状态

报告的说法经核实基本准确。官方博客与 changelog 明文写的改动如下一手(MCP 博客、changelog):

  • 移除握手:initialize/initialized 交换取消(SEP-2575)。每个请求在 _meta 里自带协议版本、客户端身份与能力。想预先了解 server 能力,可调新增的 server/discover,但不是必须。
  • 移除会话头:Mcp-Session-Id 取消(SEP-2567)。tools/list 等列表端点不得随连接变化。
  • MRTR(多轮往返请求):以前 server 要在一条长连接上反向向 client 发请求(要用户确认、要采样)。现在改为 server 返回 resultType: input_required 并列出所需输入,client 带着答案重试原请求(SEP-2322)。
  • 路由用的 HTTP 头:方法名与工具名放进 Mcp-Method、Mcp-Name 头,网关和限流器不用解析 JSON 正文就能路由与计量(SEP-2243)。
  • 列表可缓存:tools/list 等结果必须带 ttlMs 与 cacheScope(SEP-2549)。
  • 取消 SSE 断点续传:流断了,进行中的请求即丢失,client 须以新请求重发。
  • 弃用 Roots、Sampling、Logging,以及动态客户端注册(DCR,改用 CIMD);同时确立至少 12 个月的弃用窗口政策。

动机:MCP 最初为"一个桌面应用通过 stdio 连本机 server"设计,长连接加握手很自然。放到负载均衡器、Kubernetes 或多地域之后,有状态带来三类问题:客户端被钉在持有会话的实例上,必须配粘性会话或共享会话存储;连接一断会话状态即丢;维持长连接本身有额外消息开销一手,AAIF 迁移指南,基于 RCAAIF 迁移指南。改后任何请求可落到普通轮询负载均衡器后的任一实例,不需要共享存储。

状态去了哪:协议不再替你管状态,但应用仍可有状态。规范建议 server 在工具结果里发一个显式句柄(如 basket_id),由模型在后续调用中当普通参数传回;规范还建议把句柄的保留期限写进工具描述,让模型看得到一手,非规范性指导Tools 规范。也就是说,状态的索引从传输层挪进了模型的上下文。

Tasks 扩展

Tasks 解决"工具要跑几分钟到几小时"的问题(CI 流水线、批处理、等人审批)。Server 不阻塞,而是返回 resultType: task 的结果,内含 taskId、初始状态、ttlMs 与建议轮询间隔 pollIntervalMs;client 用 tasks/get 轮询,任务进入 input_required 时用 tasks/update 送输入,用 tasks/cancel 请求取消(协作式,server 可不遵从)。taskId 是持久句柄,client 断线或重启后可继续轮询一手Tasks 概览。

需要更正报告的一处措辞:Tasks 不是 2026-07-28 "新增"的。它在 2025-11-25 版已是核心协议里的实验特性,这次是移出核心、成为正式扩展 io.modelcontextprotocol/tasks 并重新设计:阻塞式的 tasks/result 换成轮询,新增 tasks/update,删除 tasks/list(没有会话后无法安全限定范围),并允许 server 自行决定是否返回任务句柄(SEP-2663)一手(changelog、RC 博客)。官方博客引用 AWS 的说法称 Tasks 由 AWS 贡献。

与主线一(KV cache)的关系

强度:中。MCP 不读写 KV cache,关系全部是间接的,但其中一条已写进规范。

规范明文的部分:

  • 工具定义会被 host 放进模型上下文,通常位于 prompt 最前面。前缀只要变一个 token,其后的 KV 就无法复用。2026-07-28 规范为此写了一条:server 应当(SHOULD)以确定性顺序返回 tools/list,理由原文是"提高 LLM prompt 缓存命中率"一手Tools 规范。官方博客也说列表带缓存提示与确定顺序,是为了让上游 prompt 缓存在重连后保持稳定一手MCP 博客。
  • 去会话化附带规定工具集不得(MUST NOT)随连接变化,只可随授权变化。这消除了"同一用户重连后工具列表不同"这一类前缀抖动。
  • ttlMs 与 cacheScope 让 client 知道工具目录可以缓存多久、能否跨用户共享。

以下是我的推断,规范没有这样写:

  • cacheScope: public 的工具目录在不同用户间逐字节相同,意味着工具定义这段前缀有机会跨用户共享 KV;按授权裁剪工具集则会把前缀切成多个变体,降低共享率。
  • Tasks 与主线一的关系是一个缺口。长时工具运行期间,该会话在推理引擎里的 KV 处于闲置,留在显存是浪费,丢掉则回来时要重算。Tasks 给了 client 两个时间信号(pollIntervalMs、ttlMs),但这些只到 host 为止,没有任何标准字段把"预计还要等多久"传给网关或推理引擎。报告在跨层问题里说的"缺少传递预期工具时长的标准接口",查证后确实如此:MCP 侧有原料,但没有通道。
  • 工具结果(content 文本)会追加到对话尾部,只增长不改写,对前缀缓存是友好的;但大体积结果会加速上下文膨胀与压缩,而压缩会使缓存失效。

与主线二(Agent 负载)的关系

强度:强。MCP 是 agent 负载的协议面之一,它定义的是"程序/会话"里工具调用这一半。

  • 2026-07-28 的改动整体是对"状态放在哪"的一次回答:协议层不存状态,状态要么在 host 的对话里(以句柄形式经过模型),要么在 server 自己的存储里(以 taskId 或业务句柄索引)。这是规范明文。
  • Tasks 把"一次工具调用"从同步请求改成可中断、可恢复、可中途要输入的持久对象,对应 agent 会话从秒级拉长到分钟或小时级。
  • MRTR 把人在回路(确认、补参数)从长连接上的反向请求改为普通的请求重试,使它能在无状态部署下工作。Supabase 称此前因无状态运行而做不了 elicitation厂商自述MCP 博客。
  • Mcp-Method/Mcp-Name 头让网关能按工具做路由、限流与计量,这是报告所说"LLM 网关与 MCP 网关合流"的协议前提。

与图中其他概念的关系

  • Open Responses:同属 AAIF。Open Responses 规范把 MCP 列为"外部托管工具"的一例,并指出此时控制权不必先交还开发者一手Open Responses 规范。两者分工是:Open Responses 管应用与模型之间,MCP 管应用(或模型提供方)与工具之间。
  • LiteLLM:报告笔记引第三方称其开源核心含 MCP 网关二手,本次未复核。
  • OpenRouter:未查到其与 MCP 规范的直接关系,不写。
  • vLLM:其 Responses 服务代码里有处理 MCP 工具请求的路径(如从 MCP 请求中提取 allowed tools 的函数)一手,代码文档vLLM v0.25.1 API 文档。
  • llm-d、GIE、Dynamo、AIBrix 等集群层:无直接关系。它们做的前缀感知路由受益于稳定的工具前缀,这是推断。
  • 其余引擎、压缩、硬件层概念:无直接关系。

存疑与未核实

  • 报告称 2026-07-28 "新增面向长时工具的 Tasks 扩展"。更准确的说法是 Tasks 从 2025-11-25 的实验性核心特性移出为正式扩展并重新设计;tasks/update 是新增的,tasks/list 被删除。
  • 报告笔记提到"AAIF 称 89% 的受访成员在生产中运行 MCP"。本次打开笔记所引的 AAIF 文章,抓取结果里没有这个数字,只有 ChatGPT 98 倍等数据;89% 的出处未能核实。
  • 笔记中 SDK 月下载量有 9700 万与 1.1 亿两种说法;官方 2026-07-28 博客的口径是 Tier 1 SDK 合计接近 5 亿/月。三者统计范围不同,不可直接比较。
  • 2025-06-18 与 2025-11-25 两版的具体内容未打开各自 changelog,文中相关描述来自后续版本的回溯与背景知识。
  • AAIF 迁移指南写于 RC 阶段(2026-07-21),其中 OAuth 2.1 与 OIDC 列为强制等细节未与终版逐条核对。
  • MCP 项目在 LF 内的确切法律形态(LF Projects Series 与 AAIF 定向基金的关系)只看到页脚与旁证,未读到 MCP 自己的章程。
