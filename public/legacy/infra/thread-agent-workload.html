主线二 · Agent 负载把服务单位改成程序与会话

一个 agent 任务是几十次相互依赖的模型调用,基础设施要按整个任务而非单次请求来优化

一句话论点

聊天时代,推理系统服务的对象是一次请求:进来一段提示词,出去一段回答,请求之间互不相关。Agent(能自己调用工具、循环多步完成任务的模型应用)改变了这一点:一个任务由几十到上百次模型调用组成,每次调用都带着此前的全部历史,调用之间夹着工具执行的等待。用户关心的是整个任务何时做完、花多少钱,而不是其中某一次调用的首 token 延迟。于是调度、缓存、基准和定价的对象都要从"请求"换成"程序"(一次任务的全部调用)或"会话"(一个用户的多次任务)。

这条主线的证据比主线一薄:负载画像主要来自一份聚合平台数据和一份单一产品的 trace,且都与编程 agent 有关。它是否适用于所有 agent,目前不能下结论。

先讲清基本概念

一个 agent 循环长什么样

以编程 agent 为例,用户说"修掉这个 bug",之后:

  1. 应用把系统提示、工具定义和用户消息发给模型。
  2. 模型输出一小段文字和一个工具调用(例如读某个文件)。
  3. 应用执行工具,把结果追加到历史末尾,把全部历史再发一遍。
  4. 重复第 2、3 步,直到模型认为任务完成,把结果交还用户。

这里有四个特征:多轮;每轮携带全量历史;轮与轮之间有工具执行的间隙,期间模型侧无事可做;agent 还可能派生子 agent 并行处理子任务,形成扇出。本文沿用 Copilot 论文的说法,把用户发起的一次交互称为一个 turn,turn 内部是若干次模型调用。

一个 token 流算例

以下是本文构造的示意算例,参数取自公开画像的量级,不是实测。

Agent 任务:系统提示加工具定义 20,000 token;共 30 步;每步模型输出 250 token,工具返回 1,250 token,即每步上下文增长 1,500 token。

  • 第 i 步的输入为 20,000 + 1,500 × (i − 1) token,30 步输入合计 1,252,500 token。
  • 输出合计 30 × 250 = 7,500 token。输入输出比约 167:1。
  • 整个任务中真正第一次出现的输入只有 63,500 token(第 30 步的上下文长度),其余 1,189,000 token 都是重发的前缀,重复率约 95%。

聊天会话:系统提示 500 token;5 轮;每轮用户输入 100 token,模型回答 400 token。

  • 各轮输入为 600、1,100、1,600、2,100、2,600,合计 8,000 token;输出 2,000 token。输入输出比 4:1。

两者的差别不只是量:agent 的成本几乎全在输入侧,而输入几乎全是重复前缀。按 Claude Sonnet 5.5 的公开价(输入每百万 2 美元、5 分钟缓存写入 2.5 美元、缓存读取 0.10 美元)一手Anthropic 文档,上面的 agent 任务输入侧不用缓存约 2.51 美元,全部命中约 0.28 美元,相差约 9 倍(本文自行计算,假设每步都命中、间隙不超过缓存有效期)。这就是"缓存命中率是 agent 成本的决定变量"的来历。

公开数据支持这个量级。Copilot 的 trace 里,每次调用的中位输入为 68K token、中位输出 247 token,中位输入输出比超过 275:1一手arXiv 2608.00101。AA-AgentPerf 回放的编程 agent 轨迹里,单次请求输入约 5K 到 131K token、均值约 27K,输出中位约 150 token一手AA-AgentPerf。SAGA 论文引用的输入输出比是 100:1一手arXiv 2605.00528。

服务单位是什么意思

服务单位指系统为之排队、计量、承诺服务质量的那个对象。请求级指标有三个:TTFT(首 token 延迟)、TPOT(每个输出 token 的间隔)、tokens/s(吞吐)。它们对 agent 不够用,原因有三:

  • 中间步骤没有人在看。agent 任务的 30 次调用里,用户只看得到最后的结果;某一步的 TTFT 快 200 毫秒没有意义,30 步加起来多久才有意义。
  • 调用之间有依赖。请求级调度器把 30 次调用当作 30 个陌生请求,每次都重新排队。Agentix 论文指出程序会在请求级和程序级两个层面遭遇队头阻塞一手,仅摘要页NSDI '26。
  • 时间不全在模型上。Sutradhara 的生产分析发现,工具调用占最终答案首 token 渲染延迟的 30–85%一手,仅摘要arXiv 2601.12967。

程序级指标因此出现:

  • 任务完成时间(job 或 task completion time):从任务提交到最终结果。
  • goodput:满足服务目标的有效工作量,而不是原始吞吐。JITServe 把它定义为满足各请求 SLO 的服务量一手,仅摘要页NSDI '26。
  • Agents per Megawatt:AA-AgentPerf 的首要指标,即在每个 agent 都达到规定的输出速度与 P95 TTFT 的前提下,每兆瓦电力能同时支撑多少个 agent一手AA-AgentPerf。它把被测对象从"芯片加模型"换成了"整套系统加真实轨迹"。

负载画像的证据

OpenRouter:agentic 占 token 的 76%

OpenRouter 2026 年 10 月的数据显示,agentic 密钥占 token 的 76%(约 600 万亿),一年前为 8%一手,平台自有数据OpenRouter。读这个数字要先看方法:它按 API 密钥逐月分类,用七个信号的加权得分——工具调用率、输入输出比、每请求轮数、缓存命中率、每请求提供的工具数、请求间隔、取消率——得分 0.50 及以上记为 agentic。分类对象是密钥而不是用户或公司;统计只含 OpenRouter 自己的流量,价格与缓存分析不含 BYOK(用户自带上游密钥)。同一页面还报告 agentic 密钥的中位缓存命中率从 6 月的 76.1% 升到 10 月的 90% 以上。

Microsoft:GitHub Copilot 生产 trace

这是目前最有分量的一份画像。论文题为 Agentic Coding in the Wild: Characterizing GitHub Copilot Traces at Production Scale,2026-07-30 提交 arXiv,数据是 2026 年 6 月的采样 trace:320 万用户、1,300 万会话、7.61 亿次模型调用、95 万亿 token一手,已读摘要与正文arXiv 2608.00101Microsoft Research。核对到的数字如下:

这组数字描出的形状是:turn 内部是紧凑的自动循环,工具大多很快但尾部很长;turn 之间是人的节奏,以分钟计。缓存在 turn 内几乎总能命中,在 turn 边界、换模型和压缩时失效。作者还做了一个空闲时间预测器,能捕获 86–90% 的总空闲时间,用来说明资源可以提前回收和预热。

作者自己列出的局限:数据是采样的,只来自 Visual Studio 与 VS Code、美国区域、6 月的一周;trace 是客户端视角,没有服务端视图;没有提示词内容,无法把效率与任务质量关联。

三篇系统论文

  • SAGA(arXiv 2605.00528):作者在 32 张 GPU 上用 vLLM v0.6.0 跑 SWE-bench 编程 agent,测得 38% 的总时间花在重新生成工具调用期间被丢弃的 KV 上。同一论文里,开启前缀缓存与亲和路由的 vLLM v0.15.1 基线把这个比例降到 22%,SAGA 相对该基线把任务完成时间降低 1.64 倍(几何平均)一手,已读正文arXiv 2605.00528。它的工具时延表显示代码执行 P50 为 180 毫秒、P99 为 28 秒,网络类工具 P99 为 45 秒。
  • Sutradhara(Microsoft,arXiv 2601.12967):除上述 30–85% 外,指出尽管迭代之间上下文大量复用,KV 命中率仍会下降;方案是让编排器给引擎传语义提示,并把工具执行与 prefill 重叠,在 A100 上同等延迟下多承载最高 77% 的负载一手,仅摘要arXiv 2601.12967。
  • Continuum(Berkeley,arXiv 2511.02230):引擎在有新请求排队时会驱逐已完成请求的 KV,而 agent 只是在等工具。方案是给 KV 设一个存活时间(TTL),按重载代价与预期排队延迟决定,到期自动释放,并配合程序级先到先服务;报告平均任务完成时间改善 8 倍以上一手,仅摘要arXiv 2511.02230。

三篇的倍数都是作者在开源模型和基准任务上的自测,条件互不相同,只能说明问题存在,不能相互比较。

它在五层里分别改变了什么

  • 引擎与运行时:输入变长、调用变密之后,GPU 之外的开销显形。vLLM v0.34.0 把 128K 提示词的每请求 CPU 开销降了 40 倍,KV 块分配的 CPU 用量降 45–50%,并新增可选的缓存感知准入排序一手vLLM v0.34.0。工具调用要求模型输出符合格式的 JSON,结构化输出因此成为必需功能。工具间隙期间 KV 留不留,是 Continuum 等论文讨论的问题;本轮在 vLLM v0.34.0 的 release notes 里没有读到与工具间隙相关的保留或 TTL 功能。
  • 压缩与编译:关系较间接。agent 输出短、输入长,投机解码这类加速输出的手段对它的收益有限;报告引用的 Red Hat 基准中,长输入负载下的提升明显小于聊天负载。
  • 集群服务与编排:调度对象变成程序。学术上有 JITServe(goodput 提升 1.4–6.3 倍)与 Agentix(同延迟下程序吞吐为 vLLM 等系统的 4–15 倍)均为论文自报;工程上,llm-d v1.0.0 的 flow control 加入 program-aware fairness 与 turn-priority scoring,并在 agent-aware serving 下列出会话状态插件与 Responses API 状态复用一手llm-d releases。Dynamo 1.0 的 release notes 列出路由器请求优先级队列、Responses API 与 Anthropic Messages 端点一手Dynamo v1.0.0;报告所说的"每请求延迟敏感度与预期输出长度 hint"和实验性 cache pinning 来自 NVIDIA 博客,本轮未复核未复核。
  • 硬件与算力:长上下文加高并发使内存容量成为约束,KV 向主机内存与闪存层外溢;每请求 CPU 开销与工具执行也抬高了对 CPU 的需求。基准随之改变:AA-AgentPerf 用 agent 轨迹和每兆瓦 agent 数评测整机架;报告称 MLPerf Inference v6.1 新增了边缘 agentic 推理测试二手,本轮未复核。
  • 接入层与经济性:协议为工具与多步调用而设计。MCP(模型调用外部工具的协议)2026-07-28 版把核心改为无状态,取消初始化握手与会话头,使任何请求可以落到任何实例;需要状态的服务器改为返回句柄,长时任务移入 Tasks 扩展一手MCP blog。服务档位把可延迟性定价:OpenAI 的 Batch 与 Flex 为标准价一半,Fast 为 2 倍,另有 Ultrafast 档一手OpenAI 定价页;Gemini 的 Batch、Flex 为半价,Priority 约 1.8 倍一手Gemini 定价页。后台 agent 可以走便宜档,交互式 agent 走加速档。缓存定价见主线一文档。

两条主线如何互相咬合

agent 负载让 KV cache 成为核心资源,机制上有两点。

第一,前缀重复。算例里 95% 的输入是重发的前缀,Copilot 实测 turn 内命中率平均 90%。只要缓存在,prefill 只需处理每步新增的一两千 token;缓存一丢,就要重算几万到上百万 token。聊天负载的前缀短,丢了也不贵。

第二,工具间隙。一步与下一步之间,模型侧空等工具返回,这段时间从 166 毫秒到 79 秒以上不等;turn 与 turn 之间则是 25 分钟量级的人类空闲。KV 留在显存里就挤占其他请求,丢掉就要重算。这个两难正是主线一里"下沉到主机内存或闪存、需要时取回"的需求来源,也是 SAGA、Continuum、Sutradhara 三篇论文的共同出发点。

由此引出跨层的"状态放在哪"。agent 会话有状态,而弹性基础设施希望每个请求可以落到任何机器。各层给出的是局部答案:引擎做 KV 分层,集群做会话亲和,硬件做闪存上下文层,MCP 把会话状态移出协议改成显式句柄,API 让调用方声明缓存断点与有效期。缺的是把信息串起来的接口——应用知道下一步工具大概要多久、这段前缀之后还用不用,引擎的驱逐策略却拿不到这些信息。Sutradhara 的"薄 API"和 Continuum 的 TTL 是研究原型层面的尝试。

应用层的选择还会直接抵消基础设施的投入:换模型使命中率降到 8%,压缩上下文同样重置缓存。路由(为省钱换模型)、压缩(为省 token)与缓存(为省 prefill)三者相互冲突。

反方与局限

  • 76% 的口径问题。OpenRouter 的分类器把缓存命中率和输入输出比本身当作判定 agentic 的信号,因此"agentic 流量缓存命中率高、输入输出比高"在一定程度上是定义的结果,不是独立发现。它按密钥分类,一个密钥下混合的流量会被整体归类;阈值 0.50 是平台自定的;数据未经外部验证。OpenRouter 的用户以开发者和编程工具为主,不能代表经由直连 API、云平台或自有产品的流量。8% 到 76% 说明这个平台上的流量结构剧变,不能直接读作"全行业四分之三的 token 是 agent"。
  • 可能只是编程 agent 的特例。Copilot trace、AA-AgentPerf 的轨迹、SAGA 与 Continuum 的 SWE-bench 实验都是编程任务。编程 agent 的工具(读文件、跑测试)大多很快,上下文增长规律。客服、浏览器操作、深度研究类 agent 的工具时延、扇出和前缀重复率可能很不一样,本轮没有找到同等规模的公开画像。
  • 头部闭源厂商没有公开画像。OpenAI、Anthropic、Google 自有 agent 产品的负载数据没有公开。Copilot 的 trace 是客户端视角,看不到服务端如何调度与缓存。
  • 学术结果的基线偏弱。SAGA 的 38% 测于 2024 年的 vLLM v0.6.0;换成带前缀缓存的新版本已降到 22%。引用这类数字时要带上基线版本。
  • 请求级指标并未过时。交互式 agent 的最后一步仍面向用户,TTFT 依然重要;AA-AgentPerf 自己的服务目标就是用每请求的输出速度与 P95 TTFT 定义的。程序级指标是叠加在请求级之上,而不是取而代之。
  • 负载在快速变化。Copilot 论文自己指出编程 agent 演进很快,需要纵向跟踪;一周的采样只是快照。

未决问题

  • 工具间隙期间 KV 该保留、下沉还是丢弃,没有通用策略;Copilot 论文的空闲预测器和 Continuum 的 TTL 都还没有成为主流引擎的默认行为。
  • 应用、网关与引擎之间没有传递"预期工具时长"与"缓存价值"的标准接口。
  • 程序级公平性如何定义:按请求公平会让调用多的 agent 多占资源,按程序公平又需要识别哪些请求属于同一程序。llm-d 已有实现,但没有公认的定义。
  • 子 agent 扇出的画像缺失:Copilot 论文提到并发来自子任务或后台 agent,但没有给出占比。
  • 集群层缺少公认的端到端 goodput 基准;AA-AgentPerf 偏硬件与整机,完整测试集不公开。
  • 编程以外的 agent 负载长什么样,缺少生产规模的公开数据。
