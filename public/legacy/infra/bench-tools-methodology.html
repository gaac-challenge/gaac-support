压测工具与测量方法论

回放用 AIPerf 作底座，真 agent 用计量代理；指标名各家不通用，必须写明计时点

结论先行

  • 2026 年仍在活跃维护、可直接对接任意 OpenAI 兼容端点的通用压测工具有三个：AIPerf（NVIDIA，GenAI-Perf 的后继）、GuideLLM（vllm-project / Red Hat）、inference-perf（kubernetes-sigs）。三者都是 Apache-2.0，都已支持 agent 轨迹回放、多轮会话、goodput。LLMPerf 已归档，GenAI-Perf 已停止开发。
  • 同一个名词在不同工具里是不同的公式。TPOT 在 GuideLLM 里含首 token，在 vLLM、SGLang、inference-perf 里不含；AIPerf 把别家叫 TPOT 的量叫 ITL。inference-perf 官方文档直说：两个工具用默认配置打同一个服务，数字能差几十个百分点，差异在工具不在服务。
  • agent 负载的公开做法（AA-AgentPerf、InferenceX AgentX）都是闭环：并发数指同时活着的 agent 数，每个 agent 等上一步返回再发下一步。这和传统的开环定速压测是两种实验，不能混着比。
  • 对我们的比赛，压测工具只能覆盖"回放轨迹"这一半；选手真 agent 上场后，Benchmark 的形态应是挂在端点前的计量代理，两种形态共用同一套指标定义。

逐个说明

AIPerf 与 GenAI-Perf

GenAI-Perf 的 README 顶部已写明"正在淘汰，不再开发新功能，请改用 AIPerf"一手。AIPerf 是多进程架构（10 个服务经 ZMQ 通信），pip install aiperf 即可用，不依赖 Kubernetes。Dynamo 的基准目录直接调用它一手。

对我们最相关的是 2026 年下半年加进来的 agent 能力：

  • v0.12.0（2026-08-06）加入 AgentX v1.0 回放栈，覆盖 Weka 轨迹与 DAG 形负载，并新增 Anthropic Messages 端点、会话亲和头、原样载荷回放。
  • v0.13.0（2026-09-24）把 cache-bust 推广到所有结构化负载，新增 reset_kv_cache 钩子、--per-chunk-usage（修正首个流式分块捆绑多个 token 造成的每用户速度虚高）、高精度定速循环。
  • --scenario inferencex-agentx-mvp 把 InferenceX AgentX 的规则锁成一个开关，违规就在结果里写 submission_valid: false。锁定的规则包括：闭环 agentic replay、ignore_eos=true、必须流式、保留轨迹里的间隔、全系统空闲不超过 10 秒、--cache-bust first_turn_prefix、数据集必须是有固定身份的公开语料；上下文溢出率超过 1% 判无效一手AgentX 教程。
  • 找 SLA 边界有两条路：adaptive scale 在一次运行里按评估窗口逐步加压，全部 SLA 过滤条件通过才继续加，失败后在最后一个通过点附近保持；搜索配方里有现成的 max-concurrency-under-sla一手adaptive scale 文档。
  • --num-profile-runs N 重复跑并给置信区间；--network-latency-automatic 在测试期间持续做 TCP 握手测 RTT，再从 TTFT 和请求延迟里扣掉均值；--gpu-telemetry 采 DCGM 或 pynvml 的功耗一手指标参考。

已知局限：README 写明输出长度无法保证，除非给服务端传 ignore_eos 或 min_tokens；adaptive scale 只能用 YAML 配置。

GuideLLM

定位是"面向 SLO 的评测平台"。负载用 --profile 选择：synchronous（串行）、concurrent（固定并发流）、throughput（尽力发）、constant 与 poisson（开环定速）、sweep（先测串行和最大吞吐，再在两者之间取速率点）、knee（按并发扫描并拟合吞吐拐点）、replay（轨迹回放）一手。

三处设计值得参考：

  • 调度延迟单列。request_dispatch_delay 是实际发出时刻减计划时刻，request_scheduled_latency 从计划时刻算到结束。对闭环策略这两个量报 null 而不是 0，因为"目标时刻"取自系统自己的响应，量出来是循环论证一手指标文档。
  • 预热边界按事件过滤。请求级指标只要请求与测量窗口有重叠就计入，token 级指标只算落在窗口内的事件（v0.7.4 改成这样，官方说明会改变被采样的请求集合）。
  • 百分位带置信区间，样本不够就报空，见下文统计一节。

v0.8.0（2026-09-30）加入 Weka 与 OTel 轨迹回放和 goodput。回放 Weka 轨迹时，预热的 tool_tokens / system_tokens 前缀和扁平化 agent 的拆分尚未实现一手轨迹回放文档。vLLM 自己的 sweep 文档建议：只测单个服务配置时用 GuideLLM，而不是 vllm bench serve一手。

inference-perf、llm-d-benchmark 与 GIE

inference-perf 出自 Kubernetes wg-serving 的基准与指标标准化工作，有 JOSS 论文。它的独特价值在文档：comparability.md 是目前最坦率的一份跨工具可比性说明（见下节），metrics.md 把 token 计数来源写成了字段级的出处表。负载侧支持 constant、Poisson、concurrent 与多阶段；conversation_replay 用分布参数在内存里生成多轮 agent 会话（共享 system prompt、每会话独有前缀、每轮输入输出长度、工具延迟的对数正态分布），按并发会话数加压，回答"能同时撑多少个多轮会话"一手conversation replay 文档。

它没有独立的预热阶段，发出的每个请求都计入，官方建议用一个短的首阶段近似。

llm-d-benchmark 不是压测器，而是 Kubernetes 上的实验编排，需要集群，对单机容器实例不适用。GIE 自己的基准文档页我没能打开（旧地址 404，仓库 site-src 下已无 performance 目录），GIE 的基准做法本次未核实。

引擎自带脚本

  • vllm bench serve 默认 --request-rate inf，即一次把所有请求发出去；有限速率下间隔按 gamma 分布抽取后再整体缩放，使最后一个请求恰好落在"请求数 ÷ 速率"时刻，所以它没有真正的无锚 Poisson 过程一手，inference-perf 文档对 v0.10.0 源码的核对。--random-range-ratio 的含义在 v0.8.4 前后反转过，曾造成"工作量只有一半"的跨工具吞吐差距。多轮脚本 benchmark_serving_multi_turn.py 是闭环的（--num-clients 与 --max-active-conversations），标题就叫"用多轮对话测 KV offload"。
  • SGLang 的 agentic-trace 数据集把服务端真实回复接回下一轮历史，其余工具多数是用录好的或合成的历史。benchmark/agentic-rollout/simulate.py 另有一套"生成、工具等待、追加结果、重复"的合成回放，工具等待期间释放并发槽位，README 明说客户端不解析也不执行模型产生的工具调用一手agentic-rollout README。
  • LMCache 的 multi-round-qa.py 用 --shared-system-prompt、--user-history-prompt、--num-users、--qps 四个旋钮构造"共享前缀加每用户长历史"；--init-user-id 用来换一批用户 ID，避免命中上一次运行留下的缓存。

通用压测工具与云厂商工具

k6、Locust、wrk 把一次请求当成一个整体，原生只有"到最后一个字节"的延迟，TTFT、token 速率要自己解析 SSE 来算二手，仅摘要tianpan.co。它们还有一个 LLM 特有的坑：客户端要逐块解析流并做分词，单进程 Python 客户端自己会先饱和，量到的 TTFT 里混进了客户端排队。GuideLLM 为此专门报 worker_loop_lag，inference-perf 报 schedule_delay（建议中位数低于 10 毫秒）。

Azure 的工具面向预置吞吐（PTU）部署，值得借鉴的是它对重试策略的提醒：retry=none 时被 429 的请求被替换、起始时间重置，延迟统计只含成功请求，看起来又稳又低；retry=exponential 时延迟会涨到最多 60 秒一手README。这正是 coordinated omission 的一个具体形态。

2025–2026 新出现的

  • Weka 轨迹格式成了事实标准：AIPerf、GuideLLM、inference-perf 三家都能回放。轨迹不含原文，只有每次请求的时间、token 数和按 64 token 分块的 hash_ids，回放时用确定性的合成 token 重建出相同的前缀重叠关系。kv-cache-tester 自带语料的统计：每请求输入中位约 11 万 token、输出中位 218 token，思考时间中位 10 秒而均值 199 秒，会话内相邻请求的缓存命中率中位 96%一手。

来源同上各家指标文档一手。几个必须知道的事实：

  • TTFT 的起点都是客户端发出请求的时刻，所以天然包含网络、网关排队、引擎排队和 prefill。没有哪个客户端工具能把排队单独拆出来；要拆只能读服务端指标。AIPerf 的 RTT 扣减是唯一的网络修正手段。
  • 推理模型让 TTFT 分裂成两个数。Artificial Analysis 的 API 测速也分 TTFT（首个任意 token，对推理模型是首个推理 token）和 TTFAT（首个答案 token，含推理耗时）一手AA 性能方法论。没有配推理解析器的服务把推理写进正文的 <think> 里，这时 TTFO 等于 TTFT，两种部署不可比。
  • 流式分块会扭曲 ITL。投机解码或 stream-interval 大于 1 时，一个分块带多个 token。vLLM 文档的例子：5 个 token 分 3 块到达，ITL 均值 40 毫秒，TPOT 是 20 毫秒一手。结论是速度类指标用"时间 ÷ token 数"的 TPOT 形式，不用分块间隔。
  • 输出速度的分母有两派。AA 在方法论 v3.0.0 里把输出速度改成"输出 token（含推理 token）÷ 整个请求时长（含 TTFT）"，token 数取各家 API 自报的 usage，不再用 tiktoken 统一换算一手。AIPerf 默认的每用户速度不含 TTFT。InferenceX AgentX 的横轴在 AIPerf 里实现为 1 / P90(请求延迟 ÷ 输出 token 数)，含 TTFT，且先取慢尾百分位再取倒数；P90(1/x) 报的是快尾，两者不是一回事一手。
  • 客户端与服务端的 token 数对不上是常态：分词器版本、chat 模板与工具 schema 的开销、流式片段重新编码，都会造成差异。inference-perf 把不一致的请求数单列为 token_count_mismatches。vLLM 的 cached_tokens 按 KV 块大小量化，不是精确 token 数一手。

方法论

开环、闭环与 coordinated omission

闭环：固定 N 个客户端，各自等到响应再发下一个。开环：按到达过程发请求，不管服务端答没答完。Schroeder 等人在 NSDI 2006 的结论是，同样的负载下开环模型的平均响应时间可以比闭环高一个数量级以上，而研究者用哪种模型常常只是因为手头的负载生成器是哪种一手，仅摘要USENIX。

Coordinated omission 是 Gil Tene 命名的测量错误：闭环客户端在服务变慢时自动少发请求，等于和被测系统"串通"跳过了最糟的时段，大部分高延迟样本根本没被采到。wrk2 的修正办法是定速发送，并从请求本应发出的时刻起算延迟一手wrk2 README。GuideLLM 的 request_scheduled_latency 是同一思路。

agent 负载有它的特殊性：单个 agent 本来就是闭环的，下一步依赖上一步的输出，所以 AA-AgentPerf 和 AgentX 用闭环是对真实行为的忠实模拟，不是偷懒。但闭环带来两个后果，要写进报告：

  • 量到的延迟是"在该并发下的延迟"，不是"在该到达率下的延迟"。新任务的到达在现实里是开环的，闭环测不出积压。
  • 闭环漂移：快的系统在同样时长里走得更远，实际处理的请求组合与慢的系统不同。InferenceX 自己把这条列为局限二手，页面标注为非官方镜像InferenceX 文章。对策是按"完成固定的一组任务"收尾，而不是按固定时长收尾。

SLO、goodput 与找拐点

goodput 有两个不同的定义，名字相同：

  • DistServe（OSDI 2024）：在满足 SLO 达标率目标（例如 90%）的前提下，系统能承受的最大请求速率。示例 SLO 是 90% 的请求 TTFT 低于 200 毫秒且 TPOT 低于 50 毫秒；找法是在 Poisson 到达下逐步提高速率，取 P90 延迟仍在 SLO 内的最高速率一手(Hao AI Lab 博客、论文)。
  • 各压测工具：当前这一档负载下，每秒完成的达标请求数。GuideLLM、AIPerf、SGLang、inference-perf 都是这个口径。AIPerf 的达标比例把出错请求放进分母，防止"丢请求反而好看"。

"SLA 并发"是 DistServe 定义换成并发维度。AA-AgentPerf 的规则见已有的 aa-agentperf 一篇，要点是每档至少 30 条轨迹、每个 agent 至少 3 条、稳态至少 10 分钟、只统计全部 agent 已活跃 30 秒以上的时段，先倍增后二分。GuideLLM 的 knee 找的是吞吐不再明显上升的点，至少需要 5 个并发点，这是"吞吐拐点"而不是"SLA 边界"，两者通常不重合。GuideLLM 的过饱和检测用的是并发数与 TTFT 两条滑动窗口回归斜率同时显著为正一手。

稳态与预热

预热要解决三件事：编译与首次加载、缓存填充、并发爬升。AgentX 的做法最细：用固定种子从每条会话 25%–75% 处切入（模拟系统已在运行，而不是所有会话同时从第 0 轮开始）；先发 max_tokens=1 的请求把活跃前缀的 KV 建起来，再每条回放道发 10 个预热请求；只统计随后的一小时二手，同上镜像；参数与 AIPerf agentx 预设一致，后者为一手。AIPerf v0.11.0 的发布说明里有一条修复："防止预热造成的前缀缓存复用歪曲结果"，说明预热与缓存控制会互相干扰。

缓存状态控制

手段 谁在用 作用
每次播放加唯一前缀 AA-AgentPerf（每档开头）、AIPerf --cache-bust first_turn_prefix（每次播放）、Azure 工具（每条请求） 让跨档位、跨轮次的残留缓存失效，只保留会话内的正常复用

AIPerf 文档给 cache-bust 的理由值得照抄：轨迹被循环使用时，不加标记的话服务端缓存会在相同内容上越跑越热，稳态命中率随运行时长虚高一手。注意标记是整棵会话树（根会话与其子 agent）共用一个，否则会把子 agent 与父会话之间本应存在的前缀共享也打掉。

命中率的报告：分子用服务端 usage 里的 prompt_tokens_details.cached_tokens，分母用服务端的 prompt_tokens；vLLM 要加 --enable-prompt-tokens-details，SGLang 要加 --enable-cache-report，两者默认关闭，不开时读数为空而不是 0。全零读数有歧义，可能是真冷，也可能是网关或 sidecar 把 usage 抹成了 0。AIPerf 另报一个"理论命中率"：由轨迹的 hash 块重叠算出的无限缓存上限，实测值与它的差距就是驱逐和路由造成的损失一手。

KV offload 层的测法，kv-cache-tester 给了两个实验模板：固定工作集、扫命中率；固定上下文长度、把工作集从 10 万 token 扫到 500 万 token，看 TTFT 在哪里出现台阶，台阶对应显存、主机内存、盘的边界。AgentX 还要求报"缓存来源分布"（来自显存、主机内存还是重算），并把非标准服务器的主机内存上限定为 3 TB 以保证公平二手。

多轮与 agent 负载特有的问题

  • 会话保持。多副本时回放器要把同一会话的请求带上稳定标识。AIPerf 支持会话亲和头与 X-Dynamo-Session-ID，inference-perf 支持回传路由器下发的会话 token。不带的话测到的是路由器的前缀感知能力，带了测的是亲和。两种都合理，但要披露。
  • 用 sleep 代替工具的失真。第一，sleep 不占 CPU，真实工具会和推理服务抢主机 CPU 与内存，AA 把"纳入工具执行的 CPU 性能"列为后续计划。第二，间隔是"上一响应结束到下一请求开始"，AIPerf 文档解释了为什么不能用"开始到开始"：那会把上一请求的服务时间重复计入，会话逐轮漂移。第三，各家对长间隔的裁剪不同：AA 的工具延迟 0.1–5 秒、中位 1 秒；AgentX 保留录制间隔但全系统空闲封顶 10 秒；真实轨迹的思考时间均值是 199 秒。裁剪越狠，缓存越不容易过期，对没有 offload 层的系统越有利。第四，回放的工具结果是录好的，模型这一轮实际说了什么不影响下一轮输入。
  • 历史用谁的。用录制的助手消息做历史，前缀确定、可复现，但上一轮真实生成的 token 与下一轮 prompt 里的助手消息不一致，那一小段要重新 prefill；把真实回复接回去（SGLang 的做法）更贴近真实，但各系统的输入从第二轮起就不再相同。这一条是我的推断，来源没有直接讨论。
  • 任务级与请求级指标的关系。任务完成时间 = Σ 模型调用延迟 + Σ 工具时间 + 客户端开销。AA 对多轮会话的端到端时间明确不含工具运行时间。请求级 P95 好看不代表任务级好看：一个任务串行几十到上百次调用，尾延迟几乎必然被踩到，所以任务时间要直接量，不能由请求级百分位推算。

成本与能耗口径

  • 每百万 token 成本：inference-perf 给的公式是（加速器每秒价格 ÷ 每秒输出 token 数）× 100 万，并注明输入输出混批时成本要按某个系数拆分（它举的例子是 1:4）一手。agent 负载输入输出比上百，且输入大多命中缓存，单一的"每百万 token"没有稳定含义。
  • 每任务成本：只有在指定运行点才有意义。机时成本 ÷ 单位时间成功任务数，后者取决于并发，所以必须在 SLA 并发点上量。
  • 功耗测量点：AA-AgentPerf 只算加速器实测功率，InferenceX 用机房供电侧口径，两者不可直接比（见 aa-agentperf）。nvidia-smi 的功耗读数在 A100、H100 上只对约 25% 的运行时间采样仅摘要arXiv 2312.02741；MLPerf Power 以整机交流侧为准，不含制冷仅摘要arXiv 2410.12032。

统计与可复现

GuideLLM 文档给了一组很实用的下限：在 95% 置信度下，要给 P95 一个双侧区间至少需要 72 个请求，P99 需要 368 个，P99.9 需要 3688 个；不到 100 个成功请求时，报出来的 P99 就是全场最慢的那一个请求。它同时提醒，单次运行内的区间只说明"这一次量得多准"，不说明"再跑一次会差多少"，因为同一次运行里的请求共享着服务端负载这样的共同条件；跨运行比较必须重复跑一手。AIPerf 的 --num-profile-runs 就是做这件事，还可以在两次之间加冷却。

输出长度不受控时的公平比较：

做法 好处 代价
固定 max_tokens 加 ignore_eos 每个系统做的 decode 工作量完全相同；AgentX 强制这样做 输出是无意义续写，测不了质量；投机解码的接受率失真（AgentX 为此另用 SPEED-Bench 的接受长度做校正）；外部 API 不支持
让模型自然结束 输出真实，可同时评质量 输出长度成了模型的属性，量化或换采样参数都会改变工作量；只能用按 token 归一的指标比

inference-perf 的检查顺序值得照做：先比两边发出和收到的 token 总数，再比输入输出长度的均值与极值，都对上了才比吞吐和延迟。随机种子能固定数据与工具延迟，固定不了 GPU 输出的逐位一致，SGLang 的 README 特意写了这一句。

对标外部 API 的方法问题

以 DeepSeek 官方 API 为例一手(限速文档、上下文缓存文档)：

  • 限速是并发口径。按账号计并发连接数，文档列出 deepseek-v4-pro 为 500、deepseek-flash 为 2,500，超出返回 429，可申请扩容。API 侧测不出"SLA 并发"的上限，只能测到限额为止。
  • 排队不可见，而且会伪装成首字节。等待期间连接保持，流式请求会持续收到 SSE 注释行，非流式收到空行；10 分钟内没开始推理则断开。所以 TTFT 必须量到第一个有内容的 delta，量首字节会得到假的低值。
  • 缓存状态不可控。缓存默认开启、尽力而为、不保证命中；构建需要几秒，所以紧接着发出的下一轮可能未命中；不用后几小时到几天内清除。usage 里有 prompt_cache_hit_tokens 与 prompt_cache_miss_tokens，AIPerf 已原生读取后者。要冷缓存只能靠唯一前缀。
  • 网络路径与时段。AA 的做法是固定从 Google Cloud us-central1 发起，每 6 小时测一轮，取各轮中位数的 5 天平均，并承认测试机位置对不同供应商有利有弊。
  • 被测对象不同。API 那边是多租户、未知硬件、未知批处理策略；它给的是价格不是成本。

对我们做 Benchmark 的启发

底座选型

回放模式用 AIPerf 作底座。 理由落到功能上：不需要 Kubernetes，能在 AutoDL 容器实例里直接跑；原样载荷回放能吃下我们自定的 JSONL 轨迹；cache-bust、KV 重置钩子、闭环 agentic replay、SLA 边界搜索、多次运行置信区间、RTT 扣减、DeepSeek 的缓存字段、DCGM 功耗都已内建；同一条命令既能打本地 vLLM、SGLang，也能打 DeepSeek API。

GuideLLM 作交叉验证。 同一份负载用第二个工具再量一遍，先对 token 总数，再对延迟。两个工具对不上时，先查配置再怀疑服务。

不采用的：llm-d-benchmark（需要集群，裸金属到手后再考虑）、LLMPerf（已归档）、GenAI-Perf（已淘汰）、k6 与 Locust（要自己补全部 LLM 指标）、vllm bench serve（默认行为是一次发完，且与引擎版本绑定）。

需要自己补的

  1. 计量代理。选手真 agent 上场后没有"回放"可言。在端点前放一个透明反向代理，对每个请求记录：到达时刻、转发时刻、首个推理 delta、首个非推理 delta、末个 delta、服务端 usage 全文、任务 ID 与轮次。Weka 语料本身就是这样用代理录出来的。回放与实跑共用这一套时间点定义。
  2. 任务层编排与判分对接。压测工具只知道请求，不知道任务。任务的起止、成功与否、三类 agent 的产出校验要自己写，并把任务 ID 贯穿到每个请求。
  3. 轨迹格式转换器。把自录的 JSONL 转成 AIPerf 可回放的形态；同时生成一份 Weka 风格的 hash 块版本，用来算理论命中率上限。
  4. 真实工具执行的对照组。至少保留一组不用 sleep、真跑工具的运行，量出 sleep 模拟相对它的偏差，否则没法回答"工具抢 CPU"的质疑。
  5. 服务端指标采集。引擎的 Prometheus 指标（排队时长、KV 使用率、驱逐次数）与客户端时间轴对齐，这是拆出"排队"的唯一办法。

六项指标的建议定义

指标 精确定义 测法与注意
任务成功率 通过 Agent Bench 质量门槛的任务数 ÷ 发起的任务数 超时、报错、上下文溢出、被限速都进分母；失败按原因分类。不允许只在成功任务上算其余指标而不披露失败数
任务完成时间 任务首个请求到达代理的时刻，到最后一个响应的末个 delta 的时刻 同时报三段：模型时间（Σ 请求延迟）、工具时间、其余。主榜建议用模型时间，与 AA 的"端到端时间不含工具"一致；墙钟时间作副榜。报 P50、P90
首 token 延迟 请求到达代理的时刻，到第一个非空内容 delta的时刻；推理模型另报到首个非推理 delta 的 TTFO 不看首字节、不看 SSE 注释。按该请求 cached_tokens ÷ prompt_tokens 分桶报（例如低于 10%、10%–90%、高于 90%），并报输入长度分布。P99 至少要 368 个样本才写出来
生成速度 每请求：（输出 token 数 − 1）÷（末个 delta 时刻 − 首个 delta 时刻），token 数取服务端 usage，含推理 token 输出不足若干 token 的请求剔除并报剔除数。报 P50 与慢尾（P5 或 P25）。对标 AA 数字时另算含 TTFT 的版本，因为 AA 现行口径含 TTFT
SLA 并发 同时活跃的任务数 N 的最大值，使得该档内 P95 TTFT ≤ 阈值、慢尾生成速度 ≥ 阈值、任务成功率 ≥ 阈值 闭环；每档加整棵会话树共用的唯一前缀；每档满足最少任务数与最短稳态时长；倍增后二分；拐点处重复 3 次，报达标曲线全貌而不只是一个数。阈值待定，可参考 AA 的三档
每成功任务成本 在 SLA 并发点上：单位时间硬件成本 ÷ 单位时间成功任务数 失败任务消耗的机时计入分子。API 参照线用 Σ（未命中输入 × 输入价 + 命中输入 × 缓存价 + 输出 × 输出价）÷ 成功任务数。两者一个是成本一个是价格，并列展示但不相减

对当前方案草稿的三处具体修改建议：

  • 草稿里"首 token 延迟：从发出到第一个输出 token"，需要补上"第一个非空内容 delta"与推理 token 的归属，否则对 DeepSeek API 会量到 keep-alive。
  • 草稿里"生成速度只算 decode 段"与 AA 现行的输出速度口径（含 TTFT）不一致，对标时要说明或两个都报。
  • 草稿里对官方 API"多次回放取分布"是对的，建议再加：分时段、每次回放加唯一前缀并另跑一组不加前缀的、记录 429 次数、固定出口机房并报 RTT。

结果披露清单

在方案草稿已有的硬件、软件、模型、拓扑、负载、结果、成本七项之外，补充：

  • 负载生成：工具名与版本、完整命令行或配置文件、开环还是闭环、到达过程、并发档位、收尾条件（按任务数还是按时长）。
  • 测量窗口：预热做法与时长、稳态判定规则、被排除的请求数。
  • 缓存：是否加唯一前缀及粒度、运行前是否清空、服务端缓存相关启动参数、实测命中率与理论上限、KV 各层容量。
  • 会话与路由：是否带会话标识、路由策略。
  • 工具间隙：sleep 还是真跑、延迟分布、是否裁剪及上限。
  • 输出控制：max_tokens、是否 ignore_eos、采样参数、是否开推理及强度。
  • 计数：token 数来自服务端还是客户端、分词器名称与版本、两者不一致的请求数。
  • 计时点：TTFT 与生成速度的起止定义原文、是否扣 RTT、压测机位置与规格、客户端调度延迟。
  • 统计：重复次数、每个百分位的样本数、置信区间、失败与重试的处理方式。
  • 功耗与成本：功耗测量点与采样方式、成本假设（折旧、电价、利用率）。
  • 外部 API 参照线：测试日期与时段、账号并发限额、429 次数、模型版本字符串。
