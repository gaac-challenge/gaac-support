ExecuTorch

Meta 主导的 PyTorch 本地推理栈，模型导出成 .pte 在设备上跑

与主线一 KV cache · 弱KV cache 在导出时定形并留在进程内；1.5 起有图外 KV 与前缀复用，但不做跨介质分层与主线二 Agent 负载 · 中有实验性的 OpenAI 兼容本地服务器，支持工具调用与多会话，可接 agent 框架

它是什么

ExecuTorch 是 PyTorch 官方的本地推理栈，由 Meta 主导开发。它解决的问题是：研究人员用 PyTorch 写出的模型，怎么放到手机、眼镜、笔记本、单片机上跑。在它之前，常见做法是把模型转成别的格式（ONNX、TFLite），或者用 C++ 重写一遍（llama.cpp 的路线），两者都容易出现数值对不上、调试信息丢失的问题一手，官方博客的自述PyTorch blog: ExecuTorch 1.0。

ExecuTorch 的做法是不离开 PyTorch：用 torch.export 把模型抓成一张计算图，针对目标硬件优化，存成一个 .pte 文件，再由一个很小的 C++ 运行时在设备上执行。README 的自我描述是"从手机、笔记本到微控制器的 PyTorch 原生推理"一手ExecuTorch README。

它做了什么

导出、委托、.pte

流程分三步：

  1. 导出：torch.export 把 PyTorch 模型抓成静态计算图。
  2. 委托（delegate）：把图切成若干段，能被某种硬件加速的段交给对应后端，剩下的用通用 CPU 内核兜底。后端就是针对某类芯片的执行器。1.0 时标为生产可用的有：XNNPACK（CPU，含 Arm Kleidi 优化）、Apple Core ML、Qualcomm AI Engine（Hexagon NPU）、Arm Ethos-U、Vulkan（GPU）；同时新增 Arm VGF、NXP eIQ Neutron、Samsung Exynos、Intel OpenVINO一手，1.0 博客。NPU 是手机芯片里专门跑神经网络的单元。
  3. 序列化：生成 .pte 文件，交给运行时加载。

README 特别强调一点：.pte 是针对所选后端特化的，为 XNNPACK 导出的文件不能直接拿去跑 Core ML 或 Qualcomm，要分别导出；它"不是一个通用模型文件"一手，README。这和 GGUF 一个文件到处跑的思路相反。兼容性承诺是：用稳定 API 生成的 .pte 至少能被下一个非补丁版本的运行时加载一手，README。

LLM 支持

LLM 走专门的 export_llm 流程，量化在导出时完成：XNNPACK 路线常用 8da4w（权重 4 位、激活动态 8 位），1.0 加入 4-bit HQQ 量化，以及"多个 LoRA .pte 共享一份基座权重"的能力一手(export_llm 文档；v1.0.0 release notes)。Hugging Face 提供 optimum-executorch 做导出；其开源负责人在 1.0 博客里称，下载量最高的端侧友好 LLM 中超过 80% 可直接跑在 ExecuTorch 上厂商自述，证言。

在 Meta 产品里跑的是什么

这里要留意：Meta 工程博客列举的线上案例都不是 LLM。它们是 Instagram Cutouts 的分割模型 SqueezeSAM、WhatsApp 的带宽估计模型、Messenger 为端到端加密而搬到端上的语种识别模型、Facebook 的 SceneX 图像理解模型一手。"服务数十亿人"说的是这类传统小模型。Reality Labs 在 Ray-Ban Display 眼镜上用它跑的也是语音识别、动作感知与视觉一手，1.0 博客证言。公开材料里没有看到 Meta 自家产品用它在端上跑生成式 LLM 的规模数字。

2026 年的现状

最新版 v1.6.0（2026-11-12）；仓库约 5181 星、1254 分叉一手，GitHub API，2026-11-18。

2026 年最大的变化是它不再只是"手机运行时"。v1.1 加入实验性的 CUDA 后端（NVIDIA GPU）与 Metal 后端；v1.5 加入 ROCm（AMD GPU）、批量请求调度与图外 KV cache；v1.6 的亮点一栏直接写着"批量服务、前缀缓存、DFlash 投机解码"，TensorRT 后端进入 beta，NXP Neutron 转为生产可用，还新增了不依赖 PyTorch 的 Python 运行时一手，各版本 release notesExecuTorch releases。README 现在把"本地 LLM 与 agent 构件"列为第一类工作负载一手。这些都是典型的服务端引擎特性，说明它在向桌面与工作站延伸，和 llama.cpp、MLX 的地盘重叠。

2026 年的一篇 arXiv 论文把它与 llama.cpp、ONNX Runtime、LiteRT、Core ML 做了对比仅摘要，未读正文数字arXiv 2605.08195。

与主线一（KV cache）的关系

弱，但有几处具体机制。

  • 导出时定形。export_llm 的配置里，use_kv_cache 与 use_sdpa_with_kv_cache 是推荐必开的选项；max_context_length 决定缓存的最大长度，在导出时就固定下来；use_attention_sink 在写满后从头部丢弃条目以继续生成；quantize_kv_cache 把 KV 量化成 int8；local_global_attention 给部分层只留一个小的滑动窗口缓存一手，export_llm 文档，经摘要工具读取。端侧内存紧，这些都是为了把 KV 的大小压住并且可预测。
  • 按后端处理。v1.6 给 Qualcomm 后端加了 8 位的 KV cache 输入输出；v1.5 给 Arm Ethos-U85 加了 KV cache 导出与 int8 KV一手，release notes。
  • 图外 KV 与前缀复用。v1.5 引入"图外（off-graph）KV cache 布局"，即 KV 不再是计算图内部的状态，而由外部执行器管理；v1.6 在 CUDA 上加了带批处理执行器的图外 KV 与前缀缓存复用，在 MLX 上加了批量 KV cache一手，release notes。实验性 LLM 服务器的说明写道，KV 与前缀状态存在 worker 进程的会话里，不在控制面；启动参数里有 --prefix-cache-entries一手LLM server README。

所有这些都发生在单个进程的内存里。没有看到把 KV 落到闪存、跨进程或跨设备传递的机制，所以它不参与主线一说的"KV 变成跨介质的存储层级"。它展示的是端侧的另一种约束：KV 的首要问题是放不放得下，不是放在哪一层。

与主线二（Agent 负载）的关系

中等，且都还标着实验性。

仓库里的 LLM 服务器提供 OpenAI 兼容的 /v1/chat/completions，目的写得很直白：让任何 OpenAI 兼容的 agent 框架把 ExecuTorch 当本地后端。它默认按 Hermes 格式解析工具调用，返回标准的 tool_calls；一个 worker 可以在一份权重上托管多个隔离会话，并支持跨轮次的"热续接"（只追加、不重算前文）。限制也写明了：只支持 tool_choice 为 auto 或 none，不支持强制调用某个函数，不支持 response_format 的受约束 JSON 输出，这些参数会被显式拒绝而不是静默忽略一手，LLM server README。

同一份文档还给出了用 Terminal-Bench 评测和用 agentx-mini 重放 agent 轨迹（含并行子 agent）的步骤一手。也就是说，项目方已经在用 agent 负载检验这个运行时，但公开的结果数字我没有找到。

与图中其他概念的关系

  • LiteRT：最直接的对手，Google 的同类栈。两者的 CPU 路径都建在 XNNPACK 上。
  • llama.cpp 与 GGUF：路线之争。llama.cpp 用 C++ 重写模型、一个 GGUF 文件通用；ExecuTorch 保留 PyTorch 图、每个后端一个 .pte。v1.6 的实验性 ExecuTorch Native 格式（.ptn）可在加载时由 ggml 引擎下沉一手，release notes 一句话，细节未核实。
  • MNN：阿里的端侧运行时，同类竞争者。
  • EAGLE-3：ExecuTorch 集成的投机解码是 DFlash，不是 EAGLE-3一手，v1.6 release notes。
  • TensorRT-LLM：v1.6 的 beta 后端是 TensorRT，不等于 TensorRT-LLM，不要混淆。
  • llm-compressor：没有直接关系。ExecuTorch 的量化走 TorchAO 与各后端自己的量化器，在导出流程里完成。

存疑与未核实

  • 报告在讲 LLM 端侧编译的段落里引用"Meta 称其驱动的端侧功能服务数十亿人"。出处属实，但 Meta 工程博客列举的都是分割、带宽估计、语种识别等非 LLM 模型，放在 LLM 语境里容易让人误解为端侧 LLM 的规模。
  • 报告与笔记把 ExecuTorch 归为纯端侧运行时。截至 v1.6 它已有 CUDA/ROCm 后端、批量服务与前缀缓存，这个定位需要更新。
  • 2023 年 10 月首次预览、2024 年 4 月 Alpha 等早期节点未找到本次打开的一手页面。
  • "图外 KV cache"只在 release notes 里各出现一句，没有找到设计文档；我对它的解释（KV 由图外执行器管理）是按字面与上下文的理解。
  • export_llm 文档经摘要工具读取，未见"静态形状"字样；"KV 大小在导出时固定"是根据 max_context_length 属于导出配置得出的。
  • ExecuTorch 论文（arXiv 2605.08195）只读了摘要页，性能对比数字未读。
