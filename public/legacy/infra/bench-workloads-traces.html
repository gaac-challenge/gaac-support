负载、trace 与数据集

公开 agent 负载已有哈希块 trace 可直接回放,但只覆盖编程;三类比赛 agent 必须自录

结论先行

推理基准的数字由负载决定。到 2026 年 11 月,可用的公开负载分成四档,可信度和适用面差别很大:

  1. 只有长度和时间戳的生产 trace(Azure 2023/2024、BurstGPT):适合研究到达过程,测不了缓存。
  2. 带前缀哈希块的生产 trace(Mooncake/Kimi、阿里百炼、SemiAnalysis AgentX、WEKA、Azure 发布的 Copilot 样本、UW TraceLab):不含文本,但保留了"哪些 token 与之前的请求相同",能直接驱动 KV 缓存实验。这是 2025–2026 年形成的事实格式。
  3. 带全文的 agent 轨迹(SWE-agent/OpenHands 轨迹、Exgentic、SWE-chat):有消息和工具定义,多数没有可靠的计时。
  4. 聊天数据集(ShareGPT、LMSYS-Chat-1M、WildChat):有文本,没有到达时间、工具和前缀结构,当 agent 负载用会系统性出错。

第 2 档几乎全是编程 agent。排版、深度调查、财务预测三类 agent 没有可直接回放的公开 trace,只有零散的每任务调用数与耗时数字,必须自录。

生产 trace 逐个看

只有长度与时间戳的一代

Azure LLM Inference Trace 只有三列:TIMESTAMP、ContextTokens、GeneratedTokens。说明页明确写出,由于隐私要求拿不到提示词内容,作者的用法是按长度造输入并强制模型生成对应数量的输出。它没有会话 ID,多轮关系、前缀复用都无从恢复。JITServe 等论文用它提供到达过程,再配别的数据集提供内容一手JITServe。

BurstGPT 来自一个由 Azure OpenAI 支撑的高校服务。字段为 Timestamp、Session ID、Elapsed time、Model(ChatGPT 或 GPT-4)、Request tokens、Response tokens、Total tokens、Log Type(对话或 API)。Elapsed time 是从提交到拿到完整回复的全程时间,README 特别说明它不是 TTFT。失败请求的 Response tokens 为 0,另有剔除失败的版本。vLLM 的 vllm bench serve 内置了它一手vLLM 基准文档。局限是 GPT-3.5/4 时代的聊天与 API 流量,无前缀信息。

带前缀哈希块的一代

这一代的共同做法是:把输入按固定大小切块,对每块做带盐哈希再映射成整数。两个请求的 hash_ids 前若干项相同,就表示这段前缀可以复用 KV。回放工具按块 ID 生成确定性的合成文本,于是不泄露内容也能复现命中模式。块大小各家不同:Mooncake 512、百炼 16、AgentX 与 WEKA 64,混用前必须换算。

  • Mooncake(Kimi):确实开源。2024-07 先随 arXiv 技术报告放出单文件 trace,2025-02 更新为 FAST 25 论文所用的三个文件。每行四个字段:timestamp(毫秒)、input_length、output_length、hash_ids。对话与工具 agent 两份各采自一小时线上流量,平均输入 12,035 与 8,596 token,平均输出 343 与 182;合成那份由公开数据集加泊松到达构成。没有会话 ID,多轮关系只能从哈希前缀反推。NVIDIA AIPerf 把它当作标准 trace 格式之一,并另外支持百炼与 BurstGPT 格式一手AIPerf 文档。
  • 阿里百炼 Qwen trace:比 Mooncake 多了 chat_id、parent_chat_id、turn 和请求类型(text、search、image、file),四份 trace 分别代表面向消费者的聊天、面向企业的 API 任务、推理模型和代码生成。README 提醒哈希是套完 chat template 之后的 token 算的,回放时不要再套一遍。官方配了一个 Rust 写的按时间戳回放器。
  • ServeGen 不是原始 trace,而是把百炼 12 个模型四个月、数十亿请求拟合成"按客户"的分布再合成负载。论文的核心论点是:到达的突发与长度分布的漂移主要由少数头部客户造成,用"泊松到达加 ShareGPT"的朴素合成会比真实负载好伺候,一个生产案例中朴素合成导致 50% 的容量低估一手,论文自报arXiv 2505.09999。
  • Aegaeon 论文引用的模型市场统计(17.7% 的 GPU 只服务 1.35% 的请求)没有查到配套的 trace 发布二手,未读原文。

Copilot:论文之外确实发布了数据

Microsoft 的 Copilot 研究(arXiv 2608.00101)分析的是 1,300 万会话的全量采样,同时在 AzurePublicDataset 发布了一个均匀采样的公开子集:2026-06-01 至 07,非企业用户,301,026 个会话、931 万次模型调用、868 万次工具调用,gzip JSONL,七天共约 3 GB。每个会话是若干 turn,每个 turn 含 llm_calls(时间戳、duration_ms、匿名模型名、tokens.prompt、completion、cached、发起者是用户还是 agent,以及 message_metadata:每个 prompt 片段的类型、角色、顺序和 token 数)和 tool_batches(每个工具的名字、状态、duration_ms)。没有任何文本,也没有块哈希,前缀结构只能由 cached 数和片段长度推断一手数据集卡。

要注意公开子集与论文数字不完全一致:公开样本平均每 turn 7.83 次调用,论文全量为均值 6.6、中位 4.5。子集只含非企业用户,引用时应写明用的是哪一份。

其他编程 agent trace

  • TraceLab(华盛顿大学):43 名开发者约八个月的 Claude Code 与 Codex 本地日志,脱敏后发布,并附采集与脱敏脚本。每行一次模型调用,带 prefix_tokens 与 newly_append_tokens 的拆分、有序的 timing_events、每个工具的墙钟耗时与结果字符数。作者自己承认它只反映一个实验室的习惯一手arXiv 2606.30560。
  • AgentX v1.0:参与者自愿接入一个 HTTP 代理,记录请求到达与完成时间、输入输出 token 数、会话 ID 和子 agent ID。入选条件是至少 20 次请求、Claude Code 2.1.139 以上、并发子 agent 不超过 10。分全量(上下文到 100 万)与 256k 两个版本。
  • WEKA kv-cache-tester:AgentX 所用格式的来源,自带 739 条 trace,把每次请求的时间拆成 api_time(服务端处理)和 think_time(客户端间隔)。
  • SMetric(arXiv 2607.08565)用了某商业编程 agent 的两份集群 trace,摘要页未见发布仅摘要。OpenRouter 的《State of AI》只有聚合统计,没有查到可下载的请求级数据仅摘要arXiv 2601.10088。

对话数据集,以及冒充 agent 负载会错在哪

ShareGPT 是 2023 年初用户分享的 ChatGPT 对话抓取,原始来源已下线未复核,基准工具用的是 Hugging Face 上的镜像;DistServe 用它代表聊天,因为没有时间戳,到达用泊松过程生成一手DistServe。LMSYS-Chat-1M 平均每个 prompt 69.5 token、回复 214.5 token。Sarathi-Serve 用的 openchat_sharegpt4 把每一轮当独立请求,prompt 中位 1,730、输出中位 415一手Sarathi-Serve。

把这类数据当 agent 负载,错在七处:

  1. 输入短两到三个数量级。聊天 prompt 几十到几千 token;编程 agent 单次调用输入中位在 6.8 万到 14.2 万之间。前者测不出长 prefill、KV 内存压力和每请求 CPU 开销。
  2. 输入输出比方向相反。LMSYS 约 1:3,输出占多数;agent 为 130:1 到 300:1。聊天负载下的排名主要反映解码速度,agent 负载下主要反映 prefill 与缓存。
  3. 没有前缀结构。把对话逐轮抽成独立请求后,可复用的只剩系统提示。agent 的实测或理想命中率在 86%–96%。前缀缓存、缓存感知路由、KV 分层在聊天负载下几乎显不出收益,结论会被带偏。
  4. 没有真实的时间结构。数据集没有时间戳,只能配泊松到达。agent 是闭环:下一次请求在上一次返回加工具执行之后才发出,间隔从几百毫秒到几十分钟,决定了 KV 是否还在。
  5. 没有工具。工具定义本身就是一段一万 token 上下的固定前缀(WEKA trace 里工具定义中位约 10,500 token、系统提示约 2,600),而且会走结构化输出与工具解析路径,聊天数据不触发这些。
  6. 没有扇出。AgentX 的 393 个会话里 175 个有子 agent,共 1,697 组并行分支。
  7. 内容不同。投机解码的接受率和 MoE 的专家路由都依赖 token 内容;AgentX 因为用合成 token,不得不按 SPEED-Bench 实测值强制设定接受长度。

聊天数据集仍有用处:做对照组(证明某项优化只对 agent 有效)和测纯解码速度。

Agent 轨迹数据与回放方法

有文本的轨迹

  • SWE-bench 系列:Nebius 发布 80,036 条 SWE-agent 轨迹,另有 OpenHands 轨迹集;NVIDIA 的 Open-SWE-Traces 查看器显示 48.9 万行,带 messages 和 tools一手,只读到表头数据集。SWE-bench 的 experiments 仓库只存条目,轨迹放在提交者自己的仓库或 S3一手仓库。这些是为训练和评分准备的,通常缺每步计时。
  • Exgentic agent-llm-traces:最接近"拿来就能回放"的全文数据。OpenTelemetry span 格式,每次调用有起止时间、输入输出 token 数、完整输入输出消息和工具定义,覆盖 SWE-bench、AppWorld、BrowseComp-Plus(深度调查)和三个 tau2 客服场景。
  • 真实会话:SWE-chat(17,968 个会话,需同意条款)、Trace Commons(志愿捐赠,查看器显示 30 行)等保留了 Claude Code、Codex 的原始日志一手SWE-chatTrace Commons。
  • AA-AgentPerf 的轨迹不公开下载,只给参测厂商 500 条调优子集,完整测试集保密。

把轨迹变成可回放的请求序列

各家做法可以归纳成四个决定:

决定 AA-AgentPerf AgentX 加 AIPerf Continuum、Sutradhara 等论文
调度 闭环,每个 agent 顺序走轨迹 闭环,轨迹转成 DAG,子 agent 分叉后在汇合点等待 整个程序按泊松到达,程序内闭环
工具间隔 按工具类型从真实时长采样,0.1 到 5 秒 用录下的请求间隔 用录下的工具时间或按比例归一
输入内容 真实文本 按哈希块生成合成 token 真实文本
防缓存串味 每个并发档给轨迹加动态前缀 每次重放加唯一标记,另有固定种子选起点和预热 未说明

AIPerf 的文档区分了两种模式:--fixed-schedule 按录制时间戳发请求;有限回放模式下每个请求既要等到相对时间,又要等前驱完成一手AIPerf Weka 教程。AgentX 方法论还指出一个后果:闭环下快的系统在同一小时里走得更远,实际请求组合会随系统而变。

输出怎么处理是另一个分歧。Azure 的做法是只强制输出长度。AgentReplay(arXiv 2609.32283)认为这不够:贪心解码也不保证各系统输出一致,只回放长度会丢掉影响前缀缓存和 MoE 路由的 token 信息,主张回放时强制输出录下的 token,同时照常做自回归计算仅摘要arXiv。

量化 KV 之后的验收。needle-in-a-haystack(在长文中埋一句话再提问)是最常见的检查,但它只要求取回一条信息,对有损的 KV 压缩不够敏感;多针或多跳任务更容易暴露退化二手,未逐篇复核。更贴近服务场景的是 LMCache 的 bench quality:同一批真实问答分别跑基准与改动后的配置,用运行指纹保证两边可比,输出通过、失败或样本不足的判定。

与比赛三类 agent 最接近的公开刻画

深度调查是三类里资料最多的,但没有一份带计时的服务侧 trace。

  • Exgentic 的 BrowseComp-Plus 轨迹 133 条:每任务调用数中位 19、均值 24.6、最多 88;单次调用平均输入 53,435、输出 534 token;每任务累计约 167 万 token。有全文与起止时间,可直接改造成回放负载。
  • 一篇研究并行 rollout 的论文给出三个开源模型在六个基准上的轨迹统计:ResearchRubrics(写报告类)每任务 15 到 34 轮、14 到 33 次工具调用、输出约 4K token;BrowseComp(找答案类)54 到 71 轮一手,读了附录表 5arXiv 2604.11753。
  • UCSD 的一项小规模测量(10 个任务)发现网页搜索平均占 GPT-5 端到端时间的 73%、LangChain 深度研究 agent 的 50%,个别任务达 91%;抓回的网页内容每任务 10 万到 250 万 token一手论文。
  • 论文评测中的替身:Continuum 的 BFCL 网页搜索每程序 6.3 轮、工具均值 1.9 秒;JITServe 的深度调查复合请求输入均值 12,223、输出均值 3,541。

财务预测与数据分析:Vals AI 的 Finance Agent 榜单公布每题成本与时长,例如 DeepSeek V4 为 0.59 美元、9 分 48 秒,Claude Opus 4.7 为 0.80 美元、4 分 31 秒一手Vals AI。这是任务级结果,不是可回放的调用序列。DABstep 上几种数据分析 agent 每任务 7 到 13 次模型调用的说法来自搜索摘要仅摘要。KVFlow 用的金融问答 prompt 只有几十到几百 token,不能代表真实财务 agent。

pptx 与文档生成:没有找到服务侧的画像。ReFigBench(arXiv 2609.18844)等质量基准记录了 agent 的轮数与工具调用,搜索摘要称某配置中位 33 轮、19 次工具调用,我没能从摘要页核实仅摘要。这类 agent 很可能有"渲染后再看图检查"的循环,带来图片输入和较长的代码输出,与编程 agent 的短输出画像不同;这是推断,需要自录验证。

对我们做 Benchmark 的启发

起步用哪些公开数据

  1. 脚手架冒烟与 KV 实验:直接用 AgentX 256k 版本加 AIPerf 回放。它有子 agent 分叉、真实间隔和前缀结构,256k 上限适配开源模型的上下文。局限是合成 token,不能评质量,投机解码要另设接受长度。
  2. 合成轨迹的参数:不要只用 Copilot 论文的一组数。按上面的参数表取区间,至少造轻(Copilot 中位)和重(AgentX 中位)两档。
  3. 到达过程:需要开环压测时用 BurstGPT 或百炼 trace 的时间戳,配自己的内容。
  4. 深度调查的替身:Exgentic 的 BrowseComp-Plus 轨迹有全文与计时,在自录完成前可以先用。
  5. 聊天数据集只留作对照组。

轨迹文件应记录的字段

plans/plan-autodl-4gpu.md 现在的设计是每行一次调用,含任务 ID、轮次、完整消息、工具定义、距上一次调用的间隔。建议补四类字段:

  • 依赖而不是只有间隔:parent_call、branch_id、join_before,用来表达子 agent 并行;线性轨迹留空即可。
  • 把间隔拆开:model_time_ms(录制时的模型耗时)与 gap_ms(上一次响应结束到本次请求发出,即工具执行加编排),并单列每个工具的 name、duration_ms、status、result_tokens。只存"距上次调用的间隔"会把录制系统的快慢混进负载。
  • 录制时的输出:output_text、output_tokens、reasoning_tokens、finish_reason,以及 max_tokens 与采样参数。
  • 前缀与元数据:input_tokens、tokenizer、按固定块大小算的 hash_ids(可事后生成,用于离线算理想命中率和对外分享),agent 类型、框架版本、轨迹文件哈希。

如何自录并在不同硬件和官方 API 上重放

  • 在 HTTP 层录。在 agent 框架与模型端点之间放一个代理(AgentX 与 WEKA 都这么做,Exgentic 用 LiteLLM 加 OpenTelemetry),记录完整请求体、流式响应的首 token 与结束时间。这样与框架无关,选手换框架也能录。
  • 回放用录下的历史,不用现场输出。第 n 次请求的消息原样取自轨迹,不管被测系统上一步实际生成了什么。这样各系统看到的输入逐 token 相同,前缀结构不漂移。
  • 输出长度:自建端点上把 max_tokens 设为录制值并禁止提前停止;DeepSeek 官方 API 做不到强制,只能设上限并把生成速度按实际 token 数归一。两边的任务完成时间因此不严格可比,报告里要写明。
  • 调度:任务内闭环,请求在前驱完成并等待 gap_ms 之后发出;任务间用固定并发或开环到达。不要按录制的绝对时间戳发。
  • 工具时间:默认用录下的 gap_ms;另设一档把它压到零,用来区分"引擎慢"和"工具慢"。
  • 质量与效率分开录:质量评测跑真实 agent,效率评测回放冻结的轨迹;各队 agent 走的步数不同,效率数字要按"每成功任务"归一。

如何控制前缀重复率

前缀重复率定义为:假设缓存无限且永不过期时,可从缓存取得的输入 token 占全部输入 token 的比例,由 hash_ids 离线算出。它是负载的属性;服务端报告的命中率是系统的属性,两者之差才是被测系统的缓存损失。控制手段:

  1. 跨任务共享前缀:系统提示与工具定义是否逐字相同。固定它可得到约一万 token 的跨会话命中;在最前面加一个按任务变化的字段则归零。
  2. 缓存隔离标记:每个并发档、每次重放在轨迹开头插入唯一前缀(AA 与 AgentX 的做法),保证测的是会话内复用。
  3. 人为破坏点:按画像注入压缩事件(约一成会话)和换模型,观察命中率下降。
  4. 间隔与存活时间:把 gap_ms 拉长到超过引擎或 API 的缓存存活时间,测未命中的代价。
  5. 分开报告:首 token 延迟按命中与未命中分桶;同时报理想命中率与实际命中率。DeepSeek 官方 API 的缓存是尽力而为、按完整前缀单元匹配,usage 里有 prompt_cache_hit_tokens 与 prompt_cache_miss_tokens 可读一手DeepSeek 文档,参照线必须带这两个数,并多次重放取分布。

不适用的部分

  • AgentX 与 AA 的轨迹都是编程任务,只能当脚手架的测试数据,不能代替三类 agent 的负载。
  • 纯长度回放(Azure 的做法)不适合本比赛:轨迹是自己录的,没有隐私约束,应保留全文。
  • needle-in-a-haystack 只能当量化 KV 的冒烟检查,验收应以 Agent Bench 的任务质量和成对问答对比为准。
