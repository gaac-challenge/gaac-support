llm-compressor

vLLM 项目旗下的模型量化与压缩工具库，产物专供 vLLM 加载

与主线一 KV cache · 中为 vLLM 的 FP8 KV cache 校准缩放系数；量化权重省下的显存间接变成 KV 容量与主线二 Agent 负载 · 弱无 agent 专属机制；只通过省显存、容纳更长上下文间接相关

它是什么

llm-compressor 是一个 Python 库，作用是在模型上线之前把它"压小"，主要手段是量化。它属于 vLLM 项目（GitHub 组织 vllm-project），README 第一句就把定位写死了：为用 vLLM 部署而优化模型的库一手llm-compressor README。

先解释量化。大模型的权重是几百亿个小数，默认每个用 16 位浮点（BF16）存。量化就是改用更少的位数来存，例如 8 位或 4 位，好比把照片从无损格式转成高质量 JPEG：体积降到一半或四分之一，画质略有损失。位数少了，模型占的显存少，每生成一个 token 需要从显存搬运的数据也少，所以通常更快。难点在于怎么舍入才不伤精度，于是有了各种算法；多数算法需要一小批样本数据跑一遍模型来观察数值分布，这一步叫校准（calibration）。

llm-compressor 做的事就是：读入一个 Hugging Face 模型，按一份"配方"（recipe）执行量化或剪枝，把结果存成 vLLM 能直接加载的检查点。

它做了什么

量化算法与格式

README 列出的算法是：Simple PTQ（直接舍入）、GPTQ、AWQ、SmoothQuant、AutoRound、基于旋转的 SpinQuant 与 QuIP、REAP 专家剪枝一手。前几个都是"训练后量化"（PTQ，不重新训练，只用校准数据调整舍入方式）的不同流派：GPTQ 逐层用二阶信息补偿舍入误差，AWQ 按激活幅度保护重要权重，SmoothQuant 把激活里的大数值挪一部分到权重上以便连激活一起量化。

支持的精度格式用"W 几 A 几"表示，W 是权重位数，A 是激活（层与层之间流动的中间结果）位数：

  • 权重加激活都量化：W8A8（int8 与 fp8）、W4AFP8，以及 NVFP4、MXFP4、MXFP6A8、MXFP8。后几种是"微缩放"格式，每一小组数值共用一个缩放系数，NVFP4 与 Blackwell 一代 GPU 的硬件支持对应。
  • 只量化权重：W4A16、W8A16、NVFP4A16、MXFP4A16 等。
  • 注意力与 KV cache 量化：FP8、NVFP4以上均一手，README。

v0.15.0 之后的新能力

  • HIGGS 混合精度：先测每层对量化的敏感度，再解一个整数线性规划，在给定平均位宽下为每层选格式。release notes 给的例子是 6.0 bit 目标下 WikiText 困惑度 11.05（配合 GPTQ 为 10.99）一手，仅此一个指标。
  • 块级 QAD（量化感知蒸馏）：QADModifier 把未量化子图的输出缓存下来当"老师"，训练量化后的权重去逼近它，不需要另外加载一个教师模型。
  • MoE 专家剪枝：REAP 直接删掉显著性最低的专家；MoNe 把低显著性专家折叠成常数向量，路由器宽度不变。
  • 逐层压缩与卸载：一次只把一层搬上 GPU，用来处理超过显存的超大模型以上均一手llm-compressor releases。

产物格式：compressed-tensors

输出是 compressed-tensors 格式。它不是新的文件类型，而是对 safetensors（Hugging Face 的标准权重文件）的扩展：权重以压缩后的位宽打包存放，config.json 里多一段 quantization_config，逐组写明位数、分组大小、缩放方式等一手compressed-tensors README。vLLM 加载时读这段配置，决定调用哪个量化内核。

为什么压缩工具绑定运行时

量化产物本身不会让模型变快，必须有运行时里对应的内核去直接计算低位宽数据。README 里有一个现成的例子：Red Hat 发布的 Muse-Spark-Open MXFP4xFP8 检查点（约 1644 GB 压到约 428 GB），注明要靠 vLLM 一个尚未合并的 PR 才能运行；GLM-5.3 的同类检查点则要求 vLLM v0.32 以上一手，README 原文；模型名按 README 记录。也就是说，新格式的检查点和运行时的支持是同一拨人成对推进的。独立的量化库没有这层配合，这是 AutoGPTQ、AutoAWQ 被归档的背景。

不过绑定没有报告说的那么绝对：compressed-tensors 的 README 写明它面向 vLLM 与 SGLang 两个引擎，并提供从 AutoAWQ、NVIDIA ModelOpt NVFP4 等格式转入的工具一手。

与主线一（KV cache）的关系

关系中等，要分清三件事。

第一，FP8 KV cache 是 vLLM 的运行时功能，不是 llm-compressor 的产物。 启动 vLLM 时加 --kv-cache-dtype fp8 就生效，默认所有缩放系数为 1.0，不需要任何校准一手vLLM Quantized KV Cache 文档。

第二，llm-compressor 提供的是可选的校准路径。 在配方里设 kv_cache_scheme，用数据集（文档示例为 512 条样本）估出 K、V 的缩放系数，随检查点保存，vLLM 加载时使用。若要"每个注意力头一个缩放系数"，文档写明必须走 llm-compressor 的校准，且只有 Flash Attention 后端支持一手，同上。vLLM 博客的建议是先用不校准的版本，观察到系统性掉点再校准，举的例子是 Kimi-K2.5 配 FlashMLA 后端一手vLLM blog。

第三，报告引用的 91%→13% 不是校准能解决的问题。 博客原文说明，原因是 Hopper GPU 的 FP8 Tensor Core 在累加时精度不足，上下文到 128k 时 Softmax × V 这一步误差爆发；修法是在 Flash Attention 3 内核里加两级累加，恢复到 89%，Blackwell 上不存在这个问题一手，同上。这是内核层的事，llm-compressor 不参与。

另有一条间接关系：权重从 BF16 量化到 4 bit 左右，省下的显存在 vLLM 里会被划给 KV cache 池，能放更多并发会话或更长上下文。这是容量上的算术关系，没有专门机制。

它不涉及主线一的核心，即 KV 在显存、内存、SSD、网络之间的分层与迁移。

与主线二（Agent 负载）的关系

弱。llm-compressor 是离线工具，不在请求路径上，没有任何感知会话、工具调用或前缀复用的机制。相关之处只有两点：agent 的长上下文让 KV 显存成为瓶颈，量化权重与量化 KV 是缓解手段之一；Red Hat 的 Nemotron 3.5 Super VL FP8 检查点在模型卡里附了 agentic 指标一手，README 提及，模型卡未读，说明量化后的验收开始看 agent 任务而不只是问答基准。

它出现在图里，是因为它是服务端量化的事实入口：vLLM 能加载什么格式，很大程度上由它产出什么决定。

与图中其他概念的关系

  • vLLM：同一个 GitHub 组织，产物专供 vLLM；新格式常与 vLLM 的 PR 成对出现。
  • SGLang：compressed-tensors README 声明兼容 SGLang一手，支持到什么程度未核实。
  • GGUF：对位关系。GGUF 是 llama.cpp 生态的量化格式，compressed-tensors 是 vLLM 生态的；两者互不通用。
  • TensorRT-LLM：NVIDIA 用自己的 Model Optimizer 量化；compressed-tensors 提供从 ModelOpt NVFP4 检查点转入的工具一手。
  • EAGLE-3：同组织下的 speculators 库负责训练 draft head，其 README 展示了"FP8 量化模型 + 投机解码"叠加使用一手speculators README。
  • Vera Rubin NVL72 等硬件：格式由芯片决定。NVFP4 对应 Blackwell 及之后；README 里的 MXFP4xFP8 检查点注明是为 Hopper 优化的。

存疑与未核实

  • 报告把 FP8 KV 的 91%→13% 标为仅摘要并称"事故"。原文已读：数字无误，但它是 vLLM 团队做压力测试时发现并已修复的内核缺陷，不是线上事故；同一篇博客的结论是 FP8 KV cache"已可作为许多长上下文部署的默认起点"。报告只取了负面一半。
  • 报告说"独立量化库因此被淘汰"、每个运行时配一个压缩工具。compressed-tensors 自称同时面向 vLLM 与 SGLang，绑定关系比报告描述的略松。
  • 仓库迁入 vllm-project 的日期、Red Hat 宣布收购意向的确切日期，未找到一手来源。
  • README 的算法列表里没有 SparseGPT，而 compressed-tensors 的 README 仍把 SparseGPT 列为支持的算法；是否已从 llm-compressor 移除未核实。
  • README 中的模型名（Muse Spark Open、GLM-5.3、Qwen3.8 等）与体积数字按原文记录，未到 Hugging Face 逐一核对。
  • 所有压缩实例都没有给出精度恢复数字。
