vLLM 与 SGLang 对比分析

机制已趋同;RTX PRO 6000 上先用 vLLM 跑通,SGLang 同步对照,谁快要自测

结论先行

  1. 两个引擎的机制已经趋同,选型应按"我们的模型 × 我们的卡"这一格上谁的路径是通的来定,而不是按引擎的总体口碑。 依据:DeepSeek 官方模型卡把 vLLM 与 SGLang 并列给出启动命令;两者都用 FlashInfer 与 TensorRT-LLM 的 kernel;vLLM 的 Rust 路由器 README 写明它是 SGLang Model Gateway 的 fork一手DeepSeek-V4-Flash-0731 模型卡vLLM Router。
  2. 在我们的场景(RTX PRO 6000、DeepSeek 系、agent 负载)先用 vLLM 做主力基线,SGLang 第一天就并行起一套做对照。 依据:唯一一份在 8 卡 RTX PRO 6000 上披露配置的同机记录里,生产最终落在 vLLM + DSpark;SGLang 官方 cookbook 明写 DeepSeek-V4 在 RTX PRO 6000 上不支持 HiCache 与 MegaMoE二手 + 一手Helix 博客SGLang DeepSeek-V4 cookbook。这条结论只对 DeepSeek-V4-Flash 成立,且那份记录的两边投机解码方法不同,不能当作"vLLM 更快"的证据。
  3. SGLang 该上的时机有三个:比赛模型不是 DeepSeek-V4 系(例如 Qwen3.8-27B 这类单卡模型);显存内 KV 驱逐成为瓶颈、需要引擎内的会话保护或可选淘汰策略;或 vLLM 在该模型上的 SM120 路径不通。 依据:同一家 Helix 在 Qwen3.8-27B 上生产用的是 SGLang;SGLang 有 7 种 radix 淘汰策略与 session_id 级软保护,vLLM 引擎内只有 LRU二手 + 一手Helix 调优记录SGLang Server Arguments。
  4. 公开横评没有一份可以直接套到我们头上。 质量最高的 InferenceX AgentX 没有 RTX PRO 6000 的数据点;其余博客版本陈旧或变量不单一,方向互相矛盾。E11(引擎对照)必须自己做,而且要按下文的"公平开关表"做。
  5. 两者共同的最大风险不是谁慢,而是 SM120 是二等公民,以及特性组合下的静默错误。 RTX PRO 6000 的计算能力代号是 SM120,数据中心 Blackwell(B200/GB300)是 SM100;大量专用 kernel 只为 SM100 写,SM120 走回退路径。两边在 2026 年都出过"跑得很快但结果错"的缺陷,见"运维与稳定性"一节。

逐项对照

出身、治理与发布

差别:vLLM 有成文的基金会治理,SGLang 由非营利组织托管但仓库里没有治理文件;人力规模 vLLM 大约是 SGLang 的 1.6 倍。

  • vLLM 出自 UC Berkeley Sky Computing Lab,2025-05 起为 PyTorch Foundation 托管项目,治理文档列出 11 位 core maintainer;SGLang 的 README 写 "hosted by LMSYS, a non-profit open-source organization"一手,沿用单篇调研vLLM GovernanceSGLang 仓库。本轮检查 SGLang 仓库根目录,GOVERNANCE.md 与 MAINTAINERS.md 均返回 404,只有 .github/CODEOWNERS一手。
  • 公司:Inferact(vLLM,2026-01,种子轮 1.5 亿美元)二手;RadixArk(SGLang,2026-05 公告种子轮 1 亿美元)一手,公司公告。两篇单篇调研已核实,此处不展开。
  • 节奏:GitHub API 显示两者 2026 年 7 月以来都是约两周一个版本。vLLM 最近为 v0.34.0(11-16)、v0.32.0(10-18)、v0.31.0(10-05);SGLang 为 v0.5.23(11-02)、v0.5.22(10-19)、v0.5.21(10-02)一手,GitHub API。
  • 规模:v0.34.0 是 "1,061 commits from 412 contributors (120 new)",v0.5.23 是 "1007 PRs from 257 contributors";star 为 97,178 对 39,040,fork 为 24,989 对 10,598一手,2026-11-18 快照vLLM v0.34.0SGLang v0.5.23。vLLM README 自称累计贡献者超过 2000 人;SGLang 没有给出累计数。
  • 许可证都是 Apache-2.0。

调度、批处理与前端

差别:两者都是连续批处理加 chunked prefill,但默认的优先方向相反;前端都在从 Python 迁往 Rust,进度不同。

  • vLLM:chunked prefill 默认开启,文档原话是 "It batches all pending decode requests before scheduling any prefill operations",prefill 只在 max_num_batched_tokens 预算有余时进入;KV 不够时抢占请求并重算(默认 RECOMPUTE)一手vLLM Optimization。v0.34.0 新增可选的 cache-aware admission(默认关)。
  • SGLang:--schedule-policy 默认 fcfs,可选 lpm(最长前缀匹配,重排等待队列以提高命中)、priority、routing-key 等 7 种;--chunked-prefill-size 控制分块;KV 池满时"retract"请求一手SGLang Server ArgumentsSGLang 调参指南。SemiAnalysis 记录了它的默认行为是 prefill 优先:在 DP attention 下,不断到来的 chunked prefill 会让 decode 批次挨饿;新增的 decode 间隔选项在 DeepSeek-V4 Pro 的 AgentX 上把输出吞吐提高 141%,代价是中位 TTFT 从 36.5 秒升到 59 秒二手,转述上游 PRSemiAnalysis AgentX。
  • 后果:同一份长上下文负载,vLLM 默认更护 TPOT,SGLang 默认更护 TTFT。六项指标里首 token 延迟和生成速度是分开评的,所以这个旋钮两边都要显式调到同一目标再比。
  • 前端与 CPU:vLLM 默认仍是 Python FastAPI 服务器;Rust 前端用 VLLM_USE_RUST_FRONTEND=1 打开,二手报道称在长 prompt、缓存已热的负载上单进程 837 req/s,对比 Python 4 进程 162 req/s(Qwen3-0.6B、4×GB200、并发 1024,vLLM 自测)二手,转述 PR #40848AlphaSignal。v0.34.0 的 Rust 前端已有无状态 Responses API,DeepSeek-V4.1-Flash 的官方 recipe 默认配置写的是 frontend rust一手vLLM recipe V4.1。vLLM 文档给出 CPU 下限:N 张 GPU 至少 2 + N 个物理核一手。
  • SGLang 的主服务器也是 Python,靠 --tokenizer-worker-num(默认 1)扩展分词;release notes 有独立的 "Rust Server" 一节(gRPC 接口、sglang-processor 渲染 chat 模板),路由器 sgl-router 可以代做分词一手。本轮没有找到 SGLang 前端每请求开销的公开数字。

前缀缓存:数据结构与淘汰

差别:结构不同是事实,但对长前缀负载,命中粒度的差别很小;真正的差别在"显存不够时踢谁"。

  • 粒度:vLLM 只缓存写满的块,默认块大小 64,DeepSeek-V4 的官方 recipe 用 --block-size 256一手vLLM recipe 0731。SGLang 的 --page-size 默认是 1 token,radix tree 可以在节点中间拆分;但 HiCache 最佳实践建议开分层时用 --page-size 64一手HiCache Best Practices。对一个 68K token 的 agent 上下文,最多少命中 255 个 token,不到 0.4%。粒度只在短前缀、高分叉(子 agent、few-shot 分支)时才有可测的差别。
  • 淘汰:vLLM 是空闲块的 LRU 链表,数据结构里没有"谁是谁的前缀"。SGLang 的 --radix-eviction-policy 有 lru、lfu、slru、priority、tlru、joint_lru、state_cost 七种,默认 lru一手。
  • 会话保护:SGLang 引擎内有两档。--enable-session-radix-cache 是软保护(先踢无 session 引用的 KV);--enable-streaming-session 是实验性的独占槽。后者在单篇调研里只有 Dynamo 文档作证,本轮在 SGLang 自己的参数文档里核到了这个开关一手。
  • vLLM 引擎没有对应物,它把这件事放在路由层。vllm-router 的 Program scheduling 把相关请求归为一个 Program,用 Progress-TTL 在短工具调用期间保护可复用的 KV。但文档写明这是间接保护:"Progress-TTL currently protects KV indirectly by controlling request admission. Physical eviction, offload, and prefetch are not executed by this feature"一手Program scheduling 文档。也就是说 vLLM 靠"少放人进来"保住缓存,SGLang 靠"踢人时避开"保住缓存。
  • 后果:计划里的 E5(工具间隙里缓存留不留得住)在 SGLang 上多两个可调变量,在 vLLM 上要加一层路由器才有对等手段。

KV 分层与外溢

差别:层级划分几乎一样,都默认关闭;差别在接口形态和在我们这张卡上是否可用。

项 vLLM SGLang
开关 --kv-transfer-config 指定 connector --enable-hierarchical-cache
主机内存层 OffloadingConnector 默认仅 CPU 层 L2,--hicache-ratio 默认 2.0
更下层 fs、obj(经 NIXL 的 S3)、p2p file、fast_file、mooncake、hf3fs、nixl、aibrix 等
写策略 写穿透为常见实现 write_through(默认)、write_through_selective、write_back

来源见两篇单篇调研与 SGLang 参数文档一手。三点补充:

  • SemiAnalysis 观察到主机内存 offload 多为写穿透,所以主机内存池要比显存 KV 池大 1.5 到 3 倍才有效;B200 上并发 196 时显存命中 73%、主机内存命中近 20%二手SemiAnalysis AgentX。
  • vLLM 的 CPU offload 对 DeepSeek-V4 这类混合注意力模型是 2026 年才补上的,PR 自报相对"放不下就重算"输出吞吐高 81.7%二手,转述 PR。
  • 对我们最关键的一条:SGLang cookbook 的原话是 "HiCache and MegaMoE are not supported on RTX PRO 6000"(DeepSeek-V4 页)一手SGLang DeepSeek-V4 cookbook。vLLM 的 offload 在 SM120 加 DeepSeek-V4 上是否可用,本轮没有找到一手说明。计划里的 E4(KV 分层)因此不能默认两边都能做。

集群形态:PD 分离与路由

差别:PD 分离 SGLang 的文档更成体系,vLLM 自己标为实验性;路由器两边同源。

  • vLLM 文档对 disaggregated prefill 的原话是 "This feature is experimental and subject to change",并写 "Disaggregated prefill DOES NOT improve throughput",收益在于分别调 TTFT 与 ITL;列出的 connector 有 NIXL、Mooncake、MoRIIO(仅 ROCm)、LMCache、FlexKV 等一手vLLM Disaggregated Prefill。
  • SGLang 的 PD 文档覆盖 Mooncake 与 NIXL 两种传输、异构 TP 的 GPU staging buffer、节点内 NVLink 传输;并写明 PD 下不支持带状态的 Responses 功能一手SGLang PD Disaggregation。
  • 路由器:sgl-router 是 Rust 写的,策略有 cache_aware(靠引擎发布的 KV 事件建全局前缀树)、power_of_two 等,支持 Kubernetes EndpointSlice 发现一手DP、DPA 与 sgl-router。vllm-router 同样是 Rust,策略为 round_robin、random、consistent_hash、power_of_two、cache_aware,README 致谢写明 fork 自 SGLang Model Gateway一手vLLM Router。两者都能以独立进程运行,不依赖 Kubernetes,适合 AutoDL 容器实例。
  • 上层集成:llm-d 以 vLLM 为默认引擎,同时发布 SGLang 镜像;KServe 的 LLM 文档只围绕 vLLM;AIBrix 三引擎一等支持(沿用各单篇调研)。Dynamo 的特性矩阵写 "vLLM offers the broadest feature coverage in Dynamo";SGLang 一栏里 KV Block Manager 与请求取消为 WIP,LoRA 不支持一手,dev 版文档Dynamo Feature Matrix。
  • 后果:要上 Kubernetes 栈时 vLLM 的路更宽;只在单机上起路由器时两边等价。

Agent 相关能力

差别:API 面基本对齐;SGLang 多一个引擎内会话,vLLM 多一个引擎外的有状态网关。

  • 工具调用:都是"按模型选解析器"。vLLM 用 --enable-auto-tool-choice --tool-call-parser deepseek_v4,并需 --tokenizer-mode deepseek_v4;SGLang 用 --tool-call-parser deepseekv4,解析器列表约 38 个,支持 auto一手。tool_choice 为 required 或指定函数时,两边都用语法约束解码保证可解析。
  • DeepSeek-V4 不提供 Jinja chat 模板,而是一个 encoding 目录的 Python 编码器一手模型卡。SGLang v0.5.23 把 V4/V4.1 的编码改为走 DeepSeek 官方 encoder,副作用是流式工具参数分片到达、tool-call id 改为 call_00_... 格式,列在破坏性变更里一手。换引擎或升级后要重测 agent 框架的解析。
  • 结构化输出:vLLM 为 xgrammar 与 guidance,默认 auto;SGLang 为 xgrammar(默认)、outlines、llguidance一手。
  • 推理内容:两边都有 reasoning parser(vLLM --reasoning-parser deepseek_v4,SGLang --reasoning-parser deepseek-v4)。
  • API 兼容:两边都有 /v1/responses 与 Anthropic /v1/messages、count_tokens。vLLM 文档提醒 max_tokens=0 的缓存预热请求会被 400 拒绝,要用 max_tokens=1一手vLLM Online Serving。SGLang 的 Anthropic 端点默认注册,文档专门讲了 Claude Code 接入时为保住前缀缓存需要的设置一手SGLang Anthropic API。
  • 状态:vLLM 的 Rust 前端 Responses 是无状态的,状态放在独立的 agentic-api 网关;SGLang 的 PD 文档提到可选的 --enable-response-store(进程内存储,PD 下禁用)一手。两者都不在引擎里保存对话。

量化与模型格式

差别:格式覆盖接近,vLLM 有自家压缩工具;在 SM120 上两边可用的 kernel 都比 SM100 少。

  • vLLM README 列出 FP8、MXFP8/MXFP4、NVFP4、INT8、INT4、GPTQ/AWQ、GGUF、compressed-tensors、ModelOpt、TorchAO;GGUF 走 vllm-gguf-plugin;配套工具是 llm-compressor一手vLLM Quantization。文档有一条容易忽略的规则:所需的激活量化 kernel 不可用时,vLLM 会回退到只量化权重的 kernel,设 VLLM_STRICT_QUANT_SCHEME=1 可禁止回退。
  • SGLang 的 --quantization 取值包括 awq、gptq、fp8、mxfp8、mxfp4、gguf、bitsandbytes、modelopt_fp8、modelopt_fp4、compressed-tensors、quark、auto-round 等;文档直接教用 llm-compressor、ModelOpt、GPTQModel、auto-round 做离线量化,自己没有压缩库一手SGLang Quantization。
  • KV 量化:vLLM 为 --kv-cache-dtype fp8。SGLang 为 fp8_e5m2、fp8_e4m3、mxfp8、nvfp4、fp4_mx_block16,其中 FP4 标为实验性;文档写明 NVFP4 KV 在 SM120 上 prefill 要先反量化成 FP8,原生路径只有 SM100一手SGLang Quantized KV Cache。Helix 在 vLLM 上的记录是 "nvfp4 asserts on SM120"二手。所以在我们的卡上,KV 量化两边都只应先试 FP8。
  • SM120 的 GEMM 后端:SGLang 文档给出自动选择顺序,块 FP8 在 SM120 走 CUTLASS,NVFP4 走 flashinfer_cutlass;DeepGEMM 与 TRTLLM 路径只到 SM90/SM100一手。

投机解码

差别:方法族几乎重合,都把 DSpark 做成了 DeepSeek-V4 的一等路径;限制条件不同。

  • vLLM:ngram、suffix、draft model、EAGLE/EAGLE3、MTP、DFlash/DFlash2、DSpark,v0.34.0 加了自定义 speculator 的插件 API;训练库是 speculators一手。
  • SGLang:EAGLE-2/3、MTP(NEXTN)、UNO、DFlash/DSpark、STANDALONE、NGRAM,另有自适应投机;训练库是 SpecForge一手SGLang Speculative Decoding。
  • 组合限制:SGLang cookbook 写 DSpark 要求 pp_size == 1,且当前版本与 DP Attention 不兼容;在捆绑 DSpark 头的检查点上误用 EAGLE 参数不会报错,但接受率为 0一手。vLLM v0.34.0 的条目显示 DSpark 已可与 PCP 组合;但 issue #49369(单张 B300 上 DSpark 比不开还慢)至今未关闭一手,GitHub APIvLLM #49369。
  • 对 agent 负载的收益要自己测。Helix 的经验是接受率在代码与散文之间差两倍,"引用的单个数字几乎总是最好的那一格"二手。

模型覆盖与首发速度

差别:对 DeepSeek 系,两者同为首日支持,官方都推荐;看不出先后。

  • DeepSeek-V4 于 2026-04-24 发布。SemiAnalysis 的说法是两者 "both supported native DeepSeek v4 Pro on the CUDA platform the moment the model was released publicly",TensorRT-LLM 当时不能开箱即用二手SemiAnalysis Day 0 to Day 43。LMSYS 博客自称 SGLang 是首个在发布日同时支持推理与训练的开源栈厂商自述,仅见于搜索摘要。
  • DeepSeek-V4-Flash-0731 的模型卡先给 vLLM 命令,再给 SGLang 命令,各自链接到 vLLM recipe 与 SGLang cookbook一手。
  • 各版本说明里的新模型数量:v0.34.0 列 10 个,v0.5.23 列 10 个(其中 5 个是扩散模型)。SGLang 把图像与视频扩散并入主仓库,vLLM 放在 vllm-omni。
  • AMD 平台上,SemiAnalysis 在 2026-06 的判断是 ROCm 版 vLLM 进展 "much slower" 于 SGLang二手。这与我们无关,但说明"谁支持得好"是按硬件分的。

硬件覆盖与 Blackwell 工作站卡

差别:两者都声称支持 RTX PRO 6000,但都不是开箱即用;问题清单不同。

先说清背景:RTX PRO 6000 Blackwell 是 SM120,没有 NVLink。一份社区部署记录列出了由此带来的限制:自定义 all-reduce 被禁用(8 张 PCIe 卡非全连接),跨卡通信走 PCIe 上的 NCCL;DeepGEMM 在 SM120 上会触发 "Unknown SF transformation" 断言二手,社区帖HF 讨论帖。

其他已知问题:

  • NVIDIA 论坛有人报告 RTX PRO 6000 工作站版在 vLLM 0.25.1 做 CUDA graph 捕获时整机硬锁,只能断电恢复,与时钟策略有关(nvidia-smi -lgc 180,2800 后 6 次全过)二手,单一用户报告NVIDIA 论坛。
  • 2026-01 的一份单卡测试里,SGLang 在这张卡上需要 --disable-cuda-graph,NVFP4 没跑通,vLLM 无问题;版本未披露,较旧二手Joshua8。
  • Server Edition 的 vBIOS 把显存时钟偏移锁在 [0, 0],社交媒体上的超频数字来自工作站版二手。
  • 冷启动很慢:vLLM + DSpark 首次约 38 分钟,有 JIT 缓存后约 5 分钟;SGLang 首次要做 FlashInfer autotune二手 + 一手。

其他硬件:vLLM 官方发布 CUDA 13.0、ROCm 10.0、Intel XPU、CPU 的 wheel,TPU、昇腾、Gaudi、Spyre、Apple Silicon 等走插件仓库;SGLang README 的硬件表列 NVIDIA、AMD、Google TPU、Intel、Apple Silicon、昇腾、摩尔线程,并称 T-Head PPU、寒武纪等在接入中一手。

运维与稳定性

差别:升级成本相当;vLLM 的指标更细;两边都有被长上下文负载才暴露出来的正确性缺陷。

  • 升级破坏性:v0.34.0 一次列 8 项破坏性变更(移除 Model Runner V1、默认块大小改 64、gpu_memory_utilization 默认 1.0 等);v0.5.23 列 12 条(DeepSeek 编码器切换、PD 两端必须同时升级、移除若干参数等)一手。
  • 正确性缺陷举例(均来自 SemiAnalysis 对上游 PR 的转述二手):SGLang 在异构 PD 加前缀命中时,KV 曾被写到错误位置,127,500 token 共享前缀测试只有 2/128 正确,修复后 128/128;vLLM 的重复轮次缓存曾 "silently losing EAGLE state";TensorRT-LLM 的一组 MoE tactic 让 7 次运行崩了 5 次。共同点是吞吐基准看不出来,要靠长上下文检索测试。
  • 可观测性:vLLM 的 /metrics 有按 token 计的 vllm:prefix_cache_hits、按缓存层拆分的 vllm:prompt_tokens_cached_by_source、KV 块寿命与复用间隔直方图、抢占计数、投机解码按位置接受数一手vLLM Metrics。SGLang 需 --enable-metrics,指标有 sglang:cache_hit_rate、sglang:token_usage、TTFT 与 ITL 直方图、队列长度;另有请求转储回放与崩溃转储一手SGLang Production Metrics。
  • 确定性:vLLM 的批不变性用 VLLM_BATCH_INVARIANT=1 打开,文档标 beta,开启后禁用 FlashInfer 等非确定路径;TP 下部分 all-reduce 尚不支持一手vLLM Batch Invariance。SGLang 用 --enable-deterministic-inference,只支持 FlashInfer、FA3、Triton 三种注意力后端,其中 FlashInfer 后端不兼容 radix cache一手SGLang Deterministic Inference。DeepSeek-V4 用的是专用注意力后端,两边的确定性模式是否覆盖它,未核实。
  • 文档:SGLang 的 cookbook 按"硬件 × 检查点 × 策略"给命令并注明验证版本;vLLM 的 recipes 站同样如此,且每个配置有 JSON 接口。两边的通用文档都落后于专用配方。

差别:vLLM 有更多第三方可确认的案例;SGLang 的大客户名单主要来自自述。

  • vLLM:Tesla 的 KServe + llm-d + vLLM 生产栈有 llm-d 博客记录;NVIDIA NIM 内置 vLLM;Inferact 官网的客户名单为自述(沿用单篇调研)。

解读:

  • 方向互相矛盾。 Helix 上 vLLM 领先 45%,Joshua8 上 SGLang 领先 17%,Spheron 上无重复负载基本持平、前缀负载 SGLang 领先,AIMultiple 上 SGLang 领先 29%。每一份的变量都不同:投机解码方法、版本、是否开前缀缓存、在线还是离线。
  • Helix 的对比不是引擎对比。 SGLang 一侧用 EAGLE(2 个草稿 token)加社区 SM120 补丁,vLLM 一侧用 DSpark(深度 7)加第三方 kernel 集。作者自己写单流提升"roughly 5×"来自 DSpark。它能说明的是:2026-08 时,在这张卡上先把 DSpark 跑通的是 vLLM 一侧的社区配方。两边都没有报告 TTFT 和缓存命中。
  • Spheron 的前缀结论要打折。 同文称 vLLM 打开前缀缓存后差距缩到 15–18%,说明主表里的 vLLM 可能没开缓存;512 token 的共享前缀也远小于 agent 负载。
  • AIMultiple 的数字就是报告里引用的那组。 报告引 PremAI 的 "约 16,200 对 12,500",与 AIMultiple 的 16,215 对 12,553 吻合,后者的 SGLang 版本是 v0.2.3,vLLM 是 0.11.0,都远早于现行版本。这组数字不应再用于 2026 年的判断。
  • AA-AgentPerf 把推理框架与版本作为配置披露项,但本轮没能打开逐项配置页,不知道各提交用的是哪个引擎未复核。
  • InferenceX 的对比页上,RTX PRO 6000 一列是空的仅搜索摘要。它的 AgentX 方法(真实轨迹、按原时间表回放、报告显存与主机内存命中率)值得我们的 Benchmark 借鉴。

所以这一节的结论只有一句:没有证据支持"在 RTX PRO 6000 的 agent 负载上谁更快"。

对我们这个场景的建议

选型

  1. 主力基线用 vLLM。 理由按分量排:这张卡上有第三方生产记录;DSpark 路径的关键修复已进上游;指标更细,便于把首 token 延迟按命中与否拆开;KServe、llm-d 等后续栈以它为默认。
  2. SGLang 第一天就起一套。 理由:引擎内的会话保护与淘汰策略是 E3、E5 的直接变量;若比赛模型不是 DeepSeek-V4-Flash,优劣可能反过来。
  3. 模型先定。 计划文档按 671B、FP8 约 700 GB 估算"满血 DeepSeek 放不下"。但 DeepSeek-V4-Flash-0731 是 304B,FP8 检查点约 156 到 167 GB(专家为 FP4)二手,两份社区记录,Helix 用 4 张卡(TP=4)跑一个实例。也就是说,4 卡机可以直接跑比赛级的 Flash 模型,不必用替身。V4-Pro 在 8×96 GB 上放不下;V4.1-Flash(552B)两边的配方都没有 RTX PRO 6000 档。比赛到底对标哪个型号,仍是首要待定项。

4 卡机上的对比实验(对应计划 E11)

拓扑以 T1(四卡一个副本,TP=4)为主。SGLang cookbook 给的是 TP=2;两卡 192 GB 装 156 GB 权重后留给 KV 的空间很小,T2 是否可行要上机看启动日志里的 KV 容量。

第一步:通路。 两边各用官方最新稳定镜像加官方配方,不打补丁,记录能否起服、冷启动耗时、实际走的 kernel 后端(启动日志)。起不来就记下缺什么,再换 nightly。这一步本身就是结论的一部分。

第二步:公平开关表。 同一检查点、同一权重格式,下列各项两边对齐:

项 vLLM SGLang 说明
KV 精度 --kv-cache-dtype fp8 --kv-cache-dtype fp8_e4m3 都不用 NVFP4 KV
KV 容量 不设 gpu_memory_utilization 调 --mem-fraction-static 以启动日志的 KV token 数为准,调到相近再比
前缀缓存 显式传 --enable-prefix-caching(默认值未核实) 默认开(关闭要传 --disable-radix-cache) vLLM 块 256;SGLang 页大小记下实际值
分块 prefill max_num_batched_tokens --chunked-prefill-size 设成同一 token 数
并发上限 --max-num-seqs --max-running-requests 设成相同,且不超过 CUDA graph 捕获的批大小
投机解码 第一轮关;第二轮 DSpark 第一轮关;第二轮 DSPARK 草稿 token 数对齐;不要一边 EAGLE 一边 DSpark
工具与推理解析 deepseek_v4 三件套 deepseekv4、deepseek-v4 用同一批工具调用样例验解析成功率
分层 offload 关 关 单独做 E4,不混进基线
指标 默认 /metrics --enable-metrics --enable-cache-report

第三步:各测什么。

  • 六项指标全量,用同一份轨迹文件、同一并发阶梯,每档前加动态前缀使上一档缓存失效。
  • 缓存命中按 token 计:vLLM 用 vllm:prompt_tokens_cached 除以总 prompt token;SGLang 用响应 usage 里的 cached tokens。两边口径要先用一条已知轨迹校准。
  • 吞吐一律用非流式请求、按服务端 completion_tokens 除以墙钟时间计算。开投机解码时流式分片数对应的是步数而不是 token 数,一份社区记录里两种算法差到 14.7 对 60.1二手Level1Techs。
  • 充分预热后再计数。同一份记录称冷态数字低约 30%,并发路径的 JIT 编译不在常规预热覆盖范围内。
  • 正确性门槛:每个配置跑一次长上下文检索测试(例如 12 万 token 里埋 128 个 needle),再跑固定的工具调用回归集。吞吐高但检索掉分的配置不进对比表。
  • 引擎特有变量单独成组:SGLang 的 --schedule-policy lpm、--radix-eviction-policy、--enable-session-radix-cache(请求带 session_id);vLLM 的 cache-aware admission、Rust 前端、vllm-router 的 Program scheduling。这些是"各自调到最好"的一组,和"默认对默认"的一组分开报。

两者都该警惕的坑

  1. SM120 不是 SM100。 网上 B200、GB300 的配方参数(MegaMoE、FP4 indexer cache、NVFP4 KV、DeepGEMM)在这张卡上多数不可用。vLLM 在激活量化 kernel 缺失时会静默回退,建议设 VLLM_STRICT_QUANT_SCHEME=1 让它报错。
  2. 没有 NVLink。 TP=4 的每一层都要跨 PCIe 做 all-reduce。计划里 T1 对 T4(四个单卡副本)的对比因此很有价值:小模型单卡多副本可能比大 TP 划算,Helix 在 Qwen3.8-27B 上就是一卡一个引擎。
  3. 并发上限与 CUDA graph。 Helix 在 SGLang 上遇到过:graph 捕获到批大小 32,EAGLE 两个草稿 token 让验证批翻倍,第 17 个并发请求起掉出 graph,吞吐从 349 跌到 78 tok/s。规则是"并发上限 × 草稿 token 数 ≤ 捕获的批大小",两边都适用。
  4. 状态缓存封顶。 混合架构模型(Qwen3.8 这类带循环状态的)在 SGLang 上并发可能被 mamba state cache 悄悄封顶,启动日志会写 max_running_requests is capped to ...二手Helix。先读启动日志再压测。
  5. 上下文记账。 引擎的 max-model-len 要大于对客户端宣称的窗口。客户端估的 token 数偏少,vLLM 在真实上限处硬拒,该轮任务直接失败。这会直接计入任务成功率。
  6. 卡的版本。 Max-Q、工作站版、Server Edition 的时钟与功耗策略不同;工作站版有 CUDA graph 捕获时整机硬锁的报告。每次结果都要记下 SKU、vBIOS 与驱动版本(Helix 为 DSpark 把驱动升到了 595.84)。
  7. 冷启动与缓存目录。 两边都有十几到几十分钟的首次编译或自动调优。把 JIT 与 autotune 缓存目录放在数据盘并做快照,否则"冻结重跑"每次都要付这笔时间。
  8. 锁版本。 两个项目都是两周一版、每版都有破坏性变更。Benchmark 记录里要有镜像 digest,而不只是版本号。

存疑与未核实

  • vLLM v0.34.0 与 SGLang v0.5.23 的原版镜像能否在 RTX PRO 6000 上直接跑 DeepSeek-V4-Flash-0731,本轮没有一手证据。vLLM 的 SM12x 总 PR #41834 关闭未合并,相关功能是否经其他 PR 进入主线,未逐个核对;SGLang 侧 Helix 当时用的是社区补丁加专用镜像。
  • "SGLang 在 RTX PRO 6000 上不支持 HiCache"出自 DeepSeek-V4 的 cookbook 页,是否对其他模型也成立,未核实。vLLM 的 CPU offload 在 SM120 上是否可用,未核实。
  • vLLM 前缀缓存是否默认开启、--scheduling-policy 的可选值,本轮抓到的文档页没有覆盖,文中未作断言。
  • Rust 前端的启用方式与性能数字来自二手报道(2026-05);v0.34.0 时它是否仍标为实验性,未核实。
  • Helix、Level1Techs、HF 讨论帖均为用户自述,没有第二来源复现。检查点大小有 156 GB 与 166.9 GB 两种说法。
  • InferenceX 上 8-21 前后 vLLM 与 SGLang 的相对位置来自文章的文字描述,图表数值未读取;其 RTX PRO 6000 数据为空一事只见于搜索摘要。
  • AA-AgentPerf 各提交使用的引擎未查到。DeepSeek 官方 API 背后用什么引擎,没有任何来源。
  • SGLang 累计贡献者数量未查到;GitHub 贡献者接口对两个仓库都返回约 450 页,疑似被接口上限截断,未采用。
  • 与既有文档的出入:其一,单篇调研称 streaming session 只在 Dynamo 文档里有据,本轮在 SGLang 参数文档里核到了 --enable-streaming-session;其二,单篇调研说 vLLM "无会话概念",引擎层面仍成立,但 vllm-router 已有 Program scheduling 这一路由层对应物;其三,报告引用的 "16,200 对 12,500 tok/s" 对应的是 SGLang v0.2.3 与 vLLM 0.11.0;其四,计划文档关于满血 DeepSeek 体量的估算与 V4-Flash 的实际大小不符,且其 E4 假设 SGLang 可用 HiCache。
