llama.cpp

用 C/C++ 写的本地大模型推理引擎,本地阵营的公共底座

与主线一 KV cache · 中单机内已有显存、主机内存、磁盘三级 KV 复用,但不跨机器、不走网络与主线二 Agent 负载 · 中本地 coding agent 的常用后端,缓存机制专为 agent 负载改过,但只服务单用户

它是什么

llama.cpp 是一个用 C/C++ 写的大语言模型推理引擎,目标是让模型在普通人手边的硬件上跑起来:笔记本 CPU、Apple Silicon 的 Mac、消费级显卡、手机,乃至浏览器。它不依赖 Python 和 PyTorch,编译出来就是几个可执行文件。项目 README 对自己的定位是:以最少的配置和最好的性能,在各种硬件上做 LLM 推理,本地和云端都行一手README。

它底下是同一批人写的张量库 ggml,配套的模型文件格式叫 GGUF(见 GGUF 一篇)。数据中心里的 vLLM、SGLang 追求的是一堆 GPU 同时服务成千上万个请求;llama.cpp 解决的是另一个问题:一台机器、一个用户、内存有限,怎么把模型装进去并跑得够快。答案主要是两件事:把权重量化到 4 bit 左右,以及为每种硬件手写计算内核。

它做了什么

多后端的手写内核

构建文档列出的后端包括:CPU、各类 BLAS、Metal(Apple GPU)、CUDA、SYCL、HIP(AMD)、Vulkan、OpenCL、WebGPU、OpenVINO、Hexagon、摩尔线程 MUSA、华为昇腾的 CANN、Arm KleidiAI、IBM Z 等一手build.md。模型放不进显存时,可以只把一部分层放到 GPU,其余留在 CPU,这是它能在小显存机器上跑大模型的原因。

量化

配套工具 llama-quantize 把高精度 GGUF 转成 2 到 8 bit 的各种档位,可选用校准数据生成的重要性矩阵(imatrix)减少精度损失。官方 README 的例子:Llama 3.1 8B 原始 32.1 GB,量化到 Q4_K_M 后 4.9 GB一手quantize README。

llama-server

llama-server(新命令是 llama serve)是一个自带网页聊天界面的 HTTP 服务。它提供 OpenAI 兼容的 /v1/chat/completions、/v1/responses、/v1/embeddings,以及 Anthropic 兼容的 /v1/messages一手server README。几个关键设计:

  • slot(槽位):服务器把上下文划成若干 slot,每个 slot 承载一段对话,-np 指定数量,默认自动。多个 slot 靠连续批处理(continuous batching,默认开启)在同一次前向计算里一起推进。
  • router 模式:不指定模型启动时,主进程按请求里的 model 字段动态加载和卸载模型,默认最多同时加载 4 个。
  • 投机解码:--spec-type 支持草稿模型、draft-eagle3、draft-mtp 和若干 n-gram 变体。

与 Ollama、LM Studio 的关系

llama.cpp 本身偏底层,打包和易用性长期由下游完成。Hugging Face 文档称 Ollama 是"基于 llama.cpp 的应用"一手HF docs: Ollama;Ollama 0.30 的发布说明写的是用 llama.cpp 改善兼容性和性能,并与 Apple Silicon 上的 MLX 引擎并存一手;页面只显示 5 月 13 日,年份 2026 为推断Ollama v0.30.0。LM Studio 的官方文档称它在三大桌面系统上用 llama.cpp 跑模型,在 Apple Silicon 上另有 MLX 引擎仅摘要LM Studio docs。也就是说,这两个更知名的产品在跑 GGUF 模型时,里面执行计算的仍是 llama.cpp。

与主线一(KV cache)的关系

关系为中等,而且方向与数据中心相反。报告的主线一讲的是 KV cache 跨机器、走网络成为共享存储层;llama.cpp 的 KV 机制全部在一台机器内,但"显存、主机内存、磁盘"三级已经齐全。以下均来自服务器文档一手server README:

  1. 前缀复用:cache_prompt 默认开启,新请求与该 slot 上一次请求比较,只计算没见过的后缀。--cache-reuse N 还能在前缀中间有改动时,通过平移 KV 来复用后面的块。
  2. 主机内存 prompt cache:--cache-ram 默认 8192 MiB。空闲 slot 的状态被搬到普通内存里,作者形容为"额外的 slot";新请求到来时服务器比较前缀相似度,划算就把缓存的状态热切换回上下文一手PR #16391。
  3. 上下文检查点:--ctx-checkpoints 默认每个 slot 最多 32 个,最小间隔 8192 token。它用于滑动窗口注意力、状态空间这类无法随意截断 KV 的模型,回退时从检查点恢复而不是整段重算。
  4. 落盘:设置 --slot-save-path 后,可用 POST /slots/{id}?action=save 和 action=restore 把某个 slot 的 KV 存成文件再读回。这是手动接口,没有自动的磁盘层;增加 --cache-disk 的提议(issue #20697)在 2026-11-07 因无人跟进被自动关闭一手issue #20697。
  5. KV 量化:--cache-type-k 与 --cache-type-v 默认 f16,可选 q8_0、q4_0、q5_1、f8_e4m3 等。官方函数调用文档警告,极端的 KV 量化(如 -ctk q4_0)会明显损害工具调用表现一手function-calling.md。

单用户场景下 KV cache 的意义也不同。数据中心关心的是命中率、跨节点路由和每 token 成本;本地只有一个用户,关心的是切换对话或 agent 来回调用时不要把几万 token 的上下文重新算一遍,因为本地 prefill 速度慢,重算一次可能要等几十秒。另外,在统一内存的机器上(Apple Silicon、AMD Strix Halo),主机内存和显存是同一块,--cache-ram 并没有把数据挪到更便宜的层级,只是多占了同一池内存,这正是上面那个 issue 的论点。

与主线二(Agent 负载)的关系

关系为中等。它不面向多租户的 agent 平台,但它是本地 agent 最常用的后端,且服务器的缓存设计明确为 agent 负载改过。

  • PR #16391 的动机写得很直白:目标是 Claude Code 这类 agent 负载,即一个很大的主上下文,中间穿插关键词提取、摘要等辅助调用。此前这些辅助调用会冲掉主对话的 KV,改动后单个 slot 也不会把 prompt cache 弄坏一手PR #16391。
  • 工具调用:/v1/chat/completions 支持 OpenAI 风格的函数调用,依赖 Jinja 模板引擎(默认开启)。对 Llama 3.x、Hermes、Qwen 2.5、Mistral Nemo、GPT-OSS 等有原生格式处理,其余走通用格式;parallel_tool_calls 默认关闭,只在部分模型上可用一手function-calling.md。
  • 接 Claude Code:/v1/messages 支持 tool_use、tool_result、流式输出和 token 计数,内部把 Anthropic 格式转成 OpenAI 格式;博客给的用法是设置 ANTHROPIC_BASE_URL 指向本机一手HF blog。
  • Hugging Face 有一页专门文档讲用 llama.cpp 跑本地 agent,列出 Pi、OpenClaw、Hermes Agent、OpenCode 的接入方式一手HF docs: agents-local。
  • 服务器自带实验性的 agent 能力:--tools 开启读写文件、搜索、执行 shell 等内置工具,--mcp-servers-config 可挂接 stdio 方式的 MCP 服务器,--agent 一键全开。文档反复提示不要在不可信环境启用一手server README。

局限同样清楚:slot 数量有限,上下文在并行 slot 之间共享;没有跨机器的会话迁移;工具调用质量取决于模型和量化档位。

与图中其他概念的关系

  • GGUF:llama.cpp 的原生模型格式,两者同源。
  • MNN:同属本地与端侧阵营。MNN-LLM 论文拿 llama.cpp 做对比基线。
  • EAGLE-3:llama-server 的 --spec-type 含 draft-eagle3。
  • MCP:llama-server 可作为 MCP 客户端挂接 stdio 服务器(实验性)。
  • Open Responses:服务器提供 /v1/responses,内部转成 chat completions;是否符合 Open Responses 规范本次未核实。
  • vLLM:数据中心的对应物;vLLM 通过插件可实验性地加载 GGUF。
  • llm-compressor:服务端的量化工具,对应本地的 llama-quantize。
  • ExecuTorch、LiteRT:端侧的厂商栈竞争者。
  • 昇腾:llama.cpp 有 CANN 后端。
  • Cerebras、Vera Rubin NVL72 等整机架硬件,llm-d、GIE、Dynamo、Mooncake 等集群组件:无直接关系。
