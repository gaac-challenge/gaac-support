Dynamo

NVIDIA 开源的分布式推理服务框架,管路由、伸缩与 KV 传输,不自己做引擎

与主线一 KV cache · 强路由器按 KV 块所在位置选 worker,NIXL 负责在显存、内存、存储之间搬 KV与主线二 Agent 负载 · 强请求可带 agent hints,路由器有会话亲和、优先级队列和程序级调度插件

它是什么

Dynamo 是 NVIDIA 开源的分布式推理服务框架。它不是推理引擎,自己不执行模型的前向计算;真正算 token 的是 vLLM、SGLang、TensorRT-LLM 这些引擎。Dynamo 站在它们上面一层,解决一个模型要铺在几十到上千块 GPU 上时才出现的问题:一个请求该发给哪台机器、prefill 和 decode 要不要拆到不同机器、流量变化时加减多少副本、KV cache(模型已经算过的上下文的中间结果)放在哪里、怎么搬。

可以把它理解成「引擎之上的一层操作系统」:一个兼容 OpenAI 接口的前端、一个知道每台 worker 缓存了什么的路由器、一个按延迟目标伸缩的规划器,加上一套 Kubernetes 上的部署与编排组件。核心用 Rust 写,引擎适配层用 Python。

它做了什么

路由器(KV-aware Router)

这是 Dynamo 最核心的组件。普通负载均衡只看谁空闲;Dynamo 的路由器还要看「谁已经缓存了这个请求的前缀」。做法是:

  1. 每个引擎 worker 在 KV 块被创建或删除时发出事件(默认走 ZMQ)。
  2. 路由器里的 indexer 用这些事件维护一棵全局的前缀树,记录每个 worker 持有哪些块。
  3. 新请求进来,先把 token 切块并哈希,在前缀树里查每个 worker 的命中长度。
  4. 按成本函数打分,选成本最低的 worker。文档给出的公式是:成本 = prefill 负载系数 ×(该 worker 在途的 prefill 块 + 本请求的 prompt 块 − 缓存命中抵扣)+ 预计的 decode 块 + 可选的活跃请求数项一手Routing Concepts。

命中抵扣按缓存所在的层级分别计:显存、主机内存、磁盘、共享缓存池各有各的折算系数。也就是说,路由器知道一段 KV 是在显存里(几乎零成本)还是要从磁盘读回来(有成本),并把这个差别算进选路。

1.3 之后路由器变成可独立部署的服务,加了分片的 KV indexer(Branch-Sharded KV Indexer);1.5 开放了自定义打分与挑选策略;1.6 把请求入口也开放给插件,请求分类器可以推迟、重排或指定去向一手Dynamo releases。

分离式服务与 NIXL

Prefill(一次性处理输入,算力密集)和 decode(逐 token 生成,内存密集)可以放在不同 worker 上,各自伸缩。两者之间要把 KV 从 prefill 机搬到 decode 机,这由 NIXL(NVIDIA Inference Xfer Library)完成。NIXL 是一个点对点的数据搬运库,用同一套接口在显存、主机内存、文件、对象存储之间做异步、非连续的块传输,底层可接 UCX(RDMA)、libfabric(AWS EFA)、POSIX 文件等后端,最新版 1.5.2(2026-10-29)一手NIXL releases。NIXL 是独立仓库,vLLM、SGLang、TensorRT-LLM、llm-d 都直接用它。

Planner 与 AISimulate

Planner 按延迟 SLA(TTFT、token 间延迟)而不是 QPS 决定 prefill 与 decode 各需要多少副本。它依赖一个性能模型来预测「这个配置在这个流量下延迟是多少」,这个模型原名 AIConfigurator,v1.5.0 起改名 AISimulate 并独立成包。用户写一份 DGDR(Dynamo Graph Deployment Request),填模型、硬件、流量目标,系统生成部署配置一手NVIDIA 博客。

KV Block Manager(KVBM),以及它已被弃用

KVBM 是 Dynamo 自己的 KV 分层管理器:把 KV 块在 G1 显存、G2 主机内存、G3 本地 SSD、G4 远端存储之间迁移,1.0 时还加了 S3 与 Azure blob 接口,可单独 pip 安装进 vLLM 或 TensorRT-LLM一手NVIDIA 博客。

但 v1.5.0(2026-09-21)的发布说明宣布 KVBM 弃用,计划在 v1.7.0 移除。 迁移建议是「用引擎自带的 KV offloading 做主机内存与磁盘分层」;跨节点 KV 共享交给一个单独的早期项目 KV Cache Runner(KVCR),并明说它不是 KVBM 的替代品一手Dynamo releases。当前文档(v1.6.1)的 offloading 页面只列三个后端:LMCache(vLLM)、HiCache(SGLang 自带)、FlexKV(腾讯与 NVIDIA 合作,实验性),每个 worker 选一个一手KV cache offloading 文档。

换句话说,Dynamo 在 2026 年下半年的方向是:不再自己存 KV,只负责知道 KV 在哪里并据此路由。存储交给引擎和第三方缓存层。

Grove 与 ModelExpress

  • Grove:Kubernetes 上的编排 API,把一组有角色的 pod(prefill、decode、前端)当成一个整体做 gang 调度和拓扑约束,例如要求 prefill 与 decode 落在同一个 NVL72 机架内以便走 NVLink 传 KV。当前版本 v0.1.0-alpha.14,仍是 alpha一手Dynamo releases。
  • ModelExpress:冷启动组件。一是 checkpoint restore(初始化一次,把就绪状态存盘,新副本从快照恢复),二是权重流式分发(一台 worker 加载后经 NIXL 直接传给其他 worker)。当前 v0.7.0。

与主线一(KV cache)的关系

关系很强,而且 Dynamo 在这条主线上的角色在 2026 年发生了变化,值得说清楚。

索引:引擎上报块级事件,路由器维护全局前缀树。1.5 把索引扩展到两种新来源:Mooncake 共享缓存池的对象事件(用于 SGLang HiCache,热路径上不再发 HTTP 查询)和 vLLM 的磁盘层事件。1.4 加了跨数据中心的 KV relay 和按租户隔离的 cache_salt(不同租户即使 prompt 相同也不共用 KV)。1.6 的 gRPC relay 把 KV 池状态暴露给数据中心外的消费者。

传输:NIXL。它既搬 prefill 到 decode 的 KV,也搬多模态的 embedding 和模型权重。NIXL 自己有一个 Mooncake Transfer Engine 后端插件,所以两套传输库并非互斥;v1.6.2 的 SGLang 与 vLLM 镜像里直接打包 Mooncake 0.3.14。

分层:早期由 KVBM 管 G1 到 G4 四层;现在弃用 KVBM,分层由引擎或 LMCache、HiCache、FlexKV 完成,Dynamo 只在路由成本里给各层命中不同的折算。

与 CMX 的关系:CMX(context memory storage,CES 2026 发布时叫 Inference Context Memory Storage)是 NVIDIA 的硬件方案:用 BlueField-4 存储处理器管理 NVMe 闪存,经 Spectrum-X 以太网 RDMA,为一个 pod 内的所有 GPU 提供共享的 KV 层。NVIDIA 的产品页把 Dynamo 列为 CMX 的四个组成部分之一,分工是:BlueField-4 上的 DOCA Memos SDK 提供键值接口并负责数据搬运、完整性与加密;Dynamo 在服务层「把请求路由到 KV 已经在的地方」厂商自述NVIDIA CMX 页面。CMX 页面自称吞吐与能效最高 5 倍,没有独立基准;二手报道称 BlueField-4 要到 2026 下半年才出货,本次没有找到已部署的证据。

与主线二(Agent 负载)的关系

关系强,且有具体接口可查。

  • Agent hints:请求体里的 nvext.agent_hints 字段。当前文档列出四项:priority(跨层的软优先级,既影响路由器排队也转给引擎用于调度和 KV 驱逐)、strict_priority(路由器队列的硬分层)、osl(预期输出长度,用于估算 decode 负载)、speculative_prefill(本轮结束后,后台用预测的下一轮前缀发一个 max_tokens=1 的请求预热 KV)一手nvext 文档。1.0 文档里的 latency_sensitivity 字段在当前字段表中已不出现,语义并入 priority 与队列策略未复核,仅据两版文档对比。
  • 会话亲和:1.4 起,没有显式会话头时,路由器会读取 Claude Code、Codex、OpenCode 这类编码 agent 自带的会话头,把同一会话钉在同一 worker;亲和状态在路由器副本间同步。1.5 分硬亲和与软亲和;1.6 加了「会话到 KV 块」的谱系索引。
  • 程序级调度:1.3 引入实验性的 ThunderAgent 路由器,以 trajectory_id 标识一次 agent 运行,在请求边界上做暂停与恢复;1.6 成为内置插件。
  • 缓存保留:cache_control(与 Anthropic Messages API 同名字段)可按 TTL 钉住一段 KV,被钉的块不删除而是降到主机内存,目前只在 SGLang HiCache 上实现,标注为实验性一手Agents 文档 v1.0.1。
  • 协议与解析:前端同时提供 /v1/responses 与 /v1/messages,并为十余个模型族维护工具调用与思考内容的解析器。
  • 厂商自述配合 NeMo Agent Toolkit,Llama 3.1 在 Hopper 上 TTFT 最多降 4 倍、吞吐升 1.5 倍;文档称 speculative prefill 使第二轮起的 TTFT 最多降约 3 倍。均无第三方复现。

与图中其他概念的关系

  • vLLM、SGLang、TensorRT-LLM:Dynamo 支持的三个引擎,每个版本钉死具体引擎版本。SGLang 的 HiCache 是 Dynamo 上功能最全的 KV 分层后端。
  • llm-d、GIE:见上文竞合关系。Dynamo 路由器可作为 GIE 的 endpoint picker。
  • Mooncake:Dynamo 镜像内置 Mooncake Transfer Engine;路由器消费 Mooncake Store 的对象事件;发布说明里有用 Mooncake 经 NVLink 传 KV 来跑 Kimi-K3 的配方。Mooncake 团队还给 AIConfigurator 贡献了 SGLang 支持。
  • AIBrix:同层竞品。AIBrix v0.4.0 的多引擎回归测试把 Dynamo 列为可部署的后端之一。
  • KServe:同层,无直接集成证据。
  • Vera Rubin NVL72:Grove 的拓扑 API 针对 NVL72 机架设计;CMX 面向 Rubin 平台。
  • EAGLE-3:1.6 增加了 SGLang EAGLE3 推测解码的测试与指南,并让 KV 路由器在启用 EAGLE 时使用引擎的 bigram 哈希。
  • Open Responses、MCP:前端实现了 Responses API 端点;与 MCP 无直接关系。
  • AA-AgentPerf:未见直接关系。Dynamo 自己的性能宣称主要引用 SemiAnalysis InferenceX。
