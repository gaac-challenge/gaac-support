EAGLE-3

第三代 EAGLE 投机解码：一层小网络复用大模型特征预猜 token

与主线一 KV cache · 弱draft head 有自己的一层 KV；被拒的草稿 token 占用的目标模型 KV 槽位要作废与主线二 Agent 负载 · 弱代码类负载实测吞吐约增两成，但长输入的 agent 上下文会稀释收益

它是什么

EAGLE-3 是一种投机解码（speculative decoding）方法，出自 2025 年 3 月的一篇论文。它不是产品，也不是独立项目，而是一种已经被 vLLM、SGLang、TensorRT-LLM 等引擎实现的加速技术。

先讲投机解码。大模型一次只生成一个 token，每生成一个都要把整个模型跑一遍，而且必须等上一个出来才能算下一个。但有一点可以利用：模型"检查一串现成的 token 对不对"可以一次并行完成，成本和生成一个 token 差不多。于是分两步走：

  1. 打草稿（draft）：让一个很小、很快的模型先猜接下来的几个 token。
  2. 验证（verify）：大模型把这几个 token 一次性过一遍，从头比对，接受前面猜对的部分，从第一个猜错的位置起改用自己的结果。

为什么说它无损：每个被接受的 token 都经过大模型核对。贪心解码时，接受条件就是与大模型自己会选的 token 相同；带随机采样时，用一套拒绝采样规则，数学上保证输出分布与大模型单独生成时一致。草稿猜得再差也只是白费算力，不会改变结果。

收益取决于两件事：草稿猜中多少（平均每轮接受几个 token），以及打草稿本身多便宜。EAGLE 系列就是在这两点上做文章。

它做了什么

三代各自的改动

EAGLE-1：在特征层面打草稿。 传统做法是另找一个小模型当草稿模型。EAGLE 的观察是，大模型最后一层输出的特征向量（进入输出层之前的那组数）已经包含了大量信息。它只训练一层 Transformer 解码层作为 draft head，输入大模型的顶层特征，预测下一个位置的特征，再借用大模型自己的输出层把特征变成 token。因为复用了大模型的"半成品"，一层网络就能猜得相当准。摘要称在 LLaMA2-Chat 70B 上延迟加速 2.7 至 3.5 倍厂商自述，论文自测。

EAGLE-2：动态草稿树。 草稿不必是一条链，可以是一棵树：每个位置保留几个候选，大模型一次验证整棵树，选出最长的正确路径。EAGLE-1 的树形是固定的；EAGLE-2 发现 draft head 给出的置信度与实际接受率很接近，于是按置信度动态决定往哪个分支多展开。摘要称加速 3.05 至 4.26 倍，比一代快 20% 至 40%厂商自述。

EAGLE-3：三处改动一手，论文 HTML 版，经摘要工具读取：

  • 去掉特征预测损失。前两代要求 draft head 的输出逼近大模型的真实特征，论文发现这个约束使得增加训练数据也难以提升效果。EAGLE-3 改为直接预测 token。
  • 训练时测试（training-time test）。推理时 draft head 连猜多步，第二步起的输入是它自己上一步的输出，而不是大模型的真实特征。于是训练时就把自己的输出喂回去多走几步，让训练条件与推理条件一致。
  • 多层特征融合。不只取顶层特征，而是把大模型低、中、高三个层的特征拼接，再用一个全连接层压回原维度。

draft head 仍然只有一层解码层加几个全连接层，训练数据约为一代的 8 倍。

论文里的数字

论文摘要称最高 6.5 倍、比 EAGLE-2 快约 1.4 倍。主表的条件是 batch size 为 1：Vicuna 13B 在温度 0 下五个任务平均 5.51 倍，平均每轮接受 6.62 个 token；Llama 3.3 70B 平均 4.12 倍；温度升到 1 时 Llama 3.1 8B 降到 3.45 倍厂商自述，论文自测。仓库 README 注明演示用的是 2 张 RTX 3090、fp16 精度的 Vicuna 13B。

论文自己也测了大批量，这组数字更有参考价值。在 SGLang v0.4.4、单张 H100、Llama 3.1 8B、MT-Bench 上，不用树、只用长度 3 的链：

batch size 2 8 16 32 64
EAGLE-3 吞吐倍数 1.81 1.62 1.48 1.32 1.38
EAGLE-1 吞吐倍数 1.40 1.23 1.02 0.94 0.99

在 vLLM 上，EAGLE-3 从 batch 2 的 1.75 倍降到 batch 56 的 1.01 倍一手，论文表 3 与表 5。

引擎支持

  • vLLM：0.8.5 起支持 EAGLE-1 与 EAGLE-3，0.9.1 起支持 CUDA graph 与接受率指标一手Red Hat Developer, 2025-07-01。配置方式是 --speculative-config 里写 method: eagle3 并指定 draft head一手vLLM 投机解码文档。同组织的 speculators 库负责训练 draft head。
  • SGLang：文档把 EAGLE-3 列为"速度与质量最佳"的推荐项，训练用 SpecForge一手SGLang 文档。
  • EAGLE 仓库列出的其他集成方有 NVIDIA TensorRT-LLM、MLC-LLM、AMD ROCm、AWS NeuronX、PaddleNLP 等 15 项一手，README。

2026 年的现状

draft head 已成为随模型发布的配套件。EAGLE 仓库的权重表里，只有 4 个是作者官方训练的，其余来自 NVIDIA、LMSYS、腾讯 AngelSlim、Red Hat 等，覆盖 gpt-oss-120b、Qwen3-235B、Llama 4 等一手，README。

Red Hat 的生产口径基准（2026-04-16）是目前最扎实的数据。条件：vLLM v0.13.0、H200、目标模型 gpt-oss-120b（MoE，MXFP4 量化）、draft head 为 nvidia/gpt-oss-120b-Eagle3-v2、3 个草稿 token、并发 1 到 200 取几何平均、前缀缓存全程开启一手Red Hat Developer, 2026-04-16：

负载 平均输入长度 输出吞吐提升
ShareGPT（聊天） 122 token +20.7%，峰值 +27.2%
SWE-bench（代码） 556 token +20.5%
MLPerf（长文摘要），单卡 5011 token +9.5%
MLPerf，双卡 5011 token +16.0%，但 TTFT P95 恶化 9.3%

草稿 token 数为 2、3、4 时，整段草稿全被接受的比例是 45.4%、35.6%、28.3%，平均每轮接受 1.91、2.07、2.13 个；从 3 加到 4，吞吐反降 8%。

为什么论文是几倍、生产是一两成。 把上面的数字放在一起，原因有四条：

  1. 批量。投机解码用多余的算力换更少的轮次。batch 为 1 时 GPU 算力大量闲置，草稿与验证几乎白送；高并发下 GPU 已经饱和，验证多出来的 token 要和别的请求抢算力。论文自己的表里，vLLM 上 batch 56 已降到 1.01 倍。
  2. 树与链。论文主表用动态草稿树，平均每轮接受 6 个以上；生产引擎为了批处理用 2 到 3 个 token 的链，Red Hat 实测每轮只接受约 2 个。
  3. 预填充不受益。输入越长，时间越多花在读输入上，这部分投机解码帮不上忙。
  4. 基线不同。论文的基线是未量化模型的朴素解码；生产基线已是量化、CUDA graph、连续批处理全开的引擎。

Berkeley 的研究在 vLLM 上系统测了多种方法，结论是目标模型的验证主导执行时间，接受长度随位置、请求、数据集波动很大，实测与理论上界有明显差距一手，仅读摘要arXiv 2601.11580。vLLM 文档对投机解码的定位也只是"在中低 QPS、受内存带宽限制的负载下降低 token 间延迟"一手。

到 2026 年底，EAGLE-3 已不是唯一选择。vLLM 文档并列了 MTP、DFlash、DSpark、suffix decoding 等方法；speculators 新增了并行出草稿的 P-EAGLE，以及 DFlash、DSpark 的训练一手speculators README。EAGLE 仓库的待办里写着 EAGLE-4，尚未发布。

与主线一（KV cache）的关系

弱，但有三个真实的交互点。

  • draft head 有自己的 KV。它是一层带注意力的解码层，连猜多步时要缓存自己的 K、V。这一点是从结构推出来的：vLLM 文档只明说了独立草稿模型一类的 speculator 由 model runner 分配 draft KV cache，对 EAGLE 一类只说它从目标模型的隐藏状态出草稿一手，vLLM 文档。相比独立的小草稿模型（每一层都有 KV），EAGLE 类只有一层，占用小得多。
  • 被拒 token 的处理。验证时，大模型要为每个草稿 token 计算并写入 KV。被拒绝的那些位置必须作废，下一轮覆盖。vLLM 的 speculator 配置里有一项描述"KV lookahead slots"，即为草稿预留的 KV 槽位一手，文档仅此一句。草稿越长，每个请求预留越多，能容纳的并发就越少。
  • 与量化 KV 的组合。笔记记录 vLLM v0.34.0 有"draft 与 target 的 KV 数据类型对齐"的改动未复核，GitHub API 限流未能重读。这属于报告说的"特性叠加后的正确性"问题。

EAGLE-3 不改变 KV 放在哪里，与分层、卸载、跨节点传输没有机制上的联系。

与主线二（Agent 负载）的关系

弱。有两点值得说，方向相反。

有利的一面：代码类输出可预测性高，Red Hat 在 SWE-bench 上测得吞吐 +20.5%，并发 100 的峰值下每百万输出 token 成本从 4.41 美元降到 3.56 美元（按 H200 实例每小时 41.62 美元计）。

不利的一面：这组 SWE-bench 测试是把 GitHub issue 当作单轮提示，平均输入只有 556 token，不是多轮、带工具结果、上下文几万 token 的 agent 轨迹。真实 agent 负载输入长、输出短，更接近 MLPerf 那一行（+9.5%）甚至更低。另外，agent 大量输出受约束的 JSON 工具调用，草稿可能不符合语法；报告提到 vLLM v0.34.0 修过"grammar-invalid drafts"的缺陷未复核，来自报告。对高度重复的工具调用输出，不需要训练的 n-gram 或 suffix decoding 可能更合适，vLLM 的 suffix decoding 会跨请求匹配历史回复一手，vLLM 文档。

它出现在图里，是因为它代表"不改模型权重、只改解码过程"这一类效率手段，并且是 2025 至 2026 年生产引擎里的默认形态。

与图中其他概念的关系

  • vLLM、SGLang、TensorRT-LLM：都内置了 EAGLE-3 支持。
  • llm-compressor：同属 vllm-project 的姊妹库是 speculators。两者可叠加，Red Hat 基准的目标模型本身就是 MXFP4 量化的。
  • Mooncake：speculators 的多节点在线训练里，vLLM 与训练器之间传递隐藏状态的后端之一是 Mooncake 分布式存储一手，speculators README。这是训练侧的用法，不是推理时的 KV 传输。
  • ExecuTorch、LiteRT、MNN：端侧运行时用的是 DFlash 或 MTP，同属"草稿加验证"，不是 EAGLE-3。

存疑与未核实

  • 报告小标题写"不是论文里的 2–3 倍"。EAGLE-3 论文摘要写的是最高 6.5 倍，主表平均 3.5 至 5.5 倍；2 至 3 倍更接近 EAGLE-1 或独立草稿模型的数字。
  • 报告的对比隐含"论文高估"。论文自己的大批量表已经显示 SGLang 上 batch 64 为 1.38 倍、vLLM 上 batch 56 为 1.01 倍，与生产数字量级一致。差距主要来自 batch 大小与树/链设置，而不是论文与现实的矛盾。
  • 论文内部有不一致：vLLM 测试的硬件正文写 RTX 3090、表注写 A100；正文称 vLLM 吞吐在 batch 56 达到峰值，表中却是单调下降。
  • 报告称 DSpark 等"没有找到说明其机制的设计文档"。speculators README 有一段描述：DSpark 在 DFlash 的锚定块草稿之上加了一个 Markov head 和一个预测逐位置接受概率的置信度 head。
  • "无损"取决于配置。vLLM 提供明确标为有损的 FLy 验证器；SGLang 的接受阈值调低后也不再无损。Red Hat 基准没有报告输出质量对比。
  • 前缀缓存命中时，目标模型不会重算前缀的隐藏状态，draft head 如何取得这部分特征、它自己的 KV 是否随前缀一起缓存，没有找到文档。
  • vLLM 的 EAGLE 专页与 v0.34.0 release notes 因限流未能读到，KV 交互细节只有文档里的两句话作依据。
