Open Responses

把 OpenAI Responses API 的请求与输出格式做成多厂商通用的开放规范

与主线一 KV cache · 中不规定缓存,但 previous_response_id、allowed_tools、连接内状态都围绕前缀复用设计与主线二 Agent 负载 · 强以 item 和 agent 循环为核心重新定义模型 API,是 agent 负载在模型一侧的协议面

它是什么

Open Responses 是一份开放规范,规定应用怎样通过 HTTP 调用大语言模型:请求体长什么样、输出是什么结构、流式事件怎么编排、工具调用怎么表示。它以 OpenAI 的 Responses API 为蓝本,目标是让同一份请求不经翻译(或只需很少翻译)就能跑在不同模型提供方上一手openresponses.org。

它要解决的问题是:各家 LLM API 的构件已经趋同(消息、工具调用、流式、多模态),但编码方式各不相同。此前的事实标准是 OpenAI 的 Chat Completions 格式,它诞生于聊天时代,对推理轨迹、多步工具调用、服务端工具这些新东西表达得很勉强。Open Responses 是一份规范加一套合规测试,不是模型,也不是产品。

它做了什么

先讲 Responses API 与 Chat Completions 的区别

Open Responses 继承的是 Responses API 的设计,所以要先弄清后者改了什么厂商自述,OpenAI 文档OpenAI 迁移指南:

方面 Chat Completions Responses API
基本单位 messages 数组,一条消息里混着文本、工具调用等 items,每个 item 是一种带类型的独立单元(消息、函数调用、函数输出、推理)
会话状态 客户端每轮重发全部历史 可用 store: true 由服务端保存,用 previous_response_id 接续
内置工具 无,OpenAI 托管工具不能原生使用 网页搜索、文件检索、代码解释器、远程 MCP 等由服务端执行
推理内容 无对应结构 推理是一种 item;无状态或零留存场景可回传 encrypted_content
函数定义 外部标签式 内部标签式,省略 strict 时默认尝试严格模式

两点常被误解。其一,有状态不等于省钱:OpenAI 文档写明,用 previous_response_id 接续时,链上此前所有输入 token 仍按输入计费。其二,Chat Completions 没有被废弃,OpenAI 的表述是继续支持,但新项目推荐用 Responses。

规范里有什么

以下均出自规范正文一手Open Responses 规范:

  • Items:上下文的基本单位,双向使用,既是模型输出,也可原样作为下一次输入。每个 item 有 id、type、status,状态在 in_progress、completed、incomplete 间流转。规范特意说明,"是状态机"不意味着"被持久化",持久化是另一回事。
  • 语义化流式事件:流不是裸文本增量,而是 response.output_item.added、response.output_text.delta、response.completed 这类有含义的事件,走 SSE。
  • Agent 循环:规范把"模型推理、调工具、看结果、再推理"的循环作为核心。工具分两类:外部托管(函数调用,控制权交还开发者,由其执行后在下一个请求回传结果)与内部托管(提供方自己执行并继续循环,不交还控制权)。
  • 推理 item:三个可选字段,content(原始推理)、encrypted_content(提供方加密的不透明载荷,可往返回传)、summary(可展示的摘要)。
  • previous_response_id:服务端必须加载被引用响应的输入与输出,模型在"旧输入 + 旧输出 + 新输入"的拼接上采样,必须保持这个语义顺序。
  • allowed_tools:不改动 tools 列表,只限制本次可实际调用的子集。
  • truncation、service_tier:是否允许服务端截断上下文;请求的优先档位提示。
  • 扩展规则:厂商自有的 item、工具、事件必须加厂商前缀(如 openai:web_search_call),被多家前沿模型采用的特性可由 TSC 纳入标准。
  • WebSocket 传输(2026-04-24 新增):同一条连接上顺序处理多轮,一次最多一个进行中的响应,连接上限 60 分钟。
  • 合规测试:官网提供可指向任意实现的验收测试二手Simon Willison。目前只有服务端测试,没有客户端一致性套件。

谁在实现

官网首页截至核查日展示的标志有 12 个:NVIDIA、Vercel(AI SDK)、OpenRouter、Hugging Face、LM Studio、Databricks、Red Hat、AWS、Ollama、OpenAI、vLLM、Llama Stack一手openresponses.org。挂标志不等于完整实现,逐个核实的结果如下:

  • vLLM:提供 /v1/responses、/v1/responses/{response_id}、/v1/responses/{response_id}/cancel,仅适用于文本生成模型一手vLLM 在线服务文档。但默认不存储:store 选项默认被静默忽略,需设环境变量 VLLM_ENABLE_RESPONSES_API_STORE 才启用;存储是进程内字典,代码注释自称是 hack,且"从不删除,可能内存泄漏"一手,v0.25.1 代码文档vLLM v0.25.1 API 文档。
  • Ollama:本地与云端都支持 /v1/responses,文档明确称其为"无状态 Responses 请求";云端 API 不支持有状态 Responses 和通过该端点的内置网页搜索一手Ollama 文档。
  • OpenRouter:文档称其 Responses API 是无状态的,设置 store: true 或非空 previous_response_id 的请求会被以 400 拒绝;支持函数调用与网页搜索一手,经摘要OpenRouter 文档。
  • Hugging Face:发布当日称可通过 Inference Providers 试用,并把 Open Responses 概括为"默认无状态"一手Hugging Face 博客。
  • Anthropic 与 Google:未见原生支持,其模型可经 OpenRouter 等中间层以该格式访问二手,搜索结果转述,未打开原文。

一个值得注意的事实:Responses API 在 OpenAI 那里以"有状态"著称,但开放生态里核实过的实现几乎都是无状态的,或默认关闭状态。

2026 年的现状

  • 规范当前版本 2026-04-24,治理于 2026-10 移交 AAIF。
  • Chat Completions 仍是覆盖最广的事实标准;报告的判断与此一致。Open Responses 的位置是"下一代候选标准":主要开源引擎和聚合网关都提供了端点,但多为子集。
  • OpenAI 称 Responses API 相比 Chat Completions 缓存利用率提高 40% 至 80%,SWE-bench 在相同提示与设置下提高 3%厂商自述,内部测试,未披露模型与负载OpenAI 迁移指南。这是 OpenAI 自家服务的数字,不能外推到其他实现。

与主线一(KV cache)的关系

强度:中。规范不定义任何缓存行为,也没有规定 KV 怎么存;但它有几处设计直接面向前缀复用。

规范明文的部分一手Open Responses 规范:

  • allowed_tools 一节直说这是"保留缓存的控制面":改动 tools 字段通常会使 prompt 或 schema 缓存失效,所以让全部工具定义留在上下文里不动,只用 allowed_tools 收窄本次可调用的子集。这是一条为了不打断前缀而专门设计的字段。
  • previous_response_id 的语义是严格的前缀追加:旧输入、旧输出、新输入,顺序不得变。新一轮的 prompt 天然以上一轮的全部内容为前缀。
  • WebSocket 续接:服务端应当把最近一次响应的状态放在"连接本地内存"里,以降低续接延迟,并让 store=false(含零数据留存)的部署也能在同一连接上续接而不落盘;若状态不在连接本地且未持久化,必须返回 previous_response_not_found。
  • /responses/compact 返回压缩后的输入窗口而非响应 ID,压缩后必须开一个不带 previous_response_id 的新响应。
  • 推理 item 可回传(含加密形式),使上一轮的推理 token 留在下一轮前缀里。

以下是我的推断,规范没有这样写:

  • 规范说的"连接本地状态"指响应对象(items),不是 KV cache。但一条绑定到单个服务实例的 WebSocket 连接,客观上就是会话亲和:同一会话的后续请求落在同一台机器上,那里的 KV 前缀最可能还在。OpenAI 所称的缓存利用率提升,合理的解释是服务端掌握了完整会话并能做亲和路由,但 OpenAI 文档没有说明机制。
  • 压缩之后前缀被改写,此前的 KV 基本作废。规范要求压缩后断开响应链,等于在协议层承认这是一次缓存重置点。
  • vLLM 的响应存储是单进程内字典,多副本部署下 previous_response_id 只有路由回同一副本才能命中。这意味着在开源栈里,有状态 Responses 把粘性路由的要求从"为了 KV 命中的优化"变成了"为了正确性的必需"。
  • 未核实规范是否纳入 prompt_cache_key 一类的显式缓存提示字段(本次只读了规范正文,没有逐项读 OpenAPI 参考)。

有一个对照值得写下:2026 年工具一侧的 MCP 把会话从协议里拿掉,模型一侧的 Open Responses 却新增了带连接内状态的 WebSocket。两者不矛盾。工具调用的状态便宜,可以用句柄外置;模型会话的状态(几万到几十万 token 的 KV)昂贵,重建成本高,所以协议要给"让请求回到原地"留出路。这是我的解读。

与主线二(Agent 负载)的关系

强度:强。这份规范本身就是"服务单位从请求变成会话"在 API 层的表达。

  • 规范把 agent 循环列为核心原则,一次请求可以包含多步推理与多次工具调用,由提供方托管循环直到满足退出条件。服务端看到的不再是单次补全,而是一段程序。
  • Items 是可往返的轨迹单元:函数调用、函数输出、推理各自成项,使多轮工具调用的历史能无损回放。
  • previous_response_id 与 store 让会话成为服务端可寻址的对象。不过如上节所述,开放生态的实现多为无状态,状态仍在客户端。所以更准确的说法是:Open Responses 让状态可以放在服务端,而不是规定它在服务端。
  • service_tier、truncation 把延迟档位与上下文截断策略显式化,供长会话选择。
  • 局限:规范没有表达"这次工具调用预计多久回来"的字段,与 MCP Tasks 之间也没有对接。工具间隙期间 KV 该留该丢,协议层没有给引擎任何信号。

与图中其他概念的关系

  • MCP:同属 AAIF。规范把 MCP 列为外部托管工具的一例,并指出此时控制权不必先交还开发者;Responses API 的内置工具中包含远程 MCP。
  • OpenRouter:首批伙伴,其 Responses 端点为无状态实现(见上)。
  • vLLM:首批伙伴,提供 Responses 端点,状态存储为可选的进程内实现(见上)。
  • llama.cpp:其 llama-server 提供 /v1/responses 路由,内部转换为 chat completions 请求处理二手,搜索结果转述,未打开 README 原文。Ollama 构建在 llama.cpp 之上,是首批伙伴。
  • LiteLLM:未核实其 Open Responses 支持情况,不写。
  • llm-d、GIE、AIBrix、Dynamo:无直接关系。这些路由层若要支持有状态 Responses,需要按会话或响应 ID 做亲和,这是推断,未查到它们对 previous_response_id 的专门处理。
  • SGLang、TensorRT-LLM、MNN 及压缩、硬件层概念:未查到关系。
